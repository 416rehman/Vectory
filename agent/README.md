# Vectory agent

The Go agent manages one explicitly adopted Vector 0.58.0 process and one JSON configuration. It connects outbound to the dedicated Vectory agent TLS listener. It never installs Vector or accepts a remotely selected agent executable, service name, or weakening of its local capability policy. Restricted mode is the default; the host operator can explicitly grant full Vector configuration capabilities as described below.

## Build and checks

Go 1.26.8 is pinned in `go.mod`, verified against the [official release feed](https://go.dev/dl/?mode=json). Normal builds are pure Go:

```powershell
cd agent
$env:CGO_ENABLED='0'
go build -trimpath -o vectory.exe ./cmd/vectory
go test ./...
go vet ./...
$env:VECTOR_TEST_BINARY='C:\absolute\path\vector.exe'
go test -v ./internal/agent -run TestNativeVectorActivationAndRollback
```

The native test uses an explicitly synthetic `demo_logs` pipeline and a blackhole sink. It actually validates, starts Vector, observes its acknowledgment and liveness, repairs drift, and rolls back a startup that terminates early. Tests without `VECTOR_TEST_BINARY` skip that native check and cannot establish native compatibility.

## Adoption and enrollment

Stop and disable the old Vector service before adoption. Inventory its command line, include files and `--config-dir` paths. Move all intended semantics into the sole managed JSON document; Vectory supplies only that document when starting its child. Preserve the original service definition so adoption can be reversed. `install --adopt` is the host operator's explicit assertion that this inventory and shutdown are complete. The agent does not take over unrelated running processes.

Use a dedicated service account and dedicated private state/config directories. The installer protects the state directory, managed file's parent directory and generated files: POSIX modes 0700/0600, Windows protected DACL for the installing identity and SYSTEM. Run installation and steady operation under the same intended account, or explicitly provision equivalent account ACLs. Do not point `--managed-config` into a shared directory: adoption deliberately makes that directory private. State and Vector data directories should be separate; never allow the agent state directory as a pipeline file root.

Create an operator-owned local policy, for example:

```json
{
  "allowed_file_roots": ["C:\\ProgramData\\VectorData"],
  "allowed_network_hosts": ["logs.example.net:443"],
  "allowed_listen_addresses": ["127.0.0.1:4318"]
}
```

Create the data directory and set the published config's `data_dir` to that existing absolute path. Full Vector validation checks the real environment; Vectory does not bypass it with `--no-environment` or `--skip-healthchecks`. On Windows, Vector's default `/var/lib/vector` normally does not exist, so an explicit `data_dir` is necessary.

```powershell
vectory install --state-dir C:\ProgramData\Vectory\agent --vector-binary 'C:\Program Files\Vector\bin\vector.exe' --managed-config C:\ProgramData\Vectory\managed\vector.json --capability-policy C:\secure\capabilities.json --adopt
Get-Content C:\secure\enrollment-token.txt | vectory enroll --state-dir C:\ProgramData\Vectory\agent --server https://vectory.example.net:8443 --ca-file C:\secure\server-ca.pem --id edge-01 --token-stdin
vectory doctor --state-dir C:\ProgramData\Vectory\agent
vectory run --state-dir C:\ProgramData\Vectory\agent
```

On Linux/macOS use the same commands with absolute platform paths. The `service` command implements Windows SCM service execution and is also usable under an external Unix supervisor. Explicit `service-install` registers the current absolute executable and state directory; `service-start`, `service-stop`, and `service-uninstall` invoke only the fixed Vectory service and reject an explicit `--state-dir` selector. On Linux/macOS supply `--service-user <existing-unprivileged-account>`; systemd/launchd registration requires root, preserves differing existing definitions, and assigns only the dedicated state/config trees to that account. Windows registration uses the dedicated `NT SERVICE\Vectory` virtual account and grants it the dedicated state/config directories. Host operators must separately provision that account's Vector binary execution and data-root access. Service installation does not start the workload or establish tested service operation. Lifecycle commands accept flags only and reject unexpected positional arguments before changing local state. The CLI never silently enables privileged services. `run --once` is a test convenience and stops the owned child when it exits; use continuous `run` for a lasting workload.

Enrollment also accepts a protected `--token-file`, hidden interactive input, or compatibility form `vectory -ip <server> -id <machine-name> -token <token>`. The token file must be a private, regular, single-link local file. On Unix, it must be owned by the enrolling account or UID 0 and have no group or other permission bits. On Windows, its owner must be the enrolling account, SYSTEM or Administrators, with a DACL granting access only to those principals; alternate data streams are refused. A browser download's default permissions may not satisfy this check; move it into a protected location and set its access before using `--token-file`, or enter the token through the hidden prompt or `--token-stdin`. Compatibility enrollment assumes installation is already completed and still requires HTTPS hostname/IP SAN validation. Command-line tokens can appear in shell history and process listings. No token is persisted. A private CA must come through a separately trusted channel; the agent never bootstraps server trust from an unverified endpoint.

For `enroll` and `recover-enrollment`, omitting `--ca-file` retains the saved CA path. Pass `--ca-file=` as one argument to explicitly use system trust without additional CA certificates; this form also works in Windows PowerShell. A supplied PEM bundle adds certificates to the operating system's trusted roots for the agent, without modifying the system trust store. Keep its stable absolute path readable by the actual agent service account and writable only by trusted administrators. Use public CA certificates, never a CA private key. The CLI saves the path rather than copying the certificates, and future agent connections read that file again.

Enrollment preparation and the request run under one stopped-agent operation lock. Invalid local input, unreadable/empty certificate files, an already enrolled ordinary request, inconsistent identity/state, or a mismatched pending request are refused before changing enrollment settings or allocating a key/request. Machine names must satisfy the server's limit of 100 bytes, with an ASCII letter or digit first and only ASCII letters, digits, hyphens, underscores and dots after trimming outer whitespace. Existing pending spelling is never rewritten. A first attempt rejected locally can be corrected and submitted again. An existing pending request retains its original server, name, request identifier and private key; a missing original key is an error, not permission to regenerate it.

After preparation is saved, filesystem, TLS, HTTP or response errors may leave a pending attempt that must be preserved. Retry the same state directory, server, name and token after resolving the reported problem; do not delete keys or journals or substitute a newly issued token into an uncertain request. If the original token has expired or been revoked, ask the administrator to inspect the server outcome. A valid explicit CA-file correction is allowed for the same pending server/name without changing its identity. Ordinary `enroll` on an already enrolled device cannot change its trust or identity; use explicit authorized recovery when replacement enrollment is required. Recovery may omit its saved server/name and preserves old and staged identities until its existing commit procedure completes. A late storage error can follow saved preparation or identity; the diagnostic distinguishes that from a preflight refusal and does not claim a multi-file transaction.

For an existing installation, stop the daemon and run `vectory install --state-dir <existing-state> --capability-policy <absolute-policy.json>` to replace all local file, destination and listener allowances. The supplied lists replace rather than merge; `{}` removes them, and omitting the flag preserves them. This operation preserves identity, adopted paths, full/restricted mode, pause state, security counters and recovery files. Changed allowances clear suppression of an earlier failed attempt; they do not imply successful activation or resume sync. Use `--allow-full-vector-config` separately to change trust mode. Removing allowances can prevent the existing workload from restarting, so first prepare a compatible configuration. Remote policy cannot perform this operation.

Supply the policy as one regular local UTF-8 JSON object without a BOM, at most 2 MiB. Malformed UTF-8 and lone Unicode surrogate escapes anywhere in the document are rejected before decoding can substitute a different resource name. Literal Unicode, deliberate replacement-character names, valid escaped surrogate pairs and escaped backslashes retain their decoded values. Duplicate properties, including equivalent escaped property names, unsupported fields, wrong types and trailing content are refused. Direct API allowance strings must also be valid UTF-8. An omitted list, a `null` list and an empty array each mean an empty replacement list; a null document or null list element is invalid. Existing allowance bounds and explicit mode authority remain unchanged.

Input refusal does not change other supplied install options or clear retry suppression. Repeating the same policy with only equivalent Unicode escape spellings preserves original settings bytes and any later failure suppression. Earlier builds could save replacement characters after accepting malformed input; a newer executable does not reconstruct those original names. Review the installed allowances against the intended resources, then submit the complete corrected policy using a verified build. This input check does not change generic saved-state parsing or create resource directories or operating-system permissions.

## Re-adopt a deliberately replaced Vector executable

The agent refuses executable bytes that differ from its locally adopted SHA-256. Repeating `install --adopt` does not approve a replacement. After independently verifying a replacement from a trusted release channel, stop the agent supervisor and its owned Vector process, retain the previously approved executable, and approve the exact new executable hash:

```powershell
$approvedVectorSha256 = 'REPLACE_WITH_TRUSTED_EXECUTABLE_SHA256'
vectory re-adopt --state-dir C:\ProgramData\Vectory\agent --expected-sha256 $approvedVectorSha256 --json
```

Uppercase and lowercase hexadecimal are accepted. The existing binary path is used unless an explicit absolute local `--vector-binary` path is supplied. On Unix, use the same flags with absolute platform paths. Symlinks, Windows network/device paths and alternate data streams are refused. This command still requires Vector **0.58.0**; it does not approve an arbitrary upstream version. A checksum calculated from an unexplained replacement is not independent approval.

Re-adoption holds the daemon operation lock and checks the approved hash before any candidate execution and throughout validation. It validates snapshots of the current managed configuration and recorded last-good configuration using the unchanged capability policy. Native validation and configuration tests can access configured resources or providers, so use the intended service environment and resource permissions. A never-established installation with no managed file and no last-good record can approve the executable, but reports no validated workload. Missing or malformed durable state, a corrupt recorded last-good artifact, and unfinished apply or identity-recovery journals are refused. Preserve a pending journal and restore the prior approved binary to complete its recovery first.

Only the binary path and digest in settings change. Identity, credentials, configuration mode, capability allowances, secret bindings, pause markers, managed and last-good bytes, counters and failed-attempt suppression stay unchanged. Existing settings and lock access metadata are preserved; inability to preserve required access metadata prevents replacement. Windows preserves owner/group, DACL and mandatory-label/resource/scoped access policy components; audit-only SACL entries and alternate data streams are outside this guarantee. Linux preserves owner/group/mode and extended attributes, including access ACLs; macOS also preserves the extended security ACL. Unexpected privileged Unix settings modes and deferred macOS ACL inheritance are refused. Linux/macOS implementation is cross-compiled and source-reviewed here; native metadata behavior still needs qualification on those hosts.

Inspect the returned path, digest, version and `validated` list, then run `doctor` and `status` before restarting the existing supervisor. Success reports `workload_started: false`; it does not start Vector, resume sync or establish activation. If an earlier candidate remains suppressed after its cause is fixed, use the separate stopped-agent `retry` command before restarting. Do not hand-edit the adopted digest or reset state. Stop package managers and other external writers during maintenance; the agent lock cannot coordinate unrelated privileged processes.

## Update local agent settings

Stop the agent before changing secret bindings, metrics, enrollment settings, local allowances or full/restricted mode. Existing installations keep their provisioned state-directory and lock permissions. A settings update preserves the settings file's ownership and access metadata, unknown top-level and nested capability fields, and unrelated settings. Repeating an unchanged request keeps the original file bytes and metadata; an empty secret-binding map deliberately removes all bindings. Allowance lists replace the corresponding lists while unknown capability extensions remain intact.

Changed allowances or mode also clear only the two retry-suppression fields in the existing state file, preserving its access metadata, unknown fields and counters. Both replacements are prepared before writing. Settings are committed first: if replacing settings is refused, suppression remains unchanged. If settings were saved but the state replacement fails, the command reports that retry-suppression reset is incomplete. Preserve the files, resolve the local access or sharing error, inspect `status`, then use the stopped-agent `retry` command. That explicit retry also preserves state access metadata and unrelated raw fields. Repeating an unchanged mode or allowance request does not silently clear later suppression.

An `install` request validates all supplied options before mutation, then takes one operation lock, rereads current settings and saves one composed settings update. An invalid later metrics URL, capability file or secret binding cannot leave an earlier mode change applied. Omitted options preserve current values; an explicit `--allow-full-vector-config=false` revokes full mode, and an empty secret-binding object removes all bindings. A supplied capability policy replaces allowance lists but its `full_vector_config` value cannot grant or revoke mode; only the explicit CLI flag changes that grant, including on fresh installation. Policy and binding files must be bounded regular local JSON objects; duplicate keys, unsupported policy fields, malformed types and trailing input are rejected. Metrics require a literal loopback IP and a port from 1 through 65535. Empty explicit option paths, empty metrics URLs and positional arguments are rejected.

Fresh installation completes option, path, managed-directory and native version preflight before creating installation files. Directory creation for the lock happens only after that preflight; protection and the final freshness decision happen under the lock. A concurrent completed installation is reread instead of overwritten. If settings were saved but initial state creation failed, the command reports incomplete initialization; repeating `install` does not invent missing generation state or report completion. Preserve the files and inspect the failed installation while stopped.

Individual file replacements are atomic, but settings and state are not a single transaction. A durability error after a rename reports that replacement happened without confirmed durability. Unenrollment preflights settings/state access before removing identity and reports possible partial completion if a later deletion or replacement fails; its intentional identity/counter reset remains separate from ordinary settings maintenance. Do not infer from an error alone that no local change occurred. The access-metadata platform boundaries described under re-adoption also apply here; this does not change runtime state or credential writers globally.

## Full Vector configuration mode

To use the complete configuration surface of the adopted Vector build, add `--allow-full-vector-config` to the local installation command:

```powershell
vectory install --state-dir C:\ProgramData\Vectory\agent --vector-binary 'C:\Program Files\Vector\bin\vector.exe' --managed-config C:\ProgramData\Vectory\managed\vector.json --adopt --allow-full-vector-config
```

This explicit host grant persists `capability_policy.full_vector_config: true` in the protected local settings. It trusts pipeline publishers with Vector's process permissions: all available component types, global settings, enrichment tables, native secret providers, external VRL files, native environment references and executable integrations. The restricted file/network/component allowances do not constrain full mode. Actual support still depends on the adopted Vector build, OS, credentials, external services and provisioned host resources. There is no remote action that grants this permission. Enrollment and authenticated heartbeats report `configuration_mode: "full"` or `"restricted"` for deployment planning.

An existing installation can change mode while the agent is stopped, without re-enrollment or changing its adopted paths:

```powershell
vectory service-stop
vectory install --state-dir C:\ProgramData\Vectory\agent --allow-full-vector-config
vectory service-start
```

For foreground operation, stop `run`, execute the same `install` command, then restart `run`. Supply `--allow-full-vector-config=false` to return to restricted mode. Omitting the flag preserves the current mode. Mode changes retain identity, generation counters, pause state and local allowances, and clear suppression of an earlier failed configuration so it can be reassessed. Downgrading can prevent a full-mode last-good configuration from restarting; first prepare a configuration that meets restricted policy.

Full mode supplies Vector's native `--dangerously-allow-env-var-interpolation` flag and inherits the agent service environment. `VECTOR_CONFIG*` and launcher logging/watch/healthcheck controls are filtered so environment variables cannot add unmanaged configuration files or override the fixed launch. Native secrets use Vector's `SECRET[backend.key]` syntax and native provider definitions. The agent does not resolve or upload these values. Native provider/environment changes follow Vector's own loading behavior; managed-file drift and digest reporting describe the file, not provider-resolved runtime bytes. Pipeline stdin has no interactive input in the managed supervisor; use an explicitly configured source endpoint or file for event input.

Every activation performs real `vector validate`. A document with nonempty top-level `tests` also runs `vector test --config-json` before commit. Both share a bounded validation deadline and bounded, suppressed diagnostics; a failing test leaves the current workload intact. Native validation/tests may access configured host resources or execute native providers. Review those effects under the same full-mode trust grant. Managed files, signed manifests, anti-rollback counters, protected local state and recovery journals retain their existing safeguards.

The owned startup record and liveness checks confirm an observed process launch under that trust model. Full-mode publishers already control executable integrations and process output, so startup output is not an independent security attestation against a malicious publisher. Use restricted mode when publishers should be constrained by the local capability policy.

## Operation and state

`reported_generation` remains the last generation whose exact effective content was verified. A newer download, secret-resolution, validation or activation failure does not advance it. `configuration_attempt` separately records the authenticated candidate's generation, version ID, signed template SHA-256, stage, local secret revision and a fixed safe error snapshot. It is durable before candidate checks and travels on heartbeats. Its `verified_applied` label alone is not activation proof: the server still checks the verified generation and actual content digest. Generic startup errors for an older retained workload cannot replace the newer candidate's error.

A changed signed candidate clears the previous attempt before pause or other early exits. Unassignment removes the attempt while preserving the local workload. Recovery journals retain their original attempt identity; an older or legacy journal cannot attribute its rollback to a newer assignment. Secret rotation updates the attempt revision atomically with the durable local counter. Counter values are never rounded or clipped; exhausted protocol-safe counters require authorized local recovery.

Upgrading does not infer a historical attempt from the old `FailedGeneration` suppression field. An already suppressed legacy failure can therefore appear as awaiting current attempt evidence. After reviewing the cause, use the existing stopped-daemon `retry` command or deploy a reviewed version at a new generation to obtain fresh evidence. Upgrading or restarting alone does not automatically retry a suppressed configuration.

- `status --json` reports actual current file digest, cached apply state, pause, drift and metric availability. It also includes read-only `diagnostics` with a next action, retry suppression (`suppressed`, `not_suppressed`, or `unknown`) and local checks of the accepted desired template. It does not invent throughput/error counters or prove current process liveness.
- `doctor --json` verifies the adopted binary digest **before** executing its fixed `--version` probe, checks the managed path, and includes the same local diagnostics. A changed or missing adopted binary is never executed by the probe. A successful doctor command does not mean a failed deployment is now valid or active; inspect its diagnostic fields and wait for verified reconciliation.
- `pause` writes a durable local emergency marker immediately. A run in progress may finish/roll back a commit already started; the next heartbeat acknowledges pause only after that work completes. Remote resume cannot remove local pause.
- `resume` removes only local pause. Manual changes are replaced on the next authorized reconciliation unless remote pause remains enabled.
- `retry` clears suppression of a rejected generation while the daemon is stopped; restart the daemon afterward. A new server generation also permits a new attempt.
- `recover-enrollment --token-stdin` uses an administrator-issued, one-use device recovery token while the daemon is stopped. It preserves the local workload and local emergency pause, generates a new local key, and enrolls the replacement UUID. A durable identity transition journal resets generations only after the explicitly authorized replacement identity is committed. The old device's groups/assignments do not transfer. Authentication failures never trigger this operation automatically.
- `unenroll` removes local key/certificate/enrollment request while stopped, retaining workload/state. Revoke the device in the dashboard separately; offline local deletion cannot revoke server authorization. Re-enrollment of the old name requires the control plane's explicit recovery procedure.
- `uninstall` preserves identity/state. Remove service registration and binaries with the package manager. `uninstall --purge --state-dir <installed-state>` requires the explicit state path and recognizable installed Vectory settings, then deletes only that state directory while stopped; the externally configured managed file is retained. Purge holds a per-path lifecycle fence through deletion, so a current-version run, local pause/resume, service installation or settings operation cannot enter during removal. A held daemon operation lock refuses purge. A protected marker **inside** the state directory permits retry after interruption, including when `settings.json` has already gone, and binds the retry to the original directory object. Windows releases its file lock immediately before deletion because an open `agent.lock` cannot be removed there; its lifecycle mutex remains held. On Unix the file lock remains held through deletion. Stop older Vectory binaries before purging, since they do not observe this new fence. If interrupted after the marker is removed but before the final directory removal, purge deliberately refuses to treat the empty directory as an installation; inspect it and remove the empty directory manually. Unix syncs removals before removing the marker; Windows testing establishes process-interruption recovery, not physical-power-loss durability. This fence coordinates Vectory operations, not unrelated host processes that ignore its locks.

On Windows the per-path global mutex grants Authenticated Users only the rights to wait and release, allowing the service account and a separate maintenance account to coordinate. A local authenticated user who knows or guesses the path can precreate or hold this mutex and deny agent operations; affected operations fail without purging state. Restrict untrusted local logons on managed hosts. The in-state purge marker uses the protected state directory; retry with the maintenance identity that created it or inspect its ACL before recovery under another account.

Exit codes: 0 successful command, 1 operational/security/preflight error, 2 invalid command/options. `--json` provides machine-readable output. Errors omit configuration text, Vector's raw output, enrollment credentials and server error bodies.

For a rejected apply, the managed file can still contain the last working configuration. The diagnostic `desired_configuration` check instead inspects the cached accepted template only when its size and SHA256 match persisted metadata. It resolves approved Vectory local-secret bindings in memory and checks the effective local capability policy. A denied destination, listener, file path, dynamic feature or unsupported component receives a fixed category and corrective action without exposing its value. Missing/corrupt cache and unreadable secret bindings remain distinct from a permitted configuration. An identical rejected effective configuration reports `suppressed`; a changed local secret permits another attempt without diagnostics advancing any counters. `unknown` means inspection could not determine whether the current effective content matches the rejected attempt.

These checks do not run `vector validate`, configuration tests, native secret/configuration providers or environment interpolation; do not contact the server or destinations; and do not change pause, identity, retry state, journal or managed content. `capability_allowed` means only the current local static checks passed. Native validation and observed activation still happen during reconciliation. For a native validation failure, review the desired published version and host environment under the actual service identity, then use the dashboard's Retry action or stopped-agent `retry` after fixing the cause. Never share rendered configuration, raw provider output or credential files when requesting help.

Generations and semantic identities are durably persisted before fetching artifacts. Every poll hashes the actual managed file. A same-generation manifest is valid only if its desired/policy identities remain unchanged. Explicit rollback requires a newer generation. Local recovery uses a content-addressed last **verified** artifact; the separate pre-attempt snapshot can contain drift and is never promoted automatically. Journal fault tests cover validation, prepare, write, reload request, observed activation and durable verification. These are simulated boundary failures, not a claim of tested physical power loss.

The supervised lifecycle is deliberate: stopping/crashing the agent causes its helper to stop its owned Vector child; restarting the agent starts the current managed workload and recovers incomplete transactions. A control-plane outage or expired/revoked credential does not stop an already running child. Expired credentials do not prevent restoration of local last-good content at startup; network TLS still rejects expired credentials. There is no token-heartbeat fallback. Ordinary supervisor startup can launch the preserved current file while sync is paused, without replacing local edits.

While the agent remains running, a local health check restores an exited established Vector workload independently of heartbeat success, including after unassignment or while a newer candidate is rejected. Checks run during heartbeat waits and between credential renewal and heartbeat requests. Local or remote sync pause blocks this automatic restore/restart; pause is checked again after validation and before activation. Explicit agent startup retains the paused-start behavior described above. An unresolved apply journal blocks the watchdog until the existing recovery path can handle it.

Local restart attempts back off through 10, 20, 40, 80, 160 and 300 seconds. Backoff resets after a minute of observed healthy runtime, so a child that repeatedly exits after startup cannot trigger a tight restart loop. The five-second check interval is not a recovery-time guarantee: the single engine loop waits for bounded network/native operations, including each outbound request's 30-second deadline. Recovery uses the protected established content and current local capability policy; it does not retry the rejected candidate, change its failure snapshot, re-render Vectory local-secret bindings or advance verified generation/secret counters. The heartbeat observation reports a dead process as `verification_unknown`, with pause flags and candidate attribution retained; specific local startup/recovery failures remain available during backoff. Native providers and environment values still follow Vector's ordinary loading behavior.

## Verification and local security boundary

The fixed binary is SHA256-pinned at adoption and checked before each validation/start. Validation and launch use argument arrays, mode-appropriate environments, strict timeouts and bounded output. Activation requires the exact Vector 0.58 startup record from this newly started child, two seconds of liveness and a matching managed-file digest. A health endpoint, unrelated process, downloaded file or write cannot establish activation.

For this pinned release, JSON internal logging uses **stdout** (`src/trace.rs`), so restricted-mode console sinks must explicitly use `target: "stderr"`; stdout/default console is denied in restricted mode to prevent pipeline payloads from forging startup acknowledgment. The wrapper discards pipeline output and does not forward logs/events to the control plane.

Supported restricted-mode component set: sources `demo_logs`, `internal_metrics`, `file`, `http_server`, `syslog`, `opentelemetry`; transforms `remap`, `filter`, `route`, `sample`, `reduce`, `log_to_metric`; sinks `console`, `blackhole`, `http`, `loki`, `elasticsearch`, `prometheus_exporter`. Unknown components/root settings fail closed in restricted mode. File roots, exact network host:port destinations and listener addresses require local allowances. Network components must provide explicit destinations/listeners so implicit defaults cannot bypass local allowances. Execution sources, secret providers, external VRL files, environment substitution (`$VAR` and `${VAR}`), dynamic resource templates and unsafe VRL external lookups are denied in restricted mode. Disk data paths and TLS material paths must fall within allowed roots. API binding must be explicit loopback.

These are configuration restrictions, **not** a complete filesystem/network sandbox. DNS rebinding, allowed HTTP redirects/endpoints, changes to resources after validation and local administrators remain outside the static allowlist guarantee. Apply host firewall/network namespace and filesystem confinement when this stronger boundary is required. Agent and its Vector child currently share an OS principal; separate credential protection against a fully compromised Vector child is a remaining hardening gate. Windows restart uses forced termination; no lossless delivery claim is made. Linux uses SIGTERM with a bounded kill fallback.

Server certificate rotation uses the separately provisioned OS/private-CA trust store. Client credential and manifest signing trust refresh through authenticated renewal; replacement server CAs require local trust provisioning. Renewal generates a replacement ECDSA key and stores it before the request. A single private `identity.json` atomically commits the corresponding key, certificate and signing trust. Old PEM files are compatibility mirrors; torn mirrors cannot replace the canonical identity. An expired/revoked offline identity needs the explicit administrator recovery token flow. Restore of an old server database must not reset agent generations.

## Optional local telemetry

Provide a visible `internal_metrics` source feeding a `prometheus_exporter` sink with an explicit loopback address in the published pipeline. Authorize that listener in the local capability policy and pass `install --metrics-url http://127.0.0.1:9598/metrics` (idempotent install can add this local setting while stopped). The agent never inserts monitoring components and never enables an unauthenticated public endpoint. Only literal loopback IPs and an explicit port/path are accepted; redirects/proxies are disabled for this scrape.

To set or replace the endpoint on an existing installation, stop the agent through its supervisor and run `vectory configure-metrics --state-dir PATH --metrics-url http://127.0.0.1:9598/metrics`. To remove the local collector setting, use `vectory configure-metrics --state-dir PATH --clear-metrics-url`. Supply exactly one action; an empty URL, `--clear-metrics-url=false`, both options or unexpected positional arguments are rejected. `install` also accepts `--clear-metrics-url` and validates it with all other supplied options before changing settings. Omitting both install options preserves the current endpoint.

These commands save only the local setting, under the existing stopped-agent lock. An identical set or repeated clear is a byte-preserving no-op; changed values preserve unrelated raw settings, state, counters, failure suppression and access metadata. Neither command contacts the endpoint or verifies reachability. Start or restart the agent through its intended supervisor to load the setting. A cleared endpoint creates no collector and contributes no new telemetry to subsequent heartbeats, even if the remote telemetry policy is enabled. Remote telemetry pause keeps the local URL for later use. Clearing does not edit the pipeline, stop its exporter or remove server history; an older local telemetry observation remains until the next poll refreshes state. To remove an exporter, review and deploy the corresponding pipeline change separately.

The adapter accepts at most 1 MiB, 5,000 series, 10,000 lines and 32 KiB per line, with a three-second timeout. It reports aggregate source events/second from `component_sent_events_total` (excluding internal_metrics sources), observed cumulative `component_errors_total` and `component_discarded_events_total`, current `buffer_size_bytes`, and `uptime_seconds`. At most 50 components with strict IDs up to 100 characters report their sent-event rate, error/discard counters and buffer bytes when observed. Component types are bounded; host, URI, filename, error-detail and arbitrary labels are discarded. The server stores bounded sample history separately. The adapter accepts the pinned `vector_` namespace or an empty namespace. First samples, counter/process resets, missing series and unreachable exporters do not become invented zeros. CPU and RSS remain unavailable because the tested Windows internal exporter does not expose those process resources. Remote telemetry pause stops collection but does not stop heartbeats or workload. No event payloads or user samples are uploaded.

## Device-local credential references

Publish the exact string `vectory-secret:API_TOKEN` in a supported sink's `auth.user`, `auth.password`, or `auth.token` field. This Vectory-specific mechanism supports only `http`, `loki` and `elasticsearch`; these references anywhere else, embedded text, or executable bindings are rejected in both modes. Names match `[A-Za-z][A-Za-z0-9_.-]{0,63}`. The host operator approves a local JSON map such as `{"API_TOKEN":"C:\\secure\\api-token.txt"}` with `install --secret-files <absolute-map.json>` or stopped-agent `configure-secrets --secret-files <absolute-map.json>`. The map and secret files stay on that device; configuring an empty map removes its bindings. In full mode, bound Vectory credential values containing `$VAR`, `${`, `$$` or `SECRET[` are rejected so native preprocessing cannot reinterpret literal credentials; use a native provider directly for such a credential.

Both registration commands use the same strict reader. Supply an absolute local path to a regular UTF-8 JSON file without a BOM, at most 2 MiB, containing one object with at most 64 bindings. Values must be absolute local path strings. Null, arrays, duplicate names (including equivalent escaped names), trailing data, malformed UTF-8 and unpaired Unicode surrogate escapes are rejected before settings change. Literal Unicode and correctly paired escapes retain their exact decoded path. The complete map replaces prior bindings; only `{}` deliberately clears them. `configure-secrets` requires a nonempty `--secret-files` option and accepts no positional arguments. Direct callers must also supply a nonnil map; an omitted install option continues to preserve existing bindings.

An unchanged map preserves the original settings bytes and access metadata. A changed map uses the existing stopped-agent lock and access-preserving settings replacement, retaining unrelated fields, counters, retry suppression and managed content. Input validation errors do not print binding paths or credential values. Correct the input or reported local access problem before submitting the complete intended map again. Saving bindings does not start Vector or verify credentials; check the next authorized, unpaused attempt after restarting the same supervisor. Earlier binaries may accept ambiguous inputs; this behavior requires a build containing the strict-input change.

Each bound file must be a regular, single-link private file owned by the agent account or system administrator, with at most 16 KiB UTF-8 text and no NUL. One final CRLF/LF is removed; other contents are inserted only as a JSON string value. Unix uses descriptor-relative no-follow traversal with handle ownership/mode checks; Windows uses pinned handles, handle DACL/owner checks, no write/delete sharing and reparse/final-path checks. Symlinks, hardlinks and broadly readable files fail closed. Provision permissions for the actual service identity. Rotate by replacing the protected local file; the next authorized, unpaused poll re-renders even when the desired generation is unchanged.

The immutable artifact hash describes the reference template. `actual_sha256` describes the rendered managed file, while `applied_template_sha256` binds the last verified rendered file to its published template. A monotonic local `secret_revision` records each new effective attempt before validation; `applied_secret_revision` identifies the last verified local revision and does not move on rollback. Failed effective digests are suppressed, but a changed local value allows another same-generation attempt. Effective configuration is rechecked against the local capability policy and actual Vector validator. Generic error categories suppress subprocess diagnostics. The rendered managed file, stages and last-good/pre-attempt backups contain credentials and are protected with the agent's private file permissions; status, heartbeat, template cache and exports contain no resolved values. These hashes are operational identifiers, not password-strength protection; use high-entropy credentials.

## Evidence and remaining release gates

See [TEST-EVIDENCE.md](TEST-EVIDENCE.md). Windows 11 amd64 native foreground, local-secret rotation and loopback telemetry tests pass with official Vector 0.58.0. A stopped foreground replacement from the prior delivered Windows executable to the current extracted package also passed in restricted and full modes, retaining identity, settings, local pause, secret bindings and last-good state, with real authenticated event delivery after restart. The [upgrade procedure](../docs/AGENT-INSTALL.md#upgrade-an-existing-agent-binary) preserves the existing installation; its [native proof](evidence/native-upgrade.json) applies only to the recorded binary pair.

Linux amd64/arm64 and macOS amd64/arm64 binaries are **cross-compiled only** here; they are not tested support claims. Native package installation, SCM/systemd/launchd replacement and reboot, other platform/version upgrade paths, earliest supported OS tests, real power-loss tests, macOS orphan-child handling after helper SIGKILL, separate Vector identity, process-resource telemetry adapters and long-duration outage tests remain release gates. Do not label these artifacts production ready.
