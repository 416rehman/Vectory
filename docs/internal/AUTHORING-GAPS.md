# Can an operator manage every aspect of Vector from Vectory?

A hands-on review of pipeline authoring and Vector coverage at commit `f4d1826`, against Vector 0.58.0 as ground truth (`vector validate --no-environment`, `vector test`, `vector list`, `vector generate-schema`). It used a blank instance with three real agents (two in full mode, one restricted), a local HTTP collector, a proxy, a TCP collector and log files. Each finding was reproduced at least twice unless marked. Line numbers are from that commit; grep for the symbol.

Fixed since this assessment: the publish check runs pipeline tests (finding 2); Save as test excludes volatile and dependent fields (finding 3); definite creation refusals keep the form and imports check for credentials before creation (finding 5). Vector's configuration warnings now appear in diagnostics (finding 7). Agent activation restarts Vector when the `api` block changes (finding 10), refuses an unhealthy candidate when `healthchecks.require_healthy` is true (finding 11), and names `api.address` on a bind collision (finding 9); the requested inline API guidance remains open. The device page now shows the exact [effective configuration it offered](../user/deployments.md#read-what-a-device-was-offered), including per-device values and a diff (missing capability 3); it does not claim the device activated those bytes. A stale draft now preserves local edits, compares them with the server, and supports an explicit three-way merge when its starting revision was stored; older recovery copies remain compare/download only (finding 1). Device search now matches bounded enrollment labels, but label filters and dynamic selectors remain missing (finding 14). The preview refuses the plaintext header, URL and token cases with a field named, but cannot use device secrets in headers or URLs without the host-bound controls in [ADR 0014](../adr/0014-device-secrets-in-headers-and-urls.md) (finding 4). The findings below retain their original reproduction and scope at `f4d1826`.

The deploy review now derives each restricted device's host commands and refusal condition from its typed variable bindings instead of the published base value (finding 6). Unit and browser regressions cover two different listener ports; native deployment with those commands remains a release verification step. After Code changes are applied, auto-check runs in Code view; unapplied text instead asks to be applied before it can be checked automatically (finding 8).

## Verdict at the assessed commit

This verdict records what the reviewers observed at `f4d1826`. The fixes above and the current coverage matrix below take precedence when describing the release candidate.

1. **What works end to end from the browser.** Import or draw a pipeline (graph or code), have the real Vector binary check it, run VRL samples and unit tests, publish, deploy with per-device values and watch it apply and deliver within seconds. A 16-component pipeline (file with multiline, `http_server`, `exec`, a `remap` with a CSV enrichment lookup, `route`, `dedupe`, `throttle`, `sample`, `lua`, `log_to_metric`, and file, HTTP, socket, console and Prometheus sinks) was imported, deployed to a real device, and every destination received correct events, including a rotated device secret reaching Vector in under 30 seconds.
2. **Schema coverage is complete and honest.** All 128 components of the pinned binary (48 sources, 18 transforms, 62 sinks) and all 16 general global options, plus enrichment tables, secrets, tests and provider, are editable as typed controls. A 144-configuration battery agreed with `vector validate` on 126; the other 18 are the deliberate plaintext-credential refusals (16) and two device-deferred cases. Visual edits change only the touched fields, and YAML, TOML and JSON exports are semantically identical and natively valid.
3. **What sends an operator to a terminal.** (a) Capability is binary: restricted mode allows 6 of 48 sources, 6 of 18 transforms and 6 of 62 sinks, no `{{ }}` templates, and refuses harmless globals (`log_schema`, `schema`, `telemetry`, `expire_metrics_secs`); everything else needs full mode, which is root-equivalent trust on every host. (b) Files Vector reads (enrichment CSV or mmdb, TLS files, Lua) must be placed on each host by hand. (c) There is no view of the configuration a device actually runs and no sample of live events. (d) Credentials in headers and URLs cannot use device secrets, and some are stored in plaintext.
4. **Defects that cost an operator's trust.** A version whose unit test fails published as "Checked" and every device then refused it (fixed); "Save as test" asserts `now()` values so its first re-run fails; on a stale edit the only button discards the second editor's work although the docs promise a merge; importing a config that contains a token ends in "Creation result needs confirmation"; `?api_key=`, Slack path tokens and `X-Honeycomb-Team` are stored in plaintext history while the safe path is closed.
5. **The two biggest missing capabilities.** A middle capability tier plus managed assets, so a Kafka, S3 or Datadog pipeline with templates and a lookup file can be delivered without giving the host full-mode trust and without SSH; and live event sampling ([ADR 0011](../adr/0011-opt-in-event-sampling.md), designed, not built).

## Historical findings at `f4d1826`

The reproductions and proposed fixes below are preserved as the original review record. For current status, use the fixed-since summary above and the current coverage matrix; some proposed capabilities remain in the work queue.

### P1

**1. A stale-edit conflict leaves only a destructive path; the promised merge does not exist.** Opened one pipeline in two tabs, saved from tab A, edited and saved from tab B: B shows "The server draft changed. Reload it before discarding or saving these local edits." with one button, "Reload server draft", behind a native `confirm()` (`Editor.tsx`). After accepting, B's edits are gone, and reopening offers no recovery because the clean state clears the recovery copy. `docs/user/pipelines.md` promises "keep your changes, review theirs and save the merged draft." Two editors on one pipeline is the normal team case. *Fix:* on a 409 keep the local edits in a "Your version" state and offer, in order: Compare with the server draft (reuse `configurationDiff.ts` and the publish-review diff); Apply my changes on top (three-way by component id and path, base = the revision the tab loaded; list real conflicts); Save mine as a new pipeline; Download mine. Never clear the recovery copy on reload. Copy: "Someone saved a newer draft (revision 8, Ada, 2 minutes ago). Your edits are safe." with [Compare] [Apply my changes on top] [Save mine as a new pipeline] [Discard mine and reload]. *Acceptance:* with two tabs B's edit is merged or exportable, and nothing is discarded without a second explicit "Discard mine".

**2. (Fixed.) The publish check never ran the pipeline's unit tests.** A version with a failing test published as "Checked" and every device refused it with `TEST_FAILED`. The publish review now runs the tests in the isolated worker, shows how they went, and the server refuses a publish over failing tests unless it is acknowledged ("Publish anyway"). Keep the regression tests.

**3. "Save as test" bakes volatile values into assertions, so the test fails on its next run.** VRL with `.ns = to_unix_timestamp(now(), unit: "nanoseconds")`, then sample tester, Save as test, Run pipeline tests: the saved condition contains `assert_eq!(.ns, 1790732396945691543)` and the next run fails. *Fix:* run each sample twice and omit fields whose values differ; also omit fields assigned from `now()`, `uuid_v4`, `uuid_v7`, `random_*`, `get_hostname`; tell the operator "3 fields change on every run and are not asserted: ns, id, processed_at". Code: the test generator behind "Save as test" in `SyntheticTester.tsx`. *Acceptance:* a `remap` adding `now()` yields a test that passes on repeated runs.

**4. Credentials in headers and URLs cannot use device secrets, and several are stored in plaintext.** `vectory-secret:` in a header or URL is refused; `${VAR}` is deferred but restricted devices refuse it; plaintext in `Authorization` or `X-Api-Key` is refused with a message that names no location (`validation.rs`); and these validate and would be stored in draft history, versions, exports and diffs, readable by the viewer role: `uri: ...?api_key=abcdef...`, a Slack webhook path token, header `X-Honeycomb-Team`, header `Cookie`. The detector is a key-name list plus URL userinfo. The safe path is closed exactly where HTTP-style sinks need credentials, so operators paste them into whatever the detector misses; the specification requires references, not plaintext, in history and exports. *Fix:* (1) allow `vectory-secret:NAME` inside `uri`, `endpoint(s)` and `request.headers.*` values (whole value or `${...}` interpolation) with today's per-destination binding, substituted by the agent and redacted in logs; (2) widen the detector: header names containing token, key, secret, auth, team, cookie or signature; query parameters `api_key`, `token`, `key`, `sig`, `signature`, `secret`, `access_token`; well-known webhook path shapes; (3) name the field in every error (`sinks.h.request.headers.Authorization`) and, on a restricted device, say "use a device secret". *Acceptance:* the four accepted-plaintext cases are refused with the field named, and a header secret round-trips through a bound device secret to the collector.

**5. Importing a config that contains a token ends in "Creation result needs confirmation".** The dialog says "2 steps, checked locally" and enables Create; the server answers `400 INVALID_INPUT "Plaintext credentials cannot be stored in draft history"` and the dialog turns into the uncertain-recovery state with a "Review saved requests" button. Every failure after the request is saved counts as uncertain (`PipelineLibrary.tsx`). In the editor the same refusal appears only at Save, generic, after the code view said "No syntax or schema issues". *Fix:* treat a 4xx that carries a server rejection (`INVALID_INPUT`, `FORBIDDEN`, `PAYLOAD_TOO_LARGE`, `VALIDATION_FAILED`) as definitive: clear the reminder, keep the form, show the message inline. Scan on import and on code Apply with the existing `holdsPlainCredential` (`draftRecovery.ts`) and say "Line 12: `request.headers.Authorization` holds what looks like a credential. Replace it with `vectory-secret:NAME`." *Acceptance:* that import stays in the dialog, names the header and needs no recovery step.

### P2

**6. "Commands for the host" ignore per-device values, so the printed `vectory allow` needs three rounds.** `TargetDialog.tsx` computes `hostApprovals(version.config)` from the published base configuration. With per-device listener and exporter ports entered, the notice still named the default listener; after running the printed commands the device refused with `LISTENER_DENIED` for each remaining port in turn. *Fix:* derive approvals per device from the device's rendered configuration (the dialog holds the overrides) and print one command per host. *Acceptance:* one `vectory allow` run per host makes the deployment apply.

**7. Vector's own config-time warnings are dropped.** `vector_diagnostics.rs` `is_log_line` removes all tracing lines, including `WARN vector::config: Source has acknowledgements enabled by a sink, but acknowledgements are not supported by this source. Silent data loss could occur.` that `vector validate` prints. Vectory says "Vector 0.58 accepted this pipeline". *Fix:* keep `WARN` lines whose target is `vector::config` or `vector::topology` as warning diagnostics, with the component from `source="..." sink="..."`. Copy: "Sink out_http asks for end-to-end acknowledgements but source tick can't provide them. Events can be lost without an error."

**8. (Fixed.) Auto-check never ran in Code view, but the status promised it.** At the assessed commit, `Editor.tsx` required the canvas view for auto-check while the verdict said "Changed since the last check. Checking again when you pause." After Apply of a valid change in Code view it still read "Not checked" 25 s later. Auto-check now runs after Apply in Code view and asks for Apply when edits are still unapplied.

**9. A failed `api` bind is reported only as "Vector exited during startup observation".** Vector's log has `Failed to bind gRPC API server to 127.0.0.1:8686: Address already in use`; the dashboard gets `VECTOR_START_FAILED` without a cause (`agent/internal/agent/vector.go`, rules in `diagnose.go`). *Fix:* on early exit attach the last redacted ERROR line and map "Failed to bind ... Address already in use" to `ADDRESS_IN_USE` with `field: api.address`.

**10. A reload that enables `api` binds the default address, not the configured one.** With `api.address: 127.0.0.1:8541` applied by reload, Vector bound `127.0.0.1:8686` and the device reported verified while the pipeline says 8541; [ADR 0011](../adr/0011-opt-in-event-sampling.md) records the same Vector 0.58 behavior. *Fix:* activate by restart when the `api` block (enabled or address) differs from the running configuration, and say so beside the `api` fields.

**11. `healthchecks.require_healthy: true` is ignored at apply and honored at start.** With a failing sink health check the agent applied the version (`vector validate` printed "configuration valid; some health checks failed") and reported verified; after an agent restart Vector refused to start (`Sinks unhealthy.`) and the device read `verification_unknown` with `vector_running: false`. The agent deliberately passes no `--require-healthy` (`vector.go`). *Fix:* when the effective configuration has `require_healthy: true` and validation saw a failing check, refuse the attempt with the existing `HEALTHCHECK_REQUIRED` diagnostic (`diagnose.go`), or at least warn in the deploy review: "This pipeline tells Vector not to start while a sink is unhealthy. `h` fails its health check now (connection refused), so any restart of Vector on this device will leave it stopped."

**12. At 54 components "Fit" lands at zoom 0.15 and the layout is a tall stack.** The minimap overlaps the last column. *Fix:* level of detail below zoom 0.4 (labels only), a wider layered layout, the minimap outside the canvas frame.

**13. Restricted-mode notices are jargon and coarse.** "It uses Global setting: enrichment_tables, source: exec, transform: lua, transform: dedupe, ... Native capability: enrichment_tables, Native secrets, environment values or dynamic templates, Native capability: command, VRL access to device resources." *Fix:* group by reason in plain names: "Runs programs: exec, lua. Reads local files: enrichment table users. Uses templates: file path. Everything else here is safe in restricted mode: dedupe, throttle, ..." and add the host command that would allow the safe subset.

**14. The Devices search advertises labels it does not search.** The placeholder says "Search devices, labels, versions" (`DeviceList.tsx`); the search text is name, OS, architecture, pipeline, Vector, agent and group names only (`fleet.rs`). Labels can be set only at enrollment and cannot select devices. *Fix:* index `key=value` labels, add label filters, later label selectors for groups.

### P3

- Runtime errors show a raw byte span ("function call error for "parse_json" at (10:31)") beside "Line 1:11".
- The "+" to insert a step appears only after selecting the connection (`PipelineEdge.tsx`); show it on hover.
- When the session ends, the page underneath says "You have read-only access to this pipeline."
- YAML export leaves `yes`, `NO`, `2026-09-30` and `1_000` unquoted, which are booleans, a date and an integer in YAML 1.1 tools (Ansible, PyYAML); quote them so the file is portable.
- Route outputs are re-sorted alphabetically on import; imported route edges still pass behind neighbouring cards.
- The publish review prints "http http" and "Remap remap" (label equals type).
- A wrong route input yields "No sinks defined in the config." next to the real error.
- At 390 px the editor opens panned into the graph (first card off-screen) though nothing overflows horizontally.
- `draftRecovery.ts` `CREDENTIAL_KEY` matches any key containing `secret` or `token`, so a pipeline with such a key never gets a local recovery copy.

## Not reviewed

Server-restart recovery of dialogs; scheduled deployments; pause, resume, cancel and unassign beyond what the pages showed; agent settings policies, tokens and retiring devices; notifications and the audit log content; Windows and macOS devices; Kubernetes; a live-fleet canary; native `SECRET[]` rotation; VRL function help for each function; `log_namespace: true` behavior on a device; restricted-mode `exec` and file allowances beyond destinations and listeners; 5,000-device scale.

## What is genuinely excellent (do not regress)

- Complete, generated schema coverage (128 of 128 components, every global option) with typed controls, and edits that touch only what you change.
- The VRL studio: completion with signatures, quick fixes that keep semantics, sample diffs, abort and timestamp handling, exact 64-bit integers.
- Canvas guidance: greyed incompatible components with the reason, valid-port highlighting while dragging, wildcard edges, paste of foreign YAML.
- Deploy: per-device values with a paste-many option, a priority-conflict screen with "Replace existing", instant apply after publish, and restricted-mode preflight with the host commands.
- Honest recovery: "not confirmed, your edits are still here" on a lost save, "your session ended, your unsaved work is still here", and a rotated device secret reaching Vector in under 30 seconds.
- Truthful runtime state: "Applied, but not delivering", per-component metrics, Vector's own error lines, and diagnostics naming the step and field (`ADDRESS_IN_USE`, `LISTENER_DENIED`).
