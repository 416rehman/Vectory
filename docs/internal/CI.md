# What CI proves

Each automated job, what a green run shows, and what it does not. The job lists match `.github/workflows/`; `node scripts/check-ci-table.mjs` fails when they drift.

## release-candidate.yml

Runs only when dispatched; [packaging/README.md](../../packaging/README.md#release-candidate-workflow) has the command. Nothing is signed or published.

| Job | A green run shows | It does not show |
| --- | --- | --- |
| `agents` | The five agents build statically; archives, catalog and checksums verify; `.deb` and `.rpm` build with the pinned nfpm | Native behaviour on each OS |
| `packages` | The `.deb` and `.rpm` install, run and remove on Debian 12 and AlmaLinux 9 without creating an account or state | Service start under systemd, upgrades, running the arm64 build |
| `msi` | The MSI installs silently, the agent runs, no service is registered, removal cleans up | Signing, upgrades, service registration |
| `images` | Both images build, run as UID 10001 and 10002, and refuse to start without their safety settings; SPDX SBOMs of both | A vulnerability verdict: the SBOMs are its input |
| `sbom` | CycloneDX SBOMs of the Rust, Go and npm dependencies and a license inventory; `packaging/audit-npm.py` finds no high or critical advisory in the dashboard's or the help center's shipped dependencies that `packaging/npm-audit-exceptions.json` does not acknowledge, and keeps both raw audits as `npm-dependency-audit.json` | License clearance; an advisory published after the run; that an acknowledged advisory is harmless beyond the reason recorded for it |
| `assemble` | One verified folder with `SHA256SUMS` and `CANDIDATE.json`, including whether the image's agents are byte-identical to the release agents | Signatures or provenance |
| `verify` | The uploaded candidate, downloaded again the way a reader of the release page gets it, passes `sha256sum -c SHA256SUMS` and `packaging/verify-release.py` without refreshing the sums | The candidate's contents beyond what `verify-release.py` reads |
| `attest` | GitHub build provenance for `SHA256SUMS`, only with `attest` and a configured `release` environment | Anything about the candidate's contents |

## platforms.yml

Runs when dispatched (`gh workflow run platforms.yml --ref <branch>`) and when the workflow or a script it runs changes, not on every push. Each job keeps its evidence as the `platforms-<job>` artifact: one JSON file per phase (the checks in order, how long each took, what it observed) and the logs. The scripts are in `tests/platform/`; `node --test tests/platform/lib.test.mjs`, an early step of each service job, unit-tests the parsers they rely on against the text the tools print.

| Job | Runs | A green run shows | It does not show |
| --- | --- | --- | --- |
| `linux-service` | On Ubuntu 24.04 with real systemd: `vectory setup --create-user --ca-sha256` registers the generated unit and enrolls against a fresh instance; `tests/native-workflow.mjs` in service mode (publish, assign, verified apply, drift repair, pause, resume); the unit's properties, the journal and `systemd-analyze security`; the service's own mount table and writes as the service account inside its mount namespace; `systemctl restart`, `kill -9` of the agent, `systemctl stop`, `vectory service-start` and `service-uninstall`; then `packaging/systemd/vectory.service`, with only `ExecStart` changed, as the packaged unit, read the same way, with a pipeline applied under it | The documented setup works as a service under the unprivileged `vectory` account; the generated unit has the properties `docs/user/installation.md` lists, and from inside the running service `/usr`, `/boot`, `/etc` and `/home` are read-only except the state and managed folders, with other folders left to the account's permissions; the unit setup registers takes precedence over the packaged one; the packaged unit makes everything read-only except `/var/lib/vectory-agent`, `/etc/vectory/managed` and `/var/lib/vector`, hides `/home`, refuses a write elsewhere with a read-only error, and still applies a pipeline; a restart, a killed agent and a stop leave the last known good intact, no supervisor or Vector behind, and the device online again; systemd's exposure score of both units is on record | Other distributions, a reboot, an upgrade over an earlier agent, installing the `.deb` or `.rpm` (the packaged unit is placed where the packages place it), SELinux or AppArmor, Arm64, metrics and device secrets under the service (`end-to-end` runs them with the foreground agent) |
| `windows` | On Windows Server 2025: the server and the validator built and run natively, started with `packaging/Start-LocalPreview.ps1` (the job starts the validator and serves the CA after the certificate, as `scripts/preview.sh` does; the script does neither); `tests/native-workflow.mjs` with a foreground agent; then `vectory setup` registers the Vectory service, the workflow runs against it, and the service is restarted with `Restart-Service`, killed with `taskkill`, stopped, started and removed | The server runs natively on Windows with a real validator; the agent registers as a service under `NT SERVICE\Vectory` with automatic delayed start and restart-on-failure actions, checks in over a pinned CA, applies a pipeline, and is restarted by the Service Control Manager after a kill with no `vector.exe` left behind; stopping drains Vector; removal keeps the state | An administrator's edits to the managed file while the service runs, when the service account's access list leaves the administrator out (the steps that edit it are skipped and listed in the evidence), a reboot, an upgrade, the MSI, other Windows versions |
| `macos` | On macOS 15 (Apple silicon): `scripts/preview.sh` under the system bash 3.2, the foreground workflow, the Add device installer without a service, then `vectory setup --create-user` registers the `io.vectory.agent` launch daemon for `_vectory`; the workflow runs against it; `launchctl kickstart -k`, `kill -9`, `vectory service-stop`, `service-start` and `service-uninstall` | `scripts/preview.sh` and the installer work with macOS's shell and tools; the daemon registers with the definition `docs/user/installation.md` describes (owner, mode, account, keep-alive), checks in, applies a pipeline, is restarted by launchd after a kill with no Vector left behind, drains on stop, and keeps the state when removed | A reboot, an upgrade, the package, other macOS versions, Intel |

## Kept out of CI

| Check | Why |
| --- | --- |
| `tests/editor-connections-browser.mjs` | Waits for autosave; the editor now saves on an explicit Save. Needs updating. |
| `tests/catalog.mjs` | Rewrites the tracked `vector-catalog/catalog.json`, and its labels differ from the committed file. Decide which is right, then make it a check. |
| `tests/fleet-browser.mjs` | Written for Windows (`vectory-server.exe`, a `python` command). |
| `tests/initialize-preview.mjs` | A helper for a preview on port 8080, not a check. |
| `dashboard/e2e`: accessibility, audit-history, catalog, deployment-history, editor-details, pipeline-lifecycle, security-actions, workflows | Fail against a fresh instance at 7ae722d: they wait for autosave, look for the Overview's former "Needs attention" heading, expect older copy, or assume one pipeline and fixed data. They need a fixture dataset and updating. |
| `server/tests/*_native.py`, `agent/tests/native-upgrade.py` | Native scenarios that need extra Python packages; the upgrade test needs Windows. |
| `tests/load` | Capacity measurements, not a pass or fail check. |
