## 2. Server capacity

**Why.** [CAPACITY.md](CAPACITY.md) measured a release build on a 4-vCPU host with simulated devices: about 170 check-ins a second for unassigned devices with the single database writer half busy, and only 140 to 160 a second once devices are assigned, with the writer 97% busy, p99 1.5 to 3 seconds and the excess refused with HTTP 503. Creating an all-at-once deployment to 10,000 devices held the writer for 15 to 20 seconds in one transaction. Downloads and enrollments share the 128 agent request slots with check-ins that wait for the writer. Telemetry history costs about 755 bytes a row (1.1 MB per device per day at the default interval, about 76 GB for 10,000 devices over the default 7 days). Serving a fleet of thousands is a promise the product makes; this item makes the measured numbers much better without weakening any guarantee the specification and tests protect.

**Work, in this order (measure first; `cargo test --locked` stays green at every step).**

1. *Profile a check-in under the writer lock.* With `tests/load/capacity.py` (memory caps on; see `tests/load/README.md`; use `--devices` below 10,000 while iterating) find where the roughly 6 ms of writer time per assigned check-in goes: statements, JSON parse and serialize of the device record, telemetry upsert and its indexes, audit, the scheduler tick's fleet scan, reconciliation of desired state. Add timing at the `vectory_server::sqlite` debug target if needed and remove noise afterwards. Write the breakdown into `CAPACITY.md`.
2. *Do less under the lock per check-in.* In the order the profile justifies:
   - a check-in that changes nothing (same reported generation, apply state and telemetry shape) writes only what must be durable, and `last_seen` is coalesced instead of rewritten every time (state a maximum staleness and keep every screen and rule that reads it honest: offline detection, "last seen", issue rules);
   - batch the writes of check-ins that arrive together into one transaction (group commit on the single writer) without acknowledging a check-in before its state is durable and without reordering one device's check-ins;
   - do not re-serialize or rewrite a device's JSON record when only telemetry changed (split hot and cold columns if the profile says so, with a migration and no data loss);
   - prepare statements once, avoid per-check-in allocation of large values, and make the scheduler's fleet scan incremental (only devices whose assignment inputs changed) if it dominates.
3. *Bound the deployment transaction.* Creating, previewing and activating a deployment for thousands of devices must not hold the writer for seconds. Use set-based SQL instead of per-device loops where possible; if a single transaction still exceeds about 250 ms at 10,000 devices, split it into bounded steps that are safe to interrupt (a crash between steps leaves the deployment in a state the scheduler resumes or reports, never half-applied silently; add a test that kills the server between steps). Also stop `winners_among` copying the whole deployment record per device (preview, group edits, rollback review, assignment removal).
4. *Separate the slots.* Downloads (which never take the writer) and enrollments get their own bounded slots so they are not refused while check-ins wait for the writer. Keep the total bounded and keep the existing limits' error codes and `Retry-After` behavior.
5. *Telemetry storage.* Bring the default cost per device per day down by at least a factor of five without losing what the dashboard shows (latest values, sparkline ranges, counter resets and gaps). Prefer fewer, wider buckets for older data (downsample after a stated age) over dropping series; keep retention configurable; migrate existing rows safely. Update the storage numbers in `docs/user/telemetry.md` from a new measurement.
6. *Measure again* with the same harness and memory caps. Record the run, hardware, source hash and raw JSON under `docs/evidence/`, and rewrite the summary paragraph of `CAPACITY.md` and the capacity paragraph of `HANDOFF.md`. Report what did not improve and why.

**Targets, not promises (report honestly what is reached).** Assigned devices: at least 4 times the 140 to 160 check-ins a second on the same shape, p99 under 1 second at the level a fleet asks for at a 60-second interval (10,000 devices is about 167 a second). An all-at-once deployment to 10,000 devices: no writer hold above 250 ms, no check-in refused or timed out because of it, half the targets verified within 2 minutes on the simulator. Downloads and enrollments succeed while check-ins queue. Server RSS under 1.5 GiB at 10,000 connected devices. No test weakened; new tests for coalesced `last_seen` staleness bounds, group-commit ordering and durability (an acknowledged check-in survives `kill -9`), the interruptible deployment steps, slot separation, the telemetry migration and downsampling, and unchanged offline detection.

Areas: `server/` including migrations and tests, `tests/load/`. Additive wire fields are fine; say so in `contracts/CONTRACT.md`. Cap memory of the server and the driver as the harness does, and run one heavy thing at a time on a shared machine.

## 5. Effective configuration per device

An operator must be able to answer, for any device: "what configuration was this device offered, is it what runs now, and what differs from the previous one?" Today the dashboard shows versions, diffs between pipeline versions and the apply state, but never the artifact bytes a device receives (the pipeline with this device's variables applied, secrets left as references). Add that, read-only, end to end.

**What exists.** Per-device artifact bytes are content addressed: `artifact_blobs(sha256, size, artifact)` is immutable and `desired_artifacts(device_id, generation, version_id, sha256, created_at)` records exactly which bytes each device was offered at each desired generation (`server/src/variables.rs`: `render`, `target_artifact`, `snapshot`, `current`, `blob`; `server/src/device.rs` serves `/agent/v1/artifacts/{sha256}`). The agent reports `actual_sha256` (recomputed before each reconciliation); the device record carries `desired_artifact_sha256`, `applied_template_sha256` and `verified_effective_sha256`. Restricted and full mode, device-local secrets (`vectory-secret:NAME`) and typed variables already exist; the server never sees resolved local secrets.

**Deliverables.**

1. `GET /devices/{id}/configuration`, readable by the same role that reads a pipeline version today: the current desired generation's artifact for that device: `{generation, version: {id, number, configuration_id, configuration_name}, sha256, size, format: "yaml"|"json", content (bounded by the 1 MiB artifact limit), variables: [{name, value|null, source: "device"|"group"|"default"}] (secret-typed variables never appear as values), running: {sha256|null, matches: boolean|null, reported_at}, previous: {generation, version, sha256}|null}`. `?generation=N` reads an older generation the device was offered (404 when it never had it). `Cache-Control: no-store`, bounded, no audit row (a read), unknown or revoked devices answer as the device read does, never reachable across accounts. Authorization tests for every role.
2. `GET /devices/{id}/configuration/diff?from=&to=` (default: previous offered generation to current): a bounded unified diff (at most 2,000 output lines with a truncation marker) plus a structured form for the dashboard (`{added, removed, changed}` counts and hunks). Reuse an existing diff implementation if one exists (grep before writing one).
3. Drift truthfulness. `running.matches` is `true` when the agent's `actual_sha256` equals the digest of what was offered at the reported generation, `false` when the agent reports a different digest (a local edit or an activation not finished), `null` when it reports none. When `false` and the agent's digest is in `artifact_blobs`, say which generation it matches. Never claim the content of a local file the server has never seen; the agent does not upload it. Document how an operator sees the local file (`vectory status` and the host path).
4. Dashboard: an "Effective configuration" section on the device page, as a new component with one mount point in `DeviceDetail.tsx`. A read-only code viewer (monospace, line numbers, wrap toggle; lazy-load it), a generation picker ("Current: v3 · generation 12", earlier offered generations), Copy and Download YAML (never claim the download was verified as activation), a diff view ("What changed since generation 11": counts, then hunks, phone friendly), the variables table, the drift line ("Running matches what Vectory offered" / "The running configuration differs from what Vectory offered at generation 12: it matches generation 10" / "Not reported by this agent") and a link to the pipeline version. Loading, empty ("Nothing offered yet: deploy a pipeline"), unauthorized and error states with the shared primitives.
5. Optionally, if the inventory rows already carry both digests, a "Differs from offered" view counted on the server (`counts.views`), documented in the contract.
6. Tests and docs: server tests (offered versus older generation, variables applied per device, a secret variable never returned, diff bounds, drift true/false/null, roles, cross-account, revoked), contract entries (regenerate; `tests/contracts.mjs` validates the responses), vitest for the diff-hunk and drift-sentence models, a Playwright harness added to the dashboard job of `.github/workflows/ci.yml` (one step, `timeout-minutes: 10`), the device page and variables docs, a changelog line.

Rehearse: deploy a pipeline with a variable to two devices with different values, open each device's effective configuration, deploy a second version and read the diff, edit the managed file on one demo agent by hand and see the drift line.

## 6. "Check on devices": validate on the real hosts before deploying

**Why.** The server validates a pipeline in an isolated Vector worker, but many failures exist only on the device: a missing device-secret binding, a data directory that is not writable, a port below 1024 for an unprivileged agent, a destination the host has not approved in restricted mode, a Vector build that lacks a component. Today the operator finds out after deploying. Add a dry run: before deploying, the review asks the target devices to validate the candidate on their own hosts, without activating it, and shows a per-device matrix.

**Design (deviate only for a reason you write down).**

1. *A validation request rides the signed manifest.* The heartbeat reply gains an optional `validation: {id, sha256, size, artifact_path, run_tests, expires_at}` for at most one outstanding validation per device (the agent reports the previous result first). It is covered by the manifest signature like every other field, bound to the recipient device UUID and nonce, and listed in the manifest `features` (`validation`) so old agents ignore it and old servers never send it. It changes no generation, desired state or policy.
2. *The candidate artifact is downloadable by the device only for the validation.* `/agent/v1/artifacts/{sha256}` authorizes an artifact for a device when it is that device's desired artifact today; extend it to authorize the digest of an unexpired validation addressed to that device and nothing else (a new table `device_validations(id, device_id, sha256, size, run_tests, requested_by, created_at, expires_at, state, result)`). Cross-device isolation tests: device B cannot fetch device A's candidate; an expired or completed validation stops authorizing the download.
3. *The agent validates a staged copy and never activates.* On a verified manifest with `validation`, download the artifact to a private staging path outside the managed directory, verify digest and size, substitute device-local secrets with the same code path as an apply (restricted-mode policy, the secret table, missing bindings), run `vector validate` with the pinned binary and, when `run_tests`, `vector test`, under the same timeouts, then delete the staging copy. Report `validation_result: {id, valid, diagnostics[], tests[], duration_ms}` in the next heartbeat (bounded: diagnostics as the apply path shapes them, redacted the same way; at most 20 diagnostics and 100 tests; never subprocess output that could contain a secret; never file paths of secrets). It never touches the managed file, the journal, last-known-good, generations or Vector's process; an apply in flight defers the validation; a paused or drifted agent still validates. Heartbeat readiness facts (additive; names and booleans only): `data_dir_writable`, `configuration_mode`, a capability profile summary (the allowed listener count, not the list), `vector_version` (check what `host_runtime` already carries and reuse it).
4. *Server API.* `POST /deployments/preview` gains `device_validation: true` (operators and above, CSRF, audited as `deployment.device_validation_requested` with counts, never the pipeline body): after the preview it creates one validation per reviewed target device that is online enough to answer soon (skip revoked; mark offline devices `offline` without waiting), at most 50 devices per request (more: validate the first 50 by name and say `truncated: true`), and returns `validation_id`. `GET /device-validations/{id}` (the caller's own, or an administrator) returns `{state: "running"|"complete", devices: [{id, name, state: "pending"|"passed"|"failed"|"offline"|"expired"|"unsupported", diagnostics[], tests[]?, secrets_missing: [name], updated_at}]}`, bounded; `unsupported` for agents that do not list the feature. Expiry 10 minutes; at most 6 requests a minute per user; one validation per device at a time. Results are advisory: the deploy button never depends on them, and no server state changes because of a result except its own record.
5. *Dashboard.* A "Check on devices" button in the deploy review (operators and above), as a new component with one mount point: a per-device matrix while it runs (passes here / fails with component, field and fix, reusing the diagnostic rendering of the rollout failure card / device secret NAME isn't bound, with the exact `vectory configure-secrets` command / offline / "Older agent: can't check"), phone cards, a summary line ("Checked on 3 of 4 devices: 2 pass, 1 needs a secret, 1 offline"), Retry for one device, and it never blocks Deploy. It says "This checks the version on each host; it doesn't start or change anything." Poll at 2 s while running and stop when complete or the dialog closes.
6. *Contracts and docs.* `contracts/CONTRACT.md` and `generate.mjs` (manifest `validation` and the `features` value, heartbeat `validation_result`, the two routes); `protocol.schema.json` must accept the new fields and old agents' heartbeats; user docs (deploy a pipeline: "Check on devices", troubleshooting rows for each failure reason); `docs/security/THREAT-MODEL.md` (what a malicious server or compromised operator can do with a validation: at most make a device download and validate an artifact it would accept anyway, and read back diagnostics that the agent redacts).

**Tests (all required).** Server: request and response lifecycle, per-device isolation of the artifact download, expiry, rate limits, roles and CSRF, bounded results, offline and unsupported handling, audit row content, old-agent heartbeat unchanged. Agent: a verified manifest with `validation` triggers staging, validation and cleanup; a bad signature or wrong recipient never does; an apply in flight defers it; a missing secret binding, a restricted-mode refusal and a failing `vector validate` produce the right diagnostics; the managed file, journal and last-known-good are byte-identical before and after; the result never contains a secret value. Native test with the pinned Vector: a passing and a failing candidate. Protocol suite subtests. Dashboard: vitest for the matrix model and copy, a Playwright harness with a synthetic transport for every state, and a live rehearsal.

## 7. `vectory status` distinguishes verified from running

Implemented: `vectory status` names the pipeline and version number from the signed manifest when known, shows the last verified version separately after a rollback or unassignment, and reports the service, check-in timing and wake-ups. These are stored outcomes, not proof that Vector is running now. The older JSON key `running_pipeline` retains its wire shape and identifies last verified metadata. New manifest fields are additive, covered by the signature and listed in `features`; the agent shows less rather than inventing when the server is older. The CLI guide and golden tests reflect the current wording.

## 9. Capability tiers and managed assets

The biggest gap between "Vectory runs Vector" and "Vectory manages all of Vector": capability is binary today. Restricted mode allows 6 of 48 sources, 6 of 18 transforms and 6 of 62 sinks, no templates and refuses harmless globals; everything else needs full mode, which is root-equivalent trust on every host.

- **Graduated capability tiers.** Host-approved component and setting allow-lists next to `vectory allow` (`--component kafka`, `--templates`, `--global log_schema`); pure transforms and harmless globals allowed by default; the dashboard shows per component "allowed / needs host approval" with the exact command, computed per device including variable overrides. A static, generated and drift-tested table in the agent decides what a tier allows (the server never tells the agent what to allow). Acceptance: a restricted device applies a version using `log_schema`, `timezone` and `dedupe`; one `vectory allow` run per host makes a Kafka pipeline apply; the deploy dialog says which components are allowed and which need approval.
- **Managed assets.** Upload a CSV, mmdb, CA bundle or Lua file once; versions reference it by name and hash (`vectory-asset:NAME`, content addressed, at most 10 MiB, delivered with the artifact); the agent fetches it over the authenticated channel, verifies it, places it in a managed directory and reports presence per device; the dashboard shows per device that the file is present with its hash. Restricted mode allows only the asset directory. Ship enrichment CSV and mmdb and CA files first.

Both are designed: [ADR 0012](../adr/0012-graduated-capability-tiers.md) (tiers, host approvals, the service sandbox), [ADR 0013](../adr/0013-managed-assets.md) (managed assets) and [CAPABILITY-IMPLEMENTATION-PLAN.md](CAPABILITY-IMPLEMENTATION-PLAN.md) (steps, wire and storage, what an independent review must attack). The recommendations in the ADRs are the defaults taken for implementation (tier names and classification, the three tightenings, full mode keeping today's sandbox, `allow` and `disallow` restarting the service after a prompt, assets in SQLite with a 1 GiB quota and 10 MiB per asset, `tls.key_file` as a device-secret field, two releases: tiers and sandbox first, then assets); change them in the ADR before building if a maintainer decides otherwise. An independent review of the agent policy changes gates each release.

## 10. Opt-in event sampling

Designed in [ADR 0011](../adr/0011-opt-in-event-sampling.md) and planned in [TAP-IMPLEMENTATION-PLAN.md](TAP-IMPLEMENTATION-PLAN.md). Do Step 0 of the plan first (it is also security finding 5): the agent owns Vector's local `api` block, so a pipeline can no longer open an unauthenticated API. Then follow the plan's order (contract, server, agent, dashboard, docs and CI, integration and independent review). Nothing in the plan ships until the independent review of the finished code signs off; the plan lists what that review must attack. "Use real events" in the VRL studio comes last.

## 11. Access and platform breadth

- **Recent-authentication step-up for sensitive actions.** One shared "confirm it's you" mechanism (password, or the account's second factor when enabled) valid for a short window (5 minutes), required for creating or inviting an administrator, issuing enrollment tokens, changing signing keys or the agent policy, and break-glass resets. Editing roles and password resets already re-enter the password: unify them behind the same helper and dialog so the UX is identical everywhere. Keyed wire formats stay exact: add the field (or a step-up token) explicitly, update `CONTRACT.md`, the OpenAPI document, the People and Add device dialogs and every test that creates administrators; audit when a step-up was used. Tests: expired window, wrong password, MFA path, viewer and operator denial.
- **Labels and selectors.** Operator-assigned device labels (setter API, audit, bounds), label selectors in the shared target selector (deployments, group previews), Devices search and filter by label, CSV import and export of per-device variable values, group default values. Fleet Vector version inventory ("3 devices on 0.58.1, 2 on 0.58.0") with package-based upgrade guidance; never silently replace Vector.
- **Single sign-on with OIDC.** An administrator configures a generic OIDC provider (issuer URL, client id, write-only client secret, scopes, allowed email domains, group or claim to role mapping with a safe default of no access). Authorization-code flow with PKCE, state and nonce; discovery fetched by the server only from the configured https issuer (timeouts, size caps, no redirects to other hosts, SSRF-safe: block loopback, link-local and metadata unless explicitly allowed). Local password login stays for break-glass administrators; document the MFA policy interplay; audit every SSO sign-in and role-mapping decision; create users just in time with the mapped role. Tests with a local fake OIDC provider (tokens, bad signature, wrong audience, replayed code, expired).
- **Platform.** Kubernetes and container mode (design note in `docs/adr/` first; implement only the agent sidecar mode if time allows), a Helm chart skeleton, OpenMetrics export of fleet metrics behind a scoped token, API tokens for automation (specification section 12).
