# Threat model and risk decisions

Scope: single-instance self-hosted control plane, browser administrators, reusable enrollment tokens, outbound agents, locally managed Vector. This is an implementation checklist; passing evidence belongs in the [requirements checklist](../internal/REQUIREMENTS.md) and the CI workflow `checks`, not in this document.

Assets include control-plane signing/device-CA and MFA sealing keys, sessions, enrollment verifiers, agent identity keys, immutable reference templates, device-local secret files, rendered managed/recovery configurations, generation/revision counters, and group membership. Pipeline event payloads are not telemetry.

| Boundary / attacker                               | Required control                                                                                                                          | Failure behavior / acceptance probe                                                                                                              |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Network attacker at bootstrap                     | HTTPS verified before sending token, independently provisioned server CA, TLS 1.3                                                         | Wrong CA/hostname fails without token disclosure; no automatic CA fetch/trust                                                                    |

| Stolen password or replayed pre-session MFA token | Password-first challenge with no session authority; five-minute expiry, five wrong codes per challenge, one account budget of ten second-factor attempts in five minutes for both sign-in forms, a five-wrong-codes lock on the combined password-and-code form, account rate limits and live credential/MFA checks | No MFA disclosure for bad credentials; account changes, enrollment changes, logout, session revocation and restart invalidate pending challenges; a correct password plus six wrong codes from two addresses is throttled, and a correct code inside the lock is refused |
| Cross-site request / stolen cookie                | HttpOnly Secure SameSite=Strict session, CSRF token, role check on every mutation                                                         | Missing/mismatched CSRF and viewer mutation fail                                                                                                 |

| Manifest or artifact replay                       | Ed25519 exact bytes, device UUID, fresh request nonce, expiry, persisted generation/digest binding                                        | Wrong recipient, reordered/same-generation changed content, bad digest/signature fail                                                            |
| Malicious pipeline author on a restricted device  | Configuration treated as code; bounded local capability allowlist; no shell; immutable sole managed path                                  | Exec, native providers, AWS credentials files, the host's own AWS identity and arbitrary roots/endpoints denied before validation/apply; `allow`, `install` and `setup` refuse file roots over `/` or the agent's own files |

| Hostile telemetry / large fleet                   | Bounded request, metrics, queues, retention; sanitized diagnostics                                                                        | Resource bounds and drop counters; no config/secrets in diagnostics                                                                              |

| Flood of idle or slow connections, or of `accept` failures, on the agent listener | A connection holds a connection-limit slot but no handshake slot while it has three seconds to deliver a complete ClientHello; handshake slots scale with `VECTORY_MAX_AGENT_CONNECTIONS`; after TLS completes, a connection has 15 seconds for its first request's headers to reach the service, including protocol detection and the HTTP/2 preface; a failed `accept` is logged, waited out and retried | Silent TCP peers do not hold handshake slots but can saturate the connection limit for up to three seconds at a time; a peer that completes TLS but sends no request, a partial preface or only a full HTTP/2 preface releases its connection slot at the first-request deadline; descriptor exhaustion never ends the server |

| Backup theft / old restore                        | Backup contains required keys and consistent SQLite snapshot; restricted encrypted storage                                                | Restore preserves trust but cannot lower agent generation floors                                                                                 |
| Supply-chain attacker                             | Lockfiles, checksum catalog, SBOM, provenance and real signing gates                                                                      | Missing artifact omitted; unsigned development outputs explicitly labeled                                                                        |

## Event sampling

Proposed in [ADR 0011](../adr/0011-opt-in-event-sampling.md); nothing is built. Sampling lets an Operator read redacted events from one component of one device, and only where the host operator allowed it with `vectory configure-sampling`. This section is the checklist an independent reviewer should attack before and after the code exists. Event content is the most sensitive data Vectory would ever hold; it is not telemetry.

Assets added: the host's consent (`event_sampling` in `settings.json`), the per-device sampling generation, the runtime overlay's `api` block, redacted events in server memory for 15 minutes, and the audit metadata about them.

| Attacker | Control | Residual risk | Acceptance probe |
| --- | --- | --- | --- |
| Compromised server or signing key | The agent reads consent from a file no manifest can write. Effective limits are the smaller of the request and the host's caps. The agent allows at most 12 sessions an hour, 30 s apart. The component ID must match a fixed rule and exist in the local managed file. Redaction runs in the agent; the default mode sends field names and types only | The server can request from any consenting device. In `values` mode it can collect up to 20 redacted events per session, 12 sessions an hour, from any component, and can time windows to open the local exposure. A redaction miss leaks | Settings bytes are identical after hostile manifests (A-02). A request without consent is refused (A-01). The 13th session in an hour is refused (A-13) |
| Operator with a stolen session | Operator or Administrator role only; CSRF and cross-site refusal; a mandatory audited reason; 6 requests a minute per user, 12 an hour per device; one open request per device; requester-only reads; 15-minute memory-only storage | Until the session is revoked, the thief can sample every consenting device and read the results for 15 minutes. A lifetime of 12 hours applies | Viewer and Editor get 403 (S-01). Limits hold (S-04). A second user or an Administrator reading gets 404 (S-08) |
| Another operator or an Administrator | Events are readable by the requester only, Administrators included. Request metadata has no event content. Copying events into a VRL sample or unit test is audited | An Administrator with access to the server host can read process memory. Not preventable in the product | Cross-user read denied (P-04). Audit and logs carry no bodies (S-09) |
| Curious or hostile local user on the host | The consent prompt names the exposure. The window is at most 120 s (30 s by default) and rate-capped, so the API is open at most 10% of an hour at the defaults. The agent watches the connection table every 500 ms, aborts on a foreign client, discards the events, and restarts Vector if any client stays attached after close. No window opens while the device is paused, drifted or unsettled | Vector's API has no authentication. A local user can read every component's raw events, unredacted, for up to 500 ms before detection, and a stream attached before the window closes survives it until Vector restarts. Hosts with untrusted local users must not allow sampling | A foreign client aborts the window and forces a restart (A-09, A-15). An attached stream survives a reload and dies with Vector (measured, ADR 0011 Appendix A, E3 to E5) |
| Local user who squats or races port 8686 | Reload can only enable the API on `127.0.0.1:8686`, and a failed bind stops Vector, so the agent binds and releases the port first and refuses if that fails. The overlay is rebuilt without the `api` block at the next restart, and supervision restarts Vector | A user who binds the port between the probe and Vector's bind stops Vector until its restart. Only possible during a requested window on a consenting host | A busy port refuses without a reload (A-08). Vector stopped by a bind failure recovers (A-15) |
| Network attacker | Outbound-only agent; mutual TLS; a manifest signed for one device with the agent's nonce; the upload uses the same mutual-TLS channel; no listener beyond Vector's loopback API | Can delay or drop a request or an upload. Cannot read or forge a sample | A replayed manifest and a manifest for another device are refused (P-02). A tampered `sampling` field fails the signature (P-02) |
| Pipeline author who names a component | Component IDs must be plain (no glob, comma, space or leading dash) and match the local file. Vector runs as an argument array with the equals form, no shell. Event content is untrusted text: bounded, and rendered as text, never as markup | In full mode a publisher can place host environment values or secrets into an event field; the agent scrubs the values it knows, not those native providers hold. That publisher already has exec and network access in full mode | ID cases (A-05). An event containing markup renders as text (B-03) |
| Compromised device | The server validates every upload: structure, bounds, one upload per request, own device only. Content is shown as text. A device cannot name another device's request | A lying device can invent events or claim consent it lacks. It cannot read another device's samples | Upload validation (S-07). Another device's request is 404 (P-03) |
| Stolen backup or database copy | No events and no keys for them exist at rest. The database holds request metadata and counts | Who sampled what, when and why is in the backup, like all audit metadata | A planted canary is absent from the database, WAL, backup, export and logs (S-08 to S-10) |

Decisions for sampling:

- Consent lives only in the host's `settings.json`, written by `vectory configure-sampling` while the agent is stopped. No manifest, policy, installer flag or dashboard action can write it, and `setup`, `install` and `enroll` never gain a sampling flag.
- Restricted mode does not accept a pipeline `api` block (`LOCAL_API_DENIED` in `CapabilityPolicy.Check`; `requires_full_mode` and the dashboard agree), so the host owns Vector's API. This was the prerequisite for sampling.
- A reload re-reads the managed file, so sampling never opens a window on a paused, drifted or unsettled device. A window that finds drift when it must close repairs the file through the ordinary path first, or stops Vector when the device is paused, instead of activating unverified content.
- The agent never leaves the API enabled: the overlay is rebuilt from scratch by every activation, and the window's closure is proven by a refused connect and an empty connection table, not assumed.
- Redaction has no remote switch and there is no raw mode. `shape` (field names, types, sizes) is the default; `values` is a separate host choice meant for sandbox and staging hosts.
- Samples exist only in server memory, for 15 minutes, for the requester. Promotion into a VRL sample or a unit test is explicit and audited because it makes the data durable.
- The measured Vector behaviors (fixed reload address, fatal bind failure, surviving streams) are pinned to 0.58. A Vector upgrade reruns the native behavior probe before sampling stays enabled.

## Graduated capability tiers

Proposed in [ADR 0012](../adr/0012-graduated-capability-tiers.md); the tiers are not built. Two of its refusals already are, without the table: restricted mode refuses an AWS credentials file and the host's own AWS identity (`CREDENTIALS_FILE_DENIED`, `AMBIENT_CREDENTIALS_DENIED`, in `policy.go`), and `vectory allow`, `install` and `setup` refuse a file root that is `/` or a volume root or that overlaps the agent's state directory, the managed configuration directory or a bound secret file (`file_roots.go`). Restricted mode gains built-in components, component types a host approves and two host capabilities (`managed-ca`, `instance-credentials`), and on Linux with systemd the service sandbox follows the host's mode and allowances. The [implementation plan](../internal/CAPABILITY-IMPLEMENTATION-PLAN.md) assigns the tests named below.

Assets added: the capability table compiled into the agent; the host's approvals (`allowed_components` and `allowed_capabilities` in `settings.json`); the generated sandbox drop-in (`/etc/systemd/system/vectory.service.d/10-vectory-sandbox.conf`); the capability report each heartbeat carries and the server's stored copy.

| Attacker | Control | Residual risk | Acceptance probe |
| --- | --- | --- | --- |
| Compromised server or signing key | The agent decides with its own compiled table and the host's local approvals. No manifest, policy or response field reaches either, and an older agent keeps its older table. The server's needs and the device's report only explain | It can deploy any built-in component, or any component the host approved, within the host's destinations, listeners and roots. An approval reaches what it says: every broker an approved Kafka cluster advertises, every bucket the host's credentials can write. With `instance-credentials` granted it signs with the host's cloud identity | Settings and drop-in bytes are identical after hostile manifests (Steps 3 and 6). An unapproved component is refused with `COMPONENT_NOT_APPROVED` (fixtures, Step 2) |
| Operator with a stolen session | Operator role and CSRF for deployments. The dashboard prints host commands and can't run them. `vectory allow` shows what it adds and asks before it restarts the service, and refuses `/`, volume roots and roots overlapping the agent's state or the managed configuration | The thief can deploy within what hosts allow, and can put a broad command in a deploy review hoping a host operator runs it unread, such as `--component docker_logs` | The printed command never carries `--yes` (Step 5). Dangerous roots are refused (Step 3) |
| Malicious pipeline author | The table refuses programs, code loading, providers, secret backends, environment interpolation, unconfined templates, passthrough options, and ambient credentials without the capability, on the configuration after every substitution. Vector confines templates and the agent checks their static parts. On Linux with systemd the kernel enforces the write half | Within approved resources the author controls everything: which approved destination, which file under an approved root, which topic under an approved prefix. A field the table misclassifies is a hole until a review finds it | Golden fixtures for each refused shape (Step 2). The native probe pins Vector's confinement. The native sandbox job refuses a write outside the roots with `SANDBOX_READ_ONLY` (Step 6) |
| Hostile event data | Vector 0.58 confines templates: an event can't change a URI's host or port, add a query, or leave a file sink's base directory. The agent refuses the opt-out. Event text that reaches a report or a terminal is neutralised: the agent and the server replace control characters, line and paragraph separators and text-direction controls in the log text and diagnostics they send and store, so an event can't make the server refuse a check-in, and `vectory logs` shows them as escapes | An event chooses suffixes (file names under a base directory, topics and keys under a prefix, labels) and can create many of them inside an approved root or destination. An escaping event is dropped and logged. `vectory logs --raw` is the file as written and can hold terminal escapes | ADR 0012's measurements [at validation](../adr/0012-graduated-capability-tiers.md#templates-at-validation) and [at run time](../adr/0012-graduated-capability-tiers.md#templates-at-run-time), reproduced by the native probe. The agent's hostile-text tests and the server's heartbeat tests send a control byte through a log summary and a diagnostic |
| Compromised Vector process or service account | The sandbox bounds where it writes (Linux with systemd). Every value regenerated into a unit is revalidated and quoted, so a value can't become a directive, and the root-run command prints every path the sandbox gains | It shares the agent's account and namespace: it can write the agent's state, including `settings.json`, and so widen the policy at the next agent start and the paths the next root-run regeneration adds. macOS and Windows have no sandbox; the account's permissions are the limit | Hostile-value tests checked with `systemd-analyze verify` (Step 6) |
| Compromised device | The server validates the capability report (keys, bounds, characters), never treats it as a grant, and audits changes as observations | A device can lie about its approvals and sandbox. That only misleads its own deploy review: a claimed approval reads "allowed" and the device then refuses | Report validation (Step 4) |
| Network attacker | Unchanged: mutual TLS and signed manifests; nothing new listens | As today | The existing protocol suite |

Decisions for capability tiers:

- The host decides. Approvals live only in local settings, written by local commands; the server never sends a capability profile, and a device's report is never a grant.
- A component is built in only when its reviewed profile shows that it reaches nothing its settings don't name, through fields the host approves one by one. Unreviewed means full mode.
- Templates are allowed only where Vector confines them, never with the opt-out, and their static parts are checked like literals.
- Ambient cloud credentials need `instance-credentials`, and CA certificates delivered by Vectory need `managed-ca`.
- A Unix socket that a component connects to is a destination named exactly. A file root never covers it, the agent's state or the managed configuration.
- On Linux with systemd the sandbox follows the mode and the allowances, in a drop-in Vectory owns; the operator's own drop-ins win. macOS and Windows claim no sandbox.
- A policy change applies at a stopped-agent checkpoint, and the host operator consents to the restart.

## Managed assets

Proposed in [ADR 0013](../adr/0013-managed-assets.md); nothing is built. Assets are files a version pins by digest, stored on the server and delivered to devices over their own mutual-TLS channel. They are configuration, not secrets. The [implementation plan](../internal/CAPABILITY-IMPLEMENTATION-PLAN.md#step-7-managed-assets-on-the-server) assigns the tests named below.

Assets added: asset bytes and revisions in the server's database and its backups; each version's pins; the asset files in each device's state directory; the agent's asset download route.

| Attacker | Control | Residual risk | Acceptance probe |
| --- | --- | --- | --- |
| Compromised server or signing key | The agent verifies size and digest against the signed manifest, bounds count and total, chooses every path itself (content-addressed), and in restricted mode allows only the files it placed, in its own table's fields. A CA certificate needs `managed-ca` | It can pin any bytes into a version it signs: a poisoned lookup table, a hostile MaxMind file for Vector's parser, or, where `managed-ca` is granted, a CA certificate that makes a pipeline trust an attacker's endpoint (the attacker still needs a network position) | A manifest list that disagrees with the artifact is refused, and no path leaves the assets directory (Step 8) |
| Editor or operator with a stolen session | Uploading needs Editor or above. A replaced asset changes no device until an operator publishes and deploys a version that pins it, and the publish review lists every changed asset. Uploads are audited, rate-limited and bounded by the quota | A replaced asset can pass an inattentive publish review. Uploads can fill the quota | The publish review lists changes (Step 9). Quota and rate limits (Step 7) |
| Viewer | Metadata only; downloading bytes needs Editor or above | Names, sizes and digests are visible | The role matrix (Step 7) |
| Malicious pipeline author | References only at the agent's asset fields, of the matching kind | Any asset of the instance can be referenced, and a lookup can copy its content to an approved destination | Reference placement tests (Steps 7 and 8) |
| Compromised device | The route serves only assets pinned by the device's current desired version or its open validation; a known digest grants nothing; one transfer at a time per device, rate-limited | It can download its own version's assets again within the limits, and lie about presence on its own page | Another device's asset and a guessed digest are refused (Step 11) |
| Network attacker | Mutual TLS, verified digests, no redirects; a cut-off download leaves no file | It can delay or drop a download; the device keeps its last verified configuration and retries | Cut-off and altered downloads (Step 8) |
| Local user or service account on the device | Files are read-only in a directory private to the service account; the agent re-verifies before each apply and fingerprints them at each check-in | The service account or root can change a file between verification and Vector's read | Drift tests (Step 8) |
| Stolen backup or database copy | Private keys are refused at upload and in drafts | Every asset's bytes are in the backup, including internal data a lookup table holds | Private-key refusal tests (Step 7) |

Decisions for managed assets:

- A version pins exact bytes inside its artifact, a rollback restores them, and the server keeps every pinned revision.
- The agent fetches only what its signed manifest lists, verifies digest and size, chooses the path, never overwrites, and keeps every file a retained configuration names.
- Assets are configuration, not secrets. Private keys are refused everywhere; TLS keys stay device secrets.
- In restricted mode a CA certificate asset needs the host's `managed-ca` approval.
- A version with assets is never released to an agent that can't receive them.

## Check on devices

Before deploying, an operator can ask the target devices to validate a candidate pipeline version on their own hosts ([contract](../../contracts/CONTRACT.md#check-on-devices)). The agent validates a staged copy with its own Vector, local capability policy and device-local secrets, deletes the copy and reports a bounded, redacted answer. It never activates the candidate and never touches the managed file, the recovery journal, last-known-good, a generation or Vector's process. This section lists what a security review should attack.

Assets added: the signed `validation` member of a manifest; the candidate bytes held with a pending row (at most 1 MiB each, 10 MiB per request, 128 MiB in all, until the answer or, at the latest, the minute-by-minute job after the ten-minute expiry); the bounded answers and the audit rows that count them; and the facts a device announces (`agent_features`, `readiness`).

| Attacker | Control | Residual risk | Acceptance probe |
| --- | --- | --- | --- |
| Compromised server or signing key | The request is a signed manifest member bound to the recipient device and the nonce, valid for at most 15 minutes by the agent's own rule. The agent fetches only the manifest's own artifact path over mutual TLS, checks the digest and size, validates under the same policy as an apply, and never activates. The server holds no device-local secret value | A compromised server can make any device that announced the feature download and validate an artifact it would accept anyway (any artifact the same server could already deploy to it), at the cost of one bounded validation at a time, and can read back the diagnostics the agent chose to send. The agent redacts them; a redaction miss leaks. It cannot make a device activate, run, fetch another URL or send a file | A tampered `validation` (digest, ID, `run_tests`, recipient, removal, one flipped byte) fails the signature check; the manifest names its recipient and nonce (protocol suite, `check-on-devices`) |
| Operator with a stolen session, or a malicious operator | Operator or Administrator role, CSRF and live authorization in the writer transaction; six requests a minute per user (`429`, creating nothing); 50 devices per request; one outstanding check per device; ten-minute expiry; a candidate is a published version, with variable values that pass the same checks as a deployment's; every request is audited with counts and the version, never the configuration | The caller can make hosts spend validation time and bandwidth (at most 300 device checks a minute per user), can read the answers to their own checks, and with a pipeline near the 1 MiB limit on enough devices can hold the server's 128 MiB of waiting candidates, so other people's checks are refused with `429 CAPACITY_BUSY` for up to ten minutes (deployments are unaffected). An answer is a bounded oracle for what the agent's diagnostics name: a port in use, an unwritable data directory, a missing file inside an allowed root, which device-secret names are unbound. On a full-mode device a check runs the validation step an apply runs, with the same native providers and `exec` secret backends: the role that can check can deploy there | Viewer and Editor are refused; a missing or wrong CSRF token creates nothing; the seventh request in a minute is `429`; a second check for a device supersedes the first; at the 128 MiB limit a request is refused and the check it would have replaced is untouched (`device_validations.rs`) |
| Another operator or an administrator | Only the requester, or an administrator, reads a check; others get the `404` an unknown ID gets. Answers hold the diagnostics the agent redacted, test results and secret names, in fixed fields with fixed limits | An administrator, and anyone with access to the server host, can read every check. Not preventable in the product | Another operator reading gets 404 identical to an unknown ID; a viewer and an editor get 403 (`device_validations.rs`, protocol suite) |
| Compromised device | The heartbeat parser is strict: allowlisted keys, charsets and bounds, unknown keys refuse the whole heartbeat atomically, the stored answer is at most 128 KiB, and a larger one is a `400`. An answer counts only for that device's own pending, unexpired check; an unknown, foreign, repeated or late one is ignored. A device downloads only its own candidate. The answer changes nothing but its row | A lying device can report `passed` for a candidate it would reject, claim features it lacks, invent readiness facts or answer with nonsense inside the bounds; it can fill its own row once per check. None of it deploys, releases or verifies anything, so the damage is false reassurance on its own row: `passed` is a report, not evidence of activation | An oversized or malformed answer refuses the heartbeat and leaves the device record unchanged; another device's candidate is `403`; an answer for another device's check is ignored (`device_validations.rs`, protocol suite) |
| Network attacker | Outbound-only agent over mutual TLS; a signed, nonce-bound manifest; the candidate arrives on the same authenticated channel | Can delay or drop a request or an answer, so a check expires. Cannot read or forge a candidate or an answer | Another nonce yields another signed payload; a payload for one device names that device (protocol suite) |
| Stolen backup or database copy | No device-local secret value reaches the server. Candidate bytes leave a row with the answer, the expiry, a newer check or a revocation; answers are pruned after 24 hours | A backup taken within about eleven minutes of a request can hold that candidate with its (non-secret) variable values, and every backup holds the last 24 hours of answers and the audit counts. Clearing a row does not zero the freed database page (`secure_delete` is off, as for every other table), so removed candidate bytes can survive in a copy until the page is reused | `device_validations.rs`: bytes are cleared with the answer and the expiry; rows older than a day are pruned |

Decisions for device checks:

- A check never gates anything. Deploy does not wait for it, no desired state, generation, policy or issue changes because of an answer, and no screen may present `passed` as a verified activation.
- The request reaches only a device that announced `validation` in the same check-in the manifest answers. A device that announced nothing is `unsupported` at once and receives nothing; an offline device is `offline` at once. Neither is waited for.
- `/agent/v1/artifacts/{sha256}` keeps its desired-artifact authorization exactly as it was, evaluated first. Only when that does not authorize the digest does it authorize the digest of this device's own pending, unexpired check, from bytes it re-hashes before serving. Another device's candidate, and one answered, superseded, expired or revoked, are the refusal the desired artifact would have given.
- Every new heartbeat member is strict. A malformed answer is a `400` that blocks the whole check-in, so an agent must drop an answer the server refused instead of resending it; an answer for a check the server does not know is never an error, so a stale answer cannot block check-ins.
- Resource bounds are constants: six requests a minute per user, 240 reads a minute per account, 50 devices and 10 MiB of candidates per request, 128 MiB of candidates in all (`429 CAPACITY_BUSY`), ten minutes to answer, 24 hours of answers.
- A committed check answers the parked wait of each device that is `pending` in it with the existing unsigned `{"changed":true}` hint, so the device checks in within seconds. The hint names no check and carries nothing, the device acts only on its signed manifest, and the existing pacing (100 at once, then 50 a second) and the six-requests-a-minute limit bound the early check-ins a forged or repeated one can cause.

## Device secrets in headers and URLs

Proposed in [ADR 0014](../adr/0014-device-secrets-in-headers-and-urls.md); nothing is built. It widens decision 7 below: a device secret may also fill a header value, a URL query value, a URL path or a whole URL, but only for a use the host bound with `vectory configure-secrets` (destination and placement), checked by the agent in both modes. The [implementation plan](../internal/SECRETS-IMPLEMENTATION-PLAN.md) assigns the tests named below.

Assets added: each binding's uses (`secret_uses` in `settings.json`); the private record of where substituted values sit in each retained effective file; the bindings report each heartbeat carries and the server's stored copy.

| Attacker | Control | Residual risk | Acceptance probe |
| --- | --- | --- | --- |
| Compromised server or signing key | The agent fills a header or URL only for a use in its own settings, compares the effective destination (scheme, host, port, path prefix) and placement (header or parameter name, path position, whole URL) after substitution, refuses a proxy for an `http` destination and disabled TLS verification, and never lets a name with uses fill a credential field. No manifest or response field reaches the uses | It can send a bound secret to its bound use whenever it likes, with event data of its choosing, and can still point a plain binding's credential field at another destination (decision 7). In full mode it can read the secret file with `exec`; the binding stops mistakes there, not a malicious publisher | Every hostile template of the compromised-server suite refuses and leaves settings and the managed file unchanged (Steps 3 and 7) |
| Malicious pipeline author | The same check, on the configuration after every substitution; references only at generated sites, one per value, never in a URL's authority or in names | Within a bound use the author chooses the data sent with the secret | Site and shape fixtures (Steps 1, 2 and 3) |
| Multi-tenant destination | Placement is bound, so a secret can't be moved into a query tag, dataset name, index or another header that the attacker's own account at the same service would read back | A bound destination that redirects, forwards headers or is compromised receives the secret, as an approved destination does today | Query, path and header moves at the bound host refuse (Step 3); redirect behavior measured by the native probe (Step 0) |
| Restricted pipeline reading files | A file root may not cover a bound secret file, in either order, and the agent re-checks at resolution | None known beyond the table's judgement | `allow`, `install`, `configure-secrets` and resolution refuse an overlap (Step 3) |
| Someone reading diagnostics, logs or the server | The server holds references only. The agent redacts every substituted value and its encoded forms in diagnostics, log summaries, device validation answers and the local Vector log, and learns them from what it substituted, not from field positions | Encodings it doesn't know (base64 of a pair, a value split across lines) and Vector's raw metrics on the loopback exporter, which local users can read | The canary suite before and after a restart and a failed rotation (Step 4) |
| Compromised device | The server validates the bindings report (keys, bounds, origins without paths) and uses it only to explain | A device can lie about its bindings; that only misleads its own review | Report validation (Step 2) |
| Operator who pastes a credential | A shared detector (header and parameter names, webhook paths, token shapes) refuses plain text at import, Apply, save and publish, naming the field and the fix | A credential under an innocent name and shape passes | Shared fixtures in Rust and TypeScript (Steps 1, 2 and 5) |

Decisions for device secrets in headers and URLs:

- The host decides where each secret goes and in what position. Uses live only in local settings, written by `configure-secrets`; a server never sends one, and a report is never a grant.
- A name with uses is exhaustive: no credential field, no other header, parameter, path or destination.
- The same check runs in restricted and full mode; only restricted mode makes it a boundary, and the docs say so.
- A secret file never lies under a restricted file root.
- Redaction follows values, not positions.

## Agent updates

Accepted in [ADR 0015](../adr/0015-operator-issued-agent-updates.md) and built ([contract](../../contracts/CONTRACT.md#agent-updates)). A team turns agent updates on, each host consents when it is enrolled or upgraded in a file only root can write, and a host installs an agent build only when a key it pinned signed it, through a small privileged step that verifies again, swaps, watches the new build and undoes it. This section lists what a security review should attack and the tests that must exist before it ships ([release gate 8](../internal/RELEASE-0.1.md)); the invariants I1 to I5 are rows of the [requirements checklist](../internal/REQUIREMENTS.md).

Assets added: the host's policy file and the keys pinned in it; the release keys (with server custody the sealed private key in `keys/agent-release-<fingerprint>.sealed` and the instance's sealing key, with offline custody a key file the server never sees); the release store (`artifacts/agent-releases/`), the signed manifests and their counters; the privileged step with its directory (journal, counter floors, installed record, staged files, a copy of the last committed build, the probe directory) and status file; update rollouts and their targets; and the facts a device reports about updates.

Decisions for agent updates:

- Agent updates are off by default and consent is per host. A host whose root-owned policy does not say `auto` or `ask` never downloads or installs an agent build, whatever the server says; a server can narrow what a host allowed and never widen it. The policy is not in `settings.json`, which the service account owns.
- A build is authorized by a release key the host pinned, never by the server's manifest signing key. Ed25519 over `"vectory-agent-release-v1\n"` and the exact bytes of one manifest, verified strictly (a canonical `S`, a canonical `R` and no small-order point, in Rust and in Go) and never re-serialized; the shared vectors pin every accepted and refused input.
- The holder of a pinned key is root on the opted-in hosts: a build it signs runs as root, and a newer agent can widen what restricted mode accepts. The documentation says so where the key is pinned.
- Custody is chosen once and is fixed while updates are on: this server signs, or a key kept offline. A key rotates within its custody through a rollover statement signed by the key it replaces. Two statements from one pinned key that name different successors freeze the host until it is re-pinned, and the privileged step is what remembers it: the agent hands it the offer's files and a request with no build, the step verifies them again from its own reading and writes the fork into root's files; a statement from a key the host already left is ignored, so relaying old statements cannot freeze a fleet.
- A host never tries a release twice. Its counter floor is the highest counter it attempted, raised and synced just before the journal says `swapping` and so before the service stops, and never lowered by a rollback, so a release that was tried and taken back is refused under any rollout, and two manifests with one counter signed by the same key cannot both be tried. The floors live in the update step's directory, which `vectory update off` and `service-uninstall` delete, so a host that turns updates off and on again starts them afresh; a build older than the one the host runs is still refused by the version check.
- Only a small privileged step installs. It copies what the service account staged, verifies again, probes the build as the service account from a directory only root writes, swaps through handles it opened and checked, keeps the previous build and rolls back from a copy of the last build that was proven on the host. The build under trial never decides its own rollback: `vectory update apply`, which runs as the installed agent, settles nothing that has already swapped, and an interrupted update is settled only by the step's own timer run. The one other way an update that has swapped ends is a person's: `vectory update off` and `service-uninstall` end a rollback only when the file at the install path already is the previous build (its digest is the one the journal names; the check reads that file, and not the image of the process that runs the command, which may have been started before the file was put back) and only its start is missing, so that a command started after that is the build that was proven here and never the build under trial, and what they record is an interruption (`INTERRUPTED`, with the floors raised when it is written, in files the same command removes with the step), never a result about a build. While the previous build isn't in place yet, or the step is watching one that runs, they refuse; where the agent's service isn't registered they can't find the install path at all, and refuse too.
- On Linux the step runs under a systemd sandbox. On a Mac it is root with no sandbox, because launchd has none to give a daemon, and on Windows it is SYSTEM with none: there it is bounded by what the step does itself, which is the same everywhere (a clean environment, no network I/O, nothing read from the service account's directories except through handles the path check opened, and the path check's refusal of an owner, a mode, an access list entry or a volume that would let another account change what it holds). The build the probe runs once is bounded differently on each system. On Linux it runs as the service account in the unit's sandbox, with the network closed and the file system read-only for it. On a Mac it runs as the service account with no sandbox. On Windows it runs as the step's own account, LocalSystem under the service, with the network and the file system open: no restricted token is built, and what bounds it is 10 seconds, 4 KiB of output, a clean environment and a job object that ends its whole process tree on a timeout, when the step ends and when the probe ends. What a correctly signed and hostile build can do in those ten seconds, its signer could do by being installed, and the signer is already root on every host that pins their key.
- On Windows the step is a service of its own, `VectoryUpdate`, that runs as SYSTEM. Every file and directory it makes has a protected access list of its own, written when it is created, with the Administrators as owner and nothing inherited, because a folder other accounts can create in would hand them rights over what they create. Its swap is two journaled renames, so a crash or a power cut between them leaves the install directory without an executable until the step's next run puts the previous build back; the new file is shared only with readers while the step writes it, and a program that holds a file (a virus scanner) makes a rename wait, never half-finish the swap.
- On Windows the path check is an owner and an access list, so it can't see an account that holds `SeBackupPrivilege`, `SeRestorePrivilege` or `SeTakeOwnershipPrivilege`. Those accounts (the Backup Operators group by default, and any account given the rights) are trusted as the Administrators are on a host that agrees to updates; no check looks for them, and the documents say how an administrator finds them.
- A device is updated only when the server saw it: a check-in after the restart that carries the new build's SHA-256 and version, a new process identity and the step's committed result. A download, a staged file or a swap is never reported as an update, and what the agent writes for people, such as the freshness `vectory update apply` shows, is advice and never authority.
- There is no remote downgrade, no remote rollback command and no remote command channel of any kind, and Vector is never updated remotely. Revoking a key on the server stops distributing what it signed; changing what a host trusts is always a local act or a statement signed by a key the host already pins.
- The privileged step's formats are fixed within a `service_definition` generation, so any committed build of that generation can finish or undo what another started. An update never rewrites a unit, plist or service definition; a release that needs a new one reaches hosts only through the Upgrade agent command.
- An operating system ships updates only with its own green native proof on a real service, and Linux, macOS and Windows each have one in this release. A build that doesn't ship an operating system reports `PLATFORM_NOT_IN_RELEASE` for its hosts, who update by hand, and its setup refuses `--updates` there.

## Consequential decisions

1. Browser TLS terminates at a private reverse proxy. The HTTP API must not be host-exposed. The HTTP listener speaks plain HTTP, so it keeps its own boundary: where `VECTORY_HTTP_ALLOWED_PEERS` is set (Compose sets it to the proxy), a connection from any other peer is closed before anything is read, so a process that shares a network with the server, such as the validator, can neither reach the API nor choose its own `X-Forwarded-For` while `VECTORY_TRUST_PROXY_HEADERS` is on. Whoever may connect is still bounded (the table above): headers within 15 seconds, a body within 30, at most 4,096 connections. A production server bound beyond loopback without allowed peers says so at startup. Agent TLS terminates in Rust; no forwarded-header authentication is trusted. Enrollment is the only agent operation without a device certificate.
2. The server does not execute untrusted Vector configuration with production credentials. Structural checks may be available while real isolated validation is unavailable; results must preserve this distinction.
3. A compromised authorized operator can change pipelines within device-local policy. Enrollment does not establish hardware identity. Approving devices and privileged group membership remains a deployment-capable operation.
4. A compromised machine administrator can access its local keys and configuration; remote protocol checks cannot protect against that administrator. Restricted agent control does not offer arbitrary command execution. Full Vector mode deliberately grants native exec and provider capabilities to authorized publishers under the adopted process's permissions; the dashboard cannot grant or widen that local permission.
5. Exact activation requires evidence for the specific applied configuration. File write, reload request, and a generic healthy old process are insufficient. Unknown verification remains visible and blocks canary success.
6. This version's release cannot claim OS, restart, MSI, signed repository, capacity, or isolated validation gates without measured evidence. Missing credentials and machines are recorded individually.
7. Vectory-managed `vectory-secret:NAME` references are restricted to the credential fields of a generated table: every field of the pinned Vector schema typed `SensitiveString`, plus reviewed plain-string credentials, per section and component type. The agent and the server each compile their own copy, drift-tested against the schema in CI. The agent substitutes only at its own table's paths, never at paths the server names, so a compromised server cannot route a host secret into a URL, header, path, command or VRL program. It can still point a credential-bearing component at another destination: restricted devices bound that with their local network allowances; full-mode devices do not. Agents report bound secret names (never paths or values). Full mode also permits native Vector secret providers and environment references resolved only on the device. Rendered files necessarily hold plaintext for Vector and share its current OS principal; stronger isolation from a compromised Vector child remains a gate. Template/effective hashes identify revisions and do not conceal weak secrets against guessing.

Review actual implementation against every row. Outstanding defects must remain visible; this document is not security certification.

8. Enrollment and authenticated heartbeats report `configuration_mode`; absent legacy reports mean restricted. This is reported configuration, not hardware attestation, and an already compromised device can lie about it. The deployment review checks reported mode while the local agent remains the authority for enforcing its own policy.
9. Full mode does not protect supervisor credentials or startup log evidence from an intentionally malicious publisher with native exec under the same OS principal. Fixed executable ownership, managed-file digest, process startup record and bounded liveness remain operational evidence, not independent attestation against that publisher. Separate principals and a protected supervisor channel would be required for that stronger boundary.
10. Isolated validation and pipeline tests use pinned Vector with a scrubbed environment, input/output/deadline/concurrency limits, and no production mounts or secrets. Provider, native secret, environment and external-file configurations explicitly defer to the device instead of resolving those resources on the API host or worker. A `lua` transform defers too: Lua can run any program, and Vector builds a transform's Lua when it builds the transform, which `vector test` does. So does an enrichment table that reads a file (every type but `memory`): Vector opens the file when it builds the table, and a lookup returns its rows to whoever wrote it. The worker therefore replaces every Lua step, and every step that looks up such a table, with an inert stand-in, and removes those tables before Vector reads the draft. An `aws_ec2_metadata` step defers too: when Vector builds it, it sends a token request and an identity document request to the step's `endpoint` and quotes the answer in its errors, so the worker replaces it with an inert stand-in as well. The API answers the tests of such a draft itself without asking the worker, and the worker refuses the same request on its own. A VRL call that passes a file (`validate_json_schema`, `parse_proto`, `encode_proto`, and `parse_groks` or `parse_etld` given `alias_sources` or `psl`) makes Vector open that file when it compiles the program, so the worker replaces such a step too and refuses such a program in samples and tests. Sources and sinks never start under `vector validate --no-environment` or `vector test`, and neither command opens a TLS, codec, credentials, kubeconfig, `data_dir`, source or sink path (a native test names each with a pipe against the pinned binary, so a Vector upgrade that starts opening one fails it). The paths a command does open are `remap` `file`/`files`, file-backed enrichment tables, the files VRL calls pass, and `file` secret backends; the worker stubs, removes or refuses each. A secret backend of type `exec` also runs under `vector test` when the configuration uses one of its secrets, so the worker removes every backend, and replaces each reference with a placeholder, before Vector reads the draft. Native tests show with marker files that no Lua form, secret backend, source or sink runs in the worker, with named pipes that the paths of enrichment tables and of VRL calls are never opened, and with a local listener that no instance metadata request is sent. Each takes a normal run of the same configuration as the control. Executed container isolation remains a separate release gate.
11. All authenticated workspace roles can read and explicitly export audit metadata. Prepared exports are private, temporary, bound to their originating user/session and subject to live authorization during download. Resource reservations survive active transfers and failed OS deletion. Export hashes establish file integrity, not a signature or independent proof against a compromised server administrator. Auth revocation cannot retract bytes already buffered by a transfer.
12. A password-verified MFA challenge is a separate, hash-only capability for the factor endpoint. It creates no browser session or CSRF token and cannot authorize other API calls. Successful factor verification, recovery-code consumption, challenge deletion, audit and session creation commit in one transaction. Existing clients may submit credentials and a factor together; that compatibility path must preserve the same atomicity and the same limits: all of an account's factor attempts, from either form, share ten in five minutes, and five wrong codes lock the combined form for the account for the rest of the five minutes. A password alone never returns the sign-in failure reservation or marks a client as known; only a completed sign-in does. Whoever knows the password can spend the account's factor budget and pause its second step for up to five minutes at a time; an administrator's password reset ends that. Restart clears all pending challenges, including those restored from backup.
13. Wake-ups (`GET /agent/v1/wait`) keep agents outbound-only: the agent opens and holds the request on its mutual-TLS channel, and the answer is an unsigned one-line hint (`{"changed":true|false}`) with no configuration, no state change and no authority. A forged, replayed or stale hint can only cause an early ordinary heartbeat, whose signed manifest and generation checks stay authoritative; a dropped or delayed hint only defers the change to the next scheduled heartbeat. A wait authenticates exactly like a heartbeat, revocation included, and is bounded to one per device, 60 a minute per device and `VECTORY_AGENT_WAKE_LIMIT` in total. It parks in memory without a database connection, the writer lock or a request slot, so a hostile enrolled device holds at most one small registry entry. Waits answer only after the writer commits, and a preview that rolls back answers none.
14. Agent updates (ADR 0015) make the holder of a release key an authority over code that runs as root on every host that pinned it, and the choice of who holds it (this server, or a key kept offline) is the team's, made when updates are turned on and fixed while they stay on. What a host trusts changes only by a local command or a statement signed by a key it already pins; the server's manifest signing key never authorizes a build. The section above lists who can do what, and none of it is built until the tests it names exist.
