# Open security findings

An independent, read-only source and runtime review of commit `f4d1826`, run against private instances with a real agent and Vector 0.58. It found no way for an unauthenticated peer, a lower role or a device to read a secret, take over an account, cross a role boundary or destroy data. It did find six availability or containment defects that are cheap to exploit, and several smaller ones. A finding is deleted from this file in the change that fixes it, together with its regression test; what is left below is what is still open, followed by the residual risks the fixes themselves left, which the next independent review should attack first.

Fixed since the review, each with regression tests (see the [changelog](../../CHANGELOG.md)): the shared sign-in, reset, invite, enrollment and installer buckets; the combined password-and-code sign-in; the `accept()` loop; idle handshakes; the Slack `text` field; enrollment audit rows; the Azure platform address; the Windows command quoting; the install command's local race; the restricted-mode `api` block; component IDs that name paths; the HTTP listener's timeouts, connection limit and allowed peers; the account routes that judged a body before authenticating; the packaged systemd unit; AWS credentials files and the host's own AWS identity in restricted mode; file roots that cover the agent's own files; the validator worker reading files a pipeline author names (file-backed enrichment tables, unit tests and Lua now run on the device, never in the worker); the validator's route to the server's own listener; a control character in a logged event, a component ID with a non-ASCII letter and a diagnostic over its size bound each taking a device off the control plane (the agent also sends a refused check-in again without its optional reports now), `vectory logs` writing event text to the terminal unescaped, and a device's own audit rows growing without a bound; line separators and text-direction controls in the names a person writes (a notification channel, pipeline, deployment, group, saved settings, enrollment token or person); a shell-quoting gap in the install command; and a front-end dependency chain in the API reference. Finding 4 below came from a later review of the capability design.

Severity: **P2** is bounded or needs a precondition; **P3** is hygiene. Where a step could not be run in the review environment, the finding says so.

## P2

### 1. The unit that `vectory setup` registers is weaker than the packaged unit

The packaged unit (`packaging/systemd/vectory.service`) is fixed: `ProtectSystem=strict`, `ProtectHome=true`, `ReadWritePaths=-/var/lib/vectory-agent -/etc/vectory/managed -/var/lib/vector`, `KillMode=mixed`, and a packaging test that keeps it so. The unit that `vectory setup` and `vectory service-install` write (`systemdUnitFile` in `agent/internal/agent/service_linux.go`) still has `ProtectSystem=full` and `ProtectHome=read-only`, so everything outside `/usr`, `/boot` and `/etc` stays writable wherever file permissions allow and home directories stay readable, and a unit in `/etc/systemd/system` takes precedence over the packaged one. It is left as it is on purpose: pipelines may write wherever the host allows (full mode, or a restricted-mode file root from `vectory allow --file-root`), and a strict sandbox would break them silently. **Fix:** the sandbox follows the host's allowances and mode, with one source for both units and a drop-in directory setup never overwrites; the design is part of [the capability tiers decision](../internal/WORK-QUEUE.md#9-capability-tiers-and-managed-assets). **Test:** the generated and the packaged unit agree on the sandbox lines; a restricted-mode file root appears in the generated `ReadWritePaths`.

### 4. A file root covering a socket directory reaches local services

A file root that covers `/run` would let a sink that connects to Unix sockets reach local service sockets. `vectory allow --file-root`, `install` and `setup` now refuse `/`, a volume root and the agent's own directories, but a directory such as `/run` or `/var/run` is still an ordinary root, and what remains is that case. Not reachable with today's restricted component set; it becomes reachable as components are approved. **Fix:** Unix-socket destinations are named exactly (`--network unix:PATH`) and a file root never implies them ([ADR 0012](../adr/0012-graduated-capability-tiers.md)).

## P3

- The help center's build tool (`astro`) depends on `http-cache-semantics`, whose advisory ([GHSA-ch52-4w7c-c8xp](https://github.com/advisories/GHSA-ch52-4w7c-c8xp), high) affects every release and has no patched one. Nothing that ships contains the package. The release-candidate gate acknowledges it in `packaging/npm-audit-exceptions.json` until 2026-12-31, after which the gate fails until someone reviews the entry ([why nothing shipped is affected](../internal/DEPENDENCY-AUDIT.md)).
- The release-candidate workflow's SBOM job uses a SHA-pinned action that downloads the SBOM tool's install script from that project's main branch at job time (the tool's version is pinned, the script is not). Replace it with the tool's release archive pinned by checksum. The job has a read-only token and runs only when started by hand.
- The dashboard's and the Help center's content security policy allows `style-src 'unsafe-inline'`. No HTML-injection sink exists today, so no style can be injected; hashing or moving the small set of inline styles would let the policy drop it as defence in depth.
- A host whose enrollment reply was lost, and which then enrolls again with a different token (a new Add device command, a mistyped token), leaves the device the first attempt created: the server judges the token first and answers every refusal alike, so the host takes "refused" to mean nothing exists for its request and starts again under a new one. That attempt is refused as `NAME_TAKEN` until the administrator authorizes recovery from the existing device's page or the host uses another name ([Troubleshooting](../user/troubleshooting.md)). The same token completes the enrollment, even when it has since expired or been used up. A recovery token that is revoked or expires between the two attempts behaves like the different token.
- Hypothesis, not demonstrated: a flood of a public endpoint delaying writers through the process-wide writer mutex. A control flood showed the same or higher write latency without the lock in the path.

## Residual risks the fixes left

Named by the authors of the fixes; none is a reproduced defect.

- Many addresses can still spend the shared budgets: about ten addresses at 60 a minute reach the 600 a minute shared sign-in budget. Enrollment, installer, downloads, password reset and invite redemption keep no reserve for known operators. The sign-in reserve (100 of the 600) is opened by any completed sign-in, including a low-privilege account's, and lives in memory.
- Valid ClientHellos that then stall still hold a handshake slot for up to 10 seconds. Slots are the connection limit divided by eight, clamped to 128 to 4,096 (2,048 by default); there is no per-address cap on handshakes in flight.
- The HTTP listener's limits bound each connection, not each client. One address can still hold `VECTORY_MAX_HTTP_CONNECTIONS` connections that send real requests, and behind the proxy every connection comes from the proxy's address. A response written to a client that stops reading is not timed. HTTP/2 over cleartext (for clients that know to speak it) keeps hyper's limits of 200 streams and 16 MiB of headers, and after its first request only its keep-alive pings time it.
- `VECTORY_HTTP_ALLOWED_PEERS` matches the address a connection comes from. Any process that can send from an allowed address, such as another process in the proxy's container, is allowed. A host name's old address stays allowed until the next lookup (30 seconds, sooner once a connection is refused), and a name with no address allows nobody, so after a cold start the proxy's first requests can wait up to the retry interval (2 seconds). Without the setting, the listener accepts every peer and a production server bound beyond loopback only warns.
- The body deadline counts the whole body: a client that needs more than 30 seconds for a 1 MiB body (under about 280 kbit/s) is cut off until `VECTORY_HTTP_BODY_TIMEOUT_SECONDS` is raised. A request that is cut off answers like any body that cannot be read (`400 INVALID_INPUT`), not with a timeout.
- Only the two account routes the review named authenticate before their body is read. Other routes that authenticate inside the handler but take the body as a `Json` argument still answer an anonymous caller with a `400` or `415`, not a `401`, when the body isn't JSON: the generic create, draft and group-edit routes under `/api/v1/{collection}`, `POST /api/v1/deployments/preview`, `POST /api/v1/deployments/binding-suggestions` and `POST /api/v1/mfa/{action}`. A body that is JSON always reaches the `401`, so nothing is disclosed.
- An `accept()` error the listener does not recognize is treated as passing (a pause of at most 100 ms, one log line per 10 seconds) and never ends the server, so a permanent error of an unknown kind would retry quietly.
- The combined sign-in form: anyone who knows a password can lock it and spend the account's factor budget (the second step pauses for up to five minutes per window) until an administrator resets the password; a right combined code does not clear its wrong-code count; a password step whose second step never completes keeps its reservation (10 per account and client in 15 minutes).
- Enrollment refusals are audited once per (token, reason, minute), which hides a second host retrying the same dead token within that minute. A refusal that carries no real token is audited once per client address (an IPv6 /64 counts as one) and reason a minute. All of them together write at most 60 rows a minute: each refusal past that is counted, and one row a minute (`device.enroll_refusals_summarized`, "37 further refusals in the minute from 04:06 UTC were not written") says how many, written when the next refusal arrives or the minute has ended. A flood from many addresses can therefore add at most 61 rows a minute, 87,840 a day: about 84 MB a day at the 952 bytes a refusal row takes with its indexes (457 bytes of JSON, measured with `dbstat` on 50,000 rows), or about 122 MB at the 1,392 bytes of a row whose every field the request controls is at its limit. Before the shared budget it was up to 600 rows a minute, 864,000 a day, 0.8 to 1.2 GB. The audit log still has no retention, so this is a slower growth, not a bound. The counts are in memory and start again after a restart, and the summary of a minute in which the server stops is not written.
- The packaged unit was verified with `systemd-analyze verify`, `systemd-analyze security --offline`, its unit test and a read-only mount namespace, not on a running systemd. A path under `/home` probably also needs `ProtectHome=read-only` in the operator's drop-in; that is untested and not documented.
- A restricted device that already runs a version with an `api` block (or an AWS credentials file, AWS credentials the host supplies, or a VRL call that passes a file) keeps running it but will not start that configuration again after a restart or reboot until a version without the block applies or the host moves to full mode (documented).
- The IDs a device reports follow one rule on both sides, and a shared fixture pins it: `vector-catalog/fixtures/component-ids.json`, which the server's `reported_component_id` (it reuses the validator's `names_a_path`) and the agent's `reportableID` (it reuses the policy's `componentIDProblem`) each judge entry by entry. `report-bounds.json` pins the diagnostics bounds and how a record's size is measured. Not pinned: the validator's other checks of a pipeline's component ID (empty, over 128 bytes, a dot) have no agent twin and are tested on their own; the validator still accepts an ID with a text-direction override, which no device reports (the agent leaves it out and the server refuses it); and the restricted top-level setting lists in the agent, server and dashboard have no drift test, though the three agree by review.
- The AWS credential rules are written out in `policy.go` for the four restricted-mode sinks that take one (`elasticsearch`, which carries the keys in `auth`, and `http`, `loki` and `prometheus_exporter`, which carry them in `auth.auth`), and a test pins them to the capability table. A component added to restricted mode later needs its own entry, or the table-driven check of ADR 0012. Keys beside `assume_role` count as ambient, as the table has it. Not tested against a real metadata service: the native tests show that Vector 0.58.0 accepts the ambient shapes and runs a `credential_process` program, that the agent refuses both before Vector runs, and that Vector rejects a lone key and keys in the wrong place. The table lists `access_key_id` alone as explicit; the agent also needs `secret_access_key`, which is stricter and agrees with Vector. GCP and Azure shapes need no rule yet: no restricted-mode component takes them.
- File roots are judged when `vectory allow`, `install` or `setup` adds or replaces them. A root allowed earlier stays until the lists are replaced, a secret file bound later under an existing root (`vectory configure-secrets`) is not judged, a `settings.json` edited by hand is not judged, and the agent doesn't re-check at resolution; ADR 0014, section 3 closes the last three. Paths are compared as written and with links followed, and on macOS and Windows without regard to case. A bind mount, a macOS firmlink (`/System/Volumes/Data`) and a Windows 8.3 short name of a path that doesn't exist yet are not recognized. The Windows path rules (drive letters, UNC shares, `\\?\` prefixes, trailing dots and spaces) are tested as string rules on every host and have not run on a Windows machine.
- The Windows command quoting was measured against PowerShell 7.5 on Linux only, not Windows PowerShell 5.1, and the new native tests have not run on Windows or macOS (on Windows the containment test runs only its refusal half).
- A device's own audit rows (apply state, configuration mode, secret reconciliation) are written only when a value changed and at most four of each kind a minute. The first apply-state row of each of `desired`, `verified_applied` and `failed` for a generation is written whatever the limit says and doesn't count toward it, so deployments that follow one another within a minute each keep their start and result; a device that repeats one generation gets that exemption once per state every ten minutes, which adds at most three rows each ten minutes, about 430 a day, to the 5,760 a day the limit allows for a kind. A change the minute's limit skips is never written later, so a device that flaps can end its audit tail on a state it has already left. The counts are in memory and start again after a restart, and their keys (the counted ones and the exempt first rows, which a deployment adds for each device) share the device partition's 40,000 slots: with about 5,000 to 10,000 devices all changing at once, eviction could loosen the limit, never tighten it. The audit log itself still has no retention ([Audit log storage](../user/telemetry.md)).
- Reported text keeps the Unicode direction marks (U+200E, U+200F, U+061C) and the zero-width characters (U+200B to U+200D, U+FEFF), which right-to-left scripts and emoji sequences use; only the controls that reorder or forge text (control characters, line and paragraph separators, embeddings, overrides and isolates) are replaced. A mark cannot reorder what follows it the way an override can, and device and channel names are held to a stricter rule, but an invisible character in free event text is not removed.
- Event text in a report is display text: the server replaces control characters, line separators and direction controls with a space and accepts the check-in. The members that name or identify things (names, IDs, versions, request and boot IDs, tokens, codes, state and data directories, and a check's test names) still refuse a control character, a line or paragraph separator, a text-direction embedding, override or isolate, and the byte order mark; a check's messages refuse a control character, and an error's message a NUL. `vectory status` prints an older state file's diagnostics unchanged; only the copy in a heartbeat is cleaned. `vectory logs --json` rewrites Vector's records compactly and a program that decodes a field and prints it must clean it itself. A name saved before the write rules (a channel, pipeline, deployment, group, saved settings, token or person) keeps its text until it is edited, and the API serves it as stored; every notification shows it as one line: each such character becomes a space, runs of spaces collapse and the ends are trimmed. A device's `os` and `arch` from an earlier enrollment keep their text until it enrolls again (its versions, directories and IDs are replaced by the next check-in).
- Some regression tests depend on the host: the descriptor-exhaustion tests use `ulimit -n` (POSIX only), two Go subtests skip without the loopback addresses 127.0.0.2 and 127.0.0.3, and the listener test skips when fewer than 140 sockets fit.
- The recorded load measurements in `docs/internal/CAPACITY.md` and `docs/security/SECURITY-REVIEW.md` were taken with 128 handshake permits; the limit now scales with the connection limit, so the runs should be repeated.

## Agent updates: what remains

The update path was attacked in independent reviews of the privileged step on Linux, on a Mac (twice, with the fixes between) and on Windows, which found no way to run unsigned code or to reach root, and it runs against hostile offers on a real service of each kind in CI ([release gate 8](../internal/RELEASE-0.1.md)). What is left are limits of the design and things no test can show; none is a reproduced defect. The [threat model](THREAT-MODEL.md#agent-updates) says who can do what.

- **Turning updates off forgets which releases a host tried.** `vectory update off` and `service-uninstall` delete the update step's directory, and with it the highest counter the host tried for each key it pins. Turned on again, the host can try a release it took back before, if a server offers it; the trial and the rollback guard it as they do any build, and a build older than the one the host runs is still refused. Keeping the floors outside the step's directory would close it, and changes where setup, the step and the agent look for them.
- **A signed release stays valid until it expires.** A host never installs a build older than the one it runs, never tries a release twice and refuses an expired one. A release that is signed, unexpired (at most 180 days) and newer than the host's build is still accepted, so a compromised server can offer one that a later release replaced (the one before the fix for a flaw), and can hold hosts on an old release by withholding newer ones. A shorter expiry narrows it; nothing else does.
- **The holder of a pinned key is root on every host that pins it.** With the key on the server, whoever gets the server's keys directory and its sealing key can sign builds for all of them. With a key kept offline the server holds a public key only, and a stolen key still needs a compromised server or an Administrator session to reach a host, because hosts fetch only from their own server.
- **Trust starts at the command.** A host pins the key whose fingerprint its setup command names, after checking it against the keys its server offers over the connection the command pinned. Whoever changes the command, or points it at another server, can have a host pin a key of their own.
- **Some hosts need a login after a key is stolen.** A host that pins only the stolen key, or that froze on a fork, is put right only by the Upgrade agent command with the new fingerprint; nothing remote may change what a host trusts except a key it already trusts.
- **A device's report is its own word.** What a device says about its eligibility, version, last result and canary health comes from the agent, which the service account can write. A compromised service account can claim anything, and cannot install anything; the gates count what devices report, so a lying canary can hide a bad build from the gate.
- **The trial proves a build starts and stays up, not that it does everything.** The new build must start, check in healthy and not be restarted within five minutes. A problem that shows later, such as events no longer delivered, is caught by the rollout's observation on the server (a data-plane issue on an updated device counts as a failure) and not by a rollback on the host.
- **Stop all updates takes a check-in to reach a host.** A host hears it at its next check-in, usually within a minute, and one that is applying finishes its trial first.
- **Downloads share 16 slots.** One server serves 16 builds at a time and six requests an hour to a device, so a batch larger than that updates in waves while the others retry.
- **A device can move the server's counter sequence.** The next release takes one more than the highest counter any device reports it attempted, so a device that reports a high one makes the counters skip (at most 1,000,000 above the stored sequence per report; larger reports are ignored).
- **Expiry and `issued_at` use each host's clock.** A host whose clock is far behind accepts a release that has expired; one far ahead refuses valid ones.
- **Power loss is shown by killing the step, not by cutting power.** The native phases kill the step with SIGKILL at each journal boundary and show one complete executable and the right counters. That the file system keeps the order of a rename and a directory sync across a real power cut is relied on, not shown.
- **A file system program that says it is local can fool the path check on a Mac.** The check refuses a volume mounted with ownership ignored and one that isn't local, so the owners and modes it reads mean something. A macFUSE volume mounted as local, with permissions left to the program that serves it, isn't recognized. Mounting one takes an administrator, who is trusted as root, so it gives no one authority they lack.
- **The probe runs a correctly signed, hostile build with more access on Windows than elsewhere.** The step runs the new build once to see which version and platform it reports. On Linux that build runs as the service account with the network closed and the file system read-only for it; on a Mac as the service account; on Windows as the step's own account, SYSTEM under the service, with the network and the file system open, because Windows has no switch of account that needs no password and no restricted token is built. A job ends the build and every program it started when the ten seconds are up, when the step stops and when the probe ends, and holds at most four processes. Whoever signed such a build is already root on every host that pins their key, so the probe gives them no authority they lack.
- **On Windows, accounts that hold the backup, restore or take-ownership right are trusted as the Administrators are.** The path check reads access lists. An account with `SeBackupPrivilege`, `SeRestorePrivilege` or `SeTakeOwnershipPrivilege` (the Backup Operators group by default, empty on a new machine, and any account given the rights) bypasses them and appears in none, and no check looks for such accounts. An administrator who wants to know who they are looks at those groups and at the rights' assignment: `whoami /priv` shows what the account that runs it holds, and `secpol.msc` shows who was given each right.
- **A Windows swap has one moment with no executable.** A running agent can be renamed and not replaced, so the swap is two renames. A crash or a power cut between them leaves the install directory without an executable until the step's next run, which puts the previous build back and starts the agent; the agent's service can't start before that. The native phase ends the step in that moment on purpose and shows the recovery, and which of the agent's and the step's services the Service Control Manager starts first at a boot isn't shown (both orders end the same).
- **A program that holds a file can make a Windows update wait or fail.** A virus scanner or an indexer that has a file open makes a rename answer with a sharing violation. The step waits for it (ten tries half a second apart) and then ends the update before the executable is touched, or puts the executable back; it never leaves a half-finished swap. A scanner that holds a file for longer than five seconds fails the update, and that release isn't tried again on the host: it takes the next one.
- **The Windows step's rules about files rest on what the system answers.** That a running program's image can be renamed and not replaced, that a folder held open without delete sharing can't be renamed or replaced by a program that respects sharing, and that a service ending with an error of its own is started again by the Service Control Manager are measured on one Windows Server version in CI (the native test prints each answer), not on every supported one.
- **What a Windows update root that was open holds isn't examined when setup closes it.** A `%ProgramData%\Vectory` that root owns and that Users could create in (what an install made before it was closed has) may already hold a directory that another account made, such as `agent`. Closing the list keeps that account from adding more and removes nothing it made; an empty directory it made, and a handle it kept open on it, aren't found. A host installed before the directory was closed, which a local user may have tried, is put right by looking at what the directory holds.

## What was attacked and held

Wake-up hint authentication order and bounds; device certificate checks and device CA rotation, including a live test that a retired key is refused; enrollment token normalization, races and idempotence; the install trust chain on POSIX (the pin equals the CA, no `-k`); `vectory allow` symlink and `host:port` matching; most of the notification address blocklist; secret sealing; CSRF; per-role list visibility.

## Not covered

List, sort and filter parameters of the fleet-scale reads; live response headers (security headers were read from source, not from a running proxy); the sample-test change in the validator worker (`server/src/bin/vector-validator.rs`, which holds stdin open until the last sample's output arrives); Windows and macOS hosts; anything after commit `f4d1826`, which includes the publish gate, canary choice, held-device, fleet-scale dashboard and agent adoption work, and the fixes listed at the top.
