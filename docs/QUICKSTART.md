# Compose quickstart

Use a single Linux Docker host with Compose, local durable disk, a DNS name, and a server certificate/key already issued for that name. The same name serves the dashboard on 443 and agents on 8443. The browser/API HTTP port is private to the Compose network. Do not expose Vector's own observability port.

1. Obtain this source and inspect [ACCEPTANCE](ACCEPTANCE.md) for current release gates. From the repository root, build the image with `docker build -f deploy/Dockerfile -t vectory-local:development .`. The first build downloads pinned-language dependencies and container images; offline installations need those caches/images preloaded.
2. Create a protected host directory for TLS and bootstrap files. Copy the issued certificate chain to `server.pem` and key to `server-key.pem`. The container UID/GID 10001 must read the files; on Linux a root-owned directory with group 10001 and mode 0750 and files mode 0440 is suitable. The key must not be generally readable. Docker Compose bind-backed secrets retain host permissions.
3. Generate a random secret without displaying it: `docker run --rm --entrypoint python3 vectory-local:development -c 'import secrets; print(secrets.token_hex(32))' > /protected/path/bootstrap`. Restrict it to the same group/mode. Never commit it. This is an instance bootstrap secret, not an enrollment token.
4. Copy `deploy/.env.example` to `deploy/.env`; set the hostname, absolute TLS/bootstrap paths and release directory. The release directory may initially be empty. No fake downloads appear. Optional development artifacts are built using `python3 packaging/build-release.py`, then copied to that directory with `catalog.json`.
5. Run `docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet`, then `docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build`. This also builds the isolated Vector validation worker. Inspect `docker compose --env-file deploy/.env -f deploy/compose.yaml ps` and `logs server proxy validator`. Verify HTTPS normally; never use `curl -k` or an insecure agent option.
6. Visit `https://<hostname>`, supply the protected bootstrap secret, and choose the first administrator and a strong password. No default credentials exist. The bootstrap endpoint cannot create another administrator afterward. Securely retire the external bootstrap secret after replacing its mounted file with a fresh random unused value and restarting; the initialization state lives in SQLite.
7. Create an enrollment token with bounded expiry, use limit/name scope, download a real available release, verify its checksum/signature status, and follow [agent installation](AGENT-INSTALL.md). Supply a private CA independently through your managed trust channel when required. Agents connect to `https://<hostname>:8443`.
8. Publish a pipeline, explicitly target a device, and inspect its reported apply stage. Enrollment leaves it unmanaged. A download, write, reload request, or unknown verification state is not success. Canary progress requires verified activation.

The named `data` volume contains the SQLite database and device CA/manifest signing keys. Back it up together using [BACKUP-RESTORE](BACKUP-RESTORE.md). Do not use a network filesystem for SQLite WAL, share the volume among replicas, or remove it during upgrade. Application containers run as UID 10001 with read-only root filesystems and no added capabilities. Caddy has no public admin API and uses TLS 1.3. No automatic ACME, analytics, cloud account, or external runtime service is required.

Size resources from real telemetry and the measured limits in [CAPACITY](CAPACITY.md). `VECTORY_MAX_AGENT_CONNECTIONS` defaults to 16,384 (bounded to 64-65,536), and each active TLS connection consumes socket/TLS memory. It is an admission bound, not a fleet capacity guarantee. `VECTORY_TELEMETRY_RETENTION_DAYS` defaults to seven and is bounded to 1-30; storage includes up to one coalesced sample per device per minute plus indexes. Shorten retention for constrained storage and monitor database growth. Security audit history is separate and is not automatically pruned.

The separate validator runs Vector 0.58.0 as UID 10002 on an internal network with no external route, no host ports, no durable/production mounts, no secrets, a read-only root filesystem, 128 MiB scratch space, 512 MiB memory, 1 CPU and 64 process limit. The worker additionally bounds requests, concurrency, runtime and captured output. It checks syntax/VRL using `vector validate --no-environment`; device environment validation and activation remain agent responsibilities. If configured validation is unavailable, publishing fails closed. The container's isolation is a deployment property, not a guarantee established by a worker environment flag; never set that flag on an ordinary unsandboxed server with production credentials.

For isolated developer tests, `go run packaging/dev-pki/main.go --out .local/pki --hosts localhost,127.0.0.1,::1` creates a short-lived CA and server key pair in a new directory. It does not install trust. Explicitly pass `ca.pem` to test clients. Its Windows output directory must inherit a private ACL; use a private workspace. This test CA is unrelated to the server-generated device CA. Real device enrollment still uses verified TLS.
