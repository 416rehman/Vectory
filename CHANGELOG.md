# Changelog

All notable changes to Vectory. Version 0.1.0 is an unsigned developer preview.

## 0.1.0 (developer preview)

The first self-hosted Vectory: a Rust and SQLite control plane, a React dashboard, an outbound-only Go agent, and a bundled Help center. See [What's new](docs/user/whats-new.md) for a tour.

### Highlights

- Visual pipeline editor for the 128 component types of Vector 0.58.0, with YAML, TOML and JSON import and export, VRL and pipeline tests, and immutable history with diffs.
- Publishing checked by an isolated Vector validator that fails closed; checks that need the device run on the device.
- Deployments to devices and groups with previews, priorities, canaries, schedules, pause, cancel and rollback.
- Outbound-only agents with mutual TLS, per-device signed manifests, protection against older configurations, drift repair and automatic restore of the last working configuration.
- Restricted and full modes, local allowances and device-local secret bindings, all controlled on the host.
- Device secrets in every credential field: a pipeline stores `vectory-secret:NAME`, each device fills in the value from its own file, and the device page shows which names each device has bound.
- Device metrics, issues, and an exportable audit log.
- Agent updates: roll out a signed agent build from the dashboard to hosts that agreed to it, with a canary, batches, a failure threshold and **Stop all updates**. A host is visited once, to agree, and installs only a build that a key it pinned signed.
- Alerts in Slack, any webhook or email when an issue opens, a rollout fails or a device goes offline, with quiet hours, a delivery log with retries, and editable detection thresholds.
- Roles, two-factor sign-in with recovery codes, and administrator-issued reset links.
- A Help center bundled with the server, searchable offline, with every page available as Markdown and an `llms.txt` index.

### Publishing and rollouts

- **Failing tests stop a publish.** Publishing a pipeline whose tests fail, that Vector couldn't build or that didn't run answers `409 TESTS_FAILED` with the same rows as the test run, and nothing is published, unless the request sends `acknowledge_test_failures: true`. The publish review runs the tests when it opens and says how they went; while a test isn't passing the primary button reads **Publish anyway**, beside **Open tests**. A publish over failing tests is audited with the counts, never the tests' contents. Pipelines without tests, or with passing ones, publish as before.
- **Choose the canary.** A canary rollout takes `rollout.canary_device_ids`, among the devices it targets, and the deploy review has **Canary devices: edge-nyc-02** with a searchable choice by name, a **Stage** column (**Canary** or **Then**) and the reason for the default. Without a choice the canary is no longer always the lowest device IDs: devices that are online, healthy and reporting metrics go first.
- **Watch the canary.** Its lane shows each canary device's events in and out per second, errors per minute and buffer fill now, against the 10 minutes before its release (`canary_watch` on `GET /deployments/{id}/rollout`); a device with nothing recorded reads **No baseline yet**, never zero. **Canary gate** says in one line what it waits for, naming the devices ("Measuring delivery on edge-nyc-02 (2 of 3 samples)"), from the same evidence as the lanes and the progress bar. One countdown, in the lane, and one refresh control.
- **Release the next stage early.** `POST /deployments/{id}/release-next-stage` releases the next stage of a canary whose released devices have applied and are delivering, without waiting for the delivery check or the observation period. It refuses otherwise, changes nothing when it refuses, records who released the stage on the rollout and audits `deployment.stage_released_early` with the stage and the gate state.
- **Held on previous version.** A device whose newest version failed but which verifiably keeps running an earlier one and delivers on it is amber **Held on previous version**, counted on its own in Fleet health, the Overview's KPI ("3 / 4 · 1 held on previous version") and `held` in the device counts and filters, not red **Failed**. **Failed** stays for devices with no working version. The Devices quick filter that read **Failing** reads **Needs attention** and lists what it holds on hover.
- **Read what a device was offered.** A device's **Effective configuration** shows the exact text it was offered, with its own variable values applied and secrets still `vectory-secret:NAME` references, in a read-only viewer with line numbers, folding and search. Choose an earlier generation, see what changed since the previous offer and the value each variable took, and read whether the file the agent reports is that text, which earlier offer it matches when it isn't, and that nothing was reported when the agent sends no digest. `GET /devices/{id}/configuration` and `GET /devices/{id}/configuration/diff` serve every signed-in role, limited per account. Nothing on the page applies or verifies a configuration, and a copy or download is not evidence that a device runs it.
- **Check on devices.** Before you deploy, `POST /deployments/preview` with `device_validation: true` asks the reviewed devices (the first 50 by name) to validate the version on their own hosts: with their own variable values, local allowances and device secrets, in a copy that is never applied. `GET /device-validations/{id}` reads one answer per device: **passed**, **failed** (with redacted diagnostics, test results and the names of unbound device secrets), **offline**, **unsupported** (an agent that can't be checked), or **expired** after ten minutes. Offline and unsupported devices are named, not waited for, and a device that keeps a request open for changes hears of the check within seconds, any other at its next check-in. A check changes no deployment, generation, setting or issue, Deploy never waits for it, and **passed** is the device's own report, not evidence that a version is applied. Only the person who asked, or an administrator, can read a check; six requests a minute per user are allowed, and answers are kept for 24 hours. The signed manifest carries the check only for a device that announced it can answer, and each device downloads only its own candidate. Manifests also name the version number and pipeline for `vectory status`, and a device reports `agent_features` and `readiness` facts (`GET /devices/{id}` shows them).
- **The deploy review says what a restricted host must allow, not that it refuses.** Vectory can't see a host's allowances, so the note and each row read "refuses it unless its host allows destination 127.0.0.1:8678", and stop saying so for a device that passed **Check on devices** or whose verified running version already uses the same destinations, listeners and file roots. The review used to say the host "refuses this version until its host approves it" every time, even beside a passing check.
- **Check on devices gives commands made for the host.** The commands that bind a missing device secret name the host's state directory when it isn't the default and stop and start its agent the way it runs (the service, or Ctrl-C for `vectory run`; on Windows, PowerShell with the full path), as the commands for an allowance do. A fix that names `vectory allow` carries the same `--state-dir`. Before, every row showed the generic commands, which failed on a host with its own state directory or without a service.
- **One sentence for a rollout's devices.** The deployment list, the rollout page, the command palette, the Overview and a group's rollouts say it the same way: **2 of 3 devices applied · 1 not delivering**, **1 of 3 devices applied before the rollback**, **2 devices moved to Edge syslog processing v3**. Before, the list, the page and the palette could disagree about one rollout.
- **Rollout cards fit a phone.** Each device result keeps its state with its name (beside it, or under a name too long to leave room), and long names, reasons and step labels wrap inside the card from 320 pixels wide, in every state.
- **The pipeline library names how a rollout ended.** When no device runs a pipeline's latest version, its row says how that version's newest rollout ended and links to it: **v4 failed on 1 device · 12m ago** or **v4 rolled back on 1 device · 12m ago**. The row reads the 20 newest failed and 20 newest rolled-back rollouts; the library API has no new field for it.

- **Check on devices in the deploy review.** **Review deployment** has a **Check on devices** button for operators and administrators. Each reviewed device validates the version on its own host, and the review shows who **Passes here**, who **Needs a fix** (the first finding with its step, field and fix, opening to the rest and to the tests), who **Needs a secret** (the exact `vectory configure-secrets` commands, with **Copy**), and who is **Offline: not checked**, gave **No answer in time** or has an **Older agent: can't check**. Answers arrive as devices give them, in a table or, on a phone, as cards, under a summary that is always true ("Checked 3 of 4 devices: 2 pass, 1 needs a secret, 1 offline."). **Retry** asks one device, or every device that didn't answer, again, and **Also run the pipeline's tests** adds the version's tests. A check never blocks **Deploy**, says its results are advisory, belongs to the review it was asked on ("These results are for the previous selection") and says when to try again if it was asked too often.

### Agent updates

- **Sign agent builds with `vectory release`.** `keygen` makes a release key, `sign` signs a `release.json` only when every build's file name and SHA-256 appear in a `SHA256SUMS` you got without the server, `verify` checks a release the way a host does and prints the code a host would report, and `rollover` hands a key over to a new one. The verbs read and write files only, with no network and no administrator rights. A private key file is created closed to other accounts and is never replaced or followed through a link. Commands can now be groups of verbs: `vectory help release` lists them.
- **Turn agent updates on with a key you choose to hold.** An administrator turns them on with their password (`PUT /agent-updates/settings`) and picks, once, who holds the release key: the server (it makes an Ed25519 key and keeps the seed sealed under the instance's key in `keys/`, so a backup of the data directory holds it) or the team (the server keeps the public key only, and each release waits for the team's signature from `vectory release sign`). A key is replaced within its custody by a statement the old key signed (`POST /agent-release-keys/rotate` for the server's, `/rollover` for an uploaded one), and revoking one withdraws the releases it signed and ends the rollouts that offer them. Turning updates off keeps the key and refuses while a rollout is active or paused; **Stop all updates** (any operator) cancels every rollout and withdraws every offer, and an administrator ends the stop. `GET /agent/v1/release-keys` on the agent listener lists the public keys a host pins: no certificate, never who holds a key, `404` while updates are off.
- **Releases come from the server's own agent builds.** `POST /agent-releases {version}` copies this server's builds of a version (the mirror's build of a platform where it has one, the image's otherwise) into a release store under their digests, writes the release manifest with a counter above every counter any host reports it attempted, and signs it (server custody) or waits for the team's signature (`PUT /agent-releases/{id}/signature`, which must verify under the current key, else `422 RELEASE_SIGNATURE_INVALID`, and is audited). The files outlive changes to the catalog; at most 20 releases that are not withdrawn are kept, and `VECTORY_AGENT_RELEASE_STORAGE_BYTES` (default 2 GiB) bounds the store (`507 RELEASE_STORAGE_FULL`).
- **Update rollouts with a review.** `POST /agent-update-rollouts/preview` lists, for every device of a selection, whether it will update or the first reason in a fixed order it won't ("edge-02 tried 0.1.1 and rolled back; it takes the next release"), with what to do on the host where something would help. Creating the rollout rechecks that review in the same transaction (`409 UPDATE_REVIEW_CHANGED`), a device is in one open update rollout at a time, and a retry with the same `request_id` returns the same rollout. A canary goes first, then batches, each followed by an observation; the rollout stops at a failure threshold that counts rollbacks, failures and devices that stopped delivering, and can be paused, resumed and cancelled. A device counts as updated only when the server sees the new build check in from a new process and the host's own result says it kept it, never from a report that the build was written.
- **The offer travels in the signed manifest.** A device released into a stage is offered the release in its next manifest: the stored release manifest and signatures exactly as signed, the key statements a host that pins an older key needs, and the build's digest. The manifest's signature binds the offer to the device and the nonce, and what a host acts on is the release manifest, which it verifies against the keys it pinned. The build downloads from `/agent/v1/agent-releases/{sha256}` only for the offered digest and the device that holds the offer, is hashed as it streams, and is limited to one transfer per device, 16 on the server and six requests an hour per device.
- **Where agent updates show.** The heartbeat member `agent_update` is checked strictly (a member that breaks a bound refuses the check-in and changes nothing) and shown read-only on `GET /devices/{id}`; `GET /agent-updates` counts the fleet's agent versions and how each device takes updates (automatic, ask, off, can't update, not reported); the device inventory filters by `agent_update` and `agent_version`; a rollback or a failed update opens the issue `AGENT_UPDATE_ROLLED_BACK` or `AGENT_UPDATE_FAILED` and the Overview's list of what needs you gains a group for it; the audit log names releases, keys and rollouts with versions, digests, counters and fingerprints and never key material; and a notification channel can ask for `agent_update.failed`, `agent_update.rolled_back`, `agent_update.stopped` and `agent_update.key_changed`.
- **A host consents to agent updates in `setup`, once.** `--updates auto|ask|off` with `--update-key-sha256` (up to 4 keys), `--update-track patch|minor` and `--update-window` (up to 7) write a policy that only root can change, outside the agent's state directory, and install the update step. The policy is written before the service exists, so consent is in place before the first check-in; the step is installed once the service is registered, which it checks, and before the service starts. `setup` checks every flag and that updates can work on the host before it changes anything: a service manager, an install directory and policy directory only root can change, an agent that isn't installed from a package, an operating system whose updates are in this release, and a server that offers updates. It finds the key to pin by the fingerprint it computes from each key in the server's list, never by the list's own `fingerprint` member, and pins nothing when the list is invalid or doesn't hold the key. A command without update flags touches none of it, and `--updates off` withdraws consent and keeps the pinned keys. Given without `--updates`, the key, the track and the windows change only what they name on a host that already agreed (a key re-pins it) and keep the level, the other parts and a pause, so no command has to say again what a host chose; on a host that agreed to nothing, or whose policy can't be used, they are refused with the usage exit code and no other effect.
- **`vectory update` shows and controls updates on the host.** `status` says what the host consented to, whether it can take a build and why not, what the update step did last, what the agent staged and how the last update ended, including that a rolled-back release won't be tried again. `apply` applies a staged build now on a host that asks first, after showing what the agent last reported about the offer; it refuses when the offer is gone or the report is more than 5 minutes old unless you confirm with `--force` on a terminal. `pause` and `resume` hold updates back without a restart, and `off` withdraws consent, deletes what the agent staged and removes the update step, and is refused while a build is being tried. Root deletes the staged files only through a path that only root can change; where the directory above the agent's state directory can be changed by another account, `off` (and `setup --updates off`) still withdraws consent and removes the step, deletes nothing, and says the files are for you to delete (`staged_left`, code `UNTRUSTED_LOCATION`, in `--json`).
- **The agent downloads and stages an offered build, and refuses what it shouldn't take.** An offer is read only from a manifest that lists the feature. The agent verifies the release against the keys the host pinned and the counters the update step attempted, so a release that was tried and rolled back is refused before one byte is downloaded, then downloads the build in the background with a 5-minute limit and a 20-second stall limit, and stages it only when its size and SHA-256 are the signed ones. It defers while a configuration apply, a check on request, a pause or the update step is busy, deletes what it staged when the offer is withdrawn or changed unless the update step has started on it, and writes nothing, not even a directory, while updates are off. It reports where the offer stands in every check-in; a server that refuses that report gets the check-in without it, and never receives it again from that agent process, so no report can take a device off the control plane.
- **`vectory status` and `vectory doctor` say how updates stand.** `status` gains an **Updates** row (and an `updates` member with `--json`), and `doctor` checks the policy, the update step, whether the host can take a build, a fork of a pinned key and the last result, with a fix for each.
- **An update rollout can't stay open for ever.** A device that holds a download or a staged build for an hour without a change is skipped, and so is one whose host drops the offer (paused, turned off, or holding another release), with the reason the host gave. A verified device that is revoked or silent for good no longer holds the next stage back or counts as failing, and the canary still needs one it can watch. A release that expires ends its rollouts as cancelled (`cancel_reason: release_expired`, audited as `agent_release.expire`). A rollout that has devices it can't move on and makes no progress for 24 hours fails as `stalled`, withdraws what it hadn't started and sends the `agent_update.failed` notification; a rollout that only waits for a person or a window is never stalled.
- **The public key list doesn't say who holds a key.** A release key the server generates is named `release-` and the first eight characters of its fingerprint, where it used to be named `server-` and those characters, so the list a host reads without a certificate no longer tells that a server compromise alone could sign a release.
- **At most 200 update rollouts are open at once.** Every active rollout is read at each scheduler tick under the writer lock the check-ins share, so starting a 201st active or paused rollout is refused with `409 UPDATE_ROLLOUT_LIMIT` ("At most 200 update rollouts can be active or paused at once. Cancel or finish one first.").
- **A restored server stops agent updates until an administrator has looked.** A backup brings back a release key revoked since, ended rollouts and withdrawn releases, so with agent updates on `vectory-admin invalidate-restored-access --apply` also does **Stop all updates** (its preview counts the rollouts it will cancel), and nothing is offered to a host until an administrator reviews them and chooses **Clear the stop**. At start the server logs one warning when the release key it holds can't be unsealed, with the fix, and removes no sealed key file while that is so.

- **Agent updates on a Mac.** The update step is the `io.vectory.update` launch daemon, which `setup --updates` registers next to `io.vectory.agent`. It runs as root every 30 seconds from its own copy of the agent, with no sandbox (launchd has none to give it) and bounded by a clean environment, no network use and the path check, stops and starts the agent's job through `launchctl` and takes a build back when it doesn't stay up, as the Linux step does. On a Mac the check that the install path and the update policy belong to root alone also reads access lists: an entry that gives another account anything but reading, listing and searching refuses the path with `UNTRUSTED_LOCATION` and names the entry, because `chmod +a` and entries a parent hands down change who can write without changing the mode bits. An agent that the installer package, Homebrew (`/opt/homebrew`, `/usr/local/Cellar`) or MacPorts (`/opt/local`) owns is `PACKAGE_MANAGED` and updates with its package manager, and one in a `/usr/local/bin` that an administrator account owns (Homebrew on an Intel Mac) is told to install where only root can write. A release that doesn't ship macOS updates leaves a Mac reporting `PLATFORM_NOT_IN_RELEASE`, and `setup` refuses `--updates` there.

- **Agent updates on Windows.** The update step is the `VectoryUpdate` service, which `setup --updates` registers next to `Vectory`. It runs as SYSTEM from its own copy of the agent every 30 seconds, uses no network, stops and starts the agent's service through the Service Control Manager and takes a build back when it doesn't stay up, as the Linux and macOS steps do. A running agent can be renamed and not replaced, so the swap is two renames that keep the build it replaces as `vectory.exe.previous`: between them the install directory holds no executable, and the step's next run after a crash or a power cut puts the previous build back and starts the agent. A program that holds a file the step renames, such as a virus scanner, makes the rename wait (ten tries half a second apart), and a hold that doesn't end fails the update before the executable is touched, or puts it back. On Windows the check that the install path and the update policy belong to root alone reads the access lists: only SYSTEM, the Administrators and TrustedInstaller may own or change the install directory, the agent, `%ProgramData%\Vectory` and what is in it, and an entry that lets another account write, delete, add files or take ownership of them refuses the path with `UNTRUSTED_LOCATION` and names the account. The directories above them (a drive root, `C:\ProgramData`, `C:\Program Files`) may let other accounts create entries, as a default Windows install does, and are refused only for the rights to delete, rename or take over what they hold. An account that holds the right to back up files, restore files or take ownership of files bypasses access lists and appears in none (the Backup Operators group, empty by default, and any account given those rights), so the host trusts such accounts as it trusts the Administrators, and the documents say how to find them. Every file and directory the step makes has an access list of its own with the Administrators as owner, and `%ProgramData%\Vectory` is closed to every other account by whichever code makes it first, before the policy's and the step's folders are made in it, so that no local account can make one first. `setup` does the same for the agent's state directory and managed configuration, which are kept in it, on every install and upgrade, with updates or without: it closes one that root owns and others can add to, and stops before it changes anything, naming the account, when another account owns it. The agent's state directory, the install directory and the agent are made with a list of their own as well. An agent that the Windows Installer lists under the MSI's upgrade code is `PACKAGE_MANAGED`. The probe, which runs the new build once to see which version and platform it reports, runs as the step's own account with the network and the files open to it, because Windows has no switch of account that needs no password; it runs in a job that ends the build and every program it started when the time is up, when the step stops and when the probe ends, and that holds at most four processes. The service's log, `update-step.log`, is opened through the path check like the step's other files: a link or anything that isn't a plain file of root's in its place is refused, the step goes on without a log and says so on its standard error, and a log longer than a megabyte starts again as it is opened. A release that doesn't ship Windows updates leaves a Windows host reporting `PLATFORM_NOT_IN_RELEASE`, and `setup` refuses `--updates` there.
- **An update interrupted after the swap is settled by the update step alone.** `vectory update apply` never takes it over: it says the background step is settling it, usually within a minute or two, writes nothing and exits `1`. The step's timer run, which is the last build proven on the host, finishes the trial or takes the build back, so the build under trial never judges its own health or undoes its own installation. The same holds for `update-helper` started by hand from the installed executable.
- **A rollback gives the previous build its five minutes.** The watch of the restored build begins when it starts, not when the rollback was decided, so a build that took the whole stop limit to stop no longer makes a healthy rollback end as `ROLLBACK_UNHEALTHY`; the trial's five minutes count from the start of the service the same way. The step frees its copy of the new build before it writes the rollback's journal, so a rollback needs only a few KiB on a full file system.
- **On a Mac, a stop waits until launchd has removed the job.** `launchctl bootout` returns when launchd has begun to remove a job, and `launchctl print` lists the job as running for a moment longer; a start that followed at once took the departing job for the agent, or had its bootstrap refused or dropped with the job, and a build that was fine ended as `START_FAILED`. The update step's stop, and the agent's own `service-stop` and `service-uninstall`, now return when `print` says there is no such job and the process the job had is gone, within the stop limit. The start bootstraps only when launchd has no such job, tries a refusal again every two seconds for a minute and returns only when `print` lists the job, so a bootstrap that was accepted and dropped is made again.
- **A start that can't be made doesn't leave a host without an agent.** When the previous build can't be started in a rollback, or the old build after a swap the file system refused, or the service manager doesn't show it afterwards, the step keeps its journal at `rolling_back` (or `swapping`), ends the run with an error and one line in its log, and tries again at its next run, 30 seconds later, for as long as it takes. It used to end the request, and the runs after it found nothing to do. `ROLLBACK_UNHEALTHY` now means a previous build that was started, is loaded and didn't report healthy within five minutes (or couldn't be put back). `vectory update status` and `vectory doctor` say that the update step is trying to start the previous build again and what to look at, the agent's service and the step's log, and send a person to the agent's service and the log before the network and the server after a `ROLLBACK_UNHEALTHY`.
- **A job that launchd keeps, loses or counts again is read as it is.** A build that exits at once leaves launchd's job loaded with its runs counting up, and three restarts, about 30 seconds, end the trial as `START_FAILED`. A job launchd no longer knows during a trial (an administrator's `bootout`) is loaded again, twice at most in one watch, before it ends the trial; a count of restarts that goes down is counted from the lower number, with a line in the step's log. The step's simulated `launchctl` in the tests answers as launchd does (a loaded job that exits, a removal that lags the bootout, a bootstrap refused or dropped while a label is being removed).
- **The access-list rule on a Mac is an allow-list.** An entry for another account passes only when every right it grants is reading, listing, searching, read attributes, read extended attributes, read security or synchronize (write attributes and write extended attributes are tolerated on purpose); any other bit refuses the path, named by the kernel or not. The kernel expands the generic write and generic all rights into write, append, delete and more when it evaluates an entry, which a list of the rights to refuse missed. The 54 combinations of generic rights and a list a fuzzer found are tests, and a fuzz target compares the verdict with a model of the kernel's expansion.
- **A volume that doesn't keep owners, or isn't local, refuses the path on a Mac.** A volume mounted with ownership ignored (an external disk or a disk image attached by default) makes every account count as an owner of every file, so the root-owned files and modes the check reads there mean nothing; a network share can be changed behind the host's back. Either is refused with `UNTRUSTED_LOCATION`, naming the volume, why and the fix (`sudo diskutil enableOwnership /Volumes/Name`, or the system volume).
- **An immutable or append-only flag is found before anything stops.** A flag on the agent or its install directory (`chattr +i` or `+a`, `chflags uchg`, `uappnd`, `schg` or `sappnd`) used to show only when the swap failed, after the service had stopped and the release's counter was spent, as an update that ended `INTERRUPTED`. The host now answers `READ_ONLY` naming the path, the flag and the command that clears it, before anything is raised or stopped.
- **`vectory update off` and `service-uninstall` take away a step whatever the gate says.** A build that doesn't ship updates for an operating system used to report nothing to remove while the step an earlier build installed kept its root launch daemon or timer. Removal now uses the system's host, and `update off` says the step is removed only when its directory is gone.
- **The agent's own launchd definition refuses what a definition can't hold.** A control character, NUL, U+FFFE or text that isn't UTF-8 in the executable, the state directory or the account is refused before anything is written, as the update step's definition already did; the XML escaper would have written another character in its place.
- **`vectory pause` holds the update step.** A staged update waits, unanswered and unrefused, until `vectory resume`, including when a window opens or the host restarts, and a build already being tried finishes its trial. `vectory update apply` refuses first and says to resume.
- **A host that saw a fork stays frozen.** When two statements of a pinned key name different successors, the agent refuses the offer and hands the update step the offer's files and a request with no build. The step verifies them again, writes the fork down in root's files and refuses every later offer until the host is pinned again, including a release signed by one of the two successors that carries only one of the statements. Before, the fork was reported once and forgotten, and such a release was taken.
- **The update step's unit has four capabilities.** `CapabilityBoundingSet` is `CAP_SETUID CAP_SETGID CAP_DAC_OVERRIDE CAP_KILL`: the step changes no owner and no mode of a file it doesn't own, so `CAP_CHOWN` and `CAP_FOWNER` are gone. Its file operations and the probe run in the tests under exactly that set.

### Security

- **The validator never runs your Lua.** Lua can run any program, and Vector runs a `lua` step's code when it builds the step for `vector test`, so a pipeline with a Lua step and a test ran its author's code in the validator. Now the check replaces each Lua step, in any form, with a pass-through stand-in and says each device checks it (`deferred_reasons` gains `Lua runs on devices`). **Run pipeline tests** and the publish review answer for a pipeline with Lua without asking the validator: its tests run only on devices (**Check on devices** with **Also run the pipeline's tests**), and publishing it needs **Publish anyway** like any tests that didn't run. Native tests show with marker files that Lua, the `exec`, `journald`, `stdin` and `file_descriptor` sources, the `file` sink and secret backends never start in the validator.
- **The validator never reads an enrichment table's file.** A pipeline with a `file`, `geoip` or `mmdb` enrichment table, a step that looked it up and a test made the validator open the path the author named and return the rows in the test result, so an editor could read any file the validator could. Those tables, and the steps that look them up, are now replaced in the check (`deferred_reasons` gains `Enrichment tables are read on devices`), and the pipeline's tests run only on devices, like a pipeline with Lua. `memory` tables are checked here as before. A native test names every path with a pipe and shows that none is opened.
- **A VRL call that passes a file is no longer run in the validator.** `parse_groks` reads the JSON files of `alias_sources`, and `parse_etld` reads the list named by `psl`, when Vector compiles the program, so a program could make the validator open a path it chose. The static check now replaces a step that passes one, and the sample tester and the tests refuse it, like `validate_json_schema`; without a file, both functions run as before. A device in full mode runs the program for real.
- **A restricted device refuses a VRL call that passes a file.** `parse_groks` opens the files its `alias_sources` argument names, and `parse_etld` the list its `psl` argument names, when Vector compiles the program, even on a branch that never runs. Restricted mode matched VRL functions by name only, so a restricted device let a pipeline make Vector open any file its service account could read, past the host's file roots. The agent now refuses such a call before Vector runs (`DYNAMIC_CAPABILITY_DENIED`, naming the function and the argument), and no allowance changes it: remove the argument, or use a full-mode device, which is unchanged. The deploy review blocks a restricted device for it with `FULL_VECTOR_MODE_REQUIRED`, and the dashboard names it **VRL access to device resources**. Without a file argument both functions work as before. The agent, the server and the dashboard scan alike, with work bounded by the size of the program, and one set of test programs fails the build when they differ. A device that already runs a version with such a call keeps running it until another version applies, but the agent won't start that configuration again after Vector or the agent restarts: deploy a version without the argument first.
- **The validator never sends an instance metadata request.** To build an `aws_ec2_metadata` step for a test, Vector asks the step's `endpoint` for a token and for the instance identity document, and quotes part of the answer in its errors, so a pipeline with that step and a test made the validator send requests to an address its author chose. The check now replaces each such step and says each device checks it (`deferred_reasons` gains `The AWS instance metadata step is checked on devices`). **Run pipeline tests** and the publish review answer for such a pipeline without asking the validator: its tests run only on devices, and when several causes apply (Lua, an enrichment table, an instance metadata step) the message names all of them. A native test counts the connections to a local listener and shows that none is made, and that Vector itself connects.
- **One address can't lock the others out.** Sign-in, the second sign-in step, password reset, invitations, enrollment, the installer and agent downloads charge the client's own limit first and the limit every client shares only for the requests the first let through. Before, one address sending a few hundred requests a minute made every other address answer `429`. On the sign-in steps part of the shared limit is reserved for addresses that have signed in, so a flood from other addresses can't lock out the people who would respond. Reset and invitation codes get a limit of 30 a minute per address. Error codes, messages and `Retry-After` are unchanged.
- **Authenticator codes are limited on every sign-in form.** Sending the code with the password in one request gave unlimited guesses at the per-address rate. Now all of an account's attempts, from either form, share ten in five minutes, and five wrong codes lock that form for the account for five minutes, from any address (`SIGNIN_THROTTLED`, with `Retry-After`). A password alone no longer returns the sign-in failure it reserved or marks the address as one that has signed in; only a finished sign-in does.
- **A failed `accept()` no longer ends the server.** The agent listener skips aborted connections, waits out descriptor and memory shortages with a log line, and ends only when its socket is unusable. Parked agent waits are answered however the server ends.
- **Silent connections can't starve real devices.** A connection has three seconds to send its ClientHello before it holds anything but a socket, and the handshake slots follow `VECTORY_MAX_AGENT_CONNECTIONS`. Before, 260 silent sockets made a real device's request fail.
- **The dashboard and API listener bounds slow and numerous clients.** A connection has 15 seconds (`VECTORY_HTTP_HEADER_TIMEOUT_SECONDS`) to deliver its first request's headers, and as long between requests. A request body has 30 seconds in all (`VECTORY_HTTP_BODY_TIMEOUT_SECONDS`). At most 4,096 connections are served at once (`VECTORY_MAX_HTTP_CONNECTIONS`), and one beyond that is closed at once. Before, 60 sockets that sent half a request stayed open for as long as the client liked, and nothing bounded a slow body or the number of connections. A failed `accept()` is logged and waited out, as on the agent listener, and a production server bound beyond loopback warns at startup.
- **Only the proxy can reach the HTTP listener in Compose.** `VECTORY_HTTP_ALLOWED_PEERS` lists the addresses, ranges and host names that may connect. Any other peer is closed before a byte is read, loopback is always allowed, and Compose sets it to `proxy`. Before, the validator, which runs untrusted pipeline code and shares a network with the server, could open `server:8080` directly and, with `VECTORY_TRUST_PROXY_HEADERS` on, choose its own `X-Forwarded-For`. The `compose` job now checks that the validator gets no answer.
- **Changing your password or ending your other sessions authenticates first.** `POST /account/password` and `POST /account/revoke-sessions` answer `401` to anyone who isn't signed in, whatever the body, and `403` without the session's CSRF token. A signed-in caller whose body isn't valid still gets `400`. Before, an anonymous caller with a malformed body got `400`.
- **A refused enrollment with a real token is recorded once a minute per token and reason**, not once per attempt.
- **Refused enrollments from many addresses add a bounded number of audit events.** The audit log is never pruned, and a peer with many addresses could add up to 600 refusals a minute, about 0.8 GB a day. All refusals together now write at most 60 events a minute; the ones past that are counted, and one **Device enroll refusals summarized** event a minute says how many ("37 further refusals in the minute from 04:06 UTC were not written"). The most a flood adds is 61 events a minute, about 84 MB a day.
- **Notification destinations** refuse Azure's platform address `168.63.129.16` like every other cloud metadata address, and Slack's `text` field escapes `&`, `<` and `>` as the blocks do (`event.headline` keeps the words as written).
- **Pipelines can't name paths or open Vector's API.** A component ID can't contain `/`, `\` or control characters, or start with a drive letter and a colon, because Vector uses it as a folder name for checkpoints and disk buffers; a pipeline with a top-level `api` block needs full mode, so the deploy review says so and a restricted device is never offered it.
- **A restricted device refuses an AWS credentials file.** A `credentials_file` anywhere under a component's `auth` (the `http`, `loki`, `prometheus_exporter` and `elasticsearch` sinks) can name a program that Vector runs while it validates, and a pipeline's own file sink could write such a file under an allowed file root. The device reports `CREDENTIALS_FILE_DENIED` before Vector runs, and no allowance changes it: give the sink its access keys as device secrets, or use a full-mode device, which is unchanged.
- **A restricted device refuses AWS credentials the host supplies.** An `auth.strategy: aws` without both `access_key_id` and `secret_access_key`, or with `assume_role`, `imds` or `profile`, would sign with the host's own AWS identity, which no allowance names. The `elasticsearch`, `http`, `loki` and `prometheus_exporter` sinks now report `AMBIENT_CREDENTIALS_DENIED` unless the keys are explicit device secrets. A device that already runs a version that relied on the host's identity keeps running it until another version applies, but the agent won't start that configuration again after Vector or the agent restarts: deploy a version with explicit keys first.
- **The deploy review blocks a restricted device for an AWS credentials file or the host's own AWS identity.** Deploying a pipeline whose AWS sink uses either to a restricted device is now blocked before the deployment, with the reason, instead of failing on the device. Full-mode devices are unchanged.
- **`vectory allow`, `install` and `setup` refuse a file root that covers the agent's own files.** A root can't be `/`, the root of a drive or a share, or be, hold or lie inside the agent's state directory, the managed configuration directory or a file bound to a device secret. The message names the root and what it overlaps, paths are compared through links and, on macOS and Windows, without regard to case, and nothing changes.
- **The packaged systemd unit** is strict again: `ProtectSystem=strict` and `ProtectHome=true`, with `ReadWritePaths=` for the state directory, the managed configuration directory and `/var/lib/vector`. A pipeline that writes anywhere else fails with `Read-only file system (os error 30)` until you add the folder with `systemctl edit vectory.service`. The unit that `vectory setup` registers still uses `ProtectSystem=full` and `ProtectHome=read-only`.
- **A control byte in Vector's log text can't take a device off the control plane.** A pipeline that logs event fields (VRL `log()`), or a Vector error that quotes an event, could put a BEL or ESC byte into the log text a device reports. The server refused the whole check-in, so the device went offline with nothing to say why, and new deployments never reached it, until the line left the one-hour summary or Vector reloaded. Now the agent and the server replace control characters, line and paragraph separators and text-direction controls in a log summary's message and a diagnostic's message, hint and field with spaces, and the server stores and shows the replaced text. Names, IDs, codes and enumerated values are still refused.
- **A component named with letters outside ASCII no longer takes its device off the control plane.** The pipeline validator and Vector accept an ID such as `café` or `日志`, and the agent reported it in the log groups and diagnostics, but the server accepted only ASCII letters, digits and `_.-` there and refused the whole check-in. The device never checked in again, got no manifest, and no rollback could reach it, though Vector ran the version. The server and the agent now judge the IDs and output names a device reports by one rule: the validator's (1 to 128 bytes, no `/` or `\`, no control character, no drive letter and colon at the start) and, for a report, no line or paragraph separator, text-direction control or byte order mark. A device that was stuck checks in again once the server is updated. A component whose name the rule refuses, such as one with a text-direction override, is reported without its name.
- **A refused check-in is sent again without its optional reports.** The agent sent the same reports at every check-in, so one the server couldn't accept kept the device from checking in. Now the agent leaves reports out one step at a time until the server answers: a check's result, then the log summary and diagnostics, then the host reports, then what it announces it can check. While the server keeps refusing one, each check-in costs one more request for each step it takes to leave it out (one for the log summary or a diagnostic, two for a host report), and the agent says so once for each kind of report it left out: "The server refused a check-in; the agent sent it again without the Vector log summary." What the agent sends is also kept within what the server accepts: a diagnostic is shortened to 512 bytes as the server measures it (a record of 100-byte IDs and sixty four-byte characters was sent and refused), an apply error's message is cut at 1,000 characters, and a directory or metrics address the server would refuse is left out.
- **Versions, request and boot IDs, directories and test names refuse more characters.** `os`, `arch`, `agent_version`, `vector_version`, `request_id`, `boot_id`, a state directory, the host runtime's data directory and a check's test names refused only a NUL or a control character. They now refuse every character that can't be shown safely in one line, as names and IDs already did: line and paragraph separators, text-direction embeddings, overrides and isolates, and the byte order mark. Release candidates, build metadata and Windows paths with spaces and non-ASCII letters are accepted as before.
- **`vectory logs` can't draw on your terminal.** Event text in the log could change the terminal's title, clear the screen or overwrite the start of a line to forge a log line. The default output now shows control characters, line and paragraph separators and text-direction controls as escapes such as `\x1b`, `--json` escapes them (`\u001b`), and `--raw` stays the file as written ([`logs`](docs/user/cli.md#logs)). The docs no longer say the command never shows your events: a pipeline that logs event fields (VRL `log()`) does.
- **A device's own audit events are bounded.** A device that changed its reported state or configuration mode on every check-in added two audit events a check-in, about 60 a minute, to a log nothing prunes. A device now adds an event only when the value changed, and at most 4 events a minute of each kind (apply state, configuration mode, secret reconciliation); a new generation under the same apply state adds none. [Audit log storage](docs/user/telemetry.md#audit-log-storage) says that the log is never pruned, what an event costs, what a busy fleet adds and how to keep a copy.
- **A notification channel's name can't hold a line separator or a text-direction control.** The name appears in the messages the channel sends, so it follows the rule the agent applies to pipeline names, and the form says what to remove.
- **A pipeline, deployment, group, saved-settings, token or person name can't forge a line in an alert.** An editor could name a pipeline with a line break and a sentence such as "Resolved on every device", and the next failed rollout sent that line, or reordered text, to Slack, webhooks and email. These names now follow the rule channel names have, and the error says which field to fix. A name saved earlier reads as one line in every alert, the subject of an email included, with each such character shown as a space and runs of spaces collapsed.

### Fixed during development

Agents built before these fixes behave differently. Rebuild agents from this revision.

- **A fix the agent prints can't run a second command.** The `vectory allow` line that a refused version names (and every other command the agent tells an operator to run) quoted a path, address or host from the pipeline with a rule that left `;`, `&`, `|`, `<` and `>` bare, so a crafted pipeline path could end the command an operator pastes. Every printed command now quotes anything but plain characters. The agent's note in `vectory logs` also refuses to follow a link at its fallback open.
- **Enrollment preflight:** an unreadable CA file or invalid local option is rejected before connection settings are saved or an enrollment request is created. Earlier builds could save the connection settings first.
- **Combined `install` options** are validated together before anything is saved. Earlier builds could save one option and then reject the next.
- **A remap with its program in a file:** its tests now run only on devices, like Lua and enrichment files (**These tests need the device environment**, and `deferred_reasons` gains `A VRL program in a file is read on devices`). A remap that names its program twice, such as `source` and `file`, fails the check with Vector's rule, `must provide exactly one of source or file or files`. Earlier builds replaced both with a pass-through, so the check read **Checked** for a remap every device refuses, and its tests failed against the pass-through.
- **Credential fields:** plain text in any field Vector marks as a credential is refused at save and publish, with the fix. Earlier builds took `vectory-secret:NAME` only in the `auth` fields of `http`, `loki` and `elasticsearch` sinks, so other credentials were stored in the pipeline. Published versions are unchanged.
- **Secret-binding maps** are parsed strictly: `null`, lists, duplicate names and trailing content are rejected. Earlier builds could treat `null` as "remove all bindings" or keep the last duplicate silently.
- **Capability-policy files** with malformed UTF-8 or unpaired Unicode escapes are rejected instead of being repaired with replacement characters.
- **Metrics endpoint:** `vectory configure-metrics` and `--clear-metrics-url` were added. Earlier builds could only set a URL with `install --metrics-url`.
- **Replaced Vector binaries** can be approved with `vectory re-adopt --expected-sha256`. Earlier builds had no approval path.

- **Restricted mode matches VRL calls, not substrings.** A metric named `http_requests_total`, a filter on `"http_request"` or a step called `http_requests` no longer needs Full Vector mode. The agent, the server and the dashboard decide from one list, and it now includes the functions that read a file (`validate_json_schema`, `parse_proto`, `encode_proto`).
- **`remap.file` is refused in restricted mode** like `files`, and an HTTP route's `path` is no longer judged as a file path. A refusal never suggests `/` as a file root.
- **Delivery health no longer fails an assignment.** A device that stops delivering pauses a persistent assignment (reason "data plane") instead of failing it, so the assignment keeps following its group and resumes when you do.
- **Tests Vector refuses to run are failures.** A misspelled test setting, an unknown step or a test with no expected output shows Vector's reason, and the tests it did not run are marked **Not run**, instead of "0 of 0 tests passed".
- **The documentation page's recovery screen** shows **Reload page** at once for a signed-out visitor; it used to appear after five seconds.
- **The installer's dry run** plans for the directory you chose with `--install-dir`.
- **A listener below port 1024** (syslog on 514, for example) now gets a `PRIVILEGED_PORT` diagnostic that says how to allow it, instead of a hint about a path.

Agents report `service_manager` and `vector_running` to servers that list those features.

The device page reads "Nothing running: Vector stopped after v1 failed to start.", its issue "<device> couldn't start <pipeline> v1", and a new device reads "Nothing yet" instead of an adopted workload that "may still be running".
- **Delivery without metrics** is judged from Vector's log: a sink failing requests two check-ins in a row opens the sink-errors issue, "measured from Vector's log (no metrics)". The synthetic example ships with it.

- **Device lists are lighter.** `GET /devices` and the Overview return list rows without the host runtime, the Vector log summary or per-component telemetry (about 80% smaller for a busy device); the device page still reads the full record.

- **The anonymous rate limiter never refuses a new client because it is full.** It evicts the entry that expires soonest; installer, download, enrollment and invite traffic have their own partition and global per-minute caps, so it cannot crowd out sign-in.
- **Membership previews no longer queue behind heartbeats.** A busy server answers "Preview busy, retrying" and the dashboard retries quietly.
- **The install command never turns certificate checks off.** Add device used to generate `curl -fsSLk` for a private CA. The command now writes the server's CA certificate (public, like its fingerprint) to `vectory-ca.pem` and runs `curl --cacert` against it; curl's `--pinnedpubkey` can't replace the CA check. **Advanced → How the host checks this server** offers the pinned CA (the default for a private CA), a CA file on the host (`--ca-file PATH`, `curl --cacert PATH`) or the host's trusted certificates (`--ca-file=`), and the installer honors the same choice for its download. The checksum line is split at the pipe so no part hides under **Copy**.
- **A command made for a typed name enrolls only that name** (`DEVICE_NAME_MISMATCH` otherwise), and a token pasted short or mangled is refused on the host before anything is sent.
- **Fingerprints are compared in full.** A pin mismatch prints both fingerprints with the first byte that differs; an untrusted CA prints the received fingerprint in Add device's rows of eight pairs, never as one value to paste as a pin.
- **Commands that need the agent stopped name what holds it** (the service, `vectory run` with its pid, or another command) and how to stop it. `vectory retry` works while the agent runs: it is queued and taken within seconds. With nothing failed, it says so and changes nothing.
- **`vectory allow --network/--listener/--file-root`** adds restricted-mode allowances and keeps the rest; refusal fixes and the deploy review's host commands use it, with the host's own `--state-dir` and service (or `vectory run`). `install --capability-policy` says what the host allows afterwards.
- **The agent's log says what changed, once:** the version it applied, a refusal in the words of its diagnostic, "Reconnected to … after 1 min 12 s", and how Vector stopped. `run --verbose` keeps a line per check-in. **Recent Vector errors** show only what Vector logged since it last loaded a configuration.
- **Upgrade agent** says when a device already runs this server's build (agents report their SHA-256) and otherwise gives the one installer command, without a token; the manual steps moved behind **By hand**. Setup run beside an older `vectory run` says to restart it.
- **Setup says what to run when an enrolled host is given another address.** A host keeps the address it enrolled with. When a command names a different one, for example `https://127.0.0.1:8673` for a host enrolled with `https://localhost:8673`, setup names both, says to run the command again with `--server` set to the enrolled address if it is the same server, and gives the move (`vectory unenroll`, revoke the device, set up again) last. It used to give only the move. The demo fleet enrolls with the address **Add device** shows, so its **Upgrade agent** command applies as shown.
- **Setup and status wording:** "Vector 0.58.0 binary pinned (SHA-256 …)", the absolute agent path in **Next**, a revoked device's status says the server no longer accepts the agent, a short Vector test run on a shared host no longer blocks setup (it re-checks after 6 s), and `service-stop` without systemd says so plainly. Setup ends with "Connected" only when it saw a check-in, and otherwise just links the device.
- **Smaller dashboard fixes:** the pipeline chooser is styled on a device page; the setup screen and every sign-in screen fit a 320 px phone; a pipeline only this device follows is replaced by default when deploying from its page; refusals read "because this host's restricted mode doesn't allow it"; a revoked device reads "Revoked · last verified running v1"; recovery codes are grouped for typing, and a recovery-code sign-in says how many are left.
- **A rolled-back rollout's first action fits a phone.** "Open rollback (Edge syslog processing (synthetic demo) v2)" ran off the right edge of a 390 px screen and widened the page; the label now wraps inside the row.
- **One attempt, one device.** The notification delivery log reads "No more tries after 1 attempt." and the confirmation of a lost reply "1 device · Priority 100", where both said "1 attempts" and "1 devices".
- **Revoking a device resolves its open issues** as revoked, so the Overview stops counting them.
- **A retired identity keeps its name.** After a recovery the old record read "edge-nyc-01#retired-0b8f3c2a-5d41-4e7a-9a16-2c4d7e9f1b35" in Devices, rollout results, the audit log and issues. Each now shows the name the device had with a **Retired identity** badge (and "(retired identity)" where a line of text has no room for one). The stored name keeps names unique.
- **Data-plane checks ignore a sample whose clock runs more than five minutes ahead**, instead of freezing evaluation until real time catches up.
- **The administrator's two-factor reset authenticates before it reads the request body**, and a rollout's device timeline shows each device's latest changes instead of the oldest 5,000 rows.
- **A live canary rolls back in one reviewed step.** **Roll back** used to be refused for an active, paused or completed rollout that hadn't reached every device. The review now works out, with the real resolver, what each device it never reached runs once the rollout stops; confirming cancels the rollout and returns the devices it reached in one transaction. Only a device that would switch to an unreviewed version or lose its pipeline blocks, by name, and the review offers **Cancel rollout, then review rollback**.
- **Rollback wording names both sides.** Lineage, the rollout header, the list, Recent changes and the rollback receipt say "Rolled back to Edge syslog processing v1" instead of a bare "v1" from another pipeline, "1 reviewed device" in the singular, and the rollback review and **Remove assignment** show device names and "Keeps Edge syslog processing v1 (no change)" instead of UUIDs.
- **A rollback returns devices to what they ran before the rollout, even after another deployment held them.** The version a rollout replaced was rewritten each time its assignment reached a device again, so a higher-priority deployment that took a device and was then removed became the "previous version", and the review blocked the rollback or offered to restore that deployment. It is now recorded once, when the rollout first takes the device (migration `0135`), and again only for a device that left and was added back. When devices would return to different versions, the review names each device and its version. A deployment that never released anything says "Nothing was released".
- **A schedule cancelled before it started offers no rollback.** It released nothing, so its page no longer lists **Roll back** beside the untrue "These devices ran their local config before this deployment.", and the cancel dialog says "Nothing has been released. The schedule never starts, and no device changes." instead of describing devices that already received it.
- **Rolling back a deployment that released nothing says so.** The rollback review reads "Nothing to roll back: Nothing was released, so there is nothing to roll back." instead of a restore plan with no devices in it.
- **Redeploying a fix after a rollback takes one review.** The deploy preview suggests the pipeline's rolled-back rollout and its rollback at the rollback's priority and returns every assignment in the way at any tier, so one **Replace existing** resolves it. **Current winner** names what the device follows today, and when a device still keeps its current assignment the button reads **Deploy to 2 of 3 devices** and asks you to confirm what stays behind.
- **Needs you clears and ranks.** A rolled-back rollout leaves it; a device problem and the rollout it stopped read as one item; devices that aren't delivering come first, with **Roll back** when the server can review it; a stopped rollout can be dismissed per person and comes back if it fails again.
- **The Overview counts the devices that follow a rollout.** A schedule's count leaves out the devices that were revoked since, and a rollout that no device follows reads "No devices follow this now" instead of "No devices targeted yet".
- **The rollout page leads with one action.** A delivery stop shows which device still runs the version, where it can't deliver and how full that buffer is, with **Roll back edge-nyc-02** first; a failure only the pipeline can fix (a port in use, a VRL error) leads with **Fix in pipeline**; Pause, Cancel, Roll back and Remove assignment moved into a **Stop rollout** menu with one line each; the device timeline has the device page's six steps and marks a reload failure at **Vector reloaded**; each failure reason prints once; the redundant copy-link row is gone because the page's address is its link.
- **Deployments reach a connected device in seconds, not at its next check-in.** Between check-ins the agent holds one request open (`GET /agent/v1/wait`, feature `wake`), and the server answers `{"changed":true}` once a change to the device's version, agent settings or access has committed; the agent then checks in as usual. The answer is an unsigned hint that carries no configuration, so the signed manifest stays the only authority, and the agent still opens every connection. On the preview, Deploy to the first apply report took 3.4 s (median of five runs; 37 to 61 s with wake-ups off). `VECTORY_AGENT_WAKE_LIMIT` bounds the waits (default 20,000; `0` turns wake-ups off), large releases are paced (100 at once, then 50 a second, never past a device's own check-in), and `vectory setup`/`install --no-wake` or `run --no-wake` keeps a host on its schedule. Device pages and rollout rows add `wake.listening` and say "connected, usually a few seconds" only while the agent holds the request. Agents and servers without `wake` keep polling as before.
- **On SIGTERM, as on Ctrl-C, the server answers parked agent waits before it exits**, so after `docker stop` or a service manager's stop, a waiting agent gets an answer instead of a reset connection. An apply's follow-up check-in now goes out one second after activation instead of two.
- **The Compose quickstart starts its TLS proxy.** The proxy container dropped every capability, and the Caddy image's binary carries a file capability that the kernel then refuses to run (`exec /usr/bin/caddy: operation not permitted`, a restart loop, and nothing listening on port 443). It keeps `NET_BIND_SERVICE` and nothing else, and now has a health check that requests the API through itself, so `docker compose up --wait` reports a proxy that serves. CI starts the stack, enrolls a device and requests the dashboard through the proxy.
- **The device certificate authority can be rotated.** `vectory-admin rotate-device-ca` creates a new device CA and keeps the old one trusted, so enrolled devices keep working and move to the new one at their next renewal; `vectory-admin retire-device-ca` stops trusting the old one once no device holds its certificates, and names the devices it waits for. **Settings → General → Device certificates** and `vectory-admin device-ca-status` show both CAs and who is left. Each credential now records its issuing CA (migration 0120). `VECTORY_PREVIOUS_DEVICE_CA` still works but logs a warning.
- **Enrollment tokens can list device names and label devices.** A token may preapprove up to 500 device names, each of which enrolls once (`NAME_NOT_PREAPPROVED` and `NAME_ALREADY_ENROLLED` in **Recent enrollment attempts**), and give every device it enrolls up to 8 labels such as `site=berlin`. Labels describe a device; they never add it to a group or a deployment. Both are optional fields under **Advanced** in **Add device** and in `POST /tokens`.
- **The late-start window of scheduled deployments is configurable.** `VECTORY_SCHEDULE_LATE_START_SECONDS` (60 seconds to 7 days, one hour by default) sets how late a schedule still starts after the server was down; `GET /settings` reports it. When a cancel races a start, the one recorded first wins, and the contract and the deployments guide say what each order means.
- **A server restart no longer reports the whole fleet offline.** Agents that could not reach the server wait up to five minutes before they try again, so the first scan after a start found every device silent and sent a **Device offline** message for each. Silence now counts from five minutes after the server starts at the earliest, and a device reported before the restart is not reported again.
- **The rolled-back message names the pipeline it restored.** When a rollback returns devices to a version of another pipeline, **Rollout rolled back** says "rolled it back to Edge syslog processing v1" instead of a bare "v1", and the event carries `restored` (`id`, `name` and `version_number`).
- **Recovery messages say what they are.** **Issue resolved** and **Device back online** end their context line with "Resolved" and "Back online", not the severity of the problem that ended.
- **A limit outside its range stops the server at startup.** `VECTORY_TELEMETRY_RETENTION_DAYS=90` kept 30 days, `abc` kept 7 and `VECTORY_MAX_AGENT_CONNECTIONS=10` ran with 64, each without a word. Both now refuse a value that isn't a whole number in the documented range (1 to 30 days, 64 to 65,536 connections) before anything starts, with a message that names the variable, the value and the range.
- **A revoked device and the devices of a removed assignment no longer count as applied.** A revoked device kept reading **Applied** in a snapshot deployment, and a rollout whose assignment was removed kept reading "1 of 2 devices applied". Both read **No longer targeted** now, in the counts, the rows and their filters, the rollout lanes and the Overview, and the rollout says **No devices follow this now**. What was stored stays as history, and a rolled-back rollout still counts what applied before the rollback.
- **Audit rows read as names.** An issue's events name the issue by its title and device instead of its 64-character ID, a device recovery is attributed to the token that authorized it ("Recovery for edge-nyc-02") instead of the token's ID, and each row carries `device_name`, the device's current name beside `device_id`.
- **Review scheduled devices names the devices a version can't reach.** When the refreshed selection holds a device that can't take the version (a restricted device for a pipeline that needs full mode, or a Vector version the server doesn't support), the review lists those devices by name and keeps **Update scheduled devices** unavailable. It used to stop at "The server response does not match this dashboard version." The contract's blocker lists `resource` and `device_ids`, which the server already sent.
- **A deployment to thousands of listed devices no longer stalls the server.** Resolving assignments copied the whole deployment record, with its list of target devices, once for every device it applied to. For an all-at-once deployment to 10,000 devices that took about 8 GB of memory on every scheduler tick and held the database writer so long that no device could check in. Resolution now reads the record in place.
- **Database load is visible.** With `RUST_LOG=vectory_server=info,vectory_server::sqlite=debug` the server logs once a minute how busy its single database writer was, how long writes waited for it, and the size of the write-ahead log.
- **Setup keeps a copy of what an existing Vector loads.** When Vector already runs, setup records how it was started (its command line, working directory, the variables that select configuration, and its service's definition), copies every configuration file it loads into `adoption-inventory` in the state directory with SHA-256 checksums (also under `adoption` in `--json`), and stops. It names the files and the fix when the topology depends on more than the agent's one JSON file: a directory or several files, `include`, a provider, configuration chosen by an environment variable, or a process it can't read. `--adopt-existing` adopts such a Vector as it is, and setup remembers that choice while you stop the old Vector. Setup now finds a running Vector on Windows too, and `vectory help` lists exit code 3.
- **A full disk is survived and said.** Every write of an apply (the staged artifact, the managed file, the last working copy, the state) reports a full disk as `DISK_FULL` with its fix, leaves the running configuration untouched and never holds the version back: the next check-in after space returns applies it. Enrollment leaves no partial key behind.
- **A download that is cut off, too large or altered writes nothing.** The findings `DOWNLOAD_INTERRUPTED`, `DOWNLOAD_TOO_LARGE` and `ARTIFACT_MISMATCH` say which, the partial file is removed and the retry waits for the next check-in.
- **A `vector validate` that outlasts its limit** rejects the version as unverified (`VECTOR_TIMEOUT`), kills the validating process and leaves Vector on the old configuration. A killed agent recovers to the last verified configuration from every step of an apply.
- **Proxies are named.** A proxy that asks for a sign-in (`PROXY_AUTH_REQUIRED`), refuses the connection or inspects TLS fails with a message that names it and how to fix it; the server pin still decides which server the agent talks to.
- **Root commands keep the service's ownership.** `pause`, `retry` and a foreground run as root no longer hand the service account's state files to root; whatever the agent writes stays private (`0600`).
- **Upgrading:** migrations only go forward. An older server refuses a migrated database, so a downgrade means restoring a backup, and the first start after this release builds the telemetry index (slower on a large table). A migration that fails keeps nothing: the server stops with a message naming the migration, its cause and the migration the database is still at, and a database from a newer server is refused by name instead of with a bare sqlx error.
- **The Windows commands quote what you type.** The commands from **Add device**, **Commands for the host** and the run command put every value in single quotes and double each single-quote character PowerShell recognizes: besides `'`, the curly quotes U+2018 to U+201B, which a value pasted from a document could use to end its string and run the rest in the elevated shell. **Advanced** refuses curly quotes, double quotes and control characters in a Windows path and names the field; for a value with a control character, a command is never built (the host commands show a note instead).
- **A restricted device refuses any `api` block.** Vector's local API has no authentication, so any user on the host could read live events from it. A restricted device used to accept an `api` block on a loopback address; it now refuses every `api` block, enabled or not, with `LOCAL_API_DENIED`, and `vectory allow` can't permit it: a pipeline that sets `api` needs a full-mode device, and the dashboard says so whatever the address. A restricted device that already runs a version with an `api` block keeps running it until it is applied again, but the agent won't start that configuration again after Vector or the agent restarts.
- **The install command keeps its files private.** The Linux and macOS command from **Add device** and **Upgrade agent** used to write `vectory-ca.pem` and `vectory-install.sh` into the current directory, where a local user who could write there could swap the installer between the checksum and the `sudo sh`, and its `curl -L` would follow a redirect to plain http. It now works in a directory only you can enter (`mktemp -d`), runs as one subshell that stops at the first failing step and removes the directory when it ends, and keeps every request on https (`--proto '=https' --proto-redir '=https'`, quoted because zsh reads an unquoted `=https` as a command).
- **The agent checks a version on request.** A signed manifest that lists the feature `validation` can carry one request to check a candidate on the host without applying it. The agent downloads it, verifies its size and digest, fills in the device's secrets as an apply does (naming every unbound one), applies restricted mode and lets the pinned Vector validate it and, when asked, run its tests. It works in a private folder in the state directory (`validation-staging`, mode `0700`, never the managed directory) and deletes its copy on every path and at the next start. It never writes the managed file, the journal, the last known good, a generation or the desired state, never starts, reloads or signals Vector, and removes a data directory it had to create. An apply under way goes first; a paused or drifted agent still checks. The result, at most 20 diagnostics and 100 tests, never Vector's output, a secret value or a secret's file, rides each heartbeat until the manifest stops carrying the request, a second after it is made. With it the agent announces `agent_features` and `readiness` (`data_dir_writable`, `allowed_listener_count`), only to servers that list `validation`; a heartbeat such a server refuses as invalid drops the result and is sent again without it, so a check can never take a device offline.
- **`vectory status` says what runs.** **Pipeline** names the pipeline and version number from the signed manifest (`desired.configuration_name` and `desired.version_number`, shown only when the server sends both), **Running** names the version that runs after a rollback, **Check-in** says when the next check-in is due (`overdue by 35 s` when past) and **Wake-ups** whether the agent holds a request open between check-ins. `--json` adds `running_pipeline`, `check_in` and `wake_ups`; every earlier key is unchanged and an older server's manifests print what they always did. The two display fields stay out of a generation's identity, so renaming a pipeline never makes a device refuse the same generation.
- **A device refuses a component ID that is a path.** Vector uses a component's ID as a directory name under its `data_dir`, so an ID such as `/tmp/x` made it create disk buffers and checkpoints anywhere the service account can write. Devices in both modes now refuse an ID with a `/`, a `\` or a control character, or one that starts with a drive letter and a colon (`C:x`), before Vector sees it, with `INVALID_COMPONENT_ID` naming the component. The rule covers the name of a memory enrichment table that takes inputs and its `source_key` too, and nothing else about an ID changes: Vector's other names (spaces, colons elsewhere, quotes, non-ASCII) still work.
- **Field help stays with the keyboard.** Help opened from the keyboard stays open while its button has focus, even when the pointer rests where the help appears and then moves away. Focusing the button right after clicking **Close** opens the help again. Earlier builds could ignore that focus in a busy browser, and closed keyboard-opened help when the pointer moved.
- **Typing on the sign-in page stays where you put it.** After **Back to sign in**, a failed sign-in or a refused form, focus moves to its field as the page changes, not a frame later. Earlier builds could move focus on a slow device while you typed, so the rest of a password went into **Email address**.

The preview and the refused save now name the device, both assignments and the priority, and say what to do; **Save changes** stays off while the preview shows the collision, and "changes nothing" is never said beside one. The `409 CONFLICT` adds `details` (the first ten collisions: device, both assignments, priority) and `details_total` to its error object, and the preview's blocker carries the same two fields. Both are additive and carry names and numbers only.

- **A Viewer reads what is true about a pipeline's check.** A Viewer, or anyone on an archived pipeline, was told a published, checked pipeline was "Not checked" and to "Run a check" they can't run. When the draft equals the latest published version, the Problems panel now says "Version 2 was checked by Vector 0.58 when it was published."; otherwise "Not checked since the last edit."

- **An offline device that verified its version stays verified on the Overview.** When the only verified device went offline, the first-run checklist reopened at **Deploy and verify** and **On desired version** read "0 / 1 · 1 not yet verified", while Devices said "Offline · v2 · Running at last report". The checklist now counts a version some device verified, online or not, and keeps a step done once this browser has seen it done; the tile reads "1 offline, last verified v2". `GET /overview` adds `devices_offline_on_desired` and `offline_on_desired_version`, both additive.
- **Sign-in says what is true now.** An email without an "@" no longer keeps the earlier "That email and password don't match" beside its own message, and the two-factor step shows the first letter of your address ("A" for ada@example.com), as the rest of the app does.

- **A channel name another channel has** is refused at the **Name** field, which is marked invalid and focused: "Another channel has this name. Choose another."
- **The audit log says "Two-factor reset"**, not "User mfa reset". Stored events are unchanged.
- **A revoked device's page** says its access is revoked and nothing can be deployed to it, instead of "The agent checks in and waits".

- **A refused recovery token no longer blocks the next one.** After `vectory recover-enrollment` was refused (an expired, revoked or mistyped token) or never left the host, the next token was turned away with "pending recovery must retry its original token". Now a new token starts a new request. A reply lost after the request was sent still requires the original token, and the message says so.

It now reports the finding `VECTOR_BINARY_UNAVAILABLE`: Vector never ran, and the issue, the device page and `vectory status` name the binary and say to restore it or approve the new one with `vectory re-adopt`.
- **`vectory allow` notes its change before Vector has ever run.** On a host whose first version was refused there is no Vector log yet, and the note in `vectory logs` was dropped. `allow` and `install --capability-policy` now create the private log, owned like the state directory, and write the note.

Each now ends with `--state-dir` and the directory, quoted for the shell.
- **Bad input exits `2` and says what to pass.** `vectory version extra`, a relative or empty `--state-dir`, `logs --lines abc`, `allow --network logs.example.net`, `re-adopt` without a whole `--expected-sha256`, `configure-metrics --metrics-url https://...` and `install --graceful-shutdown-seconds 3` now end with the usage exit code and a sentence that names the value and gives an example, as an unknown flag does. `vectory --json status` says to put the command first.
- **Plainer answers from the host commands.** `uninstall` with nothing to remove, and a second `uninstall --purge`, say `Nothing to remove` and exit `0`; `unenroll` says when the host had no credentials; a second `vectory run` says an agent already runs on the state directory; `configure-secrets` says `Saved 1 secret-file binding.` or `Removed all secret-file bindings.` and names a relative path or a bad secret name; `re-adopt` names the file and both digests; `install` calls Vector `0.58.1-rc.1` a pre-release. `allow --json` leaves out an empty list instead of printing `null`, and `logs --json` prints its error on one line.
- **The API says what it refused.** A change without a valid `X-CSRF-Token` answers `403 FORBIDDEN` with "The X-CSRF-Token header is missing or wrong" (a role refusal still reads "Permission denied"), and a `400` for an unknown or repeated query parameter names it (`Invalid query parameters: stauts isn't a parameter of this request`), never its value.
- **The API reference doesn't fill in filters.** **Send** on `GET /api/v1/devices/inventory` used to send `status=applied&view=failing` and return an empty list on a fleet that had devices. Optional filters with a fixed set of values now carry an example that is switched off.
- **`vectory-admin` names what it refuses.** `reset-password` says two-factor authentication stays on only for an account that has it. `recover-generations` names the device and the counter a report still lacks, and says to read it with `vectory status --json` on the device; it names the device when one appears twice or is unknown or revoked.
- **Quick deployments keep their start and result in the audit log, and each target's timeline shows only its own.** A device wrote at most four apply-state events a minute, so three versions deployed within a minute left no event for the third one's start or result. The first event of each of `desired`, `verified_applied` and `failed` for a generation is now always written (a device that repeats a generation still adds at most four events a minute of each kind, and three more every ten minutes). A target's timeline on the rollout page started at the second of its release, so it could show the previous deployment's last event. It now starts after the target's own release and ends before the next deployment's, by the order of the audit log.
- **A server restart no longer delays offline alerts by a whole threshold.** After a start, silence was counted from the end of the five-minute recovery window, so a channel set to 15 minutes announced a device that had been silent for 14 of them twenty minutes after the restart. An alert now goes out at the later of the device's own minutes, counted from its last check-in, and the end of the window: a device already past its minutes is announced when the window ends, and a device that checks in during the window is never announced. The contract and the notifications guide say so.
- **Every unusable validator answer leaves a log line.** A sample run or a pipeline test whose answer was in the right protocol but in the wrong form said "unavailable" with nothing in the server log, so only a failure to connect or a wrong protocol explained itself. Each of the three paths (`validate`, `tests` and `transform-test`) now logs one warning with its `path` and a fixed `reason`, never text the validator sent.
- **Issue events are named in the audit log.** Acknowledging or reopening an issue showed no name, because the name was read from a title that issue records never store. It is now built from the issue's code, as the issue list builds it, so the row reads "Vector rejected the configuration on edge-nyc-02" for every role, and the log can be searched by it.

### Documentation

- A new page, [Agent updates](docs/user/agent-updates.md), covers turning updates on, who holds the release key, what a host agrees to, preparing and signing a release, rolling out, rollbacks, keys and what stays manual when one is stolen. - The troubleshooting row for a refused enrollment is keyed on the sentence the agent prints, `The server refused this enrollment (HTTP 401).`, not on the server's `ENROLLMENT_FAILED`, and `vectory logs` says how an agent note differs from Vector's own lines.
- The Help center was reorganized around tasks: a quickstart, installing the server, connecting a device and deploying a first pipeline come first, followed by a security model and references for the agent CLI, server configuration, `vectory-admin` and ports.

- The Help center uses the dashboard's own labels (**Review scheduled devices**, **Review pause policy…**, **Recent Vector errors**), says that **Rollout rolled back** and **Canary paused** are off in a new channel and that **Reopen issue** needs a reason, and lists under known limits that a deployment needs at least one device when you create it.
