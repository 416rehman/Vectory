# Vectory v1 contract

Status: implementation contract, 2026-09-26. JSON uses snake_case. UUIDs are server-generated strings; timestamps RFC3339 UTC; counters nonnegative integers. API errors: `{ "error": { "code": "CONFLICT", "message": "safe human message" } }`. Successful responses are direct objects/arrays, no envelope. Codes: UNAUTHENTICATED, FORBIDDEN, WRONG_PASSWORD, INVALID_MFA_CODE, MFA_CHALLENGE_EXPIRED, MFA_TOO_MANY_ATTEMPTS, SIGNIN_THROTTLED, INVALID_INPUT, EMAIL_INVALID, NAME_INVALID, PASSWORD_TOO_WEAK, PASSWORD_UNCHANGED, EMAIL_TAKEN, REQUEST_ALREADY_USED, LAST_ADMIN, ACCOUNT_DISABLED, MFA_SETUP_EXPIRED, MFA_ALREADY_ENABLED, MFA_NOT_ENABLED, MFA_CHANGED, OWN_MFA, SETUP_SECRET_INVALID, ALREADY_INITIALIZED, SETUP_UNAVAILABLE, RESET_CODE_INVALID, INVITE_INVALID, SESSION_NOT_FOUND, CURRENT_SESSION, NOT_FOUND, CONFLICT, STALE_REVISION, ACTIVE_CANARY_OVERLAP, ENROLLMENT_FAILED, RATE_LIMITED, CAPACITY_BUSY, REQUEST_TIMEOUT, PAYLOAD_TOO_LARGE, EXPORT_BUSY, EXPORT_CAPACITY, EXPORT_STORAGE, EXPORT_TIMEOUT, EXPORT_TOO_LARGE, VALIDATION_FAILED, TESTS_FAILED, CAPABILITY_DENIED, AGENT_UPDATES_OFF, AGENT_UPDATES_STOPPED, AGENT_UPDATE_ROLLOUTS_ACTIVE, CUSTODY_REQUIRED, CUSTODY_LOCKED, RELEASE_KEY_INVALID, RELEASE_KEY_IN_USE, RELEASE_SIGNATURE_INVALID, RELEASE_NOT_IN_CATALOG, RELEASE_EXISTS, RELEASE_NOT_READY, RELEASE_STORAGE_FULL, UPDATE_ROLLOUT_OVERLAP, UPDATE_ROLLOUT_LIMIT, UPDATE_REVIEW_CHANGED, NOTHING_TO_UPDATE, INTERNAL. `CAPACITY_BUSY` (503 on the agent listener when its 128 request slots are taken, or with `Retry-After` when its parked waits reach `VECTORY_AGENT_WAKE_LIMIT` or the server is stopping; 429 with `Retry-After` when every agent download slot is streaming, or when a group membership preview finds the writer busy) and `REQUEST_TIMEOUT` (408, an agent request past its 15-second deadline) mean retry with jitter. `PAYLOAD_TOO_LARGE` (413) rejects a body over its limit. `EXPORT_*` codes are described under audit exports, and the update codes (`AGENT_UPDATES_OFF` to `NOTHING_TO_UPDATE`, with their statuses) under [Agent updates](#codes). Request bodies limited to 1 MiB, artifacts 1 MiB (an agent build in an update is at most 128 MiB, `MaxAgentBuild`: see [Agent updates](#the-download)). SHA256 is lowercase hexadecimal over exact UTF-8 artifact bytes; layout does not enter the artifact.

## Dashboard API /api/v1

- GET /status -> `{initialized:boolean,version:string,instance_name:string,setup_hint?}` (public, no fleet data). While uninitialized only, `setup_hint:{source:"file"|"environment"|"unknown",variable,container,path}` names where the setup secret comes from (`VECTORY_BOOTSTRAP_SECRET_FILE` and its path, or `VECTORY_BOOTSTRAP_SECRET`); it never contains the value.
- POST /bootstrap `{bootstrap_secret,email,password,name}` -> `{user,csrf_token,expires_at}` with session cookie. One-time locally provisioned secret; surrounding whitespace in the pasted secret is ignored. Errors: 403 `SETUP_SECRET_INVALID`, 409 `ALREADY_INITIALIZED`, 503 `SETUP_UNAVAILABLE`, 400 `PASSWORD_TOO_WEAK`/`EMAIL_INVALID`/`NAME_INVALID`.
- POST /login `{email,password}` -> `{user,csrf_token}` for accounts without MFA, or `{mfa_required:true,challenge_token,expires_at}` after correct credentials for an MFA account. A challenge response has no session cookie, user or CSRF token. POST /login/mfa `{challenge_token,totp_code}` or `{challenge_token,recovery_code}` completes verification and returns the session. POST /logout; GET /session -> `{user,csrf_token}`. Authenticated mutations require X-CSRF-Token; cookie HttpOnly SameSite=Strict Secure in production. User `{id,email,name,role,enabled,revision}` role viewer/editor/operator/admin. Disabled accounts cannot sign in or use existing sessions.
- Public authentication requests have no replay/idempotency key. The dashboard bounds startup and public sign-in/setup/MFA/reset redemption waits to 30 seconds including bodies and prevents concurrent local submissions. An unknown outcome allows explicit read-only `/session` recovery (enabled user with server-equivalent normalized intended email) and, for setup after an absent session, `/status`. Session401 is a current-cookie snapshot, and initialized status only proves some account exists; neither fences or attributes an earlier POST. Cookies can arrive independently of a usable body. Public reset redemption has no completion-status endpoint: an unknown result directs the person to sign in with the intended new password. No automatic secret/code replay or cancellation-as-rollback claim is permitted.
- `POST /logout` returns `{ok:true}` and expires the browser cookie after revoking its authenticated session. The dashboard bounds the send and explicit `/session` recovery reads to30seconds including bodies. A retry keeps the original actor and CSRF only in memory and explicitly sends that frozen CSRF header; a same-actor session with another CSRF is a different sign-in. Probes never call `setCSRF` or restore protected authority. Only an exact structured401 from the owned session read permits a current absent-session view, not attribution of the original logout; leaving that view rechecks current draft consent and known credential changes. A POST401 alone does not prove the browser's current cookie is absent. A delayed expiry cookie may still affect a later browser cookie even though a new server session is not revoked by an old-CSRF request. No wire change or new replay key is introduced.
- GET /overview -> `{devices_total,devices_online,configurations_total,deployments_active,issues_open,devices:DeviceListItem[],recent_activity:Audit[],devices_managed,devices_on_desired,devices_offline_on_desired,offline_on_desired_version,devices_degraded,versions_total,versions,rollouts,attention,fleet_activity,security_events_hidden}` (missing metrics null). `devices_offline_on_desired` is additive: the managed devices that are offline and whose last verified version is the one they are assigned, out of reach rather than unverified; it is never part of `devices_on_desired`, and older servers omit it. `offline_on_desired_version` is the number of the one version those devices last verified when they share one, otherwise null. `devices` holds list rows (see `GET /devices`); the aggregates are computed from the full rows. The added aggregates are read-only projections of stored state: `versions` maps each desired version to `{number,configuration_id,configuration_name}`; `rollouts` lists active/paused deployments then scheduled ones starting within 24 hours, each with `target_count` and persisted `state_counts`; `devices_degraded` (see Data-plane health); `attention` groups non-revoked devices by cause (`failed` by version and state with the most common sanitized failure summary, `check_required`, `stuck` for released versions not applied after 10 minutes, `offline` with the oldest last check-in as `since`, `paused` with requested/local counts, `unmanaged`; `failed` and `degraded` groups add `deployment_id`, the deployment all their devices share or null, and `rollback_available`, true only when the server can review that deployment for rollback now); `fleet_activity` holds up to 12 fleet-changing audit summaries from the latest 300 events, with consecutive per-device release/apply events collapsed (`repeat`, `device_names`, `first_at`) and deployment context (`deployment.{configuration_name,version_number,policy,rollout_kind,priority,target_count}`, plus the lineage `rolled_back_to_configuration_name`, `rolled_back_to_version_number` and `rolled_back_device_count` of a rolled-back deployment and `rollback_of_configuration_name` and `rollback_of_version_number` of a rollback) or the published `version_number`. A `deployment.rollback` row names the rolled-back deployment and lists up to five devices its rollback returned in `device_names`. Sign-in, account and signing-key events never enter it; `security_events_hidden` counts those skipped. `counts`, `attention_devices`, `busiest`, `running` and `slim=1`: see Fleet-scale reads. Refused enrollments (`device.enroll` with outcome `failure`) never enter it either: they change nothing in the fleet, and the audit log and Add device's recent attempts keep them with their reason. While agent updates are on, `attention` also holds a group with `cause:"agent_update"` (see [Agent updates](#device-projection-filters-audit-notifications-and-issues)).
- Own-account `POST /account/password {current_password,new_password}` atomically replaces the password, increments user revision, revokes that account's existing sessions/reset codes and issues `{user,csrf_token}` with a new session cookie. `POST /account/revoke-sessions {current_password}` returns `{ok:true}`, keeps the presented session and removes other current sessions, clearing pending login challenges. Every successful revocation invocation audits separately and can affect sessions created after a prior invocation. Both reauthenticate and recheck session/CSRF/password under the writer transaction; neither has a replay key or completion lookup. The dashboard bounds waits to 30 seconds including bodies, pins the original CSRF header and guards callbacks by actor, credential version and epoch. It accepts password receipts only for an enabled same-account user with nonempty newly rotated CSRF; unrelated account edits mean displayed revision+1 is not a valid identity constraint. Unknown password changes direct explicit sign-in with the intended new password; unknown revocation permits only a new deliberate scope review with fresh password entry. GET /session cannot prove either outcome. Dismissal suppresses late UI updates but cannot undo committed work or cookie delivery. No wire format changes are introduced.
- Overview counts configurations in SQL and reads only the latest 20 audit summaries. Recent activity includes typed actor/target identities, a current `target_name:string|null` and `target_exists:boolean`. Direct resource navigation requires a supported typed identity and `target_exists:true`; absent/deleted targets retain their audit history without a broken resource link. Pipeline version/revision targets resolve to their parent pipeline. Deployment targets (create, release, rollback, …) are named at read time after what they deploy: `<pipeline> v<n>`, `Agent settings: <saved name>` or `Agent settings`, so existing events gain names and search finds rollouts by pipeline. Names are display metadata, not identity or authorization. The stored audit event and target ID remain unchanged.
- GET /devices -> DeviceListItem[] (each managed row adds read-only `desired_version:{number,configuration_id,configuration_name}` naming its desired version); GET /devices/{id} -> Device. A list row is the Device without what only the device page reads, most of a reporting device's row: no `host_runtime`, no `vector_log_summary`, no `telemetry.components`, and `data_plane.issues` holds only the first open issue (`data_plane.issue_count` counts them all). The Overview's `devices` are the same rows; POST /devices/{id}/revoke; GET /groups -> Group[]; GET /groups/{id} -> Group; POST /groups `{name,description,device_ids}` -> Group. Group `{id,name,description,device_ids,revision}`. New groups start at revision 1; reads project stored legacy groups without a revision as 0. Revisions are nonnegative safe integers. Paged devices (`GET /devices/inventory`), group members and member-free group rows: see Fleet-scale reads.
- PUT /groups/{id} requires `{name,description,device_ids,revision}`. The server rechecks authorization and the exact reviewed revision inside its writer transaction before validating and resolving membership. Missing/invalid revisions return `400 INVALID_INPUT`; stale revisions return `409 STALE_REVISION` without changing group state, assignments or success audit. Successful saves advance the revision atomically with membership resolution and audit. Other assignment conflicts remain `409 CONFLICT` with the same message, and the error object adds `details`: at most the first ten collisions, each `{device_id,device_name,resource,priority,assignments}` naming the device and the two assignments (the deploy review's assignment description plus `targets`, `group` or `devices`, and `groups`, up to three `{id,name}` of the groups that hold the device), and `details_total`, how many there are in all. Both fields are additive: names and numbers only, never selectors, member lists or payloads, and older clients ignore them. Device revocation and identity recovery advance revisions only for groups whose membership they actually remove. Clients must not silently attach a newer revision to stale membership or retry an uncertain mutation; retain local edits and explicitly review current membership before a separate save. Revision-less responses from older servers remain readable in the dashboard but disable existing-group editing.
- A group edit that adds effective members to a persistent assignment must pass the same cross-assignment active-canary admission check as direct deployment creation. `409 ACTIVE_CANARY_OVERLAP` leaves the group revision, membership, target rows and desired generations unchanged. Checks apply to each newly selected device for the same assignment resource and exclude the assignment's own canary; redundant memberships, exclusions and metadata-only edits do not count as additions. No canary is automatically paused or cancelled. The dashboard retains local edits and offers read-only active-deployment browsing in another tab.
- GET /configurations -> Configuration[]; POST /configurations `{name,description,graph,config,variables?}` -> Configuration; GET /configurations/{id} -> Configuration; PUT /configurations/{id}/draft `{revision,graph,config,variables?,message}` -> Configuration, 409 stale revision; GET /configurations/{id}/revisions -> Revision[]; POST /configurations/{id}/validate `{config}` -> `{valid,errors:string[],warnings:string[]}`; POST /configurations/{id}/publish `{revision,message}` -> Version; GET /configurations/{id}/versions -> Version[]; GET /versions/{id} -> Version.
- Pipeline validation is available to Editors, Operators and Administrators with a valid session and CSRF token. Validation reads the named pipeline and checks the caller-supplied candidate without saving it; Operators gain no draft-write permission. Publishing remains an Operator or Administrator action.
- Configuration `{id,name,description,revision,graph,config,variables,updated_at,created_at}`; graph `{nodes:[],edges:[]}` React Flow format. Config is semantic Vector JSON object preserving unknown fields. Revision `{id,configuration_id,revision,graph,config,variables,message,created_at,author}`. Version `{id,configuration_id,number,graph,config,variables,artifact,sha256,size,created_at,message,validation}`.

Saved draft variables are `[{name,path,type}]`, where each unique name is an ASCII letter followed by at most 63 ASCII letters, digits, or underscores; `type` is `string`, `integer`, or `boolean`; and `path` is a canonical RFC6901 JSON Pointer to an existing scalar leaf in `config` with the same type. At most 64 declarations are allowed. They are revisioned draft metadata, not Vector `${ENV}` interpolation. A draft save omitting `variables` preserves the saved declarations; explicit `[]` removes them. Duplicate and restore copy declarations, and publishing snapshots them with the immutable version. The server rejects structural and known credential fields, and checks each rendered configuration against target capabilities. A scalar value such as an address can still change runtime behavior on a full-mode device, so the deployment review must show each target-specific result. Published config and artifact remain valid base Vector configuration without unbound placeholders. Variable values are nonsecret only; keep credentials in approved device-local secret references.

Pipeline library and history commands (mutations require editor or administrator, a valid session and CSRF; actor and draft revision are rechecked inside the serialized transaction. History reads allow any authenticated role):

- `GET /configurations/library?search=&state=active|archived|all&sort=updated|name&page=1&page_size=12` returns `{items,total,page,page_size}` to any authenticated role. Each item is `{id,name,description,revision,created_at,updated_at,archived,archived_at,component_counts:{sources,transforms,sinks},latest_version:null|{id,number,created_at,author,draft_changed}, assigned_devices, running_versions:[{id,number,devices}]}`. No config, graph, artifact or validation body is returned. Counts describe object entries in the saved draft, not component validity; unfinished non-object sections count as zero. The latest version is chosen numerically within that pipeline. `author` is the publisher's display name or null. `draft_changed` is true when the saved draft's `config` or `variables` differ from the latest version's (layout-only saves do not count; a version or draft with no variables has none, the same as an empty list). `assigned_devices` counts non-revoked devices whose desired version is any version of the pipeline; it is an assignment count, not evidence that Vector is running or verified there. `running_versions` groups non-revoked devices by the version of this pipeline each last verified (the same `running_version` the device list shows), highest number first, so a rolled-back release reads as "Running v2 on 3" while `latest_version` is v3. `author`, `draft_changed` and `assigned_devices` are additive; clients treat them as optional.
- Library defaults are empty search, active state, updated sort, page 1 and size 12. Page size is 1..50; overflowing pages, invalid options, repeated parameters and unknown query keys are rejected. Search is a trimmed literal substring of name or description, at most 200 Unicode scalar characters; SQLite folds ASCII case only, and non-ASCII characters match literally. `%`, `_` and brackets are ordinary characters. Sorting is updated timestamp descending, ASCII-case-insensitive name ascending, then ID; name sort uses name then ID. Count and page share a SQLite read snapshot; pages beyond the end return an empty array. Metadata indexes and a materialized bounded page keep component/version projection off unselected drafts. The legacy full `/configurations` list remains compatible for clients that require it.
- Configuration adds `archived:boolean` (legacy default `false`) and `archived_at:string|null` (default `null`). All list/detail responses retain archived pipelines; clients may filter them. Archive is organization/editing state only: it never unassigns a device, changes a generation, cancels a schedule, or stops Vector. Existing immutable versions stay readable and deployable, including for rollback. There is no destructive pipeline-delete route.
- `POST /configurations/{id}/duplicate {revision,name,description?,request_id?}` initially returns a new Configuration with a new ID, revision 1 and unarchived state. It copies only the reviewed saved configuration and graph; omitted description copies the source description. It inherits no versions, deployment bindings, or assignments. Duplicating an archived source is permitted. A keyed replay returns the current original copy, as described below.
- `POST /configurations/{id}/archive {revision}` and `/unarchive {revision}` return the Configuration with an incremented revision and append an immutable draft snapshot. Repeating an already-applied state returns 409. Archived draft save, snapshot restore and publication return 409, including a publication that finishes validation after archival.
- `POST /configurations/{id}/restore {revision,revision_id?,version_id?,message?}` requires exactly one immutable source ID from the same pipeline. It copies source configuration and graph into a new draft revision while preserving the current name and description. It applies the ordinary draft bounds and plaintext-secret checks, preserves unknown fields, and never modifies the source snapshot, published version, artifact or assignments. A stale draft revision returns `STALE_REVISION` (409); a source from another pipeline is invalid input.
- `GET /configurations/{id}/history?kind=revisions|versions&page=1&page_size=12` returns `{items,total,page,page_size}`. Kind defaults to `revisions`, pages are positive and page size is 1..50. Items preserve original metadata while excluding `config`, `graph`, `artifact` and `validation`. Results are SQL-filtered to the requested pipeline and sorted by numeric revision/version descending; count and page share one read snapshot. Pages beyond the end return an empty items array. The existing full `/revisions` and `/versions` endpoints remain compatible and use the same ordering.
- `GET /configurations/{id}/revisions/{revision_id}` returns a full Revision; a mismatched parent is 404. Published snapshots use existing `GET /versions/{id}`. New revisions include `author_id`, current name/description/archived metadata, and optional `source:{kind:"draft"|"revision"|"version",id,revision?}` provenance for duplication/restoration. New published versions include `author`, `author_id` and `source_revision`; these fields are optional on legacy immutable records.
- GET /deployments -> Deployment[]; POST /deployments/preview `{version_id?,policy?,selector,priority,target_mode,rollout,scheduled_at?}` -> `{devices:Device[],conflicts:[],warnings:string[],outcomes:PreviewOutcome[]}`; POST /deployments same -> Deployment; POST /deployments/{id}/cancel; POST /deployments/{id}/pause; POST /deployments/{id}/resume; POST /deployments/{id}/rollback -> Deployment. GET /deployments/{id} -> Deployment.
- PreviewOutcome `{device_id,resource:"configuration"|"policy",outcome:"requested"|"higher_priority"|"conflict",assignment?:{id,priority,reason}}` compares the requested resource against the resolver's current candidates. A higher-priority outcome includes its winning assignment, even when rollout admission has not released that candidate to the device. Equal-priority different payloads conflict; equal-priority identical payloads are eligible. Eligibility does not claim release, acknowledgement or activation. Scheduled previews describe current candidates; assignments are resolved again at activation.
- GET /deployments/history uses bounded SQL metadata projections with optional `search`, `status`, `scheduled`, `page`, `page_size`; returns `{items,total,page,page_size}`. Omitted `scheduled` means all history; true means a scheduled time exists, including past/cancelled/missed schedules; false means unscheduled. Items contain explicit pipeline/version labels, policy/rollout fields, `target_count`, `verified_count` and `state_counts`; no selector, target arrays, config, graph or artifact bodies. Only persisted `verified_applied` counts as verified. Ordering is created time descending then UUID ascending. GET /deployments/{id}/summary returns one such item. GET /deployments/{id}/targets pages persisted target rows with original UUID-bound `device_name` and optional `search`/exact `state`; sorts names case-insensitively then UUID. Search is literal, ASCII case-insensitive, max 200 Unicode scalar characters; it excludes config and error bodies. Page size defaults to 12, max 50; pages must be positive JavaScript-safe integers. Unknown/duplicate/malformed query parameters are rejected. Count and rows share a read transaction. Existing full list/detail and reviewed mutation endpoints remain compatible.
- Selector `{device_ids:string[],group_ids:string[],exclude_ids:string[]}`; union minus exclusions. priority integer. target_mode `snapshot` or `persistent` (scheduled always snapshot). rollout `{kind:"all"|"canary",canary_size:1,batch_size:10,observation_seconds:60,failure_threshold:0}`. Deployment `{id,name?,version_id?,policy?,selector,priority,target_mode,status,scheduled_at?,created_at,targets:DeploymentTarget[],rollout}`. Target `{device_id,state,generation,error?}`. status scheduled/active/paused/completed/cancelled/failed/missed. Equal priority different payload conflicts transactionally. Only released targets receive generations; snapshot immutable.
- **Names are one line.** A name an editor, an operator or an administrator writes (a pipeline, a deployment, a group, saved agent settings, an enrollment token, a notification channel, and a person's name) appears in notifications, the audit log, exports and headings, so it holds no control character (C0, DEL or C1), no line or paragraph separator (U+2028, U+2029) and no text-direction embedding, override or isolate (U+202A to U+202E, U+2066 to U+2069), at its ends too (a channel's name and a person's name are trimmed of surrounding white space first, so a line break at either end is dropped, not refused). A request with one is refused with `400 INVALID_INPUT` (`400 NAME_INVALID` for a person's name) and the sentence `Enter <the field> without line breaks, control characters or text-direction overrides`, and the record is unchanged. Nothing else is narrowed: a name can be in any script and hold spaces and punctuation. A name stored before this rule is read back as stored (restoring a revision keeps the current name, and a replay of a keyed request returns the original record), and every message that names it, in a webhook's `text`, `blocks` and `event` and in an email's subject and body, shows it as one line: each such character becomes a space, runs of white space collapse and the ends are trimmed (a name with nothing printable left reads as `A pipeline`, `A device` or `A deployment`). The manifest's `configuration_name` is left out for such a name.
- New deployment names are optional null/string values limited to 120 Unicode characters. Metadata projections bound legacy deployment names to the first 120 characters and map legacy non-text name/version ID extensions to null; original full detail records remain unchanged. Metadata search uses that same projected name.
- Persistent targets that leave active, paused or completed assignments are marked `removed`, including the exact old UUID retired by revocation or identity recovery. Original UUIDs, target counts, release/verification timestamps, generations and prior-version references remain historical evidence; retained positive generation on a removed row never authorizes resolution, rollback selection, retry or later heartbeat updates. Current `verified_count` includes only rows whose state is `verified_applied`; removed rows are separately represented by `state_counts.removed`. Rejoining membership resets admission and verification before the ordinary rollout gates apply. Revocation and identity recovery do not retarget a replacement identity or synchronously advance other deployments. Fixed snapshots and stopped assignment history remain unchanged. Scheduler ticks also repair already-ineligible current persistent rows before ordinary rollout progression. Rollout completion describes the remaining eligible membership, not verification of every historical target. No new response fields are introduced.
- GET /policies -> PolicyRecord[]; POST /policies `{name,policy}` -> PolicyRecord; PolicyRecord `{id,name,policy,created_at}`. AgentPolicy `{heartbeat_seconds:60,sync_paused:false,telemetry_enabled:true}` with local hard bounds heartbeat 10..3600.
- GET /tokens -> Token[]; POST /tokens `{name,expires_hours,max_uses?,name_prefix?,device_name?,allowed_names?,labels?,request_id?}` -> `{token:string,record:Token}` for legacy unkeyed calls. Keyed initial creation adds `request_id` and `request_correlation:true`. Token `{id,name,expires_at,uses,max_uses:number|null,name_prefix:string|null,device_name?,revoked,created_at,allowed_names?:string[],labels?:{[key:string]:string}}`; the scope fields appear only on tokens created with them, so other tokens keep their original shape. `device_name` binds the token to one device name (normalized to lowercase, and starting with `name_prefix` when both are set), so enrolling any other name is refused as `DEVICE_NAME_MISMATCH`; it is echoed only when it applies, since older servers ignore it. It and `allowed_names` are independent limits: a token that has both enrolls only a name that satisfies both (Add device sends only one of them: the typed name, or the list when there is one). `allowed_names` preapproves 1 to 500 device names, normalized like enrollment names (trimmed, ASCII-lowercased, 1 to 100 of `a-z 0-9 . - _`, starting with a letter or digit), distinct, and each starting with `name_prefix` when both are set; a token with a list enrolls only a device whose normalized name is on it, and each name at most once (`NAME_NOT_PREAPPROVED`, `NAME_ALREADY_ENROLLED`); the token list shows the names used as `enrolled_names`. `labels` gives every device the token enrolls at most 8 labels: keys trimmed and lowercased, 1 to 63 of `a-z 0-9 . - _` starting with a letter or digit, distinct; values trimmed, 1 to 128 characters without control characters, case kept. Labels are descriptive: they never create group membership, an assignment, a policy or secret access, and a heartbeat cannot change them. `max_uses` and `name_prefix` still apply. Invalid scope fields are refused with 400 before a token is created; POST /tokens/{id}/revoke returns `{ok:true}` and prevents future enrollment without revoking existing devices. GET /tokens adds usage to each stored record: `created_by:{id,name}|null` (the creating account; for recovery tokens the authorizing administrator), `last_used_at`, `device_count` and `devices:[{id,name,revoked,enrolled_at}]` (most recent 20). Creation receipts and request status records are unchanged.
- Enrollment-token request identities are UUIDs scoped to the authenticated account. Existing operator/admin authorization and mutation CSRF checks remain in force and are rechecked inside the serialized transaction. The ledger retains the request digest, token identity and state; it never stores the plaintext token. The same key and payload return a secret-free status, never mint another token; a changed payload conflicts once creation has bound a payload. A cancellation recorded before creation closes the key regardless of later payload contents. Legacy unkeyed clients remain supported.
- GET /tokens/requests/{request_id} returns `{request_id,request_correlation:true,found:false}` or `{request_id,request_correlation:true,found:true,state:"created"|"cancelled",record:Token|null}`. A created mapping requires its original token; an unavailable mapped row returns a conflict rather than recreating it. Reads never recover the secret. A negative lookup is not proof an in-flight creation failed.
- POST /tokens/requests/{request_id}/cancel `{}` atomically records a permanent cancellation and revokes only the token mapped to this account/request, if one exists. It can cancel a key before creation arrives; a later create with that key cannot mint a token. Repetition returns the cancelled status without another success audit. A cancelled status has either a revoked record or null when no token remains. Existing device credentials stay unchanged. Cancellation has no client-side expiry or automatic cleanup.
- The dashboard verifies correlation support before first creation, retains an account-scoped nonsecret reminder before sending and bounds each request to 30 seconds. Unknown creation or cancellation keeps that exact reminder for a read-only check or deliberate cancellation; no automatic create retry occurs. When the first secret arrives, the reminder records the created token's ID (still no secret): a confirmed creation never blocks another one. The page resolves confirmed reminders against the current token list: a token that is used up (no uses left), revoked or expired can enroll nothing more, so its reminder is removed (once saying which devices it enrolled); an unused, live token stays listed with the unused install commands and their Revoke action; a token list that fails to load removes nothing. Otherwise only an acknowledged first secret, a confirmed cancellation, or a created request whose token the server reports used up, revoked or expired permits reminder cleanup. A current token-list read verifies standalone revocation by exact token ID. Session changes clear displayed secrets and invalidate pending UI callbacks.
- GET /releases -> verified agent builds `{name,os,arch,version,sha256,size,url,signed:boolean,source:"bundled"|"mirror"}`. ### Pipeline creation and duplication recovery

`POST /configurations` and `POST /configurations/{id}/duplicate` accept an optional `request_id` UUID in one shared actor-scoped namespace. A keyed response is the original result's current `Configuration` plus the normalized `request_id`. The durable binding includes the operation, exact source UUID for duplication, and canonical supplied JSON excluding the key. Object order is insignificant; arrays, omitted fields, nulls and additional supplied fields remain significant. Reusing a key for another operation, source or payload returns `409 IDEMPOTENCY_CONFLICT`. A keyed duplicate requires the reviewed positive JavaScript-safe source revision.

Replay occurs after current authorization and CSRF checks but before reading or checking the source. It returns the original copy even if that source changed, was archived or is now missing. Later edits or archival of the result stay intact. Configuration creation, initial immutable draft revision, audit and request mapping commit atomically. A missing result returns `409 CONFLICT`; its key cannot silently create a replacement. Keys do not expire automatically. Legacy unkeyed callers retain their prior behavior.

`GET /configurations/requests/{request_id}` requires current Editor/Admin access and returns only the caller's mapping: `{request_id,found:false}` or `{request_id,found:true,operation,source_configuration_id,source_revision,configuration}`. The nested receipt repeats the matching request key. Create origins have null source fields; duplicate origins have the immutable source UUID and reviewed revision. A duplicate result UUID differs from its source. Negative lookup is a snapshot, not proof an in-flight mutation failed.

`GET /configurations/requests?page=1&page_size=12` lists bounded current-account committed metadata, newest first with a deterministic request-ID tie break. Each row contains `request_id`, `operation`, `source_configuration_id`, `source_revision`, `configuration_id`, nullable current `configuration_name` (at most 240 Unicode scalars), and `created_at`. Pages are positive safe integers, page size is at most 50, and unknown or duplicate query parameters are rejected. Count and page share a read snapshot. No configuration, graph, description, digest or original payload appears in discovery; it cannot reconstruct a retry.

The dashboard saves immutable per-account, per-request intent before network work, requires a compatible exact lookup before creation, and never falls back to unkeyed POST. Unknown responses preserve the original intent across tabs/reload. Explicit retry uses the same body and key; it never adopts a newer source revision. Result identity is checked independently of mutable content. Unresolved local requests block new create/duplicate submissions while existing draft editing and archive actions remain available. Recovery navigation keeps the current editor's unsaved-change guard and never replaces its draft with a recovered copy.

### Group creation recovery

`POST /groups` accepts an optional `request_id` UUID. A keyed response adds that exact normalized request ID to the current `Group` record. The durable actor-scoped key binds the canonical supplied JSON excluding the key itself; object order is insignificant, while arrays, omitted fields, nulls and additional supplied fields remain significant. Same-key/same-payload replay returns the same group's current saved state before revalidating original membership, and never reapplies membership or repeats reconciliation/audit. Different payloads return `409 IDEMPOTENCY_CONFLICT`. Group creation, request identity, membership reconciliation and audit commit together under live authorization/CSRF. A missing original group cannot be recreated with its old key. Keys have no automatic expiry. Unkeyed legacy requests retain their prior behavior.

`GET /groups/requests/{request_id}` requires current Operator/Admin access and returns only the caller's result: `{request_id,found:false}` or `{request_id,found:true,group}`. The nested group also includes the matching `request_id`. A negative lookup is a snapshot, not proof that an in-flight mutation failed. `GET /groups/requests?page=1&page_size=12` lists only that account's committed request metadata, newest first with request-ID tie breaking; maximum page size is 50. Items are `{request_id,group_id,group_name,created_at}` with current name nullable; no original payload or device list is exposed. Request discovery survives browser storage loss and cannot reconstruct a retry payload.

The dashboard persists an immutable actor-scoped request in local storage before sending, then requires a compatible exact-ID lookup before the first POST. It does not fall back to unkeyed creation on an old server. Unknown transport outcomes remain recoverable after close/reload. Reads never retry automatically; an explicit retry sends the original body and key. New creation waits until pending local requests are reviewed. Corrupt/unreadable storage is surfaced and cannot silently discard an uncertain request. Existing group updates continue using revision CAS, independently of create recovery. Recovery shows the exact current group, which may have changed since creation; names and memberships never establish request identity.

### Deployment creation recovery

`POST /deployments/preview` and `POST /deployments` accept optional `variable_bindings:{defaults:{[name]:value},devices:{[device_uuid]:{[name]:value}}}` for a published version's declarations. A value is a JSON string (at most 4096 UTF-8 bytes), safe integer, or boolean matching its declared scalar type. The server rejects unknown names or device UUIDs, missing selected-device bindings, type mismatches, unsafe values, and rendered artifacts above 1 MiB before creating any assignment. A persistent selector requires a complete typed default for each declaration so later group members resolve without inheriting another device's override. Preview returns `artifact_previews:[{device_id,sha256,size}]` for resolved targets, without artifact bytes or binding values; this is a render review, not evidence that an agent has applied the result. Target UUIDs and typed values are part of the durable idempotency payload. The signed agent manifest and authorized artifact fetch use the released device-specific rendered SHA-256/size, while `version_id` remains the immutable template identity. Device reads may include `desired_sha256:string|null` for that target-specific released digest, separate from `actual_sha256` of the managed file. A binding-only redeployment must issue a new desired generation if the rendered bytes differ.

`POST /deployments/preview` adds `create_idempotency:true` and `blockers:PreviewBlocker[]`. An active-canary blocker contains `{deployment_id,device_ids,resource:"configuration"|"policy",code:"ACTIVE_CANARY_OVERLAP",reason}` for a current canary intersecting the reviewed targets. Configuration compatibility blockers omit `deployment_id` and use `resource:"configuration"` with `code:"FULL_VECTOR_MODE_REQUIRED"` or `code:"VECTOR_VERSION_INCOMPATIBLE"`. A single device may appear under both compatibility codes. IDs within each blocker are unique and sorted so review tokens are stable. Final creation rechecks mode and the pinned Vector series inside its transaction (any 0.58.x patch release reported by the device, `v` prefix and trailing build details allowed); scheduled activation, later release waves and persistent group expansion recheck before admitting affected devices. Older servers may omit these additive fields; absence does not establish safe retry support.

`POST /deployments/{id}/resume` repeats the same active-canary overlap admission gate before changing a paused rollout's status or releasing any device. It checks the source's effective nonrevoked target identities (current selection for persistent assignments; retained eligible target rows for snapshots), excludes the source assignment itself, and separates configuration from agent-policy assignments. Different priorities do not bypass this admission gate. An overlap returns HTTP 409 `ACTIVE_CANARY_OVERLAP` and leaves status, targets, desired generations and audit unchanged. The dashboard retains the resume confirmation and offers read-only active-deployment browsing; no competing deployment is paused or cancelled automatically. A successful resume returns the exact source Deployment, whose status may already have advanced beyond active. Lost, timed-out, malformed or server-failure control responses require an explicit bounded status read for that source before the dashboard enables another mutation; a failed or wrong-source read does not clear uncertainty.

Current canary readiness is separate from recorded target progress. Advancement requires fresh, nonrevoked evidence for the exact effective assignment and resource, with matching desired, target and reported generations. Configuration proof binds the published version/digest, accepted local-secret materialization when applicable, current verified workload and enabled sync. Policy proof independently binds the desired policy and reported policy generation; an intentional pause policy requires acknowledgement and does not require a running configuration. Historical target success alone cannot satisfy either gate. Pausing/resuming restarts observation; changed or interrupted current evidence requires a full new observation period without rewriting historical verification into a new success.

Only `GET /deployments/{id}/summary` adds optional `canary_gate` for active/paused canaries: `{state:"waiting"|"observing"|"paused",released_count,verified_count,pending_count,reasons:{superseded,stale,paused,unverified,unavailable,measuring,degraded},observation_started_at:date|null,observation_seconds,evaluated_at:date}`. All counts are nonnegative safe integers; `verified_count + sum(reasons) == released_count`. Only observing has a nonnull observation timestamp and requires all released devices to be currently verified. Detail reads evaluate in one snapshot and never advance or reset a rollout. Paged history retains its indexed historical count projection and omits current gate computation. The target page adds optional `gate_reason:null|"superseded"|"stale"|"paused"|"unverified"|"unavailable"|"measuring"|"degraded"` for that same context using the same evidence predicate. Null also describes unreleased/no-longer-targeted rows; it is not a success flag. No fingerprints, configuration payloads or secrets are exposed. Older servers omit these fields; the dashboard labels gate details unavailable rather than inferring readiness from historical counts. Failed summary reads suppress cached gate readiness; displayed evaluation timestamps are observations, not promised release deadlines.

`POST /deployments` accepts an optional UUID `request_id`. For a given authenticated actor and request identity, creation and its mapping commit atomically. An identical retry returns the current original Deployment before fresh selector, schedule or canary validation. Every call still requires a current enabled Operator/Admin and valid CSRF. Reusing the identity with a different payload returns `IDEMPOTENCY_CONFLICT` (409). The payload digest excludes `request_id`, recursively sorts object keys, and preserves array order and null-versus-omission differences. The mapping survives restart and does not expire while the deployment is retained. Requests without an identity retain legacy behavior and cannot be safely retried after an ambiguous response.

Keyed creation and rollback return a flat `DeploymentReceipt`: the current original Deployment plus response-only `{request_id,operation,source_deployment_id}`. The normalized key, operation (`create` or `rollback`), exact original result UUID, and rollback source UUID come from the durable actor-scoped mapping. Create source is null; a rollback result differs from its source. These receipt fields are never persisted in the deployment body. Later status, schedule, target membership and other current result changes are preserved; they are not an identity check against the initial payload. A missing mapped result returns `409 CONFLICT`, retains its mapping, and is never recreated.

`GET /deployments/requests/{request_id}` requires current Operator/Admin access and returns the caller's own `{request_id,found:false}` or `{request_id,found:true,operation,source_deployment_id,deployment:DeploymentReceipt}`. Outer and nested identity metadata must exactly agree with the frozen local operation; another actor's identity is not visible. This read requires no CSRF; malformed identities and query parameters are rejected. `found:false` is not proof that an in-flight request failed; retry only the original reviewed payload with its original identity.

Preview, full Deployment and bounded DeploymentSummary reads advertise optional `request_correlation:true`. The dashboard requires this capability as well as the applicable create/rollback idempotency support before beginning a new keyed request; it never falls back to an unkeyed send. An older keyed reminder remains unresolved when a server omits correlation metadata and can be checked after upgrade. A legacy unkeyed reminder supports history review only. Legacy server requests without a key retain their behavior and do not receive receipt metadata.

`GET /deployments/requests?operation=all|create|rollback&page=1&page_size=12` requires current Operator/Admin access and returns only this actor's committed request mappings as `{items,total,page,page_size}`. Pages are safe positive integers; page size is 1..50. Unknown, duplicate or malformed parameters are rejected. Ordering is `created_at DESC, request_id DESC`; UUID ties are deterministic, not a claim of exact same-timestamp commit order. Count and page use one authorized read snapshot. `DeploymentHistoryPage` advertises optional `request_history:true` when this discovery route is supported.

Each bounded row is `{request_id,operation,source_deployment_id,deployment_id,created_at,deployment_name,deployment_status,configuration_name,version_number,resource,scheduled_at}`. `operation` is `create` or `rollback`; source ID is null for create and the exact original rollout UUID for rollback. Result ID is always the original committed deployment or rollback replacement. Names/status and unavailable version/schedule metadata are nullable. Deployment names contain at most 120 Unicode characters, pipeline names 240 and statuses 64; positive version numbers are JSON-safe integers. `resource` is configuration or policy. No original request, digest, selectors, targets or configuration payload is returned. These rows support view-only discovery, not reconstructed retry. Unreceived, uncommitted and legacy requests without identities cannot appear; an empty page is never evidence that an in-flight request failed. Mapping retention remains unchanged: keys do not expire while their deployment is retained.

The browser preserves unresolved reviewed requests in individually keyed actor/request local-storage records, not one shared list. Frozen request bytes must persist before a POST; writes that fail or exceed the bounded capacity stop submission. Separate records avoid cross-tab overwrite. Only a confirmed correlated receipt or explicit dismissal removes the exact matching operation; structured rejection, authentication failure and preflight failure retain it because another same-key attempt may have committed or may still commit. Existing tab-session reminders migrate only after a durable copy is verified. Reminders have no time-based expiration; active-request leases are bounded advisory UI state, not a distributed lock or evidence of server completion. Cross-tab replay safety still comes from server actor/request idempotency. Stored requests are not credentials and cannot grant authorization.

### Rollback recovery and reviewed device retries

Full Deployment and bounded DeploymentSummary responses add optional `rollback_idempotency:true`. Supporting servers accept `POST /deployments/{id}/rollback {request_id?:UUID,review_token?:SHA256}` and return the replacement Deployment. Only those two fields are allowed in this body. The shared actor/request namespace binds operation kind, original deployment identity and canonical body, including the review token when supplied; an identity cannot be reused across creation, rollback or another original rollout. Matching replay returns the original replacement before mutable rollback eligibility checks, with current authorization and CSRF rechecked. Existing creation mappings remain compatible. The same `GET /deployments/requests/{request_id}` lookup resolves either operation. Legacy rollback calls without identity remain supported but are not safe for blind replay.

Servers supporting reviewed rollback also advertise optional `rollback_review:true` on both deployment shapes. `GET /deployments/{id}/rollback-preview` requires current Operator/Admin access and returns a complete metadata-only `RollbackPreview` in one read snapshot. It never allocates a request identity, changes assignments or writes an audit. Combined `eligible_devices` and `excluded_devices` contain at most 10,000 distinct historical device UUIDs; larger histories fail explicitly rather than truncating. Exclusions carry `revoked`, `removed`, `not_released` or `missing`; offline live devices remain eligible. Replacement device identities are never inferred from names or substituted automatically. All eligible devices must share one available previously managed version; missing or mixed prior versions block confirmation rather than silently shrinking the scope. Prior pipeline/version display metadata may differ from the source pipeline.

The preview states the original `source_action` (`cancel` below the priority ceiling, otherwise `unassign`), replacement priority, exact included/excluded identities, blockers and `ready`. Ready requires a nonempty eligible set, a common prior version and no blockers. A target records the version it replaced once, when its deployment first takes the device, so a deployment that held the device in between is never the prior version. Devices that would return to different versions block with `MIXED_PRIOR_VERSIONS`, whose reason names each device and its version, and a deployment that released nothing blocks with `NOTHING_RELEASED`. Competing canary gates, equal-priority conflicts and higher-priority configuration assignments block an ineffective or unsafe replacement. Equal-priority same-version competitors also block because ownership would depend on the newly allocated deployment identity. Confirming also stops the rollout in the same transaction: an active, paused or completed source is cancelled (`cancelled_at` records when a live one stopped), or unassigned at the priority ceiling. Each excluded device carries `effect`, `current` and `next`: the server stops the source with the real resolver inside a rolled-back savepoint and compares what every live excluded device is set to run with what the next scheduler pass would give it anyway. `unchanged` (a replacing canary defers to the assignment it replaces until it releases a device; a layered one never reached it) and `retained_pending` (it keeps what it runs until another rollout releases it; `next` names that version) do not block. `fallback` (it would switch to `next`) and `unmanaged` (it would lose its pipeline) block with `UNSAFE_SOURCE_REMOVAL`, whose reason names the device and the version; cancelling first remains an explicit, separate choice. Revoked and missing devices, and every device when current assignments conflict (`ASSIGNMENT_CONFLICT`), carry null effects. Sources already cancelled or failed have already relinquished devices they never released, so those keep what they run. Original target history remains intact.

The lowercase SHA-256 `review_token` binds source identity/status/version/priority, exact included and excluded UUIDs with reasons, prior version, admission generations, current desired version/generation/assignment state for live target rows, including live exclusions, and each live exclusion's projected effect with its before and after desired state and any rollout still waiting to release it. Names are display-only. The first reviewed commit recomputes under the writer transaction; changed review state returns HTTP 409 `ROLLBACK_REVIEW_CHANGED` without committing source changes, a replacement or a request mapping. Authoritative admission and priority checks remain atomic. Matching successful same-key replay returns its original result before these mutable checks. Omitting the token preserves the legacy strict selection behavior, including rejection of revoked snapshot targets; it never silently filters them.

The dashboard requires `rollback_idempotency:true`, `rollback_review:true`, `request_correlation:true` and a valid ready preview for new rollback actions. It allocates the operation identity only on explicit confirmation and freezes the token and reviewed version/device context in its existing recovery registry. Only the request identity and token are sent. Every failed attempt retains the original reminder and body for correlated status lookup or explicit same-key retry, including after closing/reloading the tab; changing the request requires explicit dismissal and a new review. Existing keyed requests can recover without synthesizing a review when the server supplies correlation metadata; unkeyed legacy reminders remain history-only. Returned receipts must match the exact frozen request identity, rollback operation and source UUID, with a result UUID different from that source. Current target membership, version and status can have changed after commitment and are not compared with the original review to clear a confirmed reminder.

Device projection adds optional `retry_preconditions:true`. `POST /devices/{id}/retry` now requires exactly `{expected_version_id:UUID,expected_generation:positive safe integer}`. The authorized transaction compares these to the current desired assignment, checks a current retryable apply state and refuses paused sync. Assignment changes return `STALE_DEVICE_REVIEW` (409), ineligible states return `DEVICE_NOT_RETRYABLE` (409), and local/server pause returns `DEVICE_SYNC_PAUSED` (409). Missing or malformed fields return 400. A successful retry advances desired generation once and returns Device in a waiting state; it does not establish activation. Replaying the old reviewed tuple cannot increment it again. The dashboard offers retry only when this capability is reported, because older servers do not enforce these preconditions.

Retry authorization is checked again inside the serialized transaction against current session, account role/enabled state and CSRF. An access change committed first rejects the queued operation; it does not undo an earlier committed retry. The dashboard separately owns its bounded wait: changed assignment or eligibility, lost operating permission, session end and navigation retire obsolete retry/status feedback without automatic resubmission. Pauses and revocation can change while historical desired version/generation stay unchanged, so client review scope includes those states. This lifecycle adds no wire field or cancellation endpoint.

`reported_generation` is the agent's last verified generation, not an attempted or failed generation. A failed update may legitimately have a smaller reported generation than the desired one; the retry comparison does not equate them. The separate configuration-attempt projection below identifies the candidate without advancing verified evidence.

## Agent protocol /agent/v1 on dedicated TLS listener

POST /enroll (verified HTTPS, no client certificate): `{protocol_version:1,request_id,token,name,csr_pem,os,arch,agent_version,vector_version,configuration_mode?,service_manager?}`. `service_manager` (`systemd`, `launchd`, `windows`, `none`) is what setup registered to keep the agent running; servers that predate it ignore it, and a value this server doesn't know is ignored rather than refused. CSR must prove private key possession. `request_id` (at most 128 bytes) and `os`, `arch`, `agent_version` and `vector_version` (at most 64 bytes each) name or identify the request or the host, so each is refused, as the generic 401, when it is empty or holds a character that can't be shown safely in one line: a control character, a line or paragraph separator, a text-direction embedding, override or isolate, or the byte order mark (the same rule as every member that names or identifies something, below). Reply `{device_id,certificate_pem,ca_pem,signing_public_key,certificate_expires_at}`. CA and signing trust arrive only through verified server TLS. Public key base64 raw Ed25519 (32 bytes). Same request_id/key retries idempotent; never recover using name alone. For ordinary tokens the stored reply for a request_id is returned (same CSR key and token, device still active under that name) before the token's revocation, expiry, name and use checks, so a host whose reply was lost can finish and a refusal always means the request never enrolled; recovery tokens keep the stricter order, so cancelling a recovery also ends its replay. Refusals stay a generic 401 `ENROLLMENT_FAILED` for the device; the `device.enroll` audit event records `details:{reason_code,name,token_id,agent_os,agent_arch,agent_version,configuration_mode,client_address}` (bounded, printable, never the token; the client address is the TCP peer of the agent listener), and successes record the same details with the device as target. Enrollment allows 60 attempts per minute per client (an IPv6 /64 counts as one client) and 600 per minute per server, then answers 429 `RATE_LIMITED` with `Retry-After`. The client's limit is charged first and the server's only for attempts the client's let through, so one address never uses up the server's. A refusal that carries no real token (`TOKEN_UNKNOWN`, `MALFORMED`) is audited once per client and reason each minute; a refusal for a real token (`TOKEN_REVOKED`, `TOKEN_EXPIRED`, `TOKEN_EXHAUSTED`, the name refusals and the rest) is audited once per token and reason each minute. Repeats are refused the same way without another audit row. All refusals together add at most 60 `device.enroll` events a minute (a UTC minute): the refusals past that are counted, and one `device.enroll_refusals_summarized` event for the minute, with `details:{summary}` such as `37 further refusals in the minute from 04:06 UTC were not written`, is added when the next refusal arrives or the minute has ended, so a flood from many addresses adds at most 61 events a minute. The counts are in memory per server.

GET /install.sh (no client certificate) returns a POSIX sh installer rendered for this server: its agent address (`VECTORY_PUBLIC_AGENT_URL`, or the host the device requested), the CA pin and PEM to verify the download, the dashboard address when `VECTORY_PUBLIC_URL` is set, and one `os/arch version sha256` entry per platform with exactly one build. It holds no token or device data. It installs `DIR/vectory` (default `/usr/local/bin`, `--install-dir`) only after the downloaded bytes match, then execs `vectory setup --server ... [--ca-sha256 ...] "$@"`; setup reads the token from the terminal or `--token-file`/`--token-stdin`. GET /downloads/{os}/{arch} streams that platform's single build (rate-limited per client address; at most eight transfers at once per address and 32 overall across both listeners, beyond which it answers 429 with `Retry-After: 5`, which the installer's curl waits out; a transfer that stalls for 20 seconds or runs past five minutes is cut off). `VECTORY_PUBLIC_AGENT_DOWNLOADS=false` turns both off (404). GET /identity (mTLS) -> `{device_id,name}` for local diagnostics. Token verifier only persisted. Certificates have server-selected UUID identity and clientAuth usage.

POST /heartbeat (mTLS): `{protocol_version:1,request_id,nonce,boot_id,agent_version,vector_version,reported_generation,policy_generation,actual_sha256,apply_state,local_paused,remote_pause_acknowledged,configuration_mode?,telemetry?,error?,configuration_attempt?,applied_template_sha256?,secret_revision?,host_runtime?,vector_log_summary?,secret_names?,service_manager?,vector_running?,agent_sha256?,state_dir?,agent_features?,validation_result?,readiness?,agent_update?}`. `error` may carry `diagnostics`. `service_manager` is what keeps this agent process running (`systemd`, `launchd`, `windows`, or `none` for a foreground run, a supervisor of the operator's own, or setup's one-shot check-in) and `vector_running` whether the Vector process the agent supervises runs; the server rejects other values. `agent_sha256` is the SHA-256 of the running agent executable (64 lowercase hex) and `state_dir` the absolute path of its state directory (at most 4096 bytes, and no character that can't be shown safely in one line: a control character, a line or paragraph separator, a text-direction embedding, override or isolate, or the byte order mark); anything else is rejected. `request_id`, `boot_id`, `agent_version` and `vector_version` (each 1 to 128 bytes) and `host_runtime.data_dir` (at most 4096 characters) follow the same character rule. The members that name or identify something, here and in the reports below, all refuse such a character; only display text, which the server replaces, is forgiving. Setup's one-shot check-in sends one more, complete check-in as soon as the first manifest lists fields it didn't send, so the server sees what a running agent reports. A heartbeat adds a `device.apply_state`, `device.configuration_mode_reported` or `device.secret_reconciliation` audit event only when the value the device record held changed, and a device adds at most 4 events of each kind a minute, except that the first `device.apply_state` event of each of `desired`, `verified_applied` and `failed` for a generation is always added and does not count (a generation repeats that exemption once per state every ten minutes); the device record always takes the new value. Identity derived from registered client certificate fingerprint, checked against revocation each request. nonce random 32 bytes base64. Reply signed envelope `{payload:base64,signature:base64}`. Signature Ed25519 over exact decoded payload bytes; payload JSON `{protocol_version:1,device_id,nonce,issued_at,expires_at,generation,policy_generation,policy,desired?:{version_id,sha256,size,artifact_path,vector_version,version_number?,configuration_name?},features?:string[],validation?:{id,sha256,size,artifact_path,run_tests,expires_at},agent_update?:{rollout_id,release_id,manifest,signatures,rollovers,artifact}}`. `features` lists the additive heartbeat fields this server accepts (`diagnostics`, `host_runtime`, `vector_log_summary`, `telemetry_v2`, `secret_names`, `service_manager`, `vector_running`, `agent_sha256`, `state_dir`), `validation` (`agent_features`, `validation_result` and `readiness`, see [Check on devices](#check-on-devices)), `agent_update` (the heartbeat member and the offer of [Agent updates](#what-the-agent-reports), listed only while updates are on), and `wake` while it holds `GET /wait` (below); agents send those fields, and wait, only after a verified manifest lists them, and otherwise keep the original shape, so a newer agent never trips an older server's strict validation. An agent whose heartbeat is refused as invalid (`400 INVALID_INPUT`, nothing written) sends it again, with a new nonce and request ID, leaving reports out one step at a time until the server answers: `agent_update` first (and it stays out for the rest of the process), then the result of a check, then `vector_log_summary` and the `diagnostics` of its errors, then `host_runtime`, `state_dir`, `secret_names` and `telemetry`, then `agent_features` and `readiness`. No report can keep a device from checking in; a refusal that leaving all of them out doesn't end is a failed check-in. An agent builds each report within the bounds below, so a server that follows them never refuses one. artifact_path must be relative `/agent/v1/artifacts/{sha256}`. Agent validates recipient/nonce/time/signature and rejects stale generations or changed same-generation identity, persisting highest accepted generations before apply. Manifest validity 5 minutes, clock tolerance 60 seconds. No redirects.

GET /wait?generation=N&policy_generation=M (mTLS, no body) is a wake-up hint. `N` and `M` are the `generation` and `policy_generation` of the last manifest the agent accepted, each a nonnegative safe integer; nothing else is accepted (400 `INVALID_INPUT`). One statement authenticates it exactly as the heartbeat (registered certificate fingerprint, credential and device not revoked, credential unexpired) and reads the device's current generations: if either differs, the answer is `{"changed":true}` at once. Otherwise the wait parks in memory, holding no database connection, writer lock or agent request slot, with no database read while parked or when it times out, until the device's desired or policy generation changes or the device is revoked (`{"changed":true}`), or it ends without a change (`{"changed":false}`): 25 seconds pass, a newer wait from the same device replaces it (one wait per device), or the server stops (every parked wait is answered first). The response head (200, `application/json`, `Cache-Control: no-store`) is sent at once and the one-line body when the answer is known, so the listener's 15-second request deadline and 128 slots cover only authentication and an agent's response-header timeout never cuts a parked wait short. Writers answer waits after their transaction commits: once a request or scheduler tick that staged changed devices has finished (assignment release, scheduled activation, rollback, pause/resume, agent settings, group membership, assignment removal, retry, revocation and identity recovery), one query reads the committed generations of those that are waiting, and only the waits whose generations really changed, or whose device was revoked, answer. A preview that rolls its simulated changes back answers nothing, and a burst answers each wait once. A committed device check (see [Check on devices](#check-on-devices)) answers, the same way and whatever their generations say, the waits of the devices it is waiting for, because a check moves no generation: the answer only hints that the device should check in, and the check itself arrives in the signed manifest. A check that asks no device, and one that is refused, answers nothing. Answers are paced: up to 100 go out at once, then 50 a second, oldest first, so an all-at-once release to a large fleet doesn't bring every agent's heartbeat to the writer together; a wait held for its turn still counts as listening, and its agent's own schedule keeps running, so no device learns of a change later than its next check-in. The answer is unsigned and carries no configuration and changes no state: the agent answers `changed:true` with an ordinary heartbeat, whose signed manifest stays authoritative, so a forged or stale answer can only cause an early heartbeat, and a revoked device meets the heartbeat's ordinary 401 `UNAUTHENTICATED` there and on its next wait. 404 when wake-ups are off (`VECTORY_AGENT_WAKE_LIMIT=0`; manifests then omit `wake`); 429 `RATE_LIMITED` beyond 60 waits a minute per device; 503 `CAPACITY_BUSY` with `Retry-After` and the same seconds as body `retry_after`: 60 when `VECTORY_AGENT_WAKE_LIMIT` waits (default 20,000) are parked, 1 when the server is stopping (refused before any database read). Agents treat every failure as "keep the ordinary schedule": never an outage, never a retry loop, and no new wait before a `Retry-After` has passed. An agent checks in on `changed:true` no sooner than one second after its previous check-in, waits again when a hold ends, and never waits after a failed check-in, in setup's one-shot check-in, for a server without `wake`, or when the host operator turned wake-ups off (`vectory run --no-wake`, or the `no_wake` local setting from `setup`/`install --no-wake`). `GET /api/v1/devices/{id}` and deployment target pages add read-only `wake:{listening:boolean}` while wake-ups are on: whether that device's agent holds a wait at this instant, from the in-memory registry, never evidence of delivery.

GET /artifacts/{sha256} (mTLS) -> exact artifact bytes, only the current released digest authorized, or the digest of this device's own pending device check (see [Check on devices](#check-on-devices)). POST /renew `{csr_pem}` (mTLS, same device) -> enrollment credential fields, issued by the current device CA: after a rotation its `ca_pem` differs from the enrollment's, and the agent validates the new certificate against the `ca_pem` of the same reply; revocation every request. Retain last good workload after credential failure. No insecure fallback or token heartbeat.

## Apply state

Heartbeats may add `configuration_attempt:{generation,version_id,sha256,state,secret_revision?,error?}`. The identity names a verified signed candidate and its template digest; it is persisted before candidate preflight/download/validation, and is distinct from `reported_generation`, actual managed-file evidence and local workload state. Generation is a positive safe integer; secret revision is a nonnegative safe integer, omitted zero. The attempt states are `desired`, `downloaded`, `validated`, `written`, `reload_requested`, `verified_applied`, `verification_unknown`, `failed`, `rolled_back`, `paused`. Optional error has bounded `code`, `stage`, `message` and optional `diagnostics`; server projections allowlist categories and replace the agent's message with one rendered from the code and first diagnostic, never raw Vector output.

Only an attempt matching the current desired generation, version and template digest can update current configuration progress or failure counts. Secret-bearing attempts additionally bind the current materialization revision. Stale candidate reports cannot attribute a failure to a new retry or deployment; the heartbeat can still obtain the newest signed manifest. An attempt's `verified_applied` label alone never establishes activation: reported generation, actual/template digest and secret evidence must still satisfy the existing verification checks. Missing legacy attempt identity does not identify a failed newer candidate.

Device responses add optional `configuration_attempt` for the current candidate and `reported_apply_state` for the agent's workload report. The existing `apply_state` describes current assignment progress. Device details distinguish this progress from the last verified generation. Persisted candidate failure cannot be erased by delayed nonterminal progress; authoritative verification or a new generation/materialization revision is needed. Same-tuple report ordering is conservative rather than a claim of a total event sequence.

`unmanaged`, `desired`, `downloaded`, `validated`, `written`, `reload_requested`, `verified_applied`, `verification_unknown`, `failed`, `rolled_back`, `paused`. Only verified_applied advances canary success, and a configuration canary also needs its data plane measured and healthy (see [Data-plane health](#data-plane-health)). An agent reports `paused` while it keeps running its workload; when that workload is the exact verified generation and digest (and its current attempt, if any, is verified), the device keeps `apply_state:"verified_applied"`, its verified evidence and its deployment target, with `reported_apply_state:"paused"` and the pause flags describing the pause. A stopped workload reports `verification_unknown` instead, and a changed digest degrades as usual. Canary gates still hold while a canary device is paused (reason `paused`) and observe again after resume without a new apply. A rollback references older content with a newer generation. Drift hashes the actual managed file each poll. Local emergency pause OR remote policy pause; pause is acknowledged after prohibited work stops. Bounded sanitized errors never contain configuration or credentials.

## Validation and support

Pin Vector 0.58.0 for initial catalog. Run real validation against available binary; absent isolated server validation must be explicitly recorded as unverified, never marked Vector-validated. Existing and newly installed devices default to restricted mode: a reviewed component subset, explicit local resource permissions, and no exec/providers/environment interpolation. A host operator may explicitly install with `--allow-full-vector-config`, persisting `full_vector_config:true` in the local capability policy. Full mode trusts authorized publishers with the capabilities of the adopted Vector process, including all native components, root settings, providers, environment interpolation and exec within that process's OS permissions. Enrollment and authenticated heartbeats report `configuration_mode: "restricted" | "full"`; missing values mean restricted and unknown values are rejected. This field is never accepted in remote agent policy and cannot be widened from the dashboard. Complete configuration bytes are preserved; native topology patterns and unknown component semantics defer to Vector. Configurations requiring local environment, native secrets, enrichment data, providers or external code files defer server native validation to the device; `vector_validated:false` and `deferred:true` make that boundary explicit. Plaintext credential fields are refused; native `SECRET[backend.key]`, `$NAME` and `${NAME}` references are retained without resolution. Do not use a shell to invoke Vector. Native verified mode may supervise an explicitly adopted child Vector process from fixed local paths, validate staged config, stop old process, launch new one with exact sole managed config, and require startup acknowledgment plus bounded process liveness. Do not infer exact activation from unrelated health endpoint.

Static checks survive device-only values. Before `vector validate --no-environment`, the isolated worker replaces `${VAR}`, `$VAR` (declared `:-`/`-` defaults are used) and `SECRET[backend.key]` references with typed placeholders that still parse (a socket address for `*address`, a URL for endpoints, a path for file fields), removes `secret` backends and `provider` blocks (it never runs or fetches them), and replaces components only a device can load (remap `file`/`files`, component types missing from the worker's Vector build) with inert stand-ins. Every `lua` transform gets one too, in any form or version (inline `source`, `hooks`, `timers`, `search_dirs`, or a type that a `${NAME:-lua}` default resolves to): Lua can run any program, and Vector runs a transform's Lua when it builds the transform, so user Lua never runs on the server. The stand-in passes events through and carries a `device_check` warning, and `deferred_reasons` gains `"Lua runs on devices"`, so `vector_validated` stays false. An enrichment table that reads a file (every type but `memory`: `file`, `geoip`, `mmdb`, and any type this server does not know) is removed from the checked copy, because Vector opens its file when it builds the table and a lookup returns the rows: no author-named path is opened in the worker. Every step that calls `get_enrichment_table_record` or `find_enrichment_table_records` then gets a stand-in with a `device_check` warning, and `deferred_reasons` gains `"Enrichment tables are read on devices"`. `memory` tables stay as they are. Every `aws_ec2_metadata` transform gets a stand-in too, with a `device_check` warning: Vector sends a token request and an identity document request to its `endpoint` when it builds the step, so the server never builds it, and `deferred_reasons` gains `"The AWS instance metadata step is checked on devices"`. A remap whose only way to name its program is `file` or `files` gets a stand-in with a `device_check` warning as well: Vector opens the file when it builds the remap, so the server never builds it, and `deferred_reasons` gains `"A VRL program in a file is read on devices"`. A remap that names more than one of `source`, `file` and `files` gets none: Vector refuses it before it opens a file, and its own rule (`must provide exactly one of `source` or `file` or `files` configuration`) is the check's error on that step. VRL, option types and topology are therefore checked even when a pipeline uses secrets, environment, device files, Lua or enrichment files. Vector stops at the first option error, so the worker repeats the check up to eight times within five seconds, replacing each reported component with a stand-in, so one check reports every problem it can reach. `POST /configurations/{id}/validate` returns `{valid,vector_validated,static_checked,deferred,deferred_reasons?,placeholders?,diagnostics,errors,warnings,vector_version}`. `diagnostics` holds at most 50 findings `{severity,message,section?,component?,route_output?,field?,code?,line?,column?,length?,hint?,detail?,docs_url?,fix?}`: Vector's own message, VRL error code, position, hint and fix for the caller's draft. They derive only from that draft and Vector's fixed message catalogue; the worker scrubs its private paths and the API re-checks every bound, requires components to exist in the checked draft and drops unknown keys. `errors`/`warnings` keep one-line summaries for older clients. `static_checked:true` means pinned Vector ran on the draft; `deferred:true` means each device still checks environment, secrets, files or platform (`deferred_reasons`), and a finding caused only by a placeholder becomes a device-check warning. `vector_validated` is true only when Vector checked the exact draft with nothing deferred. Worker replies must carry `worker_protocol:2`; an older or malformed reply blocks publication rather than counting as a check. Without a configured worker only structural checks run and the result says so. Structural checks also follow event types through transforms that keep them (remap, filter, route, sample and similar): Vector types every transform output as any event, so a log source reaching a metrics-only sink through a remap passes `vector validate` yet delivers nothing; the server reports it as a `type_mismatch` error on the consumer, using a table of fixed-type sources, sinks and converting transforms that a native test keeps equal to pinned Vector.

Target Go toolchain 1.26.x; installed older toolchains are development evidence only until updated. Native target claims require actual tests. Server runs single instance SQLite WAL FULL sync/foreign_keys/busy_timeout; one serialized writer transaction for assignment changes and enrollment. DB IDs and relations enforce uniqueness. Scheduling, candidate assignments and released device generations are durable.

## Additive security and operations routes

- Administrator `POST /users` without `request_id` retains the legacy User response. With a hyphenated UUID `request_id`, the first successful call returns `{request_id,user}`; the actor and request identity are committed with the user and one `user.create` audit in the same writer transaction. The server rechecks the administrator session and CSRF inside that transaction. A repeated keyed POST always returns 409 and never reapplies or reveals the password, regardless of its later body. The registry stores actor/request/result UUIDs, terminal state and timestamps only: no plaintext password, password verifier, or password-derived digest. `GET /users/requests/{request_id}` returns `{request_id,status:"not_found"|"cancelled"}` or `{request_id,status:"created",user:User}` for the current administrator's own request. A fresh exact-key `not_found` response proves route support but does not prove an earlier in-flight POST cannot commit. `POST /users/requests/{request_id}/cancel {}` atomically tombstones an absent request before any delayed create, or returns the existing created user without deleting or disabling it; repeating cancellation is a no-op. `created` status shows the current user, which may have been edited since creation, and cannot prove the original password. The UI must not infer account authorship from a matching email or retry the creation blindly after an unread response.
- Admin `PUT /users/{id} {name,role,enabled,revision,current_password}` retains the legacy User response. A keyed body adds a hyphenated UUID `request_id`, and its original successful response is `{request_id,user:User}`. A request identity belongs to one administrator and target UUID. The exact-key PUT returns 409 after either an applied edit or a cancellation, even if its later body differs; it never reapplies. `GET /users/{id}/access-requests/{request_id}` returns `{request_id,user_id,status:"not_found"|"cancelled"}` or `{request_id,user_id,status:"applied",user:User}`. The applied User is the immutable public snapshot returned by the original commit, not a claim about the account's current state. A not-found read cannot fence an in-flight PUT. `POST` to the same exact path plus `/cancel` with `{}` atomically tombstones an absent request before a delayed PUT, or returns the applied snapshot without undoing it; repeat cancellation has no new effect. Status/cancel require the original actor's current admin authority, and cancellation requires CSRF. Self-demotion or disable revokes the actor's session, so that former administrator cannot read status afterward; the UI must not bypass this access boundary or claim a missing result. The request ledger stores only actor/request/target identities, terminal state, public User snapshot and timestamps, never a password or password-derived material. Every edit checks current admin session, CSRF, password verifier and target revision inside the serialized writer, and commits one `user.update` audit with the edit and ledger. A role or access change revokes the target's sessions and reset codes and every unused reset code the edited target issued for another account, advancing affected target revisions. A name-only edit does not revoke issued codes. At least one enabled administrator must remain.
- `POST /account/password {current_password,new_password}` rotates all of the caller's sessions, revokes unused reset codes the caller issued to other accounts, and returns a fresh Session and cookie for this browser. `POST /account/revoke-sessions {current_password}` revokes only their other sessions and returns `{ok:true}`. Incorrect current passwords return `WRONG_PASSWORD` (403), distinct from an expired or revoked session (`UNAUTHENTICATED`, 401).
- Admin `POST /users/{id}/password-reset {current_password,revision}` retains its legacy `{code,expires_at}` receipt. A keyed `{request_id,current_password,revision}` returns `{request_id,user_id,code,expires_at}` on the original successful response only. The request UUID is unique per administrator and bound to the target UUID; the exact-key POST can never issue twice and always returns 409 after it has committed or been cancelled. `GET /users/{id}/password-reset/requests/{request_id}` returns `{request_id,user_id,status:"not_found"}` when no matching administrator request has committed, `{...,status:"issued",active,expires_at}` after issuance, or `{...,status:"cancelled",was_issued}`. The status never returns the code. `active` describes only this exact verifier while it remains current, unexpired, the target enabled, and its issuing administrator still enabled with the admin role; replacement, redemption, password change, access change or expiry makes it false. A not-found read is noncausal and cannot justify a second issue. Admin `POST` to the same exact path plus `/cancel` with `{}` atomically tombstones a not-yet-issued key or revokes only that request's still-current unused verifier, then returns cancelled status. Cancellation requires the original administrator's current admin session and CSRF; it does not require re-entering the already-cleared password. `was_issued:true` does not imply the code was unused or that a redeemed password change can be undone. Status is scoped to the original administrator and target; a known key for another target conflicts. The code (`purpose:"reset"`, valid 15 minutes; or `purpose:"invite"`, valid 24 hours, for an account that has never had a password; the purpose is echoed in both receipts) replaces previous codes and advances the target revision; cancellation advances the revision only if it removes the active code. Both keyed and legacy codes persist their issuer identity with the verifier, never the code itself, and the request ledger retains no password or password-derived material. The migration invalidates all unused reset codes issued before issuer attribution; administrators must issue new codes after upgrade. The server rechecks admin authority, password verifier, target revision, and request identity under the writer transaction before issuing. Public `POST /password-reset {code,new_password}` atomically consumes a valid code for an enabled account from an administrator who still has enabled admin access, changes its password, revokes all sessions and returns `{ok:true}`. It does not create a session or change MFA. Codes, passwords and verifiers must not enter audit details.

Generated `openapi.json` (served to authenticated users at `/api/v1/openapi.json`) and `protocol.schema.json` are produced by `node contracts/generate.mjs`. `tests/contracts.mjs` checks real response bodies against the shared schemas; the dashboard also validates primary responses with Zod. Authorization, cryptographic verification and semantic constraints are additional mandatory checks, not replaced by JSON Schema.

- `GET /mfa`, password-gated `POST /mfa/setup {password}`, `POST /mfa/confirm {code}`, and `POST /mfa/disable {password,code?,recovery_code?}`. Setup returns the authenticator secret once; confirmation returns one-use recovery codes. Login still accepts optional `totp_code` or `recovery_code` for existing clients. The dashboard uses the two-step flow above. The combined form meets the same limits: all of an account's factor attempts, from either form, share ten in five minutes, and five wrong codes lock the combined form for that account, from any address, for the rest of the five minutes (`429 SIGNIN_THROTTLED` with `Retry-After`, for a right code too). Only a completed sign-in (the password for an account without a factor, the factor for one with it) returns the sign-in failure reservation or marks the client as known. `POST /login` and `POST /login/mfa` charge the client's own limit (60 a minute) before the server's (600 a minute, 100 of them reserved for clients that have completed a sign-in), and a refused request is not counted. Challenges expire after five minutes, permit five factor attempts and are single-use; issuing a new challenge replaces the previous one for that account. Only a challenge hash is persisted. Password, account or MFA enrollment changes invalidate pending challenges, as does server restart. Wrong factors return `401 INVALID_MFA_CODE` for retry; the fifth wrong factor returns `401 MFA_TOO_MANY_ATTEMPTS` and consumes the challenge; invalid, expired or consumed challenges return `401 MFA_CHALLENGE_EXPIRED`. Both require a new password sign-in. The per-account factor limit returns `429 SIGNIN_THROTTLED` with Retry-After. Verification and session creation are atomic. Codes are replay checked; MFA changes revoke other sessions. Invalid authenticator/recovery codes on authenticated MFA changes return `403 INVALID_MFA_CODE` without expiring the session; rejected login credentials still return `401 UNAUTHENTICATED`.
- `POST /devices/{id}/recover` returns `{token,record}` for a one-hour, one-use exact-name recovery authorization. Only an administrator may issue it. Its use revokes the old identity, creates a new UUID, and transfers no groups/assignments. The agent's local `recover-enrollment` operation is explicit and journaled; network failures never trigger identity replacement.
- `POST /devices/{id}/retry` is rate limited and releases a new generation for a managed device. Scheduled device refresh and assignment removal use the reviewed protocols below. Unassigned deployment status is `unassigned`.

### Reviewed scheduled device refresh

`POST /deployments/{id}/refresh-preview {}` requires current Operator/Admin authorization and CSRF. Its strict `ScheduledRefreshPreview` identifies the exact source, current `source_status`, resource, original scheduled time, `refresh_review:true`, `review_token`, readiness, blockers and warnings. `saved_devices` shows the stored snapshot; `devices` shows the current selector resolution. Each row contains its UUID, nullable current name and connection status. Identities are distinct within each list and their combined union is capped at 10,000 without truncation. An empty proposed selection is blocked. A compatibility blocker (`FULL_VECTOR_MODE_REQUIRED`, `VECTOR_VERSION_INCOMPATIBLE`) also carries `resource` and the proposed `device_ids` it affects, each once; every other blocker carries `code` and `reason` only. An originally scheduled source that has become inactive returns its saved devices, an empty proposal and `SCHEDULE_INACTIVE`; a deployment that was never scheduled is rejected. Names and connection status are display metadata, not evidence of activation.

`POST /deployments/{id}/refresh` accepts only `{review_token,expected_device_ids}`. The expected identities must be the complete reviewed proposal, unaffected by table filters. The fingerprint binds the actor, source settings, saved snapshot, proposed membership and a private monotonic refresh revision. Under the serialized writer transaction, the server rechecks current authorization, schedule eligibility and the plan before replacing targets. A changed review returns `409 SCHEDULE_REFRESH_REVIEW_CHANGED` without mutation. Missing/malformed tokens are rejected; there is no blind legacy refresh fallback. The internal revision fences delayed old requests even if membership changes away and back after a newer confirmed refresh.

Refresh changes only the unactivated saved target snapshot. It does not release targets, update a device's desired generation or verify activation; the scheduler independently checks admission when due. An unchanged saved/proposed set is a no-op without a revision change or audit. A changed set returns the exact source deployment with the reviewed targets pending at generation zero.

The dashboard bounds preview, confirmation and current-state reads. A timeout or unreadable confirmation is an uncertain result, not a failed mutation. **Check current selection** reads the saved snapshot; matching IDs establish only the current selection, not which request performed it or that an earlier request cannot still finish. A changed selection requires an explicit fresh review and separate confirmation. An inactive schedule offers exact-source status instead of another refresh. Nothing is resent automatically. Closing and reopening details in the same tab retains uncertain context; after reload a new authoritative review is required. Old preview shapes cannot enable the new action.

### Scheduled activation window and cancellation

The scheduler looks for due schedules every two seconds, including right after a restart. A `scheduled` deployment found due at most `schedule_late_start_seconds` after its `scheduled_at` activates once; a later one becomes `missed` (audit `deployment.missed`) and never activates: an operator creates a new reviewed deployment instead. The window is the server's `VECTORY_SCHEDULE_LATE_START_SECONDS`, a whole number of seconds from 60 to 604800 (default 3600); any other value stops the server at startup. `GET /settings` reports it as `schedule_late_start_seconds`.

Cancellation (`POST /deployments/{id}/cancel`) and activation are both serialized writer transactions, so when they race, the one that commits first decides:

- **Cancel commits first:** the deployment is `cancelled` before the scheduler reads it. It never activates, releases no target, gives no device a generation and never becomes `missed`.
- **Activation commits first:** the activation revalidates targets and releases its first wave (every target for all-at-once, the canary for a canary) in the same transaction. The cancel that follows stops further admissions. Released targets keep their generation, so those devices may still apply the version until a superseding generation reaches them; cancel is not a rollback.

The audit trail shows which order happened: `deployment.activate` and `deployment.release` events before `deployment.cancel`, or `deployment.cancel` alone.

### Reviewed assignment removal

`POST /deployments/{id}/unassign-preview` requires current Operator/Admin authorization and CSRF and returns a strict `AssignmentRemovalPreview`. It contains `removal_review:true`, the exact `source_deployment_id`, `source_status`, resource (`configuration` or `policy`), `review_token`, `ready`, blockers and a bounded list of distinct device identities. Every row shows the before/after removal state and one of `fallback`, `unmanaged`, `default_policy`, `retained_pending`, `unchanged`, `revoked`, `missing` or `not_targeted`. Friendly names and version numbers are nullable metadata. They do not replace identity or establish delivery.

The preview simulates the authoritative resolver and rolls its changes back. It must not commit desired generations, target state, assignment changes or audit events. Projected configuration removal may use a released fallback or become unmanaged while preserving the host's last working local workload. Policy removal may restore the server defaults. A pending higher-priority candidate is identified separately: it is not a delivered fallback. Unrelated delivery effects block review rather than being silently included in a different resource's removal. The materialized reviewed scope is capped at 10,000 identities without truncation; an unused assignment can have an empty ready scope.

`POST /deployments/{id}/unassign` requires the strict body `{review_token}`. The fingerprint binds the current actor, exact source, meaningful membership, eligibility and projected delivery effects. Display names, telemetry and ordinary progress do not invalidate an otherwise unchanged review. Under the same serialized writer transaction, the server rechecks current authorization, recomputes the plan and compares its fingerprint before removal. Missing/malformed tokens are `400 INVALID_INPUT`; changed reviews are `409 ASSIGNMENT_REMOVAL_REVIEW_CHANGED`; a blocked current plan cannot remove the assignment. No legacy empty-body removal is allowed.

After a stale or rejected review, the dashboard requires **Refresh review** and a separate explicit confirmation. After an ambiguous commit response it checks the exact source deployment's current status before offering another review. `unassigned` confirms only that the assignment is currently removed, not which attempt performed the removal or that devices have applied its effects. A still-active source does not prove an earlier request failed. The client does not resend automatically, reconstruct a different payload, or use table filters to alter the reviewed scope. Older preview responses cannot enable the new commit action.
- Deployment creation accepts optional `expected_device_ids`. The dashboard always sends the exact reviewed preview IDs; the server rejects a changed selector resolution transactionally with HTTP 409. Removing an assignment is terminal for that deployment: cancel or rollback cannot resurrect it.
- Rollback at the maximum priority (1,000,000) explicitly removes the original deployment's binding (`unassigned`) and creates the prior-version snapshot at that same priority in one transaction. Its historical targets remain intact. Competing equal-priority bindings still cause a conflict; any conflict or later failure rolls back the original status, new deployment, device generations and audits. Lower-priority rollback retains cancellation plus priority increment. Rollback still requires one common previously managed version across released targets not marked removed; removed targets retain their prior-version reference only as history.
- `POST /configurations/test {config}` runs the draft's native `tests` with pinned `vector test` through the isolated worker (same placeholders and stand-ins as validation; five seconds; 1 MiB request) and returns `{valid,tests_run,tests,errors,warnings,diagnostics,placeholders?,output,deferred,vector_version}`. `tests` lists every configured test in order `{name,passed,not_run?,refused?,message?,detail?,outputs?}` (`refused:true` marks the test Vector could not read or build; it never ran) with Vector's failure text and output payloads from the draft's own synthetic inputs (at most 100 tests, 3,000 characters of detail, ten 8 KiB payloads). A configuration that fails to load, or a refusal that names no test (`test_config` diagnostic), returns its diagnostics with `tests_run:false`. Requires Editor, Operator or Admin plus CSRF, limited to 20/minute/user, and audits `configuration.tests`. Configuration providers return `tests_run:false,deferred:true`; no configured worker returns 503. Use Check on devices with Also run the pipeline's tests."]`) and `deferred_reasons` holding `"Lua runs on devices"`, `"Enrichment tables are read on devices"`, `"The AWS instance metadata step is checked on devices"`, `"A VRL program in a file is read on devices"` or any of them together; the worker's own `/tests` refuses such a draft the same way. No API-host execution or provider resolution.

The worker runs a micro-pipeline stdin → step → console (JSON), so timestamps are real JSON, and it observes remap errors and aborts with Vector's own reason by enabling `drop_on_error`, `drop_on_abort` and `reroute_dropped` for the run. ## Telemetry

Agents send one bounded sample per check-in (`Telemetry`). All values are optional nonnegative numbers; a missing value is unavailable, never zero. Rates (`*_per_second`, `*_per_minute`) are averages over the agent's sampling window; `errors` and `discarded_*` are cumulative counters since Vector started.

- Device level: `events_per_second` (source output, "events in", excluding `internal_metrics` and `internal_logs` sources), `events_out_per_second` (sink delivery, excluding sinks fed only by those sources, such as the metrics exporter), `bytes_in_per_second`, `bytes_out_per_second`, `errors`, `errors_per_minute`, `discarded_events`, `discarded_intentional` (filter/sample drops, expected), `discarded_error` (drops caused by errors), `filtered_per_minute`, `dropped_per_minute`, `buffer_events`, `buffer_bytes`, `buffer_utilization` (0..1, fullest buffer), `uptime_seconds`, `memory_bytes`, `cpu_seconds`.
- Per component (at most 50): `{id,type?,kind?:"source"|"transform"|"sink"}` plus `events_per_second` (sent), `received_events_per_second`, `sent_by_output` (at most 16 named outputs, events/s), `received_bytes_per_second`, `sent_bytes_per_second`, `errors`, `errors_per_minute`, `discarded_*`, `filtered_per_minute`, `dropped_per_minute`, `buffer_events`, `buffer_bytes`, `buffer_max_events`, `buffer_max_bytes`, `buffer_utilization` (0..1), `utilization` (0..1, busy fraction), `latency_mean_seconds`.
- The server allowlists every field and bound; unknown fields, labels or out-of-range numbers reject the heartbeat. The device record keeps the latest full sample; minute history buckets keep device-level readings only (no component breakdown) for the retention period (`VECTORY_TELEMETRY_RETENTION_DAYS`, default 7).

Reads (any authenticated role):

- `GET /devices/{id}/telemetry` without `range` keeps its original shape: up to 120 raw minute buckets. With `range=15m|1h|2h|6h|24h|7d|30d` it adds `{range,step_seconds,from,to}` and returns at most 360 points: steps are 1 minute up to 6h, 5 minutes for 24h, 30 minutes for 7d and 2 hours for 30d, bounded by retention. Within a step rates are averaged, buffer gauges keep their peak and counters keep their latest value; each point carries `bucket` (first minute), `sampled_at` (last sample) and `samples` (count). Steps without samples are omitted, so gaps stay visible.
- `GET /telemetry/summary?range=1h` (default `1h`, same ranges) returns fleet totals now, from each non-revoked device's latest sample while it is fresh (at most max(180 s, three check-ins) old): `events_in_per_second`, `events_out_per_second`, `bytes_in_per_second`, `bytes_out_per_second`, `errors_per_minute`, `filtered_per_minute`, `dropped_per_minute` (sums, or null when no fresh device reported them), `buffer_utilization_max`, plus `devices_total`, `devices_reporting`, `devices_metrics_disabled` (agent settings turn metrics off), `devices_without_metrics_endpoint` (the agent found no exporter), `newest_sample_at` and `coverage` (devices contributing to each total). `series` has one point per step: `{bucket,at,devices_reporting,events_in_per_second,events_out_per_second,errors_per_minute,dropped_per_minute,buffer_utilization_max}`, computed as each device's mean within the step summed across devices.
- `GET /versions/{id}/telemetry` aggregates per component across devices verified to be running that exact version (their last verified candidate, while the managed file still matches its digest) and reporting a fresh sample: `{version_id,configuration_id,version_number,generated_at,devices_running,devices_reporting,device_ids,oldest_sample_at,newest_sample_at,coverage,<fleet totals>,components[]}`. Each component is `{id,kind,type,devices_reporting,received_events_per_second,sent_events_per_second,received_bytes_per_second,sent_bytes_per_second,errors_per_minute,filtered_per_minute,dropped_per_minute,buffer_events,buffer_bytes,buffer_utilization_max,utilization_max,latency_mean_seconds_max,sent_by_output}`: rates and sizes sum across devices, `*_max` keeps the worst device, and a value no device reported is null.
- `GET /configurations/{id}/telemetry` is the same aggregate across every version of one pipeline, plus `versions:[{version_id,version_number,devices_running,devices_reporting}]` (newest first). Component IDs are merged by name across versions.

## Data-plane health

A version can apply cleanly and still deliver nothing (destination down, every request failing, a buffer filling until backpressure stops every path). The server evaluates each accepted telemetry sample against the version the device verifiably runs (`running_version`; only while the device has a desired version and its policy enables telemetry). No agent change is needed and nothing is inferred: a number the agent didn't report is never judged healthy or unhealthy.

Evaluation (`server/src/data_plane.rs`). Five of these are editable by administrators within bounds (see [Detection thresholds](#detection-thresholds)); the table lists the defaults, and the rest are constants:

| Constant | Value | Meaning |
|---|---|---|
| `EVALUATION_INTERVAL_SECONDS` | 25 | At most one evaluation per device per interval (server time); a sample no newer than the last evaluated one, older than 10 minutes, or stamped more than 5 minutes ahead of server time is skipped. The last evaluated sample time is remembered as server time at the latest, so a device clock that ran ahead and was corrected never holds back later evaluations. |
| `OPEN_SAMPLES` | 2 | Consecutive bad evaluations before an issue opens. |
| `STALL_SAMPLES` | 3 | Consecutive bad evaluations before a stall opens. |
| `RESOLVE_SAMPLES` | 3 | Consecutive clean evaluations before an open issue resolves (`resolved_reason:"healthy"`). |
| `SINK_ERRORS_PER_MINUTE` | 1 | A sink failing at least this many requests a minute is bad. |
| `ERROR_DROPS_PER_MINUTE` | 1 | A component dropping at least this many events a minute to errors is bad. |
| `BUFFER_RISING` / `BUFFER_FULL` / `BUFFER_CLEAR` | 0.8 / 0.95 / 0.5 | A buffer at least 80% full and higher than at the previous evaluation, or at least 95% full, is bad; below 50% it is clear. |
| `STALL_MIN_EVENTS_PER_SECOND` / `STALL_OUT_RATIO` | 0.1 / 0.01 | Sources receiving at least 0.1 events/s while at most 1% is delivered. |
| `GATE_MIN_EVALUATIONS` | 3 | Evaluations on a version before a canary counts its data plane as measured. |
| `MAX_OPEN_PER_DEVICE` | 10 | Open data-plane issues per device; further conditions wait. |
| `ISSUE_REFRESH_SECONDS` | 300 | While its condition holds, an open issue is rewritten at most this often; the evaluations in between are counted and added to `reports` on the next write. |
| `MAX_ISSUE_WRITES_PER_EVALUATION` | 3 | Issue writes (open, refresh or resolve) per evaluation. A transition that waits keeps counting in its streak and goes out on the next evaluation. |

Codes (issue `stage:"delivery"`), each keyed by device, version, code and component:

- `DATA_PLANE_SINK_ERRORS` (per sink): `errors_per_minute >= 1`. Clean only with evidence: errors below the threshold and either the sink's buffer observed below 50% or events sent in the window. Silence is not recovery: a stuck sink backs off and stops counting errors, and Vector's Prometheus exporter drops series that haven't changed for a minute (`flush_period_secs`), so a stuck sink also loses its buffer gauge. Such evaluations hold instead of counting as clean.
- `DATA_PLANE_STALLED` (pipeline-wide, no component key): device `events_per_second >= 0.1`, `events_out_per_second <= 1%` of it, intentional filtering below half of it, and a struggling sink (errors, buffer at least 50%, or error drops; or no component breakdown). A route that matches nothing is not a stall. Its diagnostic names the likely sink. Clean when delivery resumes.
- `DATA_PLANE_BUFFER_FULL` (per component with a buffer gauge): see the buffer thresholds above.
- `DATA_PLANE_ERROR_DROPS` (per component): `dropped_per_minute >= 1` (the agent's rate of `discarded_error`).

Without metrics, Vector's log is weaker evidence, and it only ever judges `DATA_PLANE_SINK_ERRORS`. When a check-in carries no telemetry sample and the device reads no metrics (`host_runtime.metrics_source` is neither `explicit` nor `discovered`), the server evaluates the check-in's `vector_log_summary` instead, at the same `EVALUATION_INTERVAL_SECONDS` pace, with the same streaks and thresholds. A sink's warning or error groups whose `error_type` is one of `LOG_DELIVERY_ERROR_TYPES` (`request_failed`) are failed deliveries. A sink is bad while those groups grow by at least `SINK_ERRORS_PER_MINUTE` since the previous evaluation (a smaller count is a restarted agent counting again), or, for a group seen for the first time, when it occurred in the last `LOG_RECENT_SECONDS` (180); it is clean when they stop growing or no longer appear, and holds otherwise. The finding's message ends with "measured from Vector's log (no metrics)", for example `The http sink out is failing about 27 requests a minute (connection refused), measured from Vector's log (no metrics).`, so two consecutive check-ins with growing failures open the issue and `RESOLVE_SAMPLES` quiet ones resolve it. Log evaluations don't add to `evaluations`: they don't measure delivery. A device that reads metrics is never judged from its log.

An evaluation between "bad" and "clean" (for example a buffer at 70%) holds: it breaks a clean streak without adding to a bad one. Issues use the ordinary model: `count` counts openings (a recurrence after resolution clears acknowledgement and advances the revision); `reports` counts evaluations that found the condition while open; `diagnostics[0]` is the finding `{severity,code,component_id?,component_kind?,message,hint}` and an optional `diagnostics[1]` (`code:"VECTOR_LOG"`) is the component's most frequent redacted Vector log line from `vector_log_summary`. The rendered `title` names the component (`"archive can't deliver events"`, `"archive's buffer is filling up"`, `"archive is dropping events"`, `"The pipeline stopped delivering"`, at most 120 characters) and `message` is the finding's message. When the device runs another version, its open data-plane issues for other versions resolve with `resolved_reason:"superseded"`; removing the assignment resolves them with `"unassigned"`, turning the device's metrics off (agent settings `telemetry_enabled:false`) resolves them with `"unmonitored"` and removes `data_plane` from the device, since delivery can no longer be judged, and revoking the device resolves them with `"revoked"` and removes `data_plane` too. Every diagnostic is shortened (hint first, then message) to fit the 512-byte bound, so a long component ID can't reject a heartbeat. Private streak state lives in `data_plane_state` and is never served.

Read models:

- Device `data_plane:{version_id,evaluations,issues:[{issue_id,code,component_id,component_kind,title,message,hint,since}],issue_count}` (at most 10 issues, stalls first; list rows carry only the first, and `issue_count` counts them all; `evaluations` counts up to the canary measurement count (`canary_checks`, 3 by default) and the summary carries no timestamps, so a steady state doesn't rewrite the device). The dashboard shows **Not delivering** when `status` is `verified`, `data_plane.version_id` equals `desired_version_id` and `issues` is nonempty; the server `status` stays `verified` (apply state is separate).
- Held on previous version: a device whose newest version failed (status `failed` or `rolled_back`) but which verifiably keeps running an earlier one is not failed. The device row adds `held_on_previous_version:true` (only then; the row's `status` stays what the agent reported) when the version it verifiably runs (`running_version`: its managed file still matches the digest the agent verified) is not the desired one, its Vector is not reported stopped, and no open delivery issue is measured on the version it runs. A device that has no working version, whose file no longer matches, whose Vector stopped or whose earlier version is not delivering stays failed. The dashboard's display state for it is `held` ("Held on previous version", amber); it is a bucket of its own between `degraded` and `updating` in `counts.health`, `counts.status` and the `status=held` filter (which fail closed on any other word), sorts after failed, degraded and check under `sort=status`, and stays in the `failing` view (the dashboard's **Needs attention** chip, which is failed, rolled back, conflict, verification unknown, not delivering and held) and in `not_on_desired`. `attention` adds a `cause:"held"` group per desired version (severity `warning`, `state:"held"`, `reason` the most common failure summary, `deployment_id` when its devices share one rollout, never `rollback_available`) and `attention_devices` a `cause:"held"` entry (after `check_required`, before `offline`, `status:"held"`, with the failure summary and code); `failed` groups and entries keep only the devices without a working version.
- Overview `devices_degraded` counts such devices, and `attention` adds a `cause:"degraded"` group per version (severity `danger`, `state:"degraded"`) with `title`, `reason` (message), `fix`, `code` and `component_id` from the most common leading issue. Leading issues count as the same condition by `(code, component_id)`, since each message quotes its device's own measured rate; a tie goes to the first condition in that order.
- Canary gate: a configuration canary device that is otherwise verified reads `measuring` while its policy enables telemetry, it has a fresh sample (max(180 s, three check-ins)), and fewer than `GATE_MIN_EVALUATIONS` evaluations exist on the rollout's version; it reads `degraded` while it has an open data-plane issue on that version. Devices without fresh telemetry are gated on apply state alone, and on an open data-plane issue measured from their log. Both reasons keep the gate from observing.
- Scheduler: for a canary that still has devices to release, released configuration targets that applied but are degraded count as failures together with failed, rolled-back and incompatible targets. Above `failure_threshold` the rollout fails with `failure_reason:"data_plane"` (or `"threshold"` when apply failures alone exceed it); a persistent assignment is `paused` with `failure_reason:"data_plane"` instead, so it keeps following its group, and `resume` clears the reason. Rollouts with nothing left to hold back (all-at-once, or every device released) are never changed by delivery health: the degraded devices show in lanes, Overview and Issues.
- `GET /deployments/{id}/rollout`: a verified target with an open data-plane issue on the rollout's version appears as `state:"degraded"` in lane device marks and counts (a lane with one reads `failed`), and as a failure group `{state:"degraded",message:<issue title>,diagnostic:<issue message>,fix:<hint>}`. The stored target state is unchanged. `GET /deployments/{id}/targets` rows in the same situation keep `state:"verified_applied"` and add `delivery:{code,title,message,hint}`; the dashboard shows them as Not delivering and moves them from verified to failed in its progress bar.
- Canary choice: `rollout.canary_device_ids` (optional, canary rollouts only) names the devices to release first: distinct lowercase device UUIDs, at most `canary_size` and at most 100, each a device the request targets, otherwise `400 INVALID_INPUT` on preview and create alike. Fewer than `canary_size` lets the most ready of the other targets fill the canary. Absent, null or empty leaves the choice to the scheduler: online and healthy devices that report metrics first, then online and healthy devices without metrics, then failing or not delivering, then sync-paused, then devices that are not checking in, and device ID order among equals (the earlier rule, which ignored readiness, only ever broke those ties). `POST /deployments/preview` adds `canary`, `null` for other rollouts and otherwise `{size,chosen_by_you,device_ids,devices:[{device_id,device_name,chosen,readiness:"ready"|"no_metrics"|"failing"|"paused"|"away",reason}]}` in release order; a named device that is not checking in, paused or failing adds a warning that the rollout waits for it. The first wave releases exactly `canary.device_ids`. `GET /deployments/{id}/summary` echoes `rollout.canary_device_ids` when the request named any, and `GET /deployments/{id}/rollout` lists a queued canary in its release order.
- `GET /deployments/{id}/rollout` adds `canary_watch` for canary rollouts with a released canary (`null` otherwise): `{window_seconds:600,evaluated_at,devices:[{device_id,device_name,released_at,gate_reason,now,baseline,samples}],more}`, at most five canary devices by name and how many more there are. `gate_reason` is why the gate is not counting the device as verified (the same reasons and predicate as `canary_gate`), `null` when it is. `now` is the device's latest sample `{sampled_at,events_in_per_second,events_out_per_second,errors_per_minute,buffer_utilization}`, `null` when it reports no fresh telemetry. `baseline` averages the stored minute samples of the ten minutes before the canary's release (`{minutes,...}`), `null` when there are none: missing history is never a zero. `samples:{measured,needed}` counts the delivery checks on this version against the number the gate needs, `null` when the device reports no metrics. Lanes add `released_early:{by_name,at}|null` for a stage released before the stage ahead of it finished.
- `POST /deployments/{id}/release-next-stage` (Operator/Admin, CSRF, no body) releases the next stage of a running canary now, without waiting for its observation period or for delivery to be measured, and returns the Deployment. It goes through the scheduler's own admission (the same target checks, replacements and wake). Only a canary that applied on every released device qualifies, so a stage still being observed or measured may be skipped and one that has not applied, has gone quiet, is paused, is superseded or is not delivering may not. `409 CONFLICT`, with nothing changed, when the rollout is not a canary, is paused, failed or finished, when nothing has been released yet, when every device has been released, or for any of those reasons. Success records who released the stage on the rollout and writes the audit row `deployment.stage_released_early` with `details:{summary,stage:"canary"|"batch N",gate_state:"observing"|"measuring",released_count,verified_count,measuring_count,next_released_count}`; `stage` is the stage whose wait was cut short.

### Detection thresholds

`GET /detection` (any signed-in role) returns `{thresholds,defaults,bounds,revision,updated_at,updated_by_name,evaluation_interval_seconds}`. `thresholds` holds exactly `sink_errors_per_minute` (default 1, 1..10,000: `SINK_ERRORS_PER_MINUTE`), `error_drops_per_minute` (1, 1..100,000: `ERROR_DROPS_PER_MINUTE`), `buffer_full_percent` (95, 55..100: `BUFFER_FULL`), `stall_checks` (3, 2..20: `STALL_SAMPLES`) and `canary_checks` (3, 1..20: `GATE_MIN_EVALUATIONS`); `revision` is 0 until first edited. `PUT /detection {thresholds,revision}` (administrators, CSRF) requires every field as a whole number within its bounds and nothing else (400 otherwise) and the current revision (`409 STALE_REVISION`). Saving the current values changes nothing; a change advances the revision and records one `detection.update` audit whose `details.summary` names each changed value with its before and after. Evaluation reads the stored values when an evaluation is due, and the canary gate when it evaluates, so a change applies from the next evaluation without a restart. Device `data_plane.evaluations` counts up to `canary_checks`. With no stored row, or an unreadable one, the defaults apply, and they equal the previous constants, so behavior is unchanged until someone edits them. The rising (80%) and clear (50%) buffer levels, the open (2) and resolve (3) streaks, the 25-second interval and the issue refresh remain constants.

## Notifications

Administrators configure up to 20 channels under Settings → Notifications. Every route below requires an administrator session (CSRF on mutations), and every mutation is rechecked inside the writer transaction and audited (`notification.channel.create|update|delete|test`, with `details.name` and a secret-free `details.summary`; a test's outcome is `success` or `failed`, and the summary says what the receiver did). Audit history and recent activity name these events after the channel as it was called then (`target_name` from `details.name`) and `detection.update` as `Detection thresholds`; `target_id` stays null for both.

- `GET /notifications/channels` → `{items:NotificationChannel[],max_channels}`; `GET /notifications/channels/{id}` → `NotificationChannel`. A channel is `{id,name,kind:"webhook"|"email",enabled,allow_private,webhook|null,email|null,rules,secrets_readable,revision,created_at,updated_at,status:{state:"idle"|"delivering"|"failing"|"off",last_attempt_at,last_delivered_at,last_error,last_status_code,pending}}`. `webhook` is `{url_hint,host,header_name,signing_secret_set,header_value_set}` and `email` is `{host,port,security:"starttls"|"tls"|"none",username,password_set,from,to[]}`.
- Secrets are write-only everywhere: the webhook URL's path and query (Slack's carry its token), the signing secret, the header value and the SMTP password are sealed with the instance's AES-256-GCM key (`keys/mfa-sealing.key`, bound to the channel ID) and never appear in a response, audit event, log line or delivery error. A response says only whether each is set; `url_hint` is the URL's origin. A channel restored without its keys reports `secrets_readable:false` and must have them replaced.
- `POST /notifications/channels` and `PUT /notifications/channels/{id}` take `{name,kind,enabled?,allow_private?,webhook|email,rules,revision}` (revision on PUT only, `409 STALE_REVISION` when stale; `409 NAME_TAKEN` for a duplicate name). On PUT an omitted secret keeps its saved value, `null` or `""` removes it, and text replaces it; `kind` can't change. Turning a channel off or removing it (`DELETE`, returns `{ok:true}`) drops its pending messages; its delivery log ages out normally.
- Rules: `{events:[...],offline_minutes?:5..1440 (15),min_severity?:"warning"|"error",pipeline_ids?:UUID[≤50],group_ids?:UUID[≤50],quiet_hours?:{start:"HH:MM",end:"HH:MM",time_zone:IANA,errors_bypass?}|null}`. Events are `issue.opened` (a new issue, or one that came back after it resolved), `issue.resolved` (only when the problem went away: `verified` or `healthy`; issues closed by a superseding version, a removed assignment, revocation or metrics turned off send nothing), `rollout.failed` (a rollout stopped by its failure threshold, delivery health or an incompatible device, or a scheduled start that was blocked), `rollout.rolled_back`, `canary.paused` (a persistent canary held for delivery health), `device.offline` and `device.recovered`, and the four events of [Agent updates](#device-projection-filters-audit-notifications-and-issues): `agent_update.failed`, `agent_update.rolled_back`, `agent_update.stopped` and `agent_update.key_changed`. Severity: issues carry their first diagnostic's (a filling buffer is a warning), rollout failures are errors, the rest warnings; a recovery carries the severity of what it recovers from. Empty filters match everything; a pipeline filter matches events whose device, issue or deployment belongs to a chosen pipeline, and a group filter events whose device (or a rollout's selector or targets) is in a chosen group.
- Webhook destinations must be `https://`, or `http://` to a private address with `allow_private`; URLs with a user name, password or fragment are refused. Every attempt resolves the host and checks every answer before connecting to one of exactly those addresses: public addresses are allowed; private, CGNAT, unique local and loopback addresses only with `allow_private` (off by default, audited); link-local, multicast, unspecified, reserved and documentation ranges and cloud metadata addresses (`169.254.0.0/16`, `100.100.100.200`, `192.0.0.192`, `fd00:ec2::/32`, and IPv4-mapped, NAT64 and 6to4 forms of them) never. One refused answer refuses the send. Redirects are reported, never followed; at most 4 KiB of a response is read; connecting may take 5 seconds and the whole attempt 10. The server connects directly (no HTTP proxy) and trusts the public web PKI roots. Email uses the same address checks; `starttls` refuses a server that doesn't offer it, `tls` is TLS from the first byte, and `none` only reaches a relay on the server's own loopback address.
- A webhook body is `{text,blocks,event}`: Slack's `text` and `blocks` (with an Open in Vectory button when `VECTORY_PUBLIC_URL` is set) and the documented `NotificationEvent` `{schema:"vectory.notification.v1",id,type,severity,recovery,test,occurred_at,instance,headline,message,url,device,pipeline,deployment,issue}` (`rollout.rolled_back` adds `restored`, `{id,name,version_number}` of the pipeline version the rollback restored, which can belong to another pipeline; digests add `count` and the first 20 `items`). Headers: `X-Vectory-Event`, `X-Vectory-Delivery` and, with a signing secret, `X-Vectory-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">`, plus the channel's optional header. Email is plain text with subject `[<instance>] <headline>`.
- `POST /notifications/channels/{id}/test {}` sends one message marked as a test now and returns `{attempt_id,delivered,status_code,latency_ms,error,at}` from what actually happened (6 a minute per channel; audited with its outcome). `POST /notifications/preview {type,name?}` returns an example message `{example:true,headline,message,context,link,webhook,email:{subject,body}}` with placeholder names; it sends nothing.
- `GET /notifications/deliveries?channel_id=&outcome=delivered|retrying|failed|gave_up&page=&page_size=` pages every attempt newest first (`{items,total,page,page_size}`, at most 50 a page, strict query validation). An attempt is `{id,delivery_id,channel_id,channel_name,channel_exists,kind:"event"|"digest"|"test",type,title,attempt,at,outcome,status_code,latency_ms,error,next_attempt_at}`; errors are at most 500 characters with secrets, URL paths and receiver echoes of them replaced by `«redacted»`.

Delivery (`server/src/notifier.rs`): hooks write events to an outbox in the transaction that changes the issue; rollout events come from the audit trail (`deployment.gate`, `deployment.activate`, `deployment.rollback`, and for agent updates `agent_update_rollout.gate`, `device.agent_update`, `agent_update.stop`, `agent_update.enable` and `.disable` and `agent_release_key.rotate`, `.rollover` and `.revoke`) read from a cursor that starts at the upgrade, so history is never announced; outages come from a check-in scan once a minute. Each event has an identity, so a fact is one event however often it is reported, and a channel gets events from after it was created. `device.offline` goes out once per outage when it passes the channel's minutes, measured from the last check-in and never before the end of the recovery window: the 300 seconds after the server starts, during which no device reads as offline, so agents that backed off while it was down can reconnect. A device is therefore announced at `max(last check-in + minutes, end of the window)`: one already past its minutes when the window ends is announced at its end, one silent only briefly at its own minutes, and one that checks in during the window is never announced; the message still counts its silence from the last check-in. A channel announces only outages that passed its minutes after the channel was created. `device.recovered` goes out once, after the device checks in twice; going quiet again in between is the same outage. Quiet hours hold messages (errors may bypass) and send them as one digest when they end. A channel receives at most 30 messages in any 60 seconds, retries and tests included; the rest become one digest, and more than 500 pending messages go straight into one. A failed attempt that a retry could fix (a network error, a timeout, 408, 425, 429 or 5xx) is retried after 1, 5 and 30 minutes, then recorded as `gave_up`; other refusals are `failed` at once. Sending runs in its own task with at most four sends at once and one per channel, never holds the writer lock across network I/O, and a restart retries sends it interrupted, so a receiver may see a message twice (the event `id` is stable). Attempts and finished deliveries are kept 30 days.

## Vector diagnostics, host runtime and logs

Failed candidates carry `configuration_attempt.error.diagnostics` (and the workload `error.diagnostics`): at most 10 `Diagnostic` records `{severity:"error"|"warning",code,component_kind?,component_id?,route_output?,field?,line?,column?,reason?,message,hint?}`, errors first, each at most 512 serialized bytes. The size is that of the record the server parsed, serialized again in compact form, which escapes only the quotation mark, the backslash and the characters below U+0020 and writes everything else as UTF-8, so `<`, `>` and `&` count one byte each. A `component_id` or `route_output` is an ID a device reports (below). The agent measures its records the same way and fits each to 512 bytes before it sends it: the hint goes first, then the message down to 60 characters, then the field, the output name, the rest of the message and the component's ID, and a record that still doesn't fit is left out. The agent parses Vector's own output (`vector validate` findings, VRL `error[E###]` blocks with line/column and suggestions, `vector test` failures, startup/reload JSON logs and health checks) into these records. Codes include `DATA_DIR_MISSING`, `DATA_DIR_NOT_WRITABLE`, `VRL_E###`, `EVENT_TYPE_MISMATCH`, `INPUT_NOT_FOUND`, `UNKNOWN_FIELD`, `UNKNOWN_COMPONENT_TYPE`, `MISSING_FIELD`, `INVALID_ADDRESS`, `ADDRESS_IN_USE`, `PRIVILEGED_PORT` (Linux only: a listener below the host's first unprivileged port cannot bind under the unprivileged service account), `ENV_VAR_MISSING`, `TLS_FILE_UNREADABLE`, `HEALTHCHECK_FAILED` (a warning: health checks never block activation), `HEALTHCHECK_REQUIRED`, `TEST_FAILED`, `OUTPUT_UNUSED` and the device-secret findings `SECRET_BINDING_MISSING`, `SECRET_FILE_UNREADABLE`, `SECRET_VALUE_REJECTED` and `SECRET_REFERENCE_REFUSED` (a reference outside the agent's credential fields; `field` names it). `hint` is a fixed or Vector-suggested fix. Redaction happens on the device: a token is echoed only when it appears in the published, secret-free template (component IDs, paths, VRL text, field names) or the host runtime settings; resolved local secrets, referenced environment values and any other quoted, long, path, URL, address or email token become `«redacted»`, and local file paths become labels such as `managed configuration`. The server validates every field (allowlisted keys, charset, bounds; unknown fields reject the heartbeat atomically), stores the records with the attempt and the issue, and renders:

- Device `configuration_attempt.error.message` and Issue `message`: the first error diagnostic with its location, e.g. `Unhandled error: expression can result in runtime error (by_severity.errors, line 1, column 1).`, plus `N more errors.`; a fixed per-code sentence when the agent sent none.
- Deployment target `error` for failed or rolled-back targets: `Title. Reason. Fix.` in at most 500 characters, e.g. `Vector rejected the configuration. The data directory "/srv/x" does not exist on this device. Remove data_dir from the pipeline to use the device's own data directory, or create this directory on the device.`

`host_runtime` (`HostRuntime`) reports the data directory Vector uses and its source, the bounded graceful drain limit, how metrics are collected and how the last change was activated. When a pipeline omits `data_dir`, the agent supplies the host's directory through a separate runtime file that Vector loads next to the managed configuration, so the managed file and its digest evidence are unchanged. `vector_log_summary` is at most 20 `VectorLogGroup` records; the device keeps the latest as `{reported_at,items}`, and a heartbeat without the field removes it. The IDs a device reports (a group's and a diagnostic's `component_id`, and a diagnostic's `route_output`) follow one rule, the pipeline validator's text rule for a component ID with one addition: 1 to 128 bytes of UTF-8, no `/` or `\`, no control character, no drive letter and a colon at the start, and no character that can't be shown safely in one line (a line or paragraph separator, a text-direction embedding, override or isolate, or the byte order mark). A dot is allowed and any other letter, digit, space or punctuation Vector accepts (`café`, `日志`, `a b`). The agent leaves out an ID that breaks the rule and reports the group or the diagnostic without it; `vector-catalog/fixtures/component-ids.json` pins the server's and the agent's judgment of each case, and `report-bounds.json` the bounds on diagnostics and groups. A group's `message` and a diagnostic's `message`, `hint` and `field` are display text drawn from Vector's own output, which can echo event data, so the server replaces each control character, line or paragraph separator and text-direction control in them with a space, stores and serves the result, and never refuses a heartbeat for one (a message with nothing printable left shows a fixed sentence); every other member keeps its exact rule, and the length limits count the text as sent. The full local Vector log stays on the host (`vectory logs`).

## Pipeline publication recovery

`POST /configurations/{id}/publish` accepts an optional UUID `request_id`. Keyed calls require a positive JavaScript-safe `revision`; an optional `message` must be text of at most 2,000 UTF-8 bytes. The browser always supplies the reviewed note, including an empty string. Legacy unkeyed publication remains supported for compatibility.

A key belongs to the authenticated operator/administrator and the publication namespace. It binds the exact pipeline UUID and canonical supplied JSON body excluding `request_id`. Object key order is insignificant; arrays, omitted fields, explicit nulls, and unknown supplied properties remain significant. A different payload or parent under the same actor/key returns `409 IDEMPOTENCY_CONFLICT`. A successful keyed response is the original immutable `Version` with response-only `request_id`, including its `configuration_id` and `source_revision`.

Version creation, request mapping and `configuration.publish` audit commit atomically. A matching replay returns that same version without creating a version, auditing again, modifying the draft, or deploying. It works after newer draft revisions, archival or changes in validator availability. Current authorization and CSRF checks still apply. Native validation remains outside the serialized writer transaction; authorization and exact replay are checked again inside the final transaction. An unavailable original version returns a conflict and retains the key; it never recreates the version. `422 VALIDATION_FAILED` is definitive for its request: the writer transaction looked for an exact committed replay of the key before rejecting, and this request created no version. Clients may clear the request reminder and show the problems; re-running `validate` returns the structured diagnostics.

### Tests gate publishing

When the draft carries `tests` and Vector accepted it, `POST /configurations/{id}/publish` runs the tests before it creates a version, through the same isolated runner as `POST /configurations/test` (the same rows, the same verdicts). If any test failed, was refused (Vector could not read or build it) or did not run, including when no runner answered and for a draft with a `lua` transform (its tests run only on devices), the answer is `409 TESTS_FAILED` and nothing is published: `{error:{code,message},tests,tests_run,counts:{passed,failed,refused,not_run}}`. `tests` holds one `PipelineTest` row per configured test (at most 100, `not_run` rows included), each `detail` cut to 1,000 characters and no `outputs`; `POST /configurations/test` returns the full rows. Like `422 VALIDATION_FAILED`, the refusal is definitive: the writer transaction looked for an exact committed replay of the key first, and this request created no version, audit row or request mapping, so the same key can publish afterwards.

The optional boolean `acknowledge_test_failures` publishes anyway (any other type is `400 INVALID_INPUT`). The server still runs the tests, and the `configuration.publish` audit row of that publish carries `details.tests_failed:true`, `tests_failed_count`, `tests_refused_count`, `tests_not_run_count`, `tests_passed_count` and a `summary` sentence ("Published with failing tests: 1 failed, 1 didn't run, 2 passed."), never a test's name or body. The flag is part of the request's idempotency payload, so a retry of a request that carried it carries it too. A draft without tests, tests that all pass, and tests Vector skipped with a stated reason (a program that calls out; a device runs those for real) publish exactly as before with no extra field, so a client that sends no flag gets the 409 only when tests are failing. Publishing stays an Operator or Administrator action.

`GET /configurations/publish-requests/{request_id}` is restricted to current operators/administrators and their own keys. It returns `{request_id,found:false}` or `{request_id,found:true,version:PublishReceipt}`. The normalized key echo proves recovery support. A negative read is not proof that an earlier request failed or cannot still commit.

`GET /configurations/publish-requests?configuration_id=<UUID>&page=1&page_size=12` lists committed request metadata for the current account and exact required pipeline. It returns `{items,total,page,page_size}`; each item contains only `request_id`, `configuration_id`, `version_id`, `number`, `source_revision`, and `created_at`. Page size is at most 50, pages are positive safe integers, and unknown or duplicate query parameters are rejected. Count and page share a read snapshot; the query uses actor/pipeline/order indexing before pagination. No configuration, artifact, note, digest or original retry payload appears in this discovery response.

The browser retains the immutable actor/pipeline/key/revision/note request before transmission and requires a schema-checked exact lookup before a first send. It never falls back to unkeyed publication. Failed or unreadable responses retain the original request across reload. Recovery checks exact request, parent, source revision and note before accepting a receipt; it never replaces the current draft or infers identity from matching content or the latest version. Retry is explicit and reuses the original payload. Recent server requests support discovery after browser data loss but cannot reconstruct a retry payload. Confirmed publication remains confirmed if local reminder cleanup fails. These operations never deploy a version; device selection remains a separate explicit review.

## Recoverable agent-settings creation

`POST /policies` accepts an optional UUID `request_id` alongside `name` and the complete three-field `AgentPolicy`. The name is nonempty, is at most 120 UTF-8 bytes and follows the rule for names above (one line, no NUL). Legacy unkeyed requests remain supported. A keyed save returns the allowlisted original saved template `{id,name,policy,created_at,request_id,create_idempotency:true}`. The correlation fields are response-only and never part of the durable policy record.

Each key belongs to the current authenticated operator/administrator in the settings-creation namespace. It binds the canonical supplied JSON body excluding `request_id`; object key order is insignificant, while all supplied fields remain significant. A different payload under the same actor/key returns `409 IDEMPOTENCY_CONFLICT`. Template insertion, durable request mapping and `policy.create` audit commit atomically. An identical replay returns the same original template without a second save or audit. Current authorization and CSRF still apply before and inside the writer transaction. If the original template is unavailable, the mapping remains and a conflict prevents recreation under that key.

`GET /policies/requests/{request_id}` returns `{create_idempotency:true,request_id,found:false}` or `{create_idempotency:true,request_id,found:true,policy:PolicyCreateReceipt}` for the current account only. The normalized request echo, explicit capability marker and nested receipt identity must match before recovery is accepted. A negative lookup is not proof that an earlier in-flight save failed or cannot still commit.

`GET /policies/requests?page=1&page_size=12` returns `{create_idempotency:true,items,total,page,page_size}`. Each item contains only `request_id`, `policy_id`, nullable `policy_name` and the committed mapping's `created_at`. Names are bounded to 120 Unicode scalars. Page size is at most 50, pages are positive safe integers, and unknown or duplicate query parameters are rejected. Count and page share a read snapshot; per-actor ordering is creation time descending then request ID descending. This discovery endpoint never returns an original retry payload or reconstructs a missing browser reminder.

The dashboard retains the exact actor/request/name/policy operation before transmission and requires a compatible exact lookup before its first send. It never falls back to an unkeyed save. Post-begin failures keep the immutable operation available across reload; retry is explicit and reuses it. Current-account server history allows discovery when local data is unavailable. A verified result remains saved even if removing its browser reminder fails. Saving or recovering a settings template does not assign it, release devices, change desired generations or verify application. Applying it requires a separate explicit device-selection review.

## Bounded audit browsing and prepared exports

`GET /audit/history` returns `{items,total,page,page_size}` from one SQLite read snapshot. Optional `scope=changes` hides sign-in and sign-out activity (`login`, `login.*`, `logout`); `scope=security` shows only `bootstrap`, `login*`, `logout`, `account.*`, `user.*`, `mfa.*`, `signing.*` and `server.restore_access.*` events. Export bodies accept the same `scope`. Items are compact `AuditSummary` metadata; `GET /audit/{id}` adds allowlisted, action-specific `details`. `details.client_address` is shown to Editors, Operators and Admins only; Viewers read the same events without it (also in legacy `GET /audit`). Order remains original record time descending, then the durable insertion sequence descending, including after VACUUM. Names are current labels joined to exact IDs at the read snapshot, not claims about names at event time: `target_name` (an issue is named by the title of its code, built as the issue list builds it, and its device, such as `Vector rejected the configuration on edge-nyc-02`; every role that reads the log reads issues, so the name is the same for all of them), `actor` (an enrollment token that completed a device recovery is named by the token, `Recovery for edge-nyc-02`) and `device_name`, the current name of `device_id` or null. Invalid legacy times are null. Unknown raw JSON extensions, credentials and referenced configuration/artifact bodies never enter these projections. Legacy `GET /audit` remains an unbounded array for compatibility, now using the safe projection and retaining known flat issue/secret fields. Overview uses the same projection for its latest 20 events.

New successful `group.update` events record `previous_group_revision` and `group_revision` atomically with the group save. Event details and prepared exports expose these as optional nonnegative safe integers in `details`; compact history summaries do not include them. Older events without these fields remain absent rather than inferring revisions from the group's current state. The dashboard presents both recorded revisions in the main event details, including revision zero; missing values are labeled **Not recorded**.

History filters are `search`, `action`, `family`, `outcome`, `actor_id`, `device_id`, `target_id`, `from`, `to`, `page` and `page_size`. Defaults are page 1 and size 12; maximum size is 50 and pages must be positive JavaScript-safe integers. Search is a trimmed literal substring of displayed actor/target/action/outcome metadata, at most 200 Unicode scalars, with ASCII case-insensitive matching. Reasons and arbitrary details are not searchable. `action` is exact; `family` matches that action or a dot-delimited descendant, and the two are mutually exclusive. `outcome` and `actor_id` are exact. `target_id` matches the raw stored target or its stable typed target identity (including an immutable published version's parent pipeline). `from` and `to` are inclusive RFC3339 UTC timestamps with at most millisecond precision. Unknown, duplicate, malformed and overflowing parameters are rejected.

The optional `device_id` filter is a canonical UUID. It matches exact stored actor/target/device IDs and the canonical persisted UUID pairs in `deployment.release` and `device.recovery_complete` (both old and new recovery identities). A generation-recovery event may also carry the exact device UUID in its known details shape. Current groups, names and replacement membership are never used to infer historical involvement.

`POST /audit/exports` accepts the same filter object without page parameters and requires a current session plus CSRF. It prepares a complete private JSONL snapshot before returning `AuditExport`: `{id,filters,row_count,byte_count,sha256,created_at,expires_at,download_path}`. Its SHA-256 covers the entire finished file. `GET /audit/exports` lists up to two ready exports belonging to this user and originating session. `GET /audit/exports/{id}/download` requires that same user and original session; its attachment has exact Content-Length, no-store, and live authorization checks during transfer. `DELETE /audit/exports/{id}` requires the same owner/session and CSRF and returns `{ok:true}`. Discard prevents new downloads without truncating an active one. A ready file or initiated transfer is not proof the browser saved it. Export errors: 429 `EXPORT_BUSY` (two exports preparing, or four downloads active), 429 `EXPORT_CAPACITY` (two ready exports already held), 408 `EXPORT_TIMEOUT` and 413 `EXPORT_TOO_LARGE` (narrow the filters), 500 `EXPORT_STORAGE`. Viewers export events without `details.client_address`.

Each UTF-8 JSONL file contains one `metadata` record (`format: "vectory.audit.jsonl.v1"`, snapshot time/sequence, count, normalized filters, ordering and limits), then `{type:"audit",event:AuditDetail}` records, then `{type:"complete",complete:true,row_count,events_sha256}`. The trailer hash covers exact UTF-8 audit-record lines including their LF terminators. Count and hash are completed before the ready response. No partially prepared file can be downloaded.

Limits: 100,000 events, 128 MiB/file, two concurrent preparations, four concurrent downloads, four retained/preparing files globally and two per user across sessions, six preparation attempts/minute/user. Capacity is reserved before work; discarded or expired files with active handles still occupy their quota until those handles close. An OS deletion failure retains the reservation and is retried; it cannot silently free capacity while leaving the file on disk. Ready files expire after ten minutes and are removed on expiration/discard/startup; a restart invalidates prepared IDs. Preparation and transfer have 120-second cooperative application deadlines, including pool acquisition and backpressure; a stalled synchronous OS file operation cannot be forcibly interrupted. Preparation holds a read transaction for count, names and keyset rows, so SQLite WAL writers continue but that bounded snapshot can defer checkpoint reclamation. Failures and explicit row/byte limits return errors rather than silently truncating. Downloads recheck live authorization every 256 KiB, with a bounded in-flight buffer; revocation cannot retract bytes already handed to the network. Exact Content-Length makes an interrupted transfer distinguishable from the prepared complete file.

## Local secrets and signing continuity

Exact `vectory-secret:NAME` references are permitted only at the credential fields of the generated device-secret table, for the component's section and type: every field whose type resolves to Vector's `SensitiveString` (directly, optionally, as list items or map values) plus a short reviewed list of credentials Vector types as plain strings (TLS `key_pass`, the MQTT, Redis Sentinel and `prometheus_remote_write` basic passwords, the Okta token, and basic-auth `auth.user`/`auth.username`). `scripts/generate-secret-fields.mjs` writes the same table for the agent, the server and the dashboard; CI fails when a copy is stale. The agent substitutes only at its own copy: the server never chooses which fields receive device secrets, and local network allowances still constrain destinations. A reference anywhere else is refused by the server at draft save and publish and by the agent (`SECRET_REFERENCE_REFUSED`). A non-empty plain-text value at a credential field is refused with the fix "Use a device secret: vectory-secret:NAME, then bind it on each device with `vectory configure-secrets`."; native `SECRET[backend.key]`, `$NAME` and `${NAME}` references stay valid there, and `auth.user`/`auth.password`/`auth.token` of any sink keep refusing plain text. Published versions are never rewritten. The isolated check replaces each reference with a placeholder, so Vector still checks options, VRL and topology, and reports `deferred_reasons: ["device secrets"]`. Names map to protected absolute files configured by the host operator. Agents report the bound names (never files or values) as `secret_names`, at most 64, sorted, to servers that list the `secret_names` feature; the device keeps the latest list and a heartbeat without the field removes it. Resolution is literal JSON-string replacement, not a shell, environment interpolation, structural templating or remote secret distribution. The agent verifies pinned file handles, rejects unsafe links/permissions, applies the effective local capability policy, and runs actual Vector validation. Secret-bearing diagnostics omit subprocess output. Rendered working/recovery artifacts remain private; server history, exports and ordinary API responses retain references only.

Published versions mark `uses_local_secrets` after static reference validation. Heartbeats may include `applied_template_sha256` and monotonic `secret_revision`; `actual_sha256` always means actual effective managed bytes. Ordinary versions still require exact equality to the published artifact digest. For a secret-bearing version, verification additionally requires the current template digest and nonregressing secret evidence. A local file rotation triggers a tracked, journaled attempt and verified activation even at the same desired configuration generation. Failed/rolled-back attempts never become a new verified last-good artifact.

Signing-key rotation is a stopped-server maintenance operation. Each active credential is bound to the signing key it trusts; the server retains bounded old keys until authenticated renewal conveys new trust. Key pruning cannot remove a key referenced by an active credential. Restoring an old server backup must fence generations above explicitly collected per-device high-water marks; it never resets the agent's accepted counters. See the maintenance CLI and backup/restore guide for the review/apply procedure.

### Device CA rotation

The dedicated device CA (`keys/device-ca.pem`) issues every device certificate. `vectory-admin rotate-device-ca` (stopped server, exclusive data-directory lock) creates a new CA and keeps the replaced one as `keys/device-ca-previous.pem` (certificate only; its private key is not kept). From the next start, enrollment and renewal issue certificates only from the new CA, and client certificates chained to either CA pass TLS. TLS alone never authenticates: every request still needs the certificate's registered fingerprint, unexpired, unrevoked, on an unrevoked device, including pooled connections. Devices move to the new CA at their next renewal (in their certificate's last day, so within the 30-day lifetime); no agent change is needed. The manifest signing key is separate and unchanged by a CA rotation. Only one overlap exists at a time: rotation refuses while a previous CA is trusted.

Each credential records its issuing CA (`credentials.ca_id`, the SHA-256 of the CA certificate DER; NULL for credentials issued before this was recorded, which count as the previous CA's). `vectory-admin retire-device-ca` checks, and with `--apply` removes, the previous CA only when no unrevoked device holds an unexpired, unrevoked credential from it; otherwise it refuses and names them. A renewed device's superseded certificate keeps counting for the 24-hour renewal fallback. After retirement, certificates from the old CA fail the TLS handshake (a Go client that withholds a certificate the server's request doesn't name is simply unauthenticated). A rotation that stops midway is finished or undone at the next start: it stages `device-ca-next*.pem`, commits by writing `device-ca-previous.pem`, then renames the key and certificate into place; files that don't belong together stop the server with a restore-from-backup message. The older manual overlap, `VECTORY_PREVIOUS_DEVICE_CA`, still adds its bundle for as long as it is set, and the server logs a warning when it does.

`GET /settings` reports `device_ca:{current:{sha256,subject,not_before,not_after},previous:{sha256,subject,not_before,not_after,devices,device_names,last_expires_at}|null}` to any signed-in role: `devices` counts the devices still holding certificates from the previous CA, `device_names` lists up to 20 of them and `last_expires_at` is when the last such certificate expires. Audit events `signing.device_ca.rotate.prepare` (target `old:new`), `signing.device_ca.rotate` and `signing.device_ca.retire` record the maintenance as `local-admin`.

Device `effective_policy` is the current resolved server policy, read-only on device responses. Pause/resume previews copy its check-in and telemetry fields and only change `sync_paused`; bulk selections require matching settings to avoid silently replacing different device policies. These are complete reviewed policy deployments, not a remotely writable capability profile.

Configurations using the pinned platform-specific sources `dnstap`, `file_descriptor`, `journald` and `windows_event_log`, device paths, environment, secrets, enrichment data, external code, Lua steps or AWS instance metadata steps remain `deferred:true` with concrete `deferred_reasons`: each device validates them with its own Vector and environment. They are still statically checked with placeholders and stand-ins, so unrelated VRL, option and topology errors are reported before publication. Unknown component names alone never defer and are rejected by the configured native validator.

Pipeline draft saves also accept optional `name` and `description` alongside the required `revision`, `config` and `graph`. Metadata edits share the draft CAS check, authorization and audit trail. Omitted metadata is preserved; stale edits cannot overwrite a newer draft.


### Reviewed replacement

`POST /deployments/preview` and `POST /deployments` accept optional `replaces: UUID[]` (at most 100 distinct lowercase IDs, part of the idempotency payload). Each ID names an existing candidate assignment (active, paused, completed, cancelled or failed) of the same resource that selects at least one reviewed device; otherwise the request returns `409 REPLACEMENT_CHANGED` (or `400` for another resource). Replacement is explicit and reviewed: without `replaces`, equal-priority different payloads still conflict and no identity or time tie-breaker exists.

A replacing deployment defers to the assignment it replaces on each device until it releases that device; the release retires the replaced assignment there in the same transaction (target row `removed`, history retained; a persistent selector also excludes the device). Cancelling a canary before a device's release therefore leaves that device on the replaced assignment. When nothing remains for the replaced assignment to deliver (for a persistent one: its whole selector is covered by a persistent replacement), it becomes `unassigned` with `status_before_removal` preserved and `replaced_by: [{deployment_id,device_count,at}]`. Each retirement audits `deployment.replace` on the replaced assignment.

Preview additionally returns: per outcome `winner` (the current winning `AssignmentDescription`, possibly unreleased) and `replaces`; outcome `replace` when the device moves from a requested replacement; `replacements` (`{assignment,device_ids,retires_assignment}`); `suggested_replaces` (current winners of the same pipeline, or any agent settings, whose payload differs, plus every assignment of the pipeline's lineage that still binds a reviewed device at or above the requested priority: its own cancelled or rolled-back deployments and rollbacks whose `rollback_of` chain leads to one, so redeploying a fix after a rollback takes one review); `replacements_needed` (every existing assignment, at any tier at or above the request, whose different payload keeps a reviewed device from taking it, so one "Replace existing" resolves the review); `suggested_priority` (their highest priority, to reuse); `winning_priority` (lowest priority that outranks every blocking winner, or null); `paused_device_ids` (configuration targets with sync paused); `configuration_name` (the previewed version's pipeline name, null for agent settings); and `assignments` display metadata on each conflict. `AssignmentDescription` carries names, numbers, priority, target mode, status, policy values and, optionally, `created_by_name` and `rollback_of` (the deployment a rollback rolled back) only.

`POST /deployments/binding-suggestions {version_id,device_ids}` (Operator/Admin, CSRF; at most 10,000 device IDs) returns `{devices:{<device_id>:{<name>:value}},sources:{<device_id>:{deployment_id,version_number,configuration_id,configuration_name}}}`: for each device, the nonsecret variable values it last received (released target, generation > 0) from a deployment of the same pipeline, newest first, limited to names the requested version declares with the same scalar type. Values still missing come from the pipelines it was duplicated from (nearest first, at most four); unrelated pipelines never contribute. A rollback in between, which binds no values, does not hide them. Nothing is written or audited; the dashboard uses it to prefill a new version's device-specific values.

Policy deployments may carry `policy_id`, the saved settings they apply; the policy must equal their current values (409 otherwise). Devices' `assignment`/`policy_assignment` add display provenance: `name`, `target_mode`, `status`, `policy_id`, `policy_name`, `created_at`, `created_by_name`.

A rollback restores another deployment's version, often of another pipeline, so clients name the pipeline whenever it differs from the deployment's own. A rolled-back source keeps its functional status (`cancelled`, or `unassigned` at the priority ceiling) and records the status it had; the replacement records `rollback_of`. ### Deployment table ordering

`GET /api/v1/deployments/history` additionally accepts `sort=name|status|verified|created_at|scheduled_at` and `direction=asc|desc`. Defaults remain `created_at` and `desc`. Ordering applies to the whole filtered result before pagination, with UUID ascending as the final tie-break and unavailable values last. Name uses the visible deployment/pipeline/agent-settings fallback; status uses its displayed label. Verified sorts the persisted `verified_applied` count, then total target count in the same direction; it does not treat written/downloaded states as verified.

`GET /api/v1/deployments/{id}/targets` additionally accepts `sort=device_name|state|generation` and `direction=asc|desc`, defaulting to `device_name` and `asc`. Name falls back to the original device UUID, state uses its progress label, and UUID ascending is the final tie-break. Existing exact-parent/state/search restrictions and snapshot count/page consistency remain. Unknown or duplicate sorting parameters are rejected. These are read-only browsing controls and do not change rollout order.

`GET /api/v1/configurations/library` also accepts optional `direction=asc|desc` for both existing `sort=updated|name` values. Omission preserves updated descending/name ascending; explicit direction applies globally before pagination. Updated ties use name ascending then ID; name ties use ID ascending.

`GET /api/v1/issues/history` additionally accepts `sort=code|device|last_seen|count|disposition` and `direction=asc|desc` (defaults last_seen descending). Sorting uses only bounded projected metadata, before pagination; issue ID ascending breaks ties, unavailable timestamps are last. `GET /api/v1/audit/history` additionally accepts `sort=action|actor|outcome|created_at` and `direction=asc|desc` (defaults created_at descending), applying global metadata order before pagination. ## Recoverable device identity authorization

Administrator-only `POST /api/v1/devices/{id}/recover` accepts either legacy `{}` or strict `{request_id, expected_name}`. A new correlated request must match the reviewed source name exactly. The immutable ledger binds the acting account and request UUID to the source device UUID and payload digest. A successful first reply is `{request_id, request_correlation:true, device_id, token, record}`. Replays return status, never the original plaintext token; a different source or payload under that key conflicts. The secret is retained only as a verifier in the token table, never in the request ledger.

`GET /api/v1/devices/{id}/recovery-requests/{request_id}` returns the echoed request/source identity and either `found:false` or `found:true, state:created|cancelled, record`. Created records always identify the original token, including its current use/revocation status. Cancelled records are revoked or null. Recovery records bind `recovery_device_id` and `recovery_name`, allow exactly one use and no name prefix. Initial receipts require uses zero and revoked false. Status/source/payload identity must be checked before accepting a result; a negative lookup is not a cancellation fence.

`POST /api/v1/devices/{id}/recovery-requests/{request_id}/cancel {}` atomically records a permanent cancellation tombstone and revokes only the mapped token, if present. A cancel-before-create tombstone binds the source UUID without a payload digest and blocks any late creation under that key. Cancellation remains possible after the source is retired or absent. Repeated cancellation adds no duplicate success audit. The live administrator session and CSRF are checked again inside the writer transaction.

Cancellation does not undo completed device replacement or revoke the replacement's credentials. Host enrollment replay remains bound to its original pending request/key and token. A host that started recovery must retain its original staged files; cancellation can block an unfinished token-authorized enrollment or replay, including a server-accepted reply whose credentials never reached the host. Dashboard request recovery must not imply that another authorization safely replaces a token already used by a host.

## Device access revocation

Operators and Admins can read `GET /api/v1/devices/{id}/revocation`, which returns the exact `device_id`, `revocation_status:true` protocol marker and boolean `revoked`. `POST /api/v1/devices/{id}/revoke {}` requires CSRF and returns the same identity and marker with `revoked:true, ok:true`. Both routes validate UUID and request shape. Clients must validate the schema and echoed UUID before accepting the state. A status read describes the identity's current state, never which request or actor caused it.

Revocation is terminal for a device UUID. The writer transaction rechecks the live Operator/Admin session, revokes credentials, removes group membership and current persistent assignment targets, and records one success audit. An already revoked device is a true no-op with no repeated write, audit, membership revision or target churn. Historical snapshot and stopped assignment targets remain intact. There is no per-request revocation ledger; exact current state is sufficient for this monotonic operation. Recovered replacement identities are distinct and unaffected by a request for the old UUID.

The dashboard retains nonsecret actor/device intent before sending and bounds status and mutation waits. A missing or malformed reply triggers read-only reconciliation; it never triggers an automatic second POST. A current `revoked:false` read permits a separately reviewed confirmation, while warning that an earlier request may still arrive. Request abort is a client wait boundary, not a server cancellation. Exact captured reminder bytes prevent stale cleanup from deleting a peer's newer record; unavailable storage blocks new mutation. Revocation does not remotely stop Vector, erase host files or establish workload health.

## Effective configuration per device

Two additive reads answer "what was this device offered, is it what runs, and what changed?". Both are `GET`, open to any authenticated role (the role that reads a pipeline version), answer with `Cache-Control: no-store`, read one SQLite snapshot, take no writer lock, write nothing and add no audit row. An unknown device is `404 NOT_FOUND` exactly as `GET /devices/{id}` answers; a revoked device stays readable as history. Each is limited to 240 (`configuration`) and 60 (`configuration/diff`) requests a minute per account (`429 RATE_LIMITED`). Query parameters are strict: an unknown, repeated or malformed one, or a generation that is not a plain positive whole number up to 2^53-1, is `400 INVALID_INPUT`. Nothing here changes an existing route or shape.

- `GET /devices/{id}/configuration[?generation=N]` -> `DeviceConfiguration {device_id,generation,current,offered_at,version,sha256,size,format,content,uses_local_secrets,variables,running,previous,generations}`. `generation` defaults to the device's current desired generation; `?generation=N` reads an earlier generation this device was offered, `404 NOT_FOUND` when it never had it (another device's generation is never reachable here). `version` is the immutable template identity `{id,number,configuration_id,configuration_name}` and `content` is exactly the bytes the device was offered and downloads, from the immutable `artifact_blobs` store: at most 1 MiB, `sha256` and `size` describe it, and `format` is `json` for what the server renders (detected from the bytes). The server never sees a device-local secret: a `vectory-secret:NAME` reference is still the reference, and no response field ever holds a value a host resolved. A generation assigned before artifacts were stored per generation is its version's own artifact (`offered_at:null`), as check-ins serve it; one that needs device values and has no stored artifact is `409 CONFLICT`.
- `variables` lists the version's declared variables in declaration order, `{name,path,type,value,source}`. `value` is read out of the offered bytes at the declared path, so it is what the device received; it is null, never shown, when the declared field is a structural or credential field or the value is a secret or a reference to one. `source` is `device` (a value set for this device), `default` (the deployment's default) or null when no deployment of this device explains the value (a rollback binds none); `group` is reserved for group-level defaults and is not sent yet. A deployment explains the offered bytes only when its bindings hold exactly the value each shown variable carries.
- `running` is `{sha256,template_sha256,matches,matches_generation,reported_at}`. `sha256` is the managed file's digest as the agent last reported it (`actual_sha256`), null when it reports none; `reported_at` is the device's last check-in. `matches` is `true` when that digest is the digest of `content`, `false` when the agent reports a different one (a local edit, or an activation not finished: the device still runs an earlier offer) and `null` when there is nothing to compare: no digest reported, nothing offered, or a revoked device, which can no longer report. A version that reads device secrets is written to the host with the host's own values in place of its references, so its file never has the offered digest; for it the agent also reports `template_sha256`, the offered digest it applied, and `matches` is `true` when that is the offered one and the file's digest is the one the server verified, `false` when another template was applied or the file changed since (an edit, or a rotation not yet verified) and `null` when the agent reports no template digest and the file is not an earlier offer, or nothing was verified yet. `matches_generation` names the newest generation this device was offered whose artifact the agent reports running (by file digest, or by `template_sha256`) when that is not the one in the response, also when nothing is offered now; it is null when the digest was never offered to this device, because the server never sees a local file and never claims what one contains. A reported digest equal to an offered one proves identical bytes, nothing more.
- `previous` is `{generation,version,sha256}` of the newest generation offered before this one, null when there is none; its bytes can equal the current ones (a retry, or a version that only moved nodes). `generations` is `{total,items}`: the offered generations, newest first, at most 50 items, each `{generation,version,sha256,offered_at}`. With nothing offered at the current generation (a device never assigned, or whose assignment was removed) `version`, `sha256`, `size`, `format`, `content` and `offered_at` are null, `variables` is empty, `current` is true and `previous` names the last offer.
- `GET /devices/{id}/configuration/diff[?from=N][&to=M]` -> `DeviceConfigurationDiff {device_id,from,to,identical,counts,hunks,unified,truncated,total_lines,approximate}`. `to` defaults to the current generation (`404` when nothing is offered now), `from` to the generation offered before `to`; either named generation must have been offered to this device (`404` otherwise). With nothing before `to`, `from` is null and the diff is empty. `from` and `to` are `{generation,version,sha256,size,offered_at}`. The comparison is by line over the pretty-printed JSON the server renders, so a changed setting is a changed line. `counts` is `{added,removed,changed}` lines of the whole change (a line another stands in for counts once, as changed). `hunks` are `{old_start,old_lines,new_start,new_lines,section,lines}` with three lines of context; two changes at most six unchanged lines apart share a hunk, and `section` names the components around the first changed line as dotted keys (`sinks.out.buffer`), null at the top level. Each line is `{kind:"context"|"removed"|"added",old_line,new_line,text}`. `unified` is the same hunks as a unified diff after `--- generation N` and `+++ generation M`. It has at most 2,000 lines, headers and marker included: a longer diff is cut, `truncated` is true, the last line of `unified` is `\ Diff truncated: showing X of Y lines` and `hunks` stop at the same line, while `counts` and `total_lines` (the length the whole diff would have) describe all of it. A change needing more than 2,000 line edits (about 1,000 replaced lines), or more than 50 million comparison steps, is not matched line by line: the region between the unchanged start and end is shown as removed and added, and `approximate` is true when the two sides share lines that a matched diff would have kept (false when they share none, which makes that exact). Identical bytes give `identical:true` and no hunks.

## Check on devices

Before deploying, an operator can ask the target devices to validate a candidate pipeline version on their own hosts. Everything here is additive and optional: an older agent against this server, and this agent against an older server, keep working with the original shapes. A check is advisory. It never creates or changes a deployment, a desired state, a generation, a policy or an issue, the Deploy action never depends on it, and no device activates anything because of it.

- **Request.** `POST /deployments/preview` accepts `device_validation: true` and `run_tests` (booleans, default false; `run_tests` is stored with the check and does nothing alone). Operators and administrators, CSRF, as for every preview. Both fields leave the body before it is checked as a deployment, so `POST /deployments` still refuses them as unknown fields; a value that is not a boolean is `400 INVALID_INPUT`, and agent settings (`policy`) cannot be checked (`400`). The response keeps its shape and gains `validation_id` and `validation_truncated` when a check was asked for and at least one device was addressed. The preview runs first and writes nothing; the transaction keeps only the check. A check addresses the reviewed devices that are not revoked, the first 50 by name (digits compare by value, as the Devices page orders them), and `validation_truncated:true` says more were reviewed; one request also stores at most 10 MiB of candidate bytes, and a device past that is left out the same way. Six requests a minute per user: the seventh is `429 RATE_LIMITED` with `Retry-After` and creates nothing, and `429 CAPACITY_BUSY` with `Retry-After: 60` answers while 128 MiB of candidates wait for answers. A request is audited as `deployment.device_validation_requested` (target: the version) with `details:{validation_id,configuration_id,version_id,run_tests,truncated,device_count,pending_count,offline_count,unsupported_count}`: counts and the pipeline version's identity, never the configuration or an artifact. A check that addressed no device creates no row and no audit event.
- **What each device is asked to check.** The artifact the review computed for it: the version with that device's own variable values applied and device secrets still `vectory-secret:NAME` references, so its bytes and digest equal that device's `artifact_previews` entry. The server keeps those bytes (at most 1 MiB each) with the device's row only while the check is pending; the answer, the expiry, a newer check for the same device and the device's revocation all remove them.
- **States.** Decided when the check is requested, without waiting: `offline` when the device's last check-in is older than three of its own check-in intervals or it never checked in (the rule of its Offline status), else `unsupported` when its latest check-in did not announce `validation` in `agent_features`, else `pending`. A pending device becomes `passed` or `failed` when it answers (`valid`), and `expired` when ten minutes pass after the request, when a newer check for the same device is requested (one outstanding check per device: the older one ends then, whoever asked), or when the device is revoked or replaced by a recovery. A check is `running` while any device is `pending` and `complete` otherwise. The expiry is read from the clock whether or not the minute-by-minute job has recorded it.
- **Delivery.** A device learns of its check from the manifest of its next check-in. Once the check has committed, the server also answers the parked `GET /wait` of each device that is `pending` in it with the ordinary `{"changed":true}` (see above), so a device that holds a wait checks in within seconds and every other one at its own schedule. The answer is only a hint: it names no check, the device acts only on what its signed manifest carries, and a device that is `offline` or `unsupported`, or outside the request, is not answered.
- `GET /device-validations/{id}` -> `{id,state:"running"|"complete",created_at,expires_at,truncated,run_tests,devices:[{id,name,state:"pending"|"passed"|"failed"|"offline"|"expired"|"unsupported",valid?,diagnostics,tests,secrets_missing,duration_ms?,updated_at}]}`, at most 50 devices in name order. Operators and administrators; the requester or an administrator reads it, and anyone else gets the `404` an unknown ID gets (a malformed ID or any query parameter is `400`); 240 reads a minute per account. `name` is the device's name when the check was requested. `valid` and `duration_ms` appear only with an answer, and `diagnostics`, `tests` and `secrets_missing` are empty arrays without one. `updated_at` is the last change of that device's row (the expiry's time for a device that ran out). Rows, answers included, are kept 24 hours by the existing retention job; a pruned ID is `404`.
- **Manifest.** `features` lists `validation`. `desired` gains optional `version_number` and `configuration_name` for `vectory status`: the version's number within its pipeline, and the pipeline's name as the server shows it (cut to 120 characters, left out when empty or holding a control character, a line or paragraph separator or a text-direction control). They are signed like the rest, always describe `desired.version_id`, and older agents ignore them. They are display facts, not identity: the name changes at an unchanged generation when the pipeline is renamed, so an agent keeps both out of the identity it compares for a repeated generation. The manifest also gains `validation:{id,sha256,size,artifact_path,run_tests,expires_at}`, at most one, only while the device has an unexpired, unanswered check and announced `validation` in the very heartbeat the manifest answers. It is bound to the recipient device and the nonce like every member, `artifact_path` is `/agent/v1/artifacts/{sha256}` of that digest, `expires_at` is ten minutes after the request, and an agent ignores a check whose `expires_at` is in the past or later than 15 minutes after `issued_at`. `id` is shared by every device of one request; with the device it names the row.
- **Heartbeat.** After a verified manifest lists `validation` an agent may send `agent_features` (`["validation"]`: at most 16 names of `[a-z_]{1,32}`; names the server does not know are kept as given and never acted on), `readiness` (`{data_dir_writable?:boolean,allowed_listener_count?:integer 0..1000000}`: booleans and counts only) and `validation_result:{id,valid,diagnostics?,tests?,duration_ms?,secrets_missing?}`: at most 20 diagnostics (the existing record, redacted on the device, each at most 512 serialized bytes; the server keeps errors first), at most 100 tests `{name (1 to 200 bytes, without a character that can't be shown safely in one line),passed,not_run?,message? (up to 512 bytes)}`, `duration_ms` 0 to 86,400,000 and at most 64 `secrets_missing` names (each unique and shaped like a device-secret name: a letter, then up to 63 letters, digits, `_`, `.` or `-`; the server stores them sorted; names only, never a path or value); the answer as the server stores it is at most 128 KiB serialized, and a larger one is refused like any malformed one. The agent sends the answer in every heartbeat until the manifest it receives no longer carries that `validation.id`. Every member is optional and null counts as absent, also inside `validation_result` (`diagnostics`, `tests`, `duration_ms`, `secrets_missing`, a test's `not_run` and `message`) and `readiness`; the keys inside them are allowlisted, and anything else refuses the whole heartbeat atomically (`400 INVALID_INPUT`, nothing written), so an agent must not resend an answer the server refused. The device record keeps the latest `agent_features` and `readiness`, as reported, and drops them when a check-in omits them; `GET /devices/{id}` shows them. An answer counts only for that device's own pending, unexpired check: one for an unknown ID, another device's check, a check already answered or one that expired is ignored (never an error), and a repeat never overwrites. An answer changes nothing but its row: the same heartbeat's apply state, generations, policy and issues are handled exactly as without it.
- **Download.** `GET /agent/v1/artifacts/{sha256}` keeps authorizing the device's current desired artifact exactly as before and additionally authorizes the digest of this device's own pending, unexpired check. It never authorizes another device's candidate, nor one that was answered, superseded or expired, or whose device was revoked; every other refusal is the desired artifact's. A device with nothing deployed can fetch its candidate.

## Agent updates

A team turns agent updates on, a host consents to them when it is enrolled or upgraded, and a host installs an agent build only when a key it pinned signed it. [ADR 0015](../docs/adr/0015-operator-issued-agent-updates.md) gives the reasons and [the threat model](../docs/security/THREAT-MODEL.md#agent-updates) the attackers; where either differs from this section, this section is the contract. Everything here is additive: older agents, older servers and a server with updates off behave as they did. The shared vectors in `contracts/fixtures/agent-release/` (`vectors.json`, `report.json`, `examples/` and its `README.md`) state what a server and an agent must both do with release files, key lines, the key bundle and the heartbeat member; `node contracts/fixtures/agent-release/generate.mjs --check` keeps them current and keeps this section quoting its examples word for word.

**Off and on.** While updates are off (the default), every route below except `GET /api/v1/agent-updates` and `PUT /api/v1/agent-updates/settings` answers `404 AGENT_UPDATES_OFF`, both agent-listener routes answer `404`, the manifest lists no `agent_update` feature and carries no offer, an agent sends no `agent_update` member, and `Device` omits `agent_update`. Reads are open to every signed-in role. Every mutation needs CSRF and is authorized again, with its revision or request identity, inside the writer transaction. `current_password` is checked as everywhere else (`403 WRONG_PASSWORD`). Timestamps are RFC 3339 UTC with `Z`. A *fingerprint* is the lowercase hexadecimal SHA-256 of a public key's 32 raw bytes, and its first 16 characters are the *short ID* the dashboard and `vectory update status` print. A *version* is `major.minor.patch`: three numbers, each `0` or one to nine digits that start with 1 to 9, and nothing else (no pre-release or build suffix). A *reason* (a stop, a withdrawal, a revocation) is 1 to 500 Unicode scalar values after trimming, with no control character.

| Action | Roles |
| --- | --- |
| Read the settings, keys, releases, rollouts, targets and each device's update state | Every signed-in role |
| Turn updates on (choosing custody) or off, rotate or revoke a key, upload a rollover statement for the offline key | Administrator, with the password |
| Prepare a release (with server custody, sign it), upload its signature, withdraw it | Administrator |
| Preview, start, pause, resume and cancel an update rollout; Stop all updates | Operator, Administrator |
| Clear Stop all updates | Administrator |

### Settings and custody

- `GET /api/v1/agent-updates` -> `AgentUpdates {enabled,custody,revision,current_key,stopped,active_rollouts,fleet,frozen_devices,catalog}`. It answers while updates are off. `custody` is `"server"` (the server generates, seals and uses the release key), `"offline"` (the team keeps the private key and the server holds the public half) or null until a key exists; it stays what it was when updates are turned off. `revision` starts at 0 and advances when `enabled`, `custody`, the current key or the stop state changes, never when a release takes a counter. `current_key` is the `AgentReleaseKey` new releases are signed with: null until a key exists and after it was revoked; it stays while updates are off. `stopped` is null or `{reason,by_name,at}`. `active_rollouts` counts update rollouts that are `active` or `paused`. `fleet`, `frozen_devices` and `catalog` are null while updates are off. Otherwise `frozen_devices` is `{total,items:[{device_id,device_name,rollover_conflict}]}`, the non-revoked devices whose latest report carries a `rollover_conflict` (hosts frozen on a fork until they are re-pinned; at most 20 items, by name), and `fleet` is `{devices_total,versions:[{version,devices}],levels:{automatic,ask,off,cannot_update,not_reported}}` over non-revoked devices: `versions` lists the agent versions the fleet reports, newest first, at most 50 (an agent version that is not a valid version counts under `"unknown"`, last); `levels` puts each device in exactly one bucket, tested in this order, so the five add up to `devices_total`: `not_reported` (no `agent_update` report), `cannot_update` (its `eligibility` is not `eligible`), then `off`, `ask` or `automatic` by its `consent`. `catalog` lists each version of this server's agent catalog (`install::catalog`) that is newer than the agent version of at least one non-revoked device, newest first, at most 20: `{version,platforms:[{os,arch}],devices_behind,release:{id,state}|null}`, where `devices_behind` counts the devices running an older version and `release` is the newest release of that version that is not withdrawn.
- `PUT /api/v1/agent-updates/settings {enabled,custody?:{kind:"server"|"offline",public_key?},current_password,revision}` -> `AgentUpdates` (Administrator, password, CSRF). A stale `revision` is `409 STALE_REVISION`. The custody is chosen once, when updates are turned on, and is fixed while they are on; a key changes only through `rotate` or `rollover` below. `kind:"server"` has the server generate a key and seal it with the instance's AES-256-GCM key (associated data `agent-release-key:<fingerprint>`, file `keys/agent-release-<fingerprint>.sealed`); `kind:"offline"` takes the team's public key line in `public_key` (`422 RELEASE_KEY_INVALID` when it is not a valid key line, `409 RELEASE_KEY_IN_USE` when it equals the server's manifest signing key, the device CA's key or a key already registered). Unknown members, `custody` with `enabled:false`, a `public_key` with `kind:"server"` and `kind:"offline"` without a `public_key` where one is needed are `400 INVALID_INPUT`. With no current key (updates were never turned on, or the key was revoked) `enabled:true` needs `custody` (`409 CUSTODY_REQUIRED`). With a current key and updates off, an omitted `custody`, or the current kind without a `public_key`, turns updates on with that key and needs no re-pinning, and the other kind registers or generates a new key and retires the old one without any statement: hosts that pinned the old key take the new one only through the Upgrade agent command, and the settings page lists them. With a current key and updates on, `custody` may only be omitted or repeat the current kind without a `public_key`; any other `custody` is `409 CUSTODY_LOCKED`, and so is the current kind with a `public_key`. `enabled:false` is `409 AGENT_UPDATE_ROLLOUTS_ACTIVE` while any update rollout is `active` or `paused` (cancel it, or Stop all updates), and otherwise keeps keys, custody and the stop state. A request that changes nothing succeeds with no revision change and no audit row. Audit: `agent_update.enable` (details `custody` and the current key's `fingerprint`) and `agent_update.disable`.
- `POST /api/v1/agent-updates/stop {reason}` -> `AgentUpdates` (Operator or Administrator, CSRF). In one transaction it cancels every `active` or `paused` update rollout (`cancel_reason:"stop"`, unstarted offers withdrawn, devices already applying finish), makes the download route refuse, answers the parked wait of every device that held an offer (`wake::ask`) and refuses new rollouts (`409 AGENT_UPDATES_STOPPED`) until the stop is cleared. Stopping a stopped server changes nothing and keeps the first reason. A device that already downloaded a build can start applying it until its next check-in reaches it: within seconds for an agent holding a wait, within its check-in interval plus 30 seconds otherwise. Audit `agent_update.stop`.
- `POST /api/v1/agent-updates/stop/clear {revision}` -> `AgentUpdates` (Administrator, CSRF). It clears the stop and resumes nothing (`409 STALE_REVISION`; `409 CONFLICT` when nothing is stopped). Audit `agent_update.stop_clear`.

### Release keys

`AgentReleaseKey {fingerprint,public_key,custody,state,created_at,created_by_name,retired_at,revoked_at,revoked_reason,introduced_by,devices_pinning,device_names}`: `public_key` is the key line ([formats](#formats)), `state` is `current`, `retired` or `revoked`, `introduced_by` is the `{statement,signature}` envelope (base64) of the rollover that made it current, or null, and `devices_pinning` counts the non-revoked devices whose latest report lists the fingerprint (`device_names`: up to 20 of them, by name). There is one `current` key at a time. The server never registers a key equal to its manifest signing key, the device CA's key or one it already holds (`409 RELEASE_KEY_IN_USE`).

- `GET /api/v1/agent-release-keys` -> `AgentReleaseKey[]`, newest first, at most 64. This is the only place custody is published: the unauthenticated key bundle has none.
- `POST /api/v1/agent-release-keys/rotate {current_password}` -> `AgentReleaseKey` (Administrator, password, CSRF). Server custody only (`409 CONFLICT` otherwise): the server generates the successor, signs a rollover statement from the current key to the successor with the current key, makes the successor current and retires the old key. Audit `agent_release_key.rotate`, `details.source:"server"`.
- `POST /api/v1/agent-release-keys/rollover {statement,signature,current_password}` -> `AgentReleaseKey` (Administrator, password, CSRF). Offline custody only (`409 CONFLICT` otherwise): rotating the offline key within its custody. `statement` is the base64 of a rollover statement (at most 1,024 bytes) and `signature` the base64 of its 64-byte signature ([formats](#formats)). Malformed JSON or base64 is `400 INVALID_INPUT`, a `to` that is not a valid key line `422 RELEASE_KEY_INVALID`, a signature that does not verify under the `from` key `422 RELEASE_SIGNATURE_INVALID`, a `from` that is not the current key `409 CONFLICT` and a `to` the server already holds `409 RELEASE_KEY_IN_USE`. On success the `to` key becomes current, the `from` key retired, and custody stays `offline`. Audit `agent_release_key.rollover`, `details.source:"upload"`. Custody never changes by a statement; changing it is turning updates off and on again with the other kind.
- `POST /api/v1/agent-release-keys/{fingerprint}/revoke {reason,current_password}` -> `AgentReleaseKey` (Administrator, password, CSRF). In one transaction it marks the key `revoked`, withdraws the releases signed only by it, ends the rollouts that offer them (`cancel_reason:"key_revoked"`), removes the key and the statements it signed from the key bundle and stops offering anything it signed. Revoking the current key leaves `current_key` null: `custody` is then required again and a release cannot be prepared (`409 CUSTODY_REQUIRED`). `404 NOT_FOUND` for an unknown fingerprint, `409 CONFLICT` when already revoked. Audit `agent_release_key.revoke`.

### Releases

`AgentRelease {id,version,counter,state,expired,manifest_sha256,issued_at,expires_at,signer,artifacts,prepared_by_name,prepared_at,withdrawn_at,withdrawn_reason,rollouts}`: `state` is `awaiting_signature`, `ready` or `withdrawn`; `expired` is true once `expires_at` is not in the future (a release that is expired is not offered, cannot start a rollout and ends the rollouts that were still offering it, as `cancelled` with `cancel_reason` `release_expired`); `manifest_sha256` is the SHA-256 of the stored manifest bytes, the digest a host reports as `release`; `signer` is `{fingerprint,custody}` or null until a signature is stored; `artifacts` is `[{os,arch,file,size,sha256}]` as in the manifest; `rollouts` lists `{id,status}` of the update rollouts of this release, newest first, at most 50.

- `GET /api/v1/agent-releases` -> `AgentRelease[]`, newest first by `prepared_at`, at most 100.
- `POST /api/v1/agent-releases {version}` -> `AgentRelease` (Administrator, CSRF). It prepares the release of a version in this server's catalog. A `version` that is not a valid version is `400 INVALID_INPUT`; one the catalog does not hold is `409 RELEASE_NOT_IN_CATALOG`; a release of it that is not withdrawn is `409 RELEASE_EXISTS`; no current key is `409 CUSTODY_REQUIRED`; more than 20 releases that are not withdrawn, or more than `VECTORY_AGENT_RELEASE_STORAGE_BYTES` (default 2 GiB) in the release store, is `507 RELEASE_STORAGE_FULL`. In one transaction it copies each catalog entry of that version (one per platform), re-hashed, into `artifacts/agent-releases/<sha256>`, assigns the next counter ([counters](#counters-and-the-release-sequence)), builds the manifest ([formats](#formats)) with `issued_at` now and `expires_at` 180 days later, and stores its exact bytes. With server custody it signs at once (state `ready`; audit `agent_release.prepare` and `agent_release.sign`); with offline custody the state is `awaiting_signature` (audit `agent_release.prepare`).
- `GET /api/v1/agent-releases/{id}` -> `AgentRelease` (`404 NOT_FOUND`).
- `GET /api/v1/agent-releases/{id}/manifest` -> the stored manifest bytes exactly, in any state: `Content-Type: application/json`, `Content-Disposition: attachment; filename="release.json"`, `Content-Length`, `ETag: "<manifest_sha256>"`, `Cache-Control: no-store`.
- `PUT /api/v1/agent-releases/{id}/signature` (Administrator, CSRF) takes the bytes of a `release.json.sig` as the raw request body, at most 4 KiB (`413 PAYLOAD_TOO_LARGE`), whatever its `Content-Type`, and answers `AgentRelease`. Only an `awaiting_signature` release takes one (`409 CONFLICT`). The server stores the file only when it is a valid signature file ([formats](#formats)) and one of its entries names the current key and verifies over the release prefix and the stored manifest (`422 RELEASE_SIGNATURE_INVALID` otherwise, audited as `agent_release.signature_upload` with outcome `refused` and the reason). Success stores the bytes as uploaded, sets `signer` to the current key and the state to `ready`, and audits `agent_release.signature_upload` with outcome `success`.
- `POST /api/v1/agent-releases/{id}/withdraw {reason}` -> `AgentRelease` (Administrator, CSRF). The release becomes `withdrawn` and its `active` or `paused` rollouts are cancelled in the same transaction (`cancel_reason:"release_withdrawn"`, as Cancel; devices already applying finish); `409 CONFLICT` when already withdrawn. Its files are deleted from the store once no rollout references them; its row and manifest bytes stay. Audit `agent_release.withdraw`.

### Counters and the release sequence

The server keeps one sequence of counters for all keys. A release takes the next one: the larger of the stored sequence and one more than the highest `highest_counter` that devices report (the highest counter a host *attempted*), and the stored sequence becomes it. A reported `highest_counter` more than 1,000,000 above the stored sequence is ignored, so no device can use the sequence up. A manifest counter is at most 2^53-1. A host's own floor, and what it does with it, are under [verification](#verification-and-the-signed-messages).

### Update rollouts

An update rollout is its own object with its own tables. It never touches deployments, desired generations, policy generations or deployment targets, so a pipeline rollout and an update rollout cannot gate, supersede or roll back each other. It targets a fixed set of at most 10,000 devices that the review resolved, always starts with a canary, and releases the rest in batches. There is no all-at-once form.

`AgentUpdateRolloutSettings {canary_size,batch_size,observation_seconds,failure_threshold,canary_device_ids?}`: `canary_size` 1 to 100 (default 1), `batch_size` 1 to 50 (default 10), `observation_seconds` 60 to 86,400 (default 300), `failure_threshold` 0 to 100 (default 0, a count of devices) and, optionally, `canary_device_ids` with the rules of pipeline rollouts (distinct lowercase device UUIDs, at most `canary_size` and at most 100, each a device the request targets, otherwise `400 INVALID_INPUT` on preview and create alike; fewer than `canary_size` lets the most ready of the other targets fill the canary). Members a request leaves out take the defaults; stored and returned objects hold the four numbers. Unknown members are `400 INVALID_INPUT`.

`AgentUpdateRollout {id,name,release,selector,rollout,status,failure_reason,cancel_reason,revision,created_at,created_by_name,paused_at,completed_at,failed_at,cancelled_at,observation_started_at,target_count,state_counts,degraded}`: `name` is null or at most 120 characters under the one-line name rule; `release` is `{id,version,counter,manifest_sha256}`; `selector` is the `Selector` the request gave (`{device_ids,group_ids,exclude_ids}`); `status` is `active`, `paused`, `completed`, `cancelled` or `failed`; `failure_reason` is `threshold`, `data_plane`, `stalled` or null; `cancel_reason` is `operator`, `stop`, `key_revoked`, `release_withdrawn`, `release_expired` or null; `revision` advances when the status changes; `observation_started_at` is set while a stage's observation runs; `state_counts` holds the count of targets in each of the fourteen target states below (all present, zero when none); `degraded` counts `verified` targets that the observation still watches (see below) on which a data-plane issue is open (`DATA_PLANE_*`, see [Data-plane health](#data-plane-health)).

- `GET /api/v1/agent-update-rollouts?search=&status=&release_id=&page=1&page_size=12` -> `AgentUpdateRolloutPage {items,total,page,page_size}` of `AgentUpdateRollout`, newest first (`created_at` descending, then `id`). The query rules of the deployment history: `search` is a trimmed literal substring of the name or the release version, at most 200 Unicode scalars, ASCII case-insensitive; `status` is exact; `release_id` is a lowercase UUID; page size is 1 to 50; unknown, repeated or malformed parameters are `400 INVALID_INPUT`; count and page share a read snapshot.
- `POST /api/v1/agent-update-rollouts/preview {release_id,selector,rollout}` (Operator, Administrator, CSRF) -> `AgentUpdatePreview {release,will_update,wont_update,warnings,canary,review_token}` (below). It resolves the selector with the same union-minus-exclusions rule as deployments (`rollout::select`) and writes nothing. The release must be `ready` and unexpired (`409 RELEASE_NOT_READY`).
- `POST /api/v1/agent-update-rollouts {release_id,selector,rollout,name?,review_token,request_id?}` (Operator, Administrator, CSRF) -> `AgentUpdateRollout`. Every member but `name` and `request_id` is required. The review token is rechecked in the writer transaction: a changed review is `409 UPDATE_REVIEW_CHANGED` and creates nothing. It is `409 AGENT_UPDATES_STOPPED` while updates are stopped, `409 RELEASE_NOT_READY` for a release that is not ready, withdrawn or expired, `409 NOTHING_TO_UPDATE` when the review has nobody who will update, and `409 UPDATE_ROLLOUT_OVERLAP` for a device that is already in a rollout that has not ended (a device has at most one non-terminal target across all update rollouts). At most 200 update rollouts are `active` or `paused` at once, because every active one is read at each scheduler tick under the writer lock: the 201st is `409 UPDATE_ROLLOUT_LIMIT`, checked in the writer transaction, and an identical keyed retry of a request that already made its rollout still answers with it. The rollout starts `active` with every device `pending`; the first scheduler tick releases the canary. Audit `agent_update_rollout.create`.
- `request_id` (a lowercase UUID, scoped to the authenticated actor) follows the deployment request ledger: an identical retry returns the original rollout, with `request_id` added, before the review token is rechecked and before fresh selector, release or overlap validation; a retry whose body differs, or a `request_id` the same actor already used for a deployment operation, is `409 IDEMPOTENCY_CONFLICT` (deployments do not check the reverse). The digest excludes `request_id`, sorts object keys recursively, and keeps array order and the difference between `null` and omission. There is no request-status route: an unknown outcome is recovered by sending the identical body again, or by reading the list.
- `GET /api/v1/agent-update-rollouts/{id}` -> `AgentUpdateRolloutDetail`: the `AgentUpdateRollout` members plus `stages`, `failures`, `evaluated_at` and `check_in_seconds` (the longest check-in interval among targets, or null). A stage is `{kind:"canary"|"batch",index,state,released_at,size,counts,devices,more}`: `index` is 0 for the canary and 1, 2, ... for batches in release order; `state` is `queued` (nothing released), `in_progress` (released, and a device is neither terminal nor waiting), `observing` (done, the observation runs), `passed`, `failed` (the rollout failed in this stage) or `stopped` (the rollout was cancelled before it was released or finished); `counts` is the stage's count per target state; `devices` lists at most 60 `{device_id,device_name,state,code}` and `more` counts the rest. A failure group is `{state,code,message,count,device_ids,devices}`: the `rolled_back`, `failed` and `refused` targets grouped by `code`, at most 1,000 device IDs and 8 named devices each. `404 NOT_FOUND` for an unknown ID.
- `GET /api/v1/agent-update-rollouts/{id}/targets?page=1&page_size=12&search=&state=&sort=device_name&direction=asc` -> `AgentUpdateTargetPage {items,total,page,page_size}`. A target is `{device_id,device_name,stage,state,code,from_version,to_version,released_at,updated_at,verified_at}`: `device_name` is the name the device had when the rollout was created, `stage` is its stage index or null while `pending`, `code` is the agent code or `NO_REPORT` that ended it (null otherwise), `from_version` is the agent version it reported when it was released (null before) and `to_version` the release's version. The deployment target rules apply: `search` is a literal substring of the name (at most 200 scalars), `state` is exact, `sort` is `device_name`, `state` or `updated_at`, `direction` is `asc` or `desc`, page size is 1 to 50.
- `POST /api/v1/agent-update-rollouts/{id}/pause`, `/resume` and `/cancel` (Operator, Administrator, CSRF, empty body) -> `AgentUpdateRollout`. A transition that does not apply (pausing a rollout that is not `active`, resuming one that is not `paused`, cancelling one that has ended) is `409 CONFLICT` and changes nothing. **Pause** stops releasing and withdraws every offer that has not started applying: those targets return to `pending`, and agents discard what they staged; devices already applying finish. **Resume** restarts the observation of the current stage and releases again through the same gates. **Cancel** withdraws unstarted offers (those targets become `cancelled`) and ends the rollout; a cancelled or failed rollout is never resumed, a new one is reviewed. Audit `agent_update_rollout.pause`, `.resume` and `.cancel`.

**The review.** `AgentUpdatePreview` holds `release` (`{id,version,counter,manifest_sha256}`), `will_update:[{device_id,device_name,consent,windows,next_window_at}]` (the devices that will update, with the level (`auto` or `ask`) and the windows each applies under; `windows` is the host's window list, empty meaning any time, and `next_window_at` the start of its next window, null when one is open or it has none), `wont_update:[{code,reason,fix,devices:[{device_id,device_name,successors}]}]`, `warnings:[{code,message,devices:[{device_id,device_name}]}]`, `canary` (`{size,chosen_by_you,device_ids}`: the devices released first, in release order, and whether the request named them) and `review_token`. Every device of the resolved selector appears exactly once, in `will_update` or under the first reason in `wont_update` that applies, tried in this order, from each device's latest report and the release:

1. `DEVICE_REVOKED`. A preview never lists it: a selector that names an unknown or revoked device is `400 INVALID_INPUT`, as for deployments, and a revoked device is in no group. It is what a stage finds for a device revoked after the rollout began; that device's open targets end `skipped`, never `failed`.
2. `AGENT_TOO_OLD` when the device has sent no `agent_update` report: its agent does not speak updates.
3. The device's own `eligibility` when it is not `eligible` (`PACKAGE_MANAGED`, `NO_SERVICE`, `UNTRUSTED_LOCATION`, `READ_ONLY`, `HELPER_NOT_RUNNING`, `SERVICE_DEFINITION_OUTDATED`, `PLATFORM_NOT_IN_RELEASE`).
4. `UPDATES_OFF`: consent is `off`.
5. `KEY_ROLLOVER_CONFLICT`: the report carries `rollover_conflict`; `successors` holds its two fingerprints.
6. `PLATFORM_NOT_IN_RELEASE`: the release has no artifact for the device's `os` and `arch`.
7. `KEY_NOT_PINNED`: no key the device reported pinning reaches the release's signer, by itself or through the stored rollover statements.
8. `RELEASE_ALREADY_TRIED`: the report's `last` names this release's manifest SHA-256 as `rolled_back` and the counter is at or below the reported `highest_counter`.
9. `COUNTER_REPLAYED`: the release's counter is at or below the reported `highest_counter`.
10. `ALREADY_RUNNING` (the device's `agent_version` is the release's version) or `DOWNGRADE_REFUSED` (it is newer, or it is not a version and cannot be compared with the release's).
11. `VERSION_NOT_ON_TRACK`: the version is not on the device's reported `track`.
12. `AGENT_TOO_OLD`: the device's version is below the manifest's `min_from`. This server writes no `min_from` (nothing in its catalog or a request names one), so the rule applies only to a release whose stored manifest carries one.
13. `SERVICE_DEFINITION_OUTDATED`: the release needs a newer service definition than the device reported.
14. `IN_ANOTHER_UPDATE`: the device has a non-terminal target in another update rollout.

A `wont_update` group has the `code` and a `reason` sentence naming it ("edge-02 tried 0.1.1 and rolled back; it takes the next release"); `fix` is a sentence for people, or null when nothing would change it (`UPDATES_OFF`: "Run the Upgrade agent command with updates on, once."); when it sends the person to the Upgrade agent command, the dashboard turns it into the host command it generates. For `KEY_NOT_PINNED` it depends on the hosts of the group: when an older key than the current one signed the release and a host pins the current key (or a key the stored statements lead from to it), a release the current key signs reaches that host, and no command on the host does, so the fix reads "Withdraw this release and prepare it again so the current key signs it."; a host that pins no key leading to the current key needs the Upgrade agent command, once ("Run the Upgrade agent command so the host pins the current release key."); a group of both kinds says the first and then which hosts also need the command. A host that pins a retired key with no statement path to the current key is the second kind. `successors` is `[fingerprint,fingerprint]` for `KEY_ROLLOVER_CONFLICT` and null otherwise. A `warnings` group is `OFFLINE` (not within three of its check-in intervals; it updates if it checks in while the rollout runs), `WAITS_FOR_HOST` (level `ask`), `WAITS_FOR_WINDOW` (level `auto`, a window set and none open) or `PAUSED_ON_HOST`. The `review_token` is a lowercase SHA-256 binding the release, the rollout settings (with the canary devices the request named), and the exact `will_update` and `wont_update` sets with each device's level, windows and successors; it leaves out the start of a device's next window and the canary the server would pick when the request named none, and it is not bound to an actor. It is an optimistic-concurrency check on public data, not authentication; creation recomputes it under the writer lock. `canary.size` is the number of canary devices the review would release, below the setting's `canary_size` when fewer can be released now. The canary's result is what its devices report: the review says so, and naming canary devices the team trusts is how to rely on it.

**Per-device states.** Each target has one of fourteen states. A report counts only when its `release` is this rollout's release (the manifest SHA-256), and it counts only forward: a report that would move a target to an earlier row of the table never does, and `rolled_back`, `refused`, `failed`, `verified`, `cancelled` and `skipped` are final.

| State | Entered when | Next |
| --- | --- | --- |
| `pending` | The rollout was created, or an offer that had not started was withdrawn by a pause | `offered`, `skipped`, `cancelled` |
| `offered` | It was released into a stage; the next manifest carries the offer | `downloading`, `staged`, `refused`, `failed` |
| `downloading`, `staged` | Its report has that `state` | `waiting_for_host`, `waiting_for_window`, `applying`, `refused`, `failed`, `skipped` |
| `waiting_for_host` | Its report has that `state` (level `ask`, build staged) | `applying`, `skipped`, `cancelled` |
| `waiting_for_window` | Its report has that `state` (level `auto`, build staged, no window open) | `applying`, `skipped`, `cancelled` |
| `applying` | Its report has `state` `applying` or `trial` | `restarted`, `rolled_back`, `failed` |
| `restarted` | A check-in carries the offered artifact's SHA-256 as `agent_sha256`, the release's version as `agent_version` and a `boot_id` other than the one the device's previous build last reported | `verified`, `rolled_back` |
| `verified` | That build's report has `last.release` equal to this release and `last.outcome` `committed` | final |
| `rolled_back` | A report has `last.release` equal to this release and `last.outcome` `rolled_back` (`code` is `last.code`) | final |
| `refused`, `failed` | Its report has that `state` for this release, or `last.outcome` `refused` or `failed`; `code` is the agent code | final |
| `cancelled` | Cancel, a revoked key, a withdrawn release or Stop all updates reached it before it started applying | final |
| `skipped` | It never became releasable (offline, or no longer eligible) before the rollout finished, was offered, downloading or staged for 60 minutes without a change, or its host dropped the offer | final |

A device silent for 30 minutes after `applying` or `restarted` becomes `failed` with the code `NO_REPORT`: a build that cannot check in would have been rolled back and reported by the previous one by then. A device that has been `offered`, `downloading` or `staged` for 60 minutes without a change is `skipped`; a `downloading` or `staged` one carries the last `code` its host reported, or `NO_REPORT` when it reported none. A report that no longer names the release (its `state` is `idle`, or it is about another release, or the host is `paused`) ends a target that was `downloading`, `staged`, `waiting_for_host` or `waiting_for_window` as `skipped` with the report's `code` (`UPDATES_PAUSED`, `UPDATES_OFF` or whatever it carries, `NO_REPORT` when it carries none): the host dropped the offer. A report that carries a result (`last`) of this release is not a dropped offer, and a target that is still `offered` is not touched by an `idle` report, because a report lags the offer by one check-in. The rollout counts a device as updated only from `verified`: a download, a staged file or a swap is never an update.

**Stages, gates and the threshold.** The scheduler tick that runs every two seconds under the writer lock (`rollout::tick`) calls an update step after the pipeline step, in the same transaction. A stage releases only devices that checked in within three of their intervals, report `eligibility: eligible`, are not paused on the host and are in no other update rollout. Unless the request named the canary, the canary prefers `auto` devices whose window is open or absent, by the readiness order the pipeline canary uses (`canary_choice`); a device that cannot be released now stays `pending` for a later stage. Releasing a device sets its target to `offered` and answers its parked wait (`wake::ask`); the offer arrives in the signed manifest of its next check-in, so wake-ups stay content-free. A stage is done when every device it released is terminal or waiting on its host (`waiting_for_host`, `waiting_for_window`), and the canary also needs at least one `verified` device. Then the observation runs for `observation_seconds`: every verified device must keep checking in on the new build, and a device that falls back or goes silent restarts it. A verified device that will not come back is not watched: one whose access was revoked, or whose last check-in is older than the larger of three of its check-in intervals and `observation_seconds`, neither holds the observation nor counts as degraded, and the canary still needs at least one verified device that is watched. A verified device on which a data-plane issue opens during the observation counts as a failure, as `canary_gate::degraded` counts it for pipelines, so a build that starts and checks in but stops Vector delivering is caught by the gate. `rolled_back` and `failed` targets and those degraded devices count toward `failure_threshold`; `refused`, `skipped` and `cancelled` do not (the review should have caught a refusal, and the page lists them). Above the threshold the rollout is `failed` (`failure_reason` is `threshold`, or `data_plane` when the degraded devices alone pushed it over), its unstarted offers are withdrawn (those targets become `cancelled`) and devices already applying finish their trial. The rollout is `completed` when no device is `pending` or waiting, every released device is terminal and the last observation passed. A device that waits for its host or its window keeps its offer, because offers come only from an `active` rollout: the rollout stays `active` (a stage that has only waiting devices left is done, so later stages release) until that device applies or the rollout is cancelled, and cancelling withdraws the offer, so the host discards what it staged. A rollout whose devices all ended before any was released (every one `skipped`) is `failed` with `failure_reason` `threshold`. A release that expires ends its `active` and `paused` rollouts as `cancelled` with `cancel_reason` `release_expired`, as a withdrawal does (unstarted offers withdrawn, devices already applying finish). A safety net ends a rollout that cannot go on: an `active` rollout that has a target no step can move (`pending`, `offered`, `downloading`, `staged`, `applying` or `restarted`), or a verified device the observation needs, and has made no progress for 24 hours, is `failed` with `failure_reason` `stalled` (unstarted offers withdrawn, those targets `cancelled`, devices already applying finish). Progress is any change of a target's state, a stage released, an observation starting or ending, or the rollout resuming. A rollout whose only open targets wait on their host or window, or whose canary waits for its host, is not stalled: that is by design, and people cancel it. The scheduler looks for a stalled rollout at most once an hour for each. Audit `agent_update_rollout.release` (details `stage` and the released `device_ids`) at every release, `agent_update_rollout.gate` (details `gate_state` `failed` or `completed`, and `reason` for a failure: `threshold`, `data_plane` or `stalled`) when the gate ends the rollout, and `agent_release.expire` (target the release; details `release_id`, `version`, `counter`, `manifest_sha256` and `cancelled_rollouts`; the scheduler is the actor) when an expired release ends its rollouts.

### Device projection, filters, audit, notifications and issues

- **Device.** `Device` adds the read-only `agent_update:{consent,paused,track,windows,window_open,next_window_at,keys,eligibility,state,release_version,code,rollover_conflict,last,reported_at}` while updates are on and the device has sent the heartbeat member. It is the latest report as the device sent it (the members are those of [the heartbeat member](#what-the-agent-reports)), plus `release_version` (the version of the release the report's `release` digest names, null when it names none this server prepared) and `reported_at` (the check-in that carried it). A check-in without the member removes it: never inferred, never stale; the dashboard says "Not reported". List rows (`DeviceListItem`) do not carry it.
- **Filters.** `GET /api/v1/devices/inventory` and `/devices/inventory/ids` take two more filters, with the strict query rules of Fleet-scale reads: `agent_update=automatic|ask|off|cannot_update|not_reported` (the buckets of `AgentUpdates.fleet.levels`; `404 AGENT_UPDATES_OFF` while updates are off) and `agent_version=<version as reported>` (1 to 128 bytes, exact).
- **Audit.** Actions, with their targets (`target_kind` gains `agent_release_key`, `agent_release` and `agent_update_rollout`; `agent_update.*` events target the server): `agent_update.enable`, `agent_update.disable`, `agent_update.stop`, `agent_update.stop_clear`, `agent_release_key.rotate`, `agent_release_key.rollover`, `agent_release_key.revoke` (target the key by fingerprint), `agent_release.prepare`, `agent_release.sign`, `agent_release.signature_upload` (outcome `success` or `refused`, with the reason), `agent_release.withdraw` (target the release), `agent_release.expire` (target the release; the scheduler writes it when an expired release ends its rollouts), `agent_update_rollout.create`, `.pause`, `.resume`, `.cancel`, `.release` (once per stage, with the device IDs) and `.gate` (target the rollout), and per device `device.agent_update` for `verified`, `rolled_back`, `failed` and `refused`, under the per-device limit of four rows a minute (`DEVICE_AUDIT_ROWS_PER_MINUTE`). Details are allowlisted and hold versions, digests, counters, fingerprints and codes, never key material: `custody`, `fingerprint`, `from_fingerprint`, `source` (`server` or `upload`), `version`, `counter`, `manifest_sha256`, `release_id`, `rollout_id`, `stage`, `gate_state`, `device_ids` (at most 100), `released_count`, `verified_count`, `withdrawn_releases`, `cancelled_rollouts`, `from_version`, `to_version`, `code`, `state` and `reason`. `agent_update.enable` carries the `custody` and the `fingerprint` of the current key; `agent_release_key.rotate` and `.rollover` carry the new key's `fingerprint`, the `from_fingerprint` and the `source`; there is no custody-change action.
- **Notifications.** The event list gains `agent_update.failed` (error: an update rollout stopped at its failure threshold, because devices that took it stopped delivering, or after 24 hours without progress, from `agent_update_rollout.gate` with `gate_state` `failed`), `agent_update.rolled_back` (warning: a device went back to its previous build, from `device.agent_update` with state `rolled_back`), `agent_update.stopped` (warning: Stop all updates, from `agent_update.stop`) and `agent_update.key_changed` (warning: updates were turned on or off, or a key was rotated, rolled over or revoked, which decides what key new hosts pin; there is no custody-change event; from `agent_update.enable` and `.disable` and `agent_release_key.rotate`, `.rollover` and `.revoke`). They are read from the audit trail through the notifier's cursor, like `rollout.failed`, with the same identity, quiet-hour and digest rules. A pipeline filter matches none of them; a group filter matches `agent_update.rolled_back` by its device and `agent_update.failed` by the rollout's selector groups or its targets' groups; `agent_update.stopped` and `agent_update.key_changed` match only a rule with no filters. The `NotificationEvent` of these types adds `agent_update:{release_version,rollout,code,key}`, each member nullable: `rollout` is `{id,name}`, `code` the agent code of a rollback, `key` the short ID of the key that became current.
- **Issues.** `AGENT_UPDATE_ROLLED_BACK` and `AGENT_UPDATE_FAILED` (`stage:"agent_update"`), keyed by device, release version and code, opened when a target ends `rolled_back` or `failed` and counted, acknowledged and reopened like other issues. `version_id`, `version_number`, `configuration_id`, `configuration_name` and `deployment_id` are null; `title` reads like `edge-02 rolled back agent 0.1.1` or `edge-02 couldn't update to agent 0.1.1`, or `3 devices rolled back an agent update` or `3 devices couldn't update their agent` for a group, and `message` is rendered from the code. The audit log and search name these issues `Agent update rolled back` and `Agent update failed`, whatever device they are about. They resolve as `verified` only when that device verifies a later update, and as `revoked` with the device. Verifying a pipeline, removing its assignment, a changed version or turning metrics off does not resolve them (`issues::resolve_device` skips `AGENT_UPDATE_*` for every reason but `revoked`, as it skips `DATA_PLANE_*` for `verified`).
- **Overview.** `attention` adds a group `cause:"agent_update"` (severity `warning`, `state` `rolled_back` or `failed`, `reason` the most common code, the devices with such an open issue), shown as "Agent update rolled back on 2 devices". `attention_devices` and every other member are unchanged.

### What the agent reports

The manifest's `features` lists `agent_update` only while updates are on (a stopped server still lists it, so agents keep reporting). An agent sends the heartbeat member `agent_update` only after a verified manifest lists the feature, in every check-in while it does, and reads an offer only from such a manifest. A check-in without the member removes the device's stored report.

```json
{"consent":"auto","paused":false,"track":"patch","windows":["Mon-Fri 02:00-04:00 UTC"],"window_open":false,"next_window_at":"2026-10-05T02:00:00Z","keys":["05cc6c02351af0cb1be9877e7cdcd326c68310018746cb7bbbf6beb29392618b"],"highest_counter":6,"eligibility":"eligible","service_definition":1,"state":"waiting_for_window","release":"01e2380259f57e6f0a7b7b2fca2b5882fcec1cab1a94c9a1d0dc00703f0367c8","code":null,"rollover_conflict":null,"last":{"release":"36e42c85bd0a217e6d145ef4ec74d63ab34cc6e72a8133cd59b485d481f94833","outcome":"committed","code":null,"at":"2026-08-12T02:09:41Z","from_version":"0.0.9","to_version":"0.1.0","first_check_in_ms":1900}}
```

The member is an object with these members and no others (an unknown member is refused):

| Member | Value |
| --- | --- |
| `consent` | `off`, `auto` or `ask`: the level in the host's root-owned policy; `off` when there is none |
| `paused` | boolean: the policy's `paused` |
| `track` | `patch` or `minor`; never `major` |
| `windows` | at most 7 strings of 1 to 40 printable ASCII characters (U+0020 to U+007E), the update windows as written in the policy; empty means any time |
| `window_open` | boolean: true when there is no window or one is open now |
| `next_window_at` | optional, UTC instant: the start of the next window; absent or null while one is open or there is none |
| `keys` | at most 4 distinct lowercase 64-hex fingerprints: the keys the host pins now |
| `highest_counter` | 0 to 2^53-1: the highest release counter the host attempted from any key it pins (the largest value of `highest_counters` in the step's status file; 0 when it has none) |
| `eligibility` | `eligible`, or the code that says why this host cannot take an update: `PACKAGE_MANAGED`, `NO_SERVICE`, `UNTRUSTED_LOCATION`, `READ_ONLY`, `HELPER_NOT_RUNNING`, `SERVICE_DEFINITION_OUTDATED` or `PLATFORM_NOT_IN_RELEASE` (this operating system's updates are not in this release). It is reported whatever the level, so a package-managed host says so even when it is `off` |
| `service_definition` | optional, 1 to 1,000: the generation of the service definition the host has, from the step's status file; absent when the step is not installed |
| `state` | `idle`, `downloading`, `staged`, `waiting_for_host`, `waiting_for_window`, `applying`, `trial`, `refused` or `failed` |
| `release` | optional, 64 lowercase hex: the manifest SHA-256 that `state` is about; present in every state from `downloading` to `trial` |
| `code` | optional, an agent code ([codes](#codes)): the reason of `refused`, `failed`, a paused or off host; present in `refused` and `failed` |
| `rollover_conflict` | optional, `{from,to:[a,b]}` with three distinct 64-hex fingerprints: the two successors of a fork; present exactly when `code` is `KEY_ROLLOVER_CONFLICT` |
| `last` | optional, `{release,outcome,code,at,from_version,to_version,first_check_in_ms?}`: the privileged step's latest result, copied from its status file. `release` is a manifest SHA-256, `outcome` is `committed`, `rolled_back`, `failed` or `refused`, `code` is null for `committed` and an agent code otherwise, `at` is a UTC instant, `from_version` is 1 to 128 bytes of the version the host ran, `to_version` is a version or null, and `first_check_in_ms` (0 to 86,400,000) is how long after the new build started its first check-in was answered |

Optional members may be absent or null. `required` ones are `consent`, `paused`, `track`, `windows`, `window_open`, `keys`, `highest_counter`, `eligibility` and `state`. A host whose `consent` is `off` reports `state:"idle"` and no `release`. The strings `from_version` and `windows` follow the rule of every member that names or identifies something: no control character, line or paragraph separator, text-direction control or byte order mark. `state` reads from the step's status file and the agent's own work: `applying` while the step's stage is `preparing`, `swapping` or `rolling_back`, `trial` while it is `trial`. The shared fixture `contracts/fixtures/agent-release/report.json` holds the bounds above and members the server accepts and refuses; the server's parser test and the agent's report test both read it, so a bound changed on one side shows up on the other. A refused member is `400 INVALID_INPUT` and changes nothing. On a `400` the agent leaves `agent_update` out first, before the check result and every other optional report (`exchange` in `reconcile.go` drops them one step at a time), and keeps it out for the rest of the process, so this member can never take a device off the control plane. The heartbeat's existing `agent_version`, `agent_sha256` and `boot_id` (a fresh value for every agent process) are what the server compares to see a restart.

`manifest` and `signatures` are the base64 of the exact bytes of `release.json` and `release.json.sig`; `rollovers` holds at most 8 `{statement,signature}` envelopes (base64), the statements that lead from a key the device reported pinning to the release's signer, in the order a host follows them (a device whose pinned key is more than 8 statements behind the signer is not offered the release, and the review lists it as `KEY_NOT_PINNED`); `artifact` is the entry for the device's platform. The server's own manifest signature makes the offer fresh and addressed to this device and authorizes no code. The agent derives everything it acts on from `manifest` after verifying `signatures` and `rollovers` against its own pins, and requires `artifact` to equal the manifest's entry for its own platform and `path` to be exactly `/agent/v1/agent-releases/` followed by that digest. Older agents ignore the member (`Manifest` does not decode it), so it never affects their generations or identity checks. The `desired` and `validation` members are unchanged; an offer and a configuration apply can arrive in one check-in, and the apply finishes first.

### The download

`GET /agent/v1/agent-releases/{sha256}` on the agent listener, mutual TLS, authenticated like `GET /agent/v1/artifacts/{sha256}`. It answers only when updates are on and not stopped and the device holds a current offer whose artifact has that digest (`403` otherwise, `404` while updates are off or for an unknown digest). It streams the release store's file as `application/octet-stream` with `Content-Length` and `Cache-Control: no-store`, re-hashing as it goes and withholding the last chunk on a mismatch, with a 20-second stall limit and a 5-minute deadline, and never a redirect. Limits: one transfer per device at a time (a second request while one runs is `429 RATE_LIMITED` with `Retry-After: 5`), 16 on the server, 6 requests an hour per device for the offered digest (a request for any other digest never spends that budget and is counted at 60 a minute per device instead; `429 RATE_LIMITED` with `Retry-After`; `429 CAPACITY_BUSY` with `Retry-After` when all 16 slots stream; `503 CAPACITY_BUSY` when the listener's request slots are taken). There is no `Range` and no resume: a build is at most 128 MiB and usually about 15; a cut-off transfer leaves nothing under a final name and starts over at the next check-in, so the device's only partial state is a temporary file. The agent bounds the stream, and the privileged step its copy, by `MaxAgentBuild` (128 MiB); `MaxArtifact` (1 MiB) keeps bounding pipeline artifacts and the signed manifest that carries the offer. A `403` or `404` makes the agent drop the staged attempt until a manifest offers it again; `429` and `503` are waited out with `Retry-After`; anything else counts as `DOWNLOAD_FAILED`.

### The key bundle

`GET /agent/v1/release-keys`, no client certificate, rate-limited like `install.sh`, `Cache-Control: no-store`, at most 64 KiB, `404` while updates are off:


It lists every key that is not revoked (`state` `current` or `retired`) and every rollover statement among them as `{statement,signature}` envelopes. Public keys and statements are public. It carries no custody: a host needs none to verify, setup pins by the fingerprint it computes from the key bytes, and an unauthenticated peer of the agent listener should not learn whether a server compromise alone would be enough to sign a release. For that reason a key the server generates is named `release-` and the first eight characters of its fingerprint, never anything that says who made it. Setup ignores the `fingerprint` member for matching: it computes the SHA-256 of each entry's decoded key, applies the key rule, and pins the entry whose computed fingerprint equals the one the operator gave; an entry whose `fingerprint` member is missing or disagrees with its key makes the whole bundle malformed (`RELEASE_KEY_INVALID`, nothing pinned). Members it does not know are ignored. The `bundles` of the shared vectors pin each case.

### Codes

There are two vocabularies. **Agent codes** are strings an agent and its privileged step put in `code` (the heartbeat member, `last`, `status.json`, a target) and the review shows. **API error codes** are the `error.code` of a dashboard-API response.

The agent codes, what each means, the heartbeat `state` it comes with, and what the agent does:

| Code | Meaning | `state` | The agent |
| --- | --- | --- | --- |

| `COUNTER_REPLAYED`, `DOWNGRADE_REFUSED`, `VERSION_NOT_ON_TRACK`, `AGENT_TOO_OLD`, `ALREADY_RUNNING` | The host's policy refuses the release: its counter is at or below the floor, its version is older than the running one (or the running version is not a version and cannot be compared), it is not on the host's track, the running version is below `min_from`, or it is the running version | `refused` | Refuses |

### Formats

Every file here is UTF-8 text without a byte order mark. Base64 is the standard alphabet with padding, canonical (the unused bits are zero) and without whitespace. A *UTC instant* is `YYYY-MM-DDTHH:MM:SSZ` (whole seconds, years 1970 to 9999) unless a member says milliseconds. Hex is lowercase. Every key and digest in the examples is a published test value; never pin one of the keys on a real host.

**The profile of the signed files.** `release.json`, `release.json.sig` and a rollover statement are verified as bytes and then parsed, by a Rust server and a Go agent that must agree on every input, so both check the raw bytes before they decode anything: every byte is printable ASCII (0x20 to 0x7E) except at most one final line feed (0x0A); the first byte is `{`; the only whitespace is the space; a backslash occurs nowhere (so no escape sequence, and no string holds a quotation mark or a backslash); no member occurs twice in an object and no member the format does not name is allowed (names are matched exactly, so `Schema` is an unknown member); an artifact and a signature entry are objects, never arrays of their values; numbers are written `0`, or a digit 1 to 9 followed by digits, never with a sign, fraction, exponent or leading zero, and are at most 2^53-1; every other value is a string, an array or an object; and nothing follows the object but that one line feed. The profile fixes no layout: members come in any order and spaces may stand between any two tokens, so one object has many byte strings and each is verified as the bytes it is. A byte string one side accepts and the other refuses fails CI: the shared vectors pin each refusal (`1e2`, `7.0`, `-0`, `07`, 2^53, duplicate members, a member name in another case, an entry written as an array, a byte order mark, a non-ASCII byte, an escape, trailing bytes) and the layouts it accepts. The sizes are 16 KiB (16,384 bytes) for `release.json`, 4 KiB for `release.json.sig` and 1 KiB for a statement. Nobody re-serializes a signed file: the server stores the bytes it built, the offline signer signs the bytes it downloaded, and an agent verifies the bytes it received and only then parses them.

**`release.json`**, the manifest of a release (the server writes one line with the members in the order shown, no spaces and no final line feed; a tool may add one line feed, and the signature covers every byte):

```json
{"schema":"vectory.agent-release.v1","version":"0.1.1","counter":7,"issued_at":"2026-10-03T12:00:00Z","expires_at":"2027-04-01T12:00:00Z","min_from":"0.1.0","service_definition":1,"artifacts":[{"os":"linux","arch":"amd64","format":"executable","file":"vectory-0.1.1-linux-amd64","size":15204352,"sha256":"4206fd2a4cefdeff00f444007d1346ec2ca0d60edf58c0392d5f15a0f275981f"},{"os":"windows","arch":"amd64","format":"executable","file":"vectory-0.1.1-windows-amd64.exe","size":15892480,"sha256":"25043433d22cf8f6f5ffb531abb6a0b0fe0952af2bb946586b5868b4bdf4e201"}]}
```

| Member | Rule |
| --- | --- |
| `schema` | Exactly `vectory.agent-release.v1`. A future schema is refused, never half-read |
| `version` | A version (`major.minor.patch`; pre-releases and build metadata are refused) |
| `counter` | 1 to 2^53-1. Strictly greater than every counter the host attempted from the signing key |
| `issued_at`, `expires_at` | UTC instants; `expires_at` is after `issued_at` and at most 400 days later (the server writes 180 days) |
| `min_from` | Optional version. A host running an older one refuses (`AGENT_TOO_OLD`): the release needs a step it cannot take from there |
| `service_definition` | An integer of 1 or more: the generation of the unit, plist or service definition the build needs. 0.1 builds say `1` |
| `artifacts` | 1 to 8 entries, unique by `os` and `arch` |

An artifact is `{os,arch,format,file,size,sha256}`: `os` is `linux`, `darwin` or `windows`, `arch` is `amd64` or `arm64`, `format` is `executable` (the only format: the artifact is the agent executable itself, byte for byte the file in the server's catalog, and no archive is ever unpacked as root), `file` is `vectory-<version>-<os>-<arch>` plus `.exe` on Windows, `size` is 1 byte to 128 MiB (134,217,728) and `sha256` is 64 hex.

**`release.json.sig`**, the detached signatures (at most 4 KiB; the tools write one line in the order shown, with no spaces):

```json
{"schema":"vectory.agent-release-signatures.v1","signatures":[{"key":"05cc6c02351af0cb1be9877e7cdcd326c68310018746cb7bbbf6beb29392618b","signature":"92Djw+8q0PShRNfEeTrnmFmFFmfd/QA+Tc/tmfgVAh+hAMMtcEOYJAoAav8IQCXEql5SQcO3rdpCDDaQGqlbAA=="}]}
```

`schema` is exactly `vectory.agent-release-signatures.v1`; `signatures` holds 1 to 4 entries with distinct `key` members. `key` is a 64-hex fingerprint and only selects which pinned key to try: verification always uses the pinned key's own bytes. `signature` is the base64 of 64 bytes. A release is valid on a host when at least one entry names a pinned key and verifies; entries for keys the host does not pin are ignored. This is what lets a project-wide release key be added later as one more pinned key, or a release carry two signatures during a rollover, without changing the agent.

**Public key line**, one line, no line terminator in the value:

```text
vectory-release-key ed25519 3n1kX5uZnEN2wf+ZrjTlfd3sqUPQff1ANP0I/elZz7o= team
```

`vectory-release-key ed25519 <base64 of the 32 raw bytes> <name>`, single spaces, the name 1 to 64 printable ASCII characters that neither start nor end with a space and hold no quotation mark and no backslash (the line is quoted inside the JSON of a statement and of the policy, where an escape cannot occur). The key rule: the 32 bytes must be the canonical encoding of a curve point (the `y` coordinate below 2^255-19, the sign bit clear when `x` is 0) that is not one of the eight points of order 1, 2, 4 or 8; otherwise `RELEASE_KEY_INVALID`. The vectors list the eight small-order encodings and non-canonical encodings of the same points. The *fingerprint* is the hex SHA-256 of the 32 bytes, always computed from the key and never taken from a field beside it.

**Private key file** (`vectory release keygen`, offline custody), mode `0600`, one line and a final line feed:

```text
vectory-release-private-key ed25519 m/S3niTMlf9AEtH9rnFvuoW2tEC7eSBdR91Jr/S+hRg=
```

`vectory-release-private-key ed25519 <base64 of the 32-byte seed>`. The file above is the fixed seed of the published test key `team`, never a real key; a real one is written by `vectory release keygen` under the name the operator gives it.

**Rollover statement**, which replaces one key with another (at most 1 KiB, written in the order shown with no spaces):

```json
{"schema":"vectory.release-key-rollover.v1","from":"05cc6c02351af0cb1be9877e7cdcd326c68310018746cb7bbbf6beb29392618b","to":"vectory-release-key ed25519 EfEAEZ4zQhLJkpS72PMa8tlIIRVq/eIn895jrezMZpY= team-next","issued_at":"2026-11-02T09:00:00Z"}
```

`schema` is exactly `vectory.release-key-rollover.v1`, `from` is the fingerprint of the key it replaces, `to` is a key line that passes the key rule and whose fingerprint is not `from`, and `issued_at` is a UTC instant. It is signed by the `from` key over `"vectory-release-key-rollover-v1\n"` followed by the statement's bytes, and delivered as an envelope with both parts in base64:

```json
{"statement":"eyJzY2hlbWEiOiJ2ZWN0b3J5LnJlbGVhc2Uta2V5LXJvbGxvdmVyLnYxIiwiZnJvbSI6IjA1Y2M2YzAyMzUxYWYwY2IxYmU5ODc3ZTdjZGNkMzI2YzY4MzEwMDE4NzQ2Y2I3YmJiZjZiZWIyOTM5MjYxOGIiLCJ0byI6InZlY3RvcnktcmVsZWFzZS1rZXkgZWQyNTUxOSBFZkVBRVo0elFoTEprcFM3MlBNYTh0bElJUlZxL2VJbjg5NWpyZXpNWnBZPSB0ZWFtLW5leHQiLCJpc3N1ZWRfYXQiOiIyMDI2LTExLTAyVDA5OjAwOjAwWiJ9","signature":"mzO9h8MIeHaIgfeTLc5mHlE3k1EEeGTLff4gDN8RyXqQE2yHitf4WCF9MTKwgbI+PZrWriwVbwL/sbUD5mQhDw=="}
```

**Host policy**, the host's consent, written only by root (`vectory setup`, `vectory update`, and the privileged step for the pins after a rollover):

```json
{"schema":"vectory.update-policy.v1","consent":"auto","track":"patch","windows":["Mon-Fri 02:00-04:00 UTC"],"paused":false,"keys":[{"public_key":"vectory-release-key ed25519 3n1kX5uZnEN2wf+ZrjTlfd3sqUPQff1ANP0I/elZz7o= team","pinned_at":"2026-10-03T12:30:00Z"}],"updated_at":"2026-10-03T12:30:00Z"}
```

| Member | Rule |
| --- | --- |
| `schema` | `vectory.update-policy.v1` |
| `consent` | `off`, `auto` or `ask`. A missing file means `off` |
| `track` | `patch` (the default) or `minor`; `major` is refused by setup and by the reader: "This release offers patch and minor tracks. Upgrade to a new major version by hand." |
| `windows` | At most 7 windows, each at most 40 characters, in the grammar below; empty means any time |
| `paused` | boolean: keeps the level and stops every download and apply until `vectory update resume` |
| `keys` | At most 4 pinned keys `{public_key,pinned_at}`: key lines that pass the key rule, with the instant they were pinned; at least one when `consent` is `auto` or `ask` |
| `updated_at` | UTC instant |

`vectory setup` writes the policy from `--updates auto|ask|off`, `--update-key-sha256 HEX` (required with `auto` or `ask`, repeatable up to 4: setup fetches the key bundle and pins the entry whose computed fingerprint equals the value, and passing the flag again replaces the pin set), `--update-track patch|minor` (default `patch`) and `--update-window SPEC` (repeatable up to 7); with none of the update flags it writes and touches nothing.

A window is `DAYS HH:MM-HH:MM` or `DAYS HH:MM-HH:MM UTC`: `DAYS` is `daily`, a day (`Mon`, `Tue`, `Wed`, `Thu`, `Fri`, `Sat`, `Sun`), a range of days (`Mon-Fri`, which wraps the week: `Sat-Mon` is Saturday, Sunday and Monday) or a list of distinct days (`Sat,Sun`); the times are 24-hour and the end differs from the start; they are in the host's local time unless `UTC` follows. A window that ends before it starts crosses midnight and belongs to the day it starts. Daylight-saving changes follow the host's time zone. A window gates the start of an apply; a trial that started inside it may finish after it. The spec is at most 40 characters, so a list of all seven days with `UTC` is written `daily`. The policy is not in `settings.json`: that file belongs to the service account, and for updates it would turn the service account into root.

### The privileged step and its files

A small step, run by root (SYSTEM on Windows), applies a build; the agent's service account never does. The agent downloads and stages, and the step copies, verifies and swaps. The step is started by a timer or its equivalent every 30 seconds and at boot, runs from a copy of the last build that was proven on the host (`private/helper/`), does no network I/O, and reads nothing the service account wrote without copying it first.

| | Linux (systemd) | macOS (launchd) | Windows (SCM) |
| --- | --- | --- | --- |
| The policy | `/etc/vectory/updates/policy.json` (`updates/` root `0755`, file `0644`) | `/Library/Application Support/Vectory/updates/policy.json` | `%ProgramData%\Vectory\updates\policy.json` (owner Administrators, protected DACL, SYSTEM and Administrators full control, `NT SERVICE\Vectory` read) |
| The step's directory | `/var/lib/vectory-update/` (root `0755`) | `/Library/Application Support/Vectory/update-state/` | `%ProgramData%\Vectory\update-state\` |
| `status.json` in it | `0644`, what the agent reads | same | also readable by the service SID |
| `probe/` in it | root `0755`, files `0755`: the one place the service account runs a verified build from | same | writable only by SYSTEM and Administrators |
| `private/` in it | root `0700`: `journal.json`, `counters.json`, `installed.json`, `staging/`, `helper/` and the lock | same | SYSTEM and Administrators only |
| What the service account writes | `<state>/updates/` (`<state>` is the agent's state directory): `incoming/<manifest sha256>/`, `request.json`, `health.json` | same | same |

A path is trusted only when every directory on it, and the final file, is owned by root (Windows: SYSTEM, Administrators or TrustedInstaller) and writable by nobody else, checked through opened handles that every later use goes through (`openRootOwned`); otherwise the code is `UNTRUSTED_LOCATION`. On Windows the directory that holds the file, and the file, may be changed by nobody but those accounts; a directory above it may let other accounts create new entries, as a default install does in ProgramData and in a drive root, but none may delete, rename or take over what it holds. Under `<state>/updates/` the agent writes `incoming/<manifest sha256>/vectory.part` (the download, renamed to `vectory`, or `vectory.exe` on Windows, only when its size and SHA-256 match the signed ones), then `release.json`, `release.json.sig` and `rollovers.json` beside it, then `request.json` last. A withdrawn or changed offer deletes them unless the step has started, and so does a result: the agent deletes `request.json` and the staged files once `last.release` in the step's status file equals the request's `manifest_sha256`. The step reads `<state>/updates/` only by copying and never writes there. `vectory version --json` prints `{"version","vector_version","go","os","arch"}`; the step's probe copies the verified build into `probe/`, runs it from there as the service account (as LocalSystem on Windows) with a 10-second limit and output of at most 4 KiB, and requires `version`, `os` and `arch` to be the manifest's version and the host's platform, otherwise `PROBE_FAILED`.

**The on-disk formats of the journal, `counters.json`, `installed.json`, `status.json`, `request.json` and `health.json` are fixed within a `service_definition` generation.** Any committed build of a generation can therefore drive any apply or rollback from any state another build of the same generation left, and a helper copy left one build behind by an interrupted commit stays correct. A change to a format needs a new generation. Each file is strict JSON of one object with exactly the members listed (a reader refuses a duplicate or unknown member and a value that is not what is listed), every member is always written (`null` where nothing applies), and `request.json`, `health.json` and `status.json` are at most 4 KiB.

The stages: `preparing` (the request was accepted; the step copies, verifies, probes and stages the build beside the executable, and nothing outside its own directory has changed: an interruption removes the staging and records `INTERRUPTED`, outcome `failed`), `swapping` (written, with the counter floors raised, before the service stops; recovery reads the installed digest: the new build continues at `trial`, the old build removes the temporary file and records `INTERRUPTED`, and on Windows an absent executable between its two renames takes the previous one back), `trial` (the new build runs; the step watches every two seconds, and a crash or power loss continues the watch once with a fresh deadline), `rolling_back` (the trial failed with `code` `START_FAILED`, `NO_CHECK_IN`, `UNHEALTHY` or `INTERRUPTED`: the previous build is being restored, from the helper copy of the last committed build and never by the build under trial), `committed` and `rolled_back` (terminal). No file, or a terminal stage, is idle. The result goes to `status.json` (`last`), `installed.json` is rewritten at `committed`, and the helper copy is replaced by the new build only after a commit. The new build is healthy when the service manager reports it active with no restart since the trial began, `health.json` names its SHA-256, a `boot_id` written after the trial began and a check-in after it, and Vector, if it ran before, runs; the server's own count requires more ([states](#update-rollouts)).

### Verification and the signed messages

Both signed messages are Ed25519 (RFC 8032) over exact bytes, with a prefix that keeps a release signature from ever validating as anything else and anything else as a release:

```text
release:   "vectory-agent-release-v1\n"          || the bytes of release.json, as stored and delivered
rollover:  "vectory-release-key-rollover-v1\n"   || the bytes of the statement, as delivered
```

Verification is strict and the same in both languages: it is cofactorless, `S` must be canonical (less than the group order), and `R` and the public key must be canonical encodings of points that are not of small order. Rust uses `verify_strict` (`ed25519-dalek`) and also refuses an `R` whose encoding is not canonical; Go uses `ed25519.Verify`, which refuses a non-canonical `S`, plus a check of `R` against the same encodings the key rule refuses. A host verifies with the pinned key's own bytes, never with a key a message carries beside the signature. The shared vectors hold a signature with a non-canonical `S`, and one whose `R` is the identity point, made from the test key's own scalar so that it satisfies the verification equation of a verifier without the check (a verifier that accepts it fails CI).

**The decision.** A host decides an offered release in this order and stops at the first refusal; the shared vectors pin the order with cases that break two rules at once. Its inputs are the manifest bytes, the signature file bytes, the rollover envelopes, its pins, its counter floors, its last result, its running version, its operating system and architecture, its track, the generation of its service definition and its clock.

1. More than 8 rollover envelopes: `MANIFEST_INVALID`.
2. The signature file does not parse: `SIGNATURE_INVALID`.
3. The rollover chain, in the order given. A statement is ignored when it does not parse, when its `from` is not a key the host pins at that point of the chain, or when its signature does not verify under that key. Otherwise the host pins `to`, drops `from`, and carries `from`'s counter floor to `to` (the higher of the two when `to` already had one); the `to` key's fingerprint is computed from its bytes. A **fork** is two statements from one currently pinned key that both verify and name different `to` keys, neither followed yet: `KEY_ROLLOVER_CONFLICT`, naming the first statement's successor and the first later one that differs (two fingerprints, reported in ascending order), and nothing else is done. A key is replaced once: two statements naming the same `to` key are not a fork, and once the host has followed `A -> B`, `A` is no longer pinned, so a later statement from `A` is ignored and never a conflict (a server that relays old public statements cannot freeze a fleet).
4. No signature entry names a pinned key: `KEY_NOT_PINNED`.
5. No entry for a pinned key verifies: `SIGNATURE_INVALID`. The entries that do are the release's *signers*, the first in file order the *signer*.
6. The manifest does not parse, breaks a rule of its format, or has an `issued_at` more than 24 hours after the host's clock: `MANIFEST_INVALID`.
7. The host's clock is at or after `expires_at`: `MANIFEST_EXPIRED`.
8. The release has no artifact for the host's operating system and architecture: `PLATFORM_NOT_IN_RELEASE`.
9. The counter is at or below the floor of any signer: `RELEASE_ALREADY_TRIED` when the host's last result names this manifest's SHA-256 as `rolled_back`, `COUNTER_REPLAYED` otherwise.
10. The release's version equals the running version: `ALREADY_RUNNING`; it is older: `DOWNGRADE_REFUSED`. A running version that is not a version (`0.1.0-dev`, `v0.1.0`, an empty string) cannot be compared with the release's, so it is `DOWNGRADE_REFUSED` as well: the host never guesses which of the two is newer. Versions compare as numbers (`0.1.10` is newer than `0.1.9`) and only move forward on a host, so a downgrade is never remote: going back is the automatic rollback or a local upgrade by hand.
11. The version is not on the host's track: `VERSION_NOT_ON_TRACK`. `patch` accepts the running major and minor with a newer patch; `minor` accepts the running major with a newer minor or patch; `major` is not a track.
12. The running version is older than `min_from`: `AGENT_TOO_OLD`.
13. The release's `service_definition` is newer than the host's: `SERVICE_DEFINITION_OUTDATED`.

Otherwise the release is valid, and the result gives the signer, the pins after the chain and the floors after it, with the floor of every signer raised to the counter. Only pinned keys with a floor above 0 are listed: a key the host no longer pins, or one it has never attempted a release from, has no floor. The same function runs in the agent before it downloads, in the privileged step before it swaps and in `vectory release verify`, which has no floors or running version of its own. The server uses the same functions for a signature or a statement it is given (`PUT /api/v1/agent-releases/{id}/signature`, a rollover upload).

**Counter floors.** A host keeps, in its root-owned state, a floor per pinned key: the highest counter of a release signed by that key that the privileged step *attempted* on this host. The step raises the floor, and syncs it to disk, when it journals `swapping`, before it stops the service, and a rollback never lowers it, so a release that was tried and taken back stays at or below the floor. A release is checked against, and raises, the floor of every pinned key whose signature on it verifies; a release at or below the floor is refused, `RELEASE_ALREADY_TRIED` when the host's last result names that manifest as rolled back and `COUNTER_REPLAYED` otherwise. A server, compromised or not, therefore cannot make a host try a release twice under fresh rollouts, which would stop and start Vector each time, and two different manifests with one counter cannot both be tried. The agent does not download or stage an offer whose manifest SHA-256 its last result reports as rolled back, and a fixed release ships with a higher counter. A host counts versions and counters only forward and an expired release is refused: `highest_counter` and `highest_counters` always mean the highest counter *attempted*.

**Clocks.** Expiry and the 24-hour rule use the host's own clock: a host whose clock runs far behind accepts a release that has expired, and one far ahead refuses valid ones.

**The shared vectors** are in `contracts/fixtures/agent-release/`. `vectors.json` holds the published test keys (fixed seeds), `key_lines` (every key-line rule, the eight small-order encodings and the non-canonical ones), `bundles` (what setup does with a key bundle and an operator's fingerprint) and `cases` (one offered release, the host's inputs and the expected result: `valid` with the signer, the pins after and the floors after, or the refusal code, with `rollover_conflict` for a fork). `report.json` holds the bounds of the heartbeat member and the members a server accepts and refuses. `examples/` holds the examples this section quotes, and `generate.mjs` writes all of them from fixed seeds with Node's own crypto and a reference of the rules; its `--check` fails when a file differs, when this section stops quoting an example as written or leaves out a code, or when an example breaks the schemas. The Rust server and the Go agent both run every case and every key line and must give the answer in the file; a case that needs different code to agree is a defect in one of them or in this section.

**Migrations** `0136_agent_update_settings.sql`, `0137_agent_releases.sql` and `0138_agent_update_rollouts.sql` are reserved for the setting and keys, the releases and their artifacts, and the rollouts and their targets, in that order; `0139` is held back and no other design takes it.

## Account security, first run and recovery (additive)

- Sessions: `Session` adds `expires_at` (sign-in plus 12 hours, no sliding renewal). The server records user agent (max 256 characters), client address (the TCP peer, or the last `X-Forwarded-For` hop behind a trusted proxy), creation and coarse last-active time (5-minute precision) per session. `GET /account/sessions` -> `{sessions:[{id,current,created_at,last_seen_at,expires_at,user_agent,client_address}]}` lists only the caller's active sessions, this browser first; `id` is a 32-hex public identifier derived from, and never revealing, the session verifier. `POST /account/sessions/{id}/revoke {}` (session + CSRF, no password: it only removes access) ends one other session; `404 SESSION_NOT_FOUND` when it already ended, `409 CURRENT_SESSION` for this browser.
- Session endings: every ended session leaves a reason for 7 days, keyed by its verifier: `expired`, `signed_out`, `signed_out_elsewhere` (revoke-sessions or per-session revoke), `password_changed`, `access_changed`, `mfa_changed`, `mfa_reset`, `replaced` (rotated by a new sign-in), `revoked` (other deletions such as restore invalidation). `GET /session` 401 bodies add `error.reason` (or null) for the presenting cookie only. The dashboard uses it to explain a sign-out and offers re-sign-in in place.
- Passwords: new passwords (setup, creation, change, reset, invitation) must be 12+ characters, not a known common password, not a keyboard/alphabet run or a repeated short unit, and not the account's own name or email (optionally followed by digits/symbols): `400 PASSWORD_TOO_WEAK` with a human message. A change to the current password is `400 PASSWORD_UNCHANGED`. Sign-in never applies the policy.
- Humane rejections: duplicate email `409 EMAIL_TAKEN`; reused request identity `409 REQUEST_ALREADY_USED` (the only ambiguous account 409: clients read the exact request status); last active administrator `409 LAST_ADMIN`; reset for a disabled account `409 ACCOUNT_DISABLED`; stale revision `409 STALE_REVISION`; wrong current password `403 WRONG_PASSWORD` ("Your current password didn't match."). Clients show these next to the form and keep its non-secret values.
- Invitations: a keyed `POST /users` may send `invite:true` instead of `password`; the account is created without a usable password and the first response adds `invite:{code,expires_at}` (single use, 24 hours, issuer-bound like reset codes). `GET /users` returns `Person` rows: `User` plus `status` (`invited`/`active`/`disabled`), `mfa_enabled`, `last_login_at`, `invite_expires_at`. Public `POST /invite/preview {code}` -> `{email,name,expires_at,instance_name}` and `POST /invite/accept {code,new_password}` -> `Session` with cookie; both return `401 INVITE_INVALID` for an unusable code and are rate limited per client and per code. `POST /password-reset` also redeems invitations and now returns `{ok:true,email}`; an unusable code is `401 RESET_CODE_INVALID`. Links carry the code only in the URL fragment (`/#/invite?code=…`, `/#/reset?code=…`), so it never reaches server or proxy logs.
- Two-factor: `POST /mfa/setup` adds `expires_at` (10-minute window); confirming after it returns `409 MFA_SETUP_EXPIRED`, a wrong setup code `403 INVALID_MFA_CODE`, setup while enabled `409 MFA_ALREADY_ENABLED`, and a concurrent lifecycle change `409 MFA_CHANGED`. `GET /mfa` adds `recovery_codes_remaining` (null while off). `POST /mfa/recovery-codes {password,code|recovery_code}` replaces all eight recovery codes. Codes are accepted with pasted spaces or dashes. Admin `POST /users/{id}/two-factor-reset {current_password,revision}` -> `{user}` removes another person's authenticator and recovery codes and ends all their sessions (`mfa_reset`); `409 OWN_MFA` for oneself, `409 MFA_NOT_ENABLED` when already off. Audited as `user.mfa_reset`.
- Sign-in audit: failures stay `login`/`denied` with the matched account UUID as target (empty for unknown emails) and `details:{client_address,reason}` (`wrong_password`, `unknown_account`, `account_disabled`, `password_changed`); the first throttled attempt per account and client in 15 minutes is `login`/`throttled`. Throttles count IPv6 clients per /64 and reserve each attempt's failure before checking the password (docs/adr/0003-sign-in-throttling.md); audits keep the full address. Neither ever records the attempted password or code. All sign-in audits share the `login` action family for filtering.
- Offline break-glass: `vectory-admin --data-dir PATH reset-password --email EMAIL [--url URL]` prints a single-use reset link, valid for one hour, with no administrator issuer (`purpose:"local"`); `disable-mfa --email EMAIL` removes two-factor and ends that person's sessions. Both need the server stopped (exclusive state lock) and are audited as `local-admin`. `vectory-admin --help` prints usage (exit 0); usage errors exit 2 and failures exit 1, without backtraces.
